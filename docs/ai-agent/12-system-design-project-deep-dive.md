## Q115｜系统设计：请设计一个 KYC 审核 Agent。

**考察意图｜**综合考察业务边界、文档理解、工具、合规、人机协同、评估和审计。

**标准答案**

- 先定义边界：Agent 负责材料归纳、信息抽取、风险提示、证据整理和建议；确定性合规规则与最终高风险裁决由规则引擎/人工负责。

- 入口接收用户身份、证件、活体、地址、企业资料等，文件先做恶意内容检测、OCR/版面解析与质量评分。

- 工具层连接身份验证供应商、制裁/PEP、工商、地址、设备风险和内部历史；每个结果带来源、时间与 trace_id。

- 编排采用 Case 状态机：资料待补充 → 自动校验 → 风险分析 → 规则判定 → 低风险通过/高风险人工 → 结果通知。

- 模型输出结构化 Findings：字段、证据、异常、严重度、置信度、需要补充材料；不得直接伪造缺失信息。

- 风险动作与审批绑定具体 Case、证据与版本，保留完整 Decision Ledger 和人工修改。

- 评估关注字段抽取、证据准确、误放行/误拒绝、人工审核时长、自动化率、供应商失败恢复和群体差异。

- 安全包括 PII 最小化、区域驻留、访问隔离、日志脱敏、模型供应商策略和对抗文件/Prompt Injection。

<blockquote>
<p><strong>P7 合格线：</strong>P7 要讲清架构、状态机、规则与模型边界、异常恢复和指标，不能只说“接 OCR + 大模型”。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 还要说明多国家规则版本、供应商路由、案件队列优先级、模型治理、偏差监测、审计与运营闭环。</p>
</blockquote>

高频追问与参考答案

**追问 1｜置信度达到多少可以自动通过？
参考答案｜**没有通用阈值。应基于标注数据做概率校准，并结合国家/产品、欺诈损失、监管要求和人群分段设置阈值；自动通过只适用于所有硬规则通过、证据完整且风险低的 Case，中间区间进入人工。

**追问 2｜供应商结果互相冲突怎么办？
参考答案｜**先按数据源权威性、时效、错误码和历史可靠性分类，检查是否只是格式或时间差；关键身份字段冲突时不得让模型‘投票’，应调用权威源复核或转人工，并保留每个供应商原始证据。

**追问 3｜如何防止模型对某类人群产生系统性偏差？
参考答案｜**在不同受保护群体上持续比较误拒、误放、人工升级和处理时长，检查数据与特征代理偏差；高风险决策使用可解释规则、双人复核和申诉通道，并对模型/阈值变更做公平性回归。

**追问 4｜Case 执行一半规则更新怎么办？
参考答案｜**Case 记录 policy_version。非关键更新可让存量 Case 固定旧版本完成；影响合规或风险判断的重大更新应在最终决定前按新规则重新评估，并同时保留旧/新结果、变化原因和人工处置记录。

## Q116｜系统设计：请设计一个安全告警研判与处置 Agent。

**考察意图｜**综合考察告警数据工程、RAG、工具编排、自动化边界和 Precision/Recall。

**标准答案**

- 告警入口统一标准化来源、规则、资产、账号、时间、证据和严重度，先做去重、聚合、抑制和关联，形成 Incident 候选。

- Enrichment 工具查询资产 CMDB、身份、进程/网络日志、威胁情报、历史告警、工单和变更记录；所有结果带时效和权限。

- RAG 同时检索处置制度、规则说明、历史相似案例和资产上下文：制度决定“应该怎么处置”，案例帮助“过去如何判断”，两者不能互相替代。

- Agent 输出结构化研判：是否真实事件、事件类型、证据、影响资产、攻击链、置信度、建议动作和未确认项。

- 自动化分级：低风险只补充信息/建单；可逆动作在阈值内自动；隔离主机、封禁账号等高风险动作要求人工审批。

- 真实告警识别要用混淆矩阵：Precision=判为真实的告警中有多少是真的；Recall=所有真实告警中找出了多少。两者与 RAG 的检索 Recall 不是同一个评估层。

- 反馈闭环将人工确认、最终 Incident、误报原因和处置结果回流规则、检索、模型评估，但避免未经审核直接写长期记忆。

- 观测包括 MTTD/MTTR、真实事件 Recall、研判 Precision、自动化率、误封/漏报、人工耗时、证据完整率和单位告警成本。

真实情况 Agent 判真实 Agent 判非真实
真实事件 TP FN
非真实/误报 FP TN

Precision = TP / (TP + FP)
Recall = TP / (TP + FN)

<blockquote>
<p><strong>P7 合格线：</strong>P7 要能从一万个告警如何找出真实告警讲到数据标注、阈值、人工抽检和处置幂等。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 还要设计跨数据源事件关联、风险成本函数、规则与模型协同、租户隔离、审计和攻击者对 Agent 的反制。</p>
</blockquote>

高频追问与参考答案

**追问 1｜检索到历史案例后还要不要查处置制度？
参考答案｜**通常仍要查。历史案例提供相似情境和处置经验，但制度/Playbook 才是当前规范与权限边界；可先用案例帮助理解，再以当前生效制度和实时资产数据校验，不能用旧案例替代新规则。

**追问 2｜如何区分“告警召回”与“RAG 召回”？
参考答案｜**告警侧 Recall 是所有真实安全事件中被检测/识别出来的比例，衡量漏报；RAG Recall@K 是所需制度、案例或证据是否进入检索候选。前者评价研判系统业务效果，后者只评价知识检索组件，两者不能混用。

**追问 3｜高 Recall 导致误报很多怎么办？
参考答案｜**不要简单牺牲高危 Recall。可按风险分级设置阈值，用规则、资产上下文、去重聚合、Rerank 和二阶段模型提高 Precision；低风险进入延迟处理或抽样，高风险保持高 Recall 并由人工快速确认。

**追问 4｜自动封禁超时但实际成功怎么恢复？
参考答案｜**把封禁调用标记为 UNKNOWN，使用 action_id/idempotency_key 查询防火墙或账号系统的最终状态。已成功则补写本地记录，未执行才重试；状态无法确认时冻结后续冲突动作并人工对账，避免重复封禁或误解封。

## Q117｜系统设计：请设计一个企业客服/售后 Agent。

**考察意图｜**综合考察意图路由、知识、订单工具、政策、安全和人机协同。

**标准答案**

- 入口做身份认证、语言识别、意图与情绪/风险分类，按账户、订单和渠道建立会话状态。

- RAG 检索产品、政策、FAQ 和历史工单，严格按地区、产品版本、时间与用户权限过滤并提供引用。

- 工具连接订单、物流、退款、优惠券、CRM 和工单系统；只读查询与写操作分级，退款/补偿按金额和规则审批。

- 编排通常是 Router + 确定性 Workflow：模型理解问题与填槽，规则决定资格、金额和状态迁移。

- 回答必须区分事实、政策和建议；证据不足时澄清，用户不满意或风险高时平滑转人工，并传递完整摘要与已做操作。

- 评估看一次解决率、转人工率、平均处理时长、错误承诺、退款损失、CSAT、工具成功和每会话成本。

- 防止 Prompt Injection、越权查询其他订单、重复退款、敏感数据外泄和不当对外承诺。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能详细讲一条退款流程的状态机、权限、幂等和异常恢复。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会进一步考虑全球多语言、多品牌政策、流量峰值、坐席协作、商业 KPI 与风险优化。</p>
</blockquote>

高频追问与参考答案

**追问 1｜用户要求跳过退款规则怎么办？
参考答案｜**Agent 不能因用户要求绕过确定性退款政策。应解释可适用的规则、收集例外证据，并在存在授权的特殊通道时发起人工审批；没有授权就明确拒绝执行。

**追问 2｜转人工时摘要错了如何防止？
参考答案｜**转人工包应包含结构化字段、原始消息引用、订单/工具结果和未确认项，人工可一键查看原文。摘要只用于加速，不作为唯一事实源；涉及退款等动作前由人工核对关键字段。

**追问 3｜同一订单重复发起退款如何处理？
参考答案｜**以 order_id、商品/服务项、退款原因和业务阶段生成幂等键，在退款服务使用唯一约束或状态机锁。重复请求返回第一次退款单及当前状态，不再次创建或简单返回‘重复’。

## Q118｜系统设计：请设计一个 Coding Agent。

**考察意图｜**综合考察代码上下文、计划执行、沙箱、测试、安全和评估。

**标准答案**

- 先解析需求与仓库边界，构建代码索引、符号/依赖图、文档与历史变更检索，避免把整个仓库塞进上下文。

- Planner 生成变更计划和受影响文件，Executor 在隔离工作区读取、编辑、运行构建/测试/静态扫描，Verifier 检查 Diff 与测试。

- 所有代码、命令和依赖安装在沙箱执行，限制网络、资源和密钥；默认不能访问生产环境。

- 修改使用 Patch/Diff，保留文件版本与冲突检测；工具调用和测试结果结构化写入 Trace。

- 高风险变更、依赖升级、数据库迁移、CI/CD 和合并需要人工审批；Agent 不能直接绕过分支保护。

- 失败时根据编译错误、测试失败、Lint、安全扫描或需求不清分类修复，限制循环次数。

- 评估使用真实任务、隐藏测试、代码质量、安全、改动范围、回归、成功时间和成本，防止只对公开测试过拟合。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能讲清 Repository Context、编辑工具、测试闭环、沙箱和 PR 流程。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会设计多仓库/大单体索引、并行子 Agent、远程执行集群、企业权限与代码供应链安全。</p>
</blockquote>

高频追问与参考答案

**追问 1｜Agent 修改了测试来让自己通过怎么办？
参考答案｜**把测试文件分为受保护基线、用户可修改测试和隐藏测试；Agent 修改受保护测试或降低断言应被策略阻止并在 Diff 审查中标红。最终验证由独立测试环境运行，不能只相信 Agent 自己提交的测试。

**追问 2｜如何处理超大仓库？
参考答案｜**先构建符号/依赖/调用图和分层代码索引，根据 Issue 定位相关模块、文件和测试，再按需读取局部上下文；使用仓库摘要、增量索引和任务级工作树，避免把整个仓库塞进窗口。

**追问 3｜命令执行如何防止读取云凭证？
参考答案｜**执行环境默认禁止访问云元数据地址和公网，环境变量不注入长期凭证，秘密只通过按需凭证代理提供短期最小 Scope。使用只读挂载、网络白名单、进程/文件系统隔离并扫描输出，防止命令读取或外传秘密。

**追问 4｜隐藏测试失败后怎么回放？
参考答案｜**记录 commit、工作区 Diff、基础镜像、依赖锁、命令、环境配置、随机种子、工具输出和隐藏测试版本，在不可变环境重建运行。隐藏测试正文不暴露给 Agent，只返回受控错误类别和必要诊断。

## Q119｜系统设计：请设计一个企业级知识助手。

**考察意图｜**综合考察文档平台、ACL、检索、引用、知识治理和高并发。

**标准答案**

- 数据源包括网盘、Wiki、数据库、工单、代码和网页；入库前做权限同步、文件安全、解析、版本与删除。

- 文档恢复标题、表格、图片、页码和来源，生成稳定 Canonical Block，采用按类型 Chunk 与父子索引。

- 查询时传播用户身份，做 ACL 预过滤、Query Rewrite、Hybrid Search、Rerank、去重和证据编排。

- 回答逐句/逐字段绑定来源，处理无答案、冲突版本、历史时间点和文档时效；允许用户反馈证据错误。

- 支持多租户索引、增量更新、缓存隔离、索引版本灰度、可观测和离线评估。

- 安全重点是文档 Prompt Injection、跨权限泄漏、恶意文件、敏感日志和删除传播。

- 指标覆盖解析质量、Recall@K、引用准确、答案可信、无答案策略、延迟、成本和知识缺口。

<blockquote>
<p><strong>P7 合格线：</strong>P7 要能讲到 Document AI、ACL、Hybrid、Rerank、引用和评估。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会进一步设计知识治理组织、权威源、冲突检测、全球区域部署和平台化服务。</p>
</blockquote>

高频追问与参考答案

**追问 1｜权限变更多久生效？
参考答案｜**高风险撤权应在查询时实时校验，目标通常是秒级或分钟级，而不是等待向量重建。索引 ACL 可异步更新，但资源读取和引用跳转必须经过当前权限网关；SLA 要按敏感等级定义。

**追问 2｜旧政策和新政策同时命中怎么办？
参考答案｜**依据权威级别、适用范围、审批状态和 valid_from/valid_to 过滤，默认使用当前生效版本。用户问历史时使用 as_of 检索；若两份都声称有效且冲突，应展示冲突并转权威部门确认。

**追问 3｜为什么有引用仍可能答错？
参考答案｜**引用可能只与主题相关却不支持具体结论，可能过期、权限不适用或只覆盖部分条件，模型也可能错误拼接多个来源。因此需要 Claim 级蕴含、版本和冲突校验，而非只检查‘有没有引用’。

## Q120｜系统设计：请设计一个全球高并发 Agent 平台。

**考察意图｜**综合考察流量入口、区域架构、模型路由、状态、队列、数据驻留、可观测与容灾。

**标准答案**

- 入口使用 Anycast/GSLB/CDN/WAF/API Gateway，就近接入并完成鉴权、租户限流、请求分级和 Region Routing。

- 控制面管理 Agent/Prompt/工具/模型/策略/评估版本，全球分发配置；数据面按区域运行 Runtime、RAG、Memory、工具网关和 Worker。

- 会话采用区域亲和，thread/task 状态写区域存储；允许跨区的低敏状态异步复制，高敏数据保持驻留。

- Model Router 按能力、区域、健康、成本和租户策略选择供应商，配合配额、熔断、排队和回退。

- 长任务进入区域队列，按优先级和租户公平调度；产物存对象存储，实时进度通过事件网关推送。

- 工具调用经统一网关执行身份传播、策略、幂等、审计、沙箱和网络出口控制。

- Observability 统一 Trace Context，区域聚合脱敏指标；审计和内容日志按数据政策存放。

- 灾备要定义 RTO/RPO、任务接管、供应商故障、区域隔离和“合规优先于自动跨区”的降级。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能给出从流量入口到数据、模型、工具、队列和监控的完整架构及容量计算。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会讲清控制面/数据面、全球配置一致性、区域自治、成本调度、演进路线和组织治理。</p>
</blockquote>

高频追问与参考答案

**追问 1｜用户从美国切到欧洲登录，历史会话如何快速访问？
参考答案｜**为用户/会话设置 Home Region，关键会话状态在合规允许范围内做加密多区复制或全局元数据索引；欧洲入口优先读取边缘缓存并路由回 Home Region。若允许迁移，则在 Checkpoint 完成受控复制和版本切换，不能双写推进。

**追问 2｜区域故障但数据不能跨境怎么办？
参考答案｜**按数据驻留策略 Fail-closed：在本区域切备用模型/工具、降级为只读、排队或暂停高敏任务，并明确 RTO/RPO。不能为了可用性把受限数据临时复制到禁止区域。

**追问 3｜如何统计全球 DAU 与任务成功率？
参考答案｜**各区域生成带 global_user_id、event_id 和 event_time 的登录/任务事件，本地先去重聚合，再汇总到允许的全球指标层。DAU 按用户—自然日集合去重，成功率按终态事件计算，并处理迟到、重放和隐私阈值。

**追问 4｜模型供应商全球配额如何协调？
参考答案｜**控制面维护供应商—区域—模型的总配额和成本预算，向各区域下发可借用的 Token Bucket/并发额度；根据实时使用和故障动态再分配，设置本地保底与全局熔断，避免某一区域耗尽全部额度。

## Q121｜项目深挖：请用 3 分钟介绍一个完整 Agent 项目。

**考察意图｜**考察候选人的结构化表达、个人贡献和结果可信度。

**标准答案**

- 第一段讲背景与目标：业务痛点、用户、规模、原流程、为什么普通 Workflow 不够。

- 第二段讲总体架构：入口、编排、模型、RAG、工具、Memory、安全、评估与观测，突出关键数据流。

- 第三段讲你的职责：你主导了哪些设计、关键代码、跨团队决策和上线工作，避免只说“我们”。

- 第四段讲两个难点：例如工具幂等、检索时效、长任务恢复、Prompt Injection、评估集，并说明方案与权衡。

- 第五段讲量化结果：任务成功、时长、成本、自动化率、风险指标和上线规模，明确基线与统计口径。

- 最后主动给出可深挖方向，让面试官选择架构、RAG、生产故障或评估。

背景/目标（30秒）→ 架构与链路（60秒）→ 个人职责（30秒）
→ 两个难点与权衡（40秒）→ 结果与复盘（20秒）

<blockquote>
<p><strong>P7 合格线：</strong>P7 表达必须做到边界清晰、架构完整、难点真实、指标可验证。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 还要体现路线选择、组织推动、风险治理、平台复用和长期演进，而不仅是个人编码。</p>
</blockquote>

高频追问与参考答案

**追问 1｜你在项目中具体写了什么？
参考答案｜**回答必须落到可验证的个人产出：例如你设计了状态机与幂等协议、实现了 Tool Gateway/RAG、搭建评估和 Trace，列出关键代码模块、设计决策、上线范围和指标。不要只说‘我们团队做了什么’。

**追问 2｜为什么不用纯 Workflow？
参考答案｜**说明业务存在输入不完整、步骤顺序不固定、需动态选择工具或跨系统取证等长尾，纯 Workflow 会产生大量组合分支；同时强调身份、审批和状态迁移仍保留确定性骨架。

**追问 3｜最关键指标如何采集？
参考答案｜**离线用标注集和轨迹回放采集任务成功、召回、工具参数与安全指标；线上通过统一 Trace、业务终态表、人工复核和投诉/回滚事件关联 task_id，避免只统计模型自报完成。

**追问 4｜如果重做你会改什么？
参考答案｜**选择一个真实改进点并说明原因，例如先建立评估集和错误分类、缩小自治边界、把状态从上下文迁到 Checkpointer，或先做幂等与可观测再扩工具。回答要体现复盘，而不是说‘没有需要改的’。

## Q122｜项目深挖：你为什么选择 Agent，而不是普通 Workflow？

**考察意图｜**考察候选人能否证明选型有业务必要性。

**标准答案**

- 先说明输入是否非结构化、路径是否动态、工具是否需要根据证据选择、步骤数是否不确定。

- 给出 Workflow 基线：固定流程在哪些长尾场景失败、维护成本如何、需要多少人工。

- 说明 Agent 只负责不确定部分，关键规则、权限、交易与审批仍保持确定性。

- 用实验比较任务成功率、覆盖长尾、处理时长、维护成本、延迟和错误风险。

- 如果 Agent 收益不显著，应诚实退回 Workflow 或采用 Hybrid，不要把技术潮流当理由。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能用真实数据和失败样本证明 Agent 的边际价值。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会定义渐进自治路线、止损阈值和长期单位经济，推动组织做正确而非最炫的选择。</p>
</blockquote>

高频追问与参考答案

**追问 1｜最复杂的长尾是什么？
参考答案｜**应举出最典型的动态长尾，例如用户材料缺失且补充顺序不定、多个工具返回冲突、政策条件组合变化或外部系统间歇失败；这些场景需要根据观察改变下一步，而不是预先枚举固定路径。

**追问 2｜不用 Agent 要增加多少规则？
参考答案｜**可用条件维度和组合数说明规则爆炸，并给出历史维护数据：新增一种渠道/政策需要修改多少分支、回归多久、长尾仍覆盖多少。不要凭空说‘需要很多规则’，要与现有基线比较。

**追问 3｜Agent 失败时能否退回固定流程？
参考答案｜**应该能。外层状态机保留一个安全、能力较弱的固定流程；当模型不可用、置信度低或触发风险策略时，退回人工表单、规则路由或只读建议模式，并保持已完成步骤和副作用不丢失。

## Q123｜项目深挖：请讲一次最严重的生产故障。

**考察意图｜**考察候选人的真实经验、根因分析和系统性改进。

**标准答案**

- 按时间线说明影响、发现、止血、根因、恢复和复盘，明确用户与业务损失。

- 根因不要停在“模型不稳定”：继续追到 Prompt/Schema、工具超时、重试幂等、状态竞争、限流、数据时效或发布流程。

- 说明为什么原监控、测试和评审没有发现，属于设计缺陷、实现缺陷还是运营缺口。

- 修复分短期止血和长期治理，例如关闭自动执行、回滚版本、补状态查询、增加幂等账本、构造回归集和混沌测试。

- 给出修复后的量化结果、验证方法与仍未完全消除的风险。

- 面试中不要甩锅模型或同事，要体现 Owner 意识和透明沟通。

<blockquote>
<p><strong>P7 合格线：</strong>P7 要讲出技术细节、决策与验证，不可只讲流程。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 还要说明如何推动跨团队机制、平台能力和发布治理，防止同类事故在其他业务重复发生。</p>
</blockquote>

高频追问与参考答案

**追问 1｜为什么之前没监控到？
参考答案｜**应诚实说明监控缺口，例如只监控 HTTP 成功率却没有业务终态、没有 UNKNOWN 副作用指标、Trace 未关联下游或告警阈值只看平均值。随后说明如何补组件与业务双层可观测。

**追问 2｜当时最先关闭了什么能力？
参考答案｜**通常先通过 Kill Switch 关闭写操作、批量能力或高风险自动执行，保留查询、只读分析和人工辅助，以最快速度缩小影响面。具体选择取决于事故根因和可逆性。

**追问 3｜如果工具超时但已成功，系统怎么知道？
参考答案｜**每次调用使用幂等键并写执行 Ledger；超时后查询下游业务单号或状态接口，状态成功则补记，未执行才重试，无法确认则人工对账。不能把网络超时直接等同失败。

**追问 4｜修复后怎么证明不会再发生？
参考答案｜**补充最小复现用例、自动回归、契约/混沌测试和线上指标门禁，先 Shadow/Canary 再放量；同时验证幂等和恢复路径。‘不会再发生’应表述为显著降低同类风险并能更早发现，而不是绝对承诺。

## Q124｜项目深挖：你如何证明 Agent 质量提升转化成业务收益？

**考察意图｜**考察候选人的评估、实验和数据归因能力。

**标准答案**

- 建立上线前基线：人工流程、旧模型或 Workflow 的成功、时长、成本和风险。

- 指标树连接组件指标、端到端任务指标和业务 KPI，明确每层统计口径与责任。

- 离线回归保证安全与能力，在线通过 A/B、灰度或时间分段实验验证真实流量收益。

- 同时计算负面影响：错误动作、投诉、人工返工、尾延迟、Token/工具费用和审核成本。

- 对选择偏差、流量结构、季节、运营策略和人员变化做控制，避免把所有改善归因于 Agent。

- 最终用单位成功任务成本、风险调整收益和可持续性决定扩大自动化。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能给出一套真实的指标、实验和结果数字。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会使用业务价值模型决定模型预算、阈值、人工资源和功能路线。</p>
</blockquote>

高频追问与参考答案

**追问 1｜任务成功率提升但投诉增加怎么办？
参考答案｜**说明技术成功指标与用户体验错位，先暂停放量并按投诉类型、用户群和轨迹归因。把投诉、误操作和升级率设为 Guardrail 指标，只有任务成功与这些指标同时达标才算提升。

**追问 2｜人工处理时长下降是否等于节省人力？
参考答案｜**不等于。要看释放的时间是否转化为更高处理量、SLA 改善、减少加班/外包/招聘，或人员转向更高价值工作；若等待时间和复核工作增加，表面处理时长下降可能没有净收益。

**追问 3｜如何计算风险调整收益？
参考答案｜**可用：业务增益 + 避免损失 - 模型/平台成本 - 人工审核与运营成本 - Σ(失败概率 × 影响金额) - 合规与机会成本。对高影响尾部事件单独做压力测试，不能只用平均损失。

## Q125｜技术领导力：你如何带 3—8 人团队交付 Agent 项目？

**考察意图｜**考察候选人的任务拆解、质量机制和跨团队协作。

**标准答案**

- 按能力域拆分：Agent Runtime/编排、RAG/数据、Tool Platform、评估/观测、安全/业务集成，明确接口与 Owner。

- 先建立可演示的基线与评估集，再并行优化；每个迭代有可量化验收，不以“感觉更智能”为完成标准。

- 用 ADR/RFC 记录关键选型与权衡，代码评审覆盖 Prompt、Schema、策略和数据变更，不只审业务代码。

- 建立发布门槛、On-call、Runbook、故障复盘和安全评审，把生产责任前置。

- 与产品、法务、业务专家定义 Agent 边界、人工兜底与风险责任，避免技术团队单方面承诺自治。

- 通过 Pair Design、技术分享、故障演练和模块轮岗提升团队整体能力，避免一个“Prompt 大师”成为单点。

<blockquote>
<p><strong>P7 合格线：</strong>P7 要体现自己能带小团队按质量目标交付，并解决跨模块问题。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 还要体现平台化复用、组织协同、人才培养、资源争取、风险决策和多项目路线规划。</p>
</blockquote>

高频追问与参考答案

**追问 1｜团队如何分工避免互相等待？
参考答案｜**按可独立验收的纵向能力切分，如 Runtime/状态、工具与安全、RAG、评估观测和业务场景，每块明确 Owner 与接口契约；先共建骨架和测试桩，使团队能并行开发而不是等待完整上游。

**追问 2｜产品要求快速上线但评估未完成怎么办？
参考答案｜**把上线范围缩为 Shadow、内部 Copilot 或低风险只读场景，明确哪些评估和安全门禁不可跳过。若业务仍要求承担风险，应形成可追溯的风险接受和 Kill Switch，而不是工程团队口头承诺。

**追问 3｜如何判断该自研还是使用框架？
参考答案｜**从战略差异、可控性、安全/合规、扩展性、团队能力、社区成熟度、锁定风险和三年总成本评估。通用编排可用框架，核心状态、权限、幂等和评估通常应掌握在自己手里。

**追问 4｜你如何培养后端同学转 Agent？
参考答案｜**先补 LLM/Token/Tool Calling 基础，再让后端同学从确定性的 Tool Gateway、状态机和 Trace 做起，配对完成一个小 Agent；用真实错误回放和代码评审培养 Context、评估与安全思维，逐步承担端到端 Owner。

## Q126｜从 Demo 到生产，Agent 项目应该经过哪些阶段？

**考察意图｜**考察候选人是否具备完整落地方法论。

**标准答案**

- 阶段 1：定义任务、用户、成功标准、失败成本和非 Agent 基线，验证问题值得做。

- 阶段 2：离线 PoC，打通模型、RAG、工具和最小编排，同时建立第一版评估集。

- 阶段 3：工程化，补状态、幂等、超时、队列、权限、Guardrail、Trace、版本和成本。

- 阶段 4：安全试点，使用影子模式或 Copilot，只给建议，由人工确认并收集真实反馈。

- 阶段 5：按风险开放有限自动化，灰度、审批、回滚、On-call 和 SLO 齐备。

- 阶段 6：规模化，做多租户、平台化、容量、全球化、数据治理和持续评估。

- 每个阶段都有退出条件；质量或经济性不成立时停止，而不是为了“上线 Agent”强行推进。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能给出自己项目的阶段、门槛和当时最关键的工程补齐。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建立组织级成熟度模型和治理流程，让多个业务以一致标准从试验走向生产。</p>
</blockquote>

高频追问与参考答案

**追问 1｜PoC 阶段哪些能力可以先不做？
参考答案｜**可以暂不做多区域、极致容量、完整运营后台和所有模型适配，但不能跳过最基本的成功标准、离线样本、数据权限和副作用隔离。PoC 也应只使用测试环境或只读工具，避免把安全债务带入演示。

**追问 2｜什么时候允许自动执行？
参考答案｜**当低风险范围内的离线评估、Shadow 和人工复核持续达标，并具备最小权限、幂等、审计、超时恢复、审批、回滚/Kill Switch 后，才允许小比例自动执行；再按风险和指标逐级扩容。

**追问 3｜如何选择第一批试点用户？
参考答案｜**选择业务代表性较高但风险可控、反馈意愿强、能接受试验且有明确基线的内部用户或友好客户。覆盖几类真实长尾即可，不要一开始同时服务所有地区和复杂人群。

**追问 4｜项目失败时如何及时止损？
参考答案｜**每阶段设置时间盒、成本上限和可量化 Go/No-Go 门槛，如成功率、人工节省和风险事件；连续几个周期不达标就缩范围、回退 Workflow 或终止。沉淀可复用的评估、工具和状态平台，避免全部投入成为一次性成本。
