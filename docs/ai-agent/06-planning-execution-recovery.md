# Planning、Execution 与可恢复编排

> 来源模块：模块六。本页保留完整标准答案、P7/P8 判断线和连续追问。

**让 Agent 不只是“多想几步”，而是可控地完成复杂任务**

<blockquote>
<p><strong>本模块考察：</strong>重点判断候选人能否设计任务分解、动态重规划、验证、预算、检查点与补偿事务。</p>
</blockquote>

本模块共 10 题｜建议先用 90 秒作答，再接受 2—3 轮追问。

## Q054｜一个好的任务分解应该满足什么条件？

**考察意图｜**考察候选人能否把复杂目标拆成可执行、可验证的步骤。

**标准答案**

- 每一步有清晰目标、输入、输出、依赖、可用工具和成功标准，能被 Executor 直接执行。

- 粒度既不能过粗到一步包含多个不可控动作，也不能过细到产生大量无价值模型调用。

- 优先暴露外部依赖、不可逆动作、权限需求和可并行关系，便于提前审批与调度。

- 计划应区分“必须步骤、可选步骤、验证步骤和补救步骤”，允许部分完成。

- 对不确定信息使用条件分支，不要在计划阶段假设尚未验证的事实。

- 最终计划必须能映射到任务状态和 Trace，而不是只存在一段自然语言里。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计 typed plan，并用历史任务验证分解后成功率和调用成本。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会将分解策略做成可学习或可配置能力，按风险、复杂度和工具健康动态调整粒度。</p>
</blockquote>

高频追问与参考答案

**追问 1｜计划越详细越好吗？
参考答案｜**不是。计划过细会增加调用与验证成本，并在信息不足时形成脆弱的早期承诺。好的计划应细到每步可执行、可验证和有清晰依赖，但允许 Executor 在局部展开。

**追问 2｜如何判断一步是否可验证？
参考答案｜**一步应产生明确 Artifact 或状态变化，并有外部验收方法，例如 Schema 校验、数据库查询、测试用例、证据覆盖或用户确认。若只能靠模型说‘看起来完成’，可验证性不足。

**追问 3｜不确定依赖如何表达？
参考答案｜**用条件分支、假设、置信度和待解析依赖显式表示，例如‘若接口支持 X 则走 A，否则走 B’。在依赖确认前不调度有副作用的后续步骤。

## Q055｜Agent 在什么情况下需要 Replan？如何避免反复重规划？

**考察意图｜**考察候选人对动态环境与计划稳定性的平衡。

**标准答案**

- 触发条件包括工具失败、关键假设被证伪、新约束出现、证据冲突、用户修改目标或剩余预算不足。

- 重规划应保留已验证完成的步骤和副作用，只调整受影响的后续部分，避免从头再来。

- 向 Planner 提供结构化失败原因、当前状态、剩余资源和不可重复动作，而不是把整个聊天记录重新丢进去。

- 设置最大重规划次数、冷却期和无进展检测；连续相似计划应触发降级或人工。

- 重规划前先判断是否存在确定性补救，例如换数据源、等待重试、补充权限或向用户澄清。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能实现增量 Replan 与计划差异记录。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会基于历史失败模式和预估收益决定是否重规划，并控制全局预算。</p>
</blockquote>

高频追问与参考答案

**追问 1｜工具超时一定要 Replan 吗？
参考答案｜**不一定。网络抖动等瞬态失败可以在原计划内重试或切换等价依赖；只有工具能力不可用、关键假设被推翻、目标变化或现有路径无法满足约束时才需要 Replan。

**追问 2｜如何防止 Planner 每次都输出完全不同的方案？
参考答案｜**计划包含稳定的 goal、constraints、step_id 和已完成事实，重规划优先输出增量 Patch，而不是每次重写全部内容。再用相似度/规则检查无依据的大幅漂移，并限制重规划次数。

**追问 3｜已执行副作用如何纳入新计划？
参考答案｜**把所有已执行副作用写入不可变 Ledger，新计划必须把它们视为既成约束：继续、补偿或请求人工决策。Planner 不能假装这些动作没有发生，也不能重复安排同一动作。

## Q056｜Verifier 应检查什么？为什么不能只让同一个模型自我反思？

**考察意图｜**考察候选人是否理解外部验证比“再想一遍”更可靠。

**标准答案**

- Verifier 检查目标是否达成、Schema 是否有效、关键字段是否有证据、工具副作用是否成功、规则/测试是否通过。

- 验证标准应尽量来自确定性规则、单元测试、数据库状态、第二数据源或人工，而不是只看答案是否“像对的”。

- 同一模型自我反思容易共享同样盲点，并可能为原错误生成更有说服力的解释。

- 可使用不同模型或不同上下文的 Judge，但需要校准偏差、设定明确 Rubric，并保留外部证据。

- Verifier 输出应是结构化判定：pass/fail、失败项、证据、可修复性和下一步建议。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能为关键任务建立规则验证 + 模型验证的组合。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会按风险分层设计多级验证和责任边界，高风险结论必须达到可审计证据标准。</p>
</blockquote>

高频追问与参考答案

**追问 1｜第二个模型就一定更客观吗？
参考答案｜**不一定。第二个模型可能共享训练偏差、提示和证据，因此错误高度相关。应尽量加入规则、测试、数据库和独立数据源等异质信号，并对 Judge 做校准。

**追问 2｜Verifier 与业务规则冲突时听谁的？
参考答案｜**业务规则是最终权威，Verifier 只能发现规则与模型结果不一致并阻止执行，不能覆盖规则。若规则本身疑似错误，应走规则变更流程而不是让模型临时绕过。

**追问 3｜验证失败后是修复还是重做？
参考答案｜**先分类失败范围：字段/格式局部错误可定向修复当前步骤；关键假设或计划路径错误应重规划；已产生错误副作用则先阻断并补偿。重做范围应最小化且受预算约束。

## Q057｜Self-reflection/Reflection 有哪些局限？

**考察意图｜**考察候选人是否理性看待“让模型反思即可变聪明”。

**标准答案**

- Reflection 会增加调用次数和延迟，但未必提供新信息；没有外部反馈时容易重复或合理化原结论。

- 同模型、同上下文、同提示下的自检高度相关，不能等价于独立验证。

- 对事实问题，新增检索或工具验证通常比继续思考更有效；对代码问题，运行测试比文字反思更可靠。

- Reflection 适合检查计划遗漏、输出格式、明显矛盾和可修复错误，但应有明确触发条件。

- 需要最大次数、收益门槛和无进展检测，不能形成“反思—重写—再反思”的无限循环。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能通过实验说明 Reflection 在哪些任务有效、在哪些任务浪费成本。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会把 Reflection 视为一种可选择的策略动作，与检索、验证、换模型和人工升级共同优化。</p>
</blockquote>

高频追问与参考答案

**追问 1｜什么时候应该反思，什么时候应该查工具？
参考答案｜**需要检查推理完整性、表达或计划一致性时可做 Reflection；缺少实时事实、计算结果或外部状态时应直接查工具，因为反思不能凭空创造新证据。

**追问 2｜如何量化 Reflection 的收益？
参考答案｜**在相同评估集上比较开启/关闭 Reflection 的成功率、错误类型、Token、延迟和重试，最好只对高不确定样本触发。若质量增益小于成本和稳定性损失，就不应默认开启。

**追问 3｜Reflection 会不会降低答案稳定性？
参考答案｜**会。Reflection 增加一次随机生成，可能把原本正确答案改坏。应使用结构化检查清单、外部成功标准、有限轮次，并保留原答案与修改理由供 Verifier 比较。

## Q058｜如何做 Budget-aware Planning？

**考察意图｜**考察候选人能否控制 Agent 的时间、Token 和费用。

**标准答案**

- 任务开始时设定最大墙钟时间、模型调用数、Token、费用、工具调用数和并发上限。

- Planner 为步骤估算成本、依赖和价值，优先执行高信息增益或能尽早排除路径的步骤。

- 执行过程中持续更新剩余预算；当预算不足时缩短上下文、换小模型、减少候选、跳过可选步骤或转人工。

- 终止判断应比较继续一步的预期收益与边际成本，而不是机械用完所有额度。

- 不同租户、任务风险和业务价值使用不同预算策略，并防止单个任务拖垮共享资源。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能给出任务级预算器与超限降级方案。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会把预算与在线路由、队列优先级、SLA 和业务价值联动，做多目标调度。</p>
</blockquote>

高频追问与参考答案

**追问 1｜如何估算下一步模型调用成本？
参考答案｜**根据当前 Context Token、预计输出长度、模型单价、工具调用费用和历史步骤分布估算期望值，并保留 P95 安全余量。估算结果随着新计划和实际消耗动态更新。

**追问 2｜预算不足但任务高风险怎么办？
参考答案｜**不能为了省钱降低安全门槛。可以暂停并请求追加预算、改为人工处理、使用确定性校验或缩小任务范围；只有低风险、可逆步骤才允许切换更便宜模型。

**追问 3｜费用上限和成功率如何权衡？
参考答案｜**把每个候选步骤的边际成功率提升、成本、延迟和风险转换为效用，优先执行单位成本信息增益最高的步骤。费用上限是硬约束，高风险失败成本应显著高于模型费用。

## Q059｜Human-in-the-Loop 应放在哪些节点？

**考察意图｜**考察候选人能否做风险驱动的人机协同设计。

**标准答案**

- 高风险、不可逆、对外承诺、资金、删除、权限变更、合规判定和低置信度异常应设置人工检查点。

- 审批发生在动作执行前，展示目标、具体工具、参数、影响范围、证据、模型理由和可替代方案。

- 暂停状态必须持久化，审批人可以修改、拒绝、过期或追加条件，恢复后再次校验资源版本和权限。

- 不要让人工审核所有步骤；通过风险评分、金额阈值、用户等级和历史准确率动态抽检。

- 记录人工决定并回流评估，但不能未经治理直接把所有人工操作当训练真值。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计可恢复审批节点和清晰的审批 UI 信息。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建立风险策略平台和抽检机制，在自动化率、审核成本和错误损失之间优化。</p>
</blockquote>

高频追问与参考答案

**追问 1｜审批后订单状态变化怎么办？
参考答案｜**执行前必须重新读取订单/Case 当前状态并验证审批绑定的前置条件。状态已变化时审批作废或重新评估，不能拿旧审批执行新状态下的动作。

**追问 2｜审批人修改参数是否算新动作？
参考答案｜**若修改影响对象、金额、范围、风险或副作用，就应视为新动作，重新做校验和必要审批；仅修正无风险展示字段可按策略保留原审批。所有变更必须留审计记录。

**追问 3｜如何避免人工成为吞吐瓶颈？
参考答案｜**采用风险分级，只把高风险、低置信度和异常样本交给人工；提供完整证据与建议、支持批量审批、SLA 和队列优先级，并用反馈持续提高低风险自动化率。

## Q060｜Agent 如何通过 Checkpoint 与 Event Sourcing 实现恢复？

**考察意图｜**考察候选人对长任务可靠执行的理解。

**标准答案**

- 在关键节点和副作用边界保存 Checkpoint，包含任务状态、计划、步骤结果、外部调用引用、预算和版本信息。

- Event Sourcing 记录状态变化事件，可重建任务历史、审计原因并支持时间点回放。

- 恢复时读取最后一致检查点，核对未决工具调用的真实状态，不能假设中断前最后一步未执行。

- 状态与事件 Schema 要版本化；新版本代码必须能读取存量任务，或提供迁移器。

- 敏感 Prompt/工具内容是否持久化要受数据策略控制，可保存哈希和受限引用。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能实现宕机恢复与重复执行测试。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会设计跨区域复制、版本迁移、事件压缩和大规模任务回放平台。</p>
</blockquote>

高频追问与参考答案

**追问 1｜Checkpoint 多久一次？
参考答案｜**在每个外部副作用、昂贵模型/工具调用、人工等待和长时间边界保存，而不是每生成一个 Token 都保存。频率要在恢复重做成本、写放大和状态大小之间权衡。

**追问 2｜只做 Event Sourcing 不做快照有什么问题？
参考答案｜**每次恢复都从头回放会越来越慢，事件格式升级也增加兼容负担；长链路还可能需要访问已失效外部数据。因此通常结合周期快照、事件归档和 Schema 迁移。

**追问 3｜恢复时模型输出能完全一致吗？
参考答案｜**不能保证。即使输入相同，模型也可能非确定；恢复应优先复用已记录的模型输出和工具结果，必须重新调用时把它视为新决策并重新验证，而不是追求逐 Token 一致。

## Q061｜如何调度可并行的子任务？

**考察意图｜**考察候选人对依赖、并发、取消和资源配额的理解。

**标准答案**

- 把计划表达为带依赖的 DAG，只有前置条件满足的节点进入 Ready 队列。

- 根据工具限流、模型并发、租户额度和任务优先级做有界并发，避免一次计划扇出几百个调用。

- 共享同一资源的写操作使用锁、串行分区或乐观并发控制；只读任务也要考虑下游容量。

- 任一关键分支失败时，根据聚合策略决定取消其余分支、继续收集部分结果或触发补救。

- 统一传播 Deadline、取消信号和 Trace Context，结果按 step_id 聚合，不依赖返回顺序。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能实现 DAG Scheduler 与部分失败语义。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会做基于成本和尾延迟的动态调度、投机重试与跨集群资源编排。</p>
</blockquote>

高频追问与参考答案

**追问 1｜并行任务如何共享上下文？
参考答案｜**共享的是版本化、不可变的任务快照和各自权限范围内的输出引用，而不是多人同时修改一段聊天记录。每个分支写独立命名空间，汇聚节点再原子合并。

**追问 2｜一个慢分支拖住整体怎么办？
参考答案｜**为分支设置 Deadline、阶段超时和可接受的部分结果策略。必需分支超时可启动备用执行、降级或取消整体；非必需分支则在截止时间后跳过，避免尾延迟无限放大。

**追问 3｜投机执行会不会产生重复副作用？
参考答案｜**会，因此投机执行优先用于只读或纯计算。涉及写操作时必须采用幂等键、Reserve/Commit 或仅允许一个 Winner 提交，其他分支取消并核对是否产生副作用。

## Q062｜Agent 执行失败后如何做补偿与回滚？

**考察意图｜**考察候选人是否理解跨系统事务不能靠数据库回滚解决。

**标准答案**

- 对每个有副作用的工具声明是否可撤销、补偿动作、补偿期限和不可逆风险。

- 跨系统流程通常采用 Saga：步骤成功后记录补偿信息，后续失败按逆序执行补偿。

- 补偿不是物理回滚，例如已发邮件只能再发更正，已对外提交的申请可能只能撤回或创建修正单。

- 补偿本身也要幂等、可重试、可审计，并处理补偿失败和人工介入。

- 不可逆动作应前置审批和最终确认，把风险放在执行前，而不是寄希望于事后回滚。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能为一个订单/工单/告警处置流程设计 Saga 与补偿表。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会把补偿语义纳入 Tool Registry 和编排引擎，形成平台级副作用治理。</p>
</blockquote>

高频追问与参考答案

**追问 1｜退款和撤销是一回事吗？
参考答案｜**不完全一样。撤销/void 往往发生在交易尚未结算前，使原动作不生效；退款是原交易完成后新建一笔反向交易，具有独立单号、费用和状态。补偿设计必须遵循下游真实语义。

**追问 2｜补偿失败怎么办？
参考答案｜**补偿本身也要幂等、可重试并写入独立状态机。多次失败后进入死信和人工运营队列，持续告警与对账；不能因为补偿失败就把原任务标记为成功。

**追问 3｜哪些动作应该明确标记为不可补偿？
参考答案｜**例如已发送的外部通知、已公开发布、实物已交付、数据已泄露或已提交监管报告等。计划阶段要标明不可补偿动作，并在执行前提高审批、验证和分段提交级别。

## Q063｜Agent 是否可以做到完全确定性重放？

**考察意图｜**考察候选人对可复现性边界的理解。

**标准答案**

- 模型输出具有非确定性，供应商后端、模型版本、并行执行和工具实时数据都会影响结果，因此很难保证字节级重放。

- 可实现的是“可解释重放”：固定 Prompt/模型/参数/工具 Schema 版本，保存输入、检索候选、工具结果和状态迁移。

- 调试时可使用 Mock Tool 和历史模型输出进行离线回放，定位编排逻辑；也可重新调用模型比较行为差异。

- 副作用重放默认禁用，使用历史结果或沙箱；确需执行时使用新幂等键和明确授权。

- 重放结果需要标注 Replay Mode、数据时间点和是否使用真实外部依赖。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能构建 Trace Replay，复现大部分故障路径。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会把可重放性作为平台发布门槛，支持回归、取证、模型迁移和批量反事实评估。</p>
</blockquote>

高频追问与参考答案

**追问 1｜Temperature=0 能否保证重放？
参考答案｜**不能。Temperature=0 仍受模型版本、推理后端和数值实现影响，只能降低随机性；完全重放需要记录实际模型响应、Prompt 制品、工具输入输出和状态版本。

**追问 2｜线上工具数据变化怎么办？
参考答案｜**调试重放应使用当时的快照或录制结果，否则得到的是基于新世界状态的一次新运行。若业务必须读取最新数据，应明确标记为重新执行，而不是声称复现原轨迹。

**追问 3｜如何安全重放写操作？
参考答案｜**提供 Replay/Dry-run 模式，默认禁用所有写工具并复用历史结果；确需重新执行写操作时使用新幂等键或隔离沙箱、显式审批和影响面限制，绝不能直接回放生产副作用。
