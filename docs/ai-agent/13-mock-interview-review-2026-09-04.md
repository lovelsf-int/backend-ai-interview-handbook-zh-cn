# 2026-09-04 正式面试复盘：LLM 平台治理与多租户稳定性

> 本页记录本轮 JD 定向正式面试中暴露的问题、面试官期望、标准答案与下一轮训练重点。目标不是堆概念，而是把回答提升为“可量化、可归因、可执行、可验证”。

## 1. 总体问题画像

本轮 AI/平台架构部分的主要问题不是没有思路，而是回答经常停留在“可以合并、可以限流、可以监控”的层面，缺少：

- 量化指标；
- 清晰边界；
- 迁移顺序；
- 触发阈值；
- 回退条件；
- 改造后的验收指标。

面试建议统一使用：

> **现状基线 → 判断标准 → 治理动作 → 灰度迁移 → 监控回退 → 指标验收**

## 2. 服务边界合理性：不能只说“哪些能合并”

### 本轮不足

你能判断 Model Gateway 应独立，也能提出 Orchestrator、Conversation 等模块可能合并，但缺少一套架构评估方法论。

### 面试高分框架

服务边界是否合理，至少看五类指标：

1. **调用耦合**：一次请求跨多少服务、同步 hop 数、扇出数、关键路径长度；
2. **变更耦合**：两个服务是否经常一起改、一起发、一起联调；
3. **数据耦合**：是否频繁跨服务事务、双写、共享表、同步查同一份状态；
4. **运行耦合**：是否必须同时扩缩容、故障是否相互传播；
5. **团队边界**：是否存在独立 ownership、独立 SLA、独立合规/安全责任。

### 哪些模块更应该独立

**Model Gateway** 通常应保留独立边界，因为它天然承担：

- 模型路由；
- 供应商适配；
- 认证与权限；
- Token/成本计量；
- 限流配额；
- 审计；
- 熔断回退。

这些职责构成清晰的安全与成本边界。

**Evaluation Service** 也常适合独立，因为它偏离线/异步、资源模型不同，并且不应让线上主链路被评估逻辑拖慢。

### 哪些模块可能合并

如果 Prompt、Conversation、Memory、Orchestrator 之间：

- 调用高度同频；
- 每次需求都一起改；
- QPS 低；
- 没有独立扩缩容需求；
- 没有独立安全边界；

则可以考虑模块化单体或粗粒度服务，而不是为了“微服务”继续保持网络边界。

### 必背结论

> 微服务边界不是按功能名拆，而是按独立变化、独立扩缩容、独立故障、独立安全/合规边界来拆。

## 3. 如何识别“过度拆分”

可以从数据直接证明：

```text
Trace 调用拓扑
   +
服务间同步调用次数
   +
跨服务 P99 延迟
   +
Git 变更同频率
   +
联合发布次数
   +
联调工时
   +
共享数据/跨服务事务
```

如果两个服务长期表现为：

```text
一起改
一起发
一起扩
一起故障
彼此高频同步调用
```

那它们很可能只是“物理拆开，逻辑仍然是一个服务”。

## 4. 不停机架构治理怎么做

### 本轮不足

回答里提到了 A/B 和双写，但缺少完整迁移路径。

### 标准迁移顺序

1. 建立基线：P50/P95/P99、错误率、调用 hop、成本、发布失败率；
2. 新旧架构并存；
3. Feature Flag 控制流量；
4. Shadow Traffic 验证新链路行为；
5. 小流量灰度；
6. 必要时做数据双写/事件同步，但要明确一致性风险；
7. 对比输出与指标；
8. 阶梯放量；
9. 保留回滚入口；
10. 稳定后再下线旧服务。

### 关键术语

- Strangler Fig；
- Shadow Traffic；
- Feature Flag；
- Canary；
- 双写/CDC；
- 一键回滚。

### 验收指标

- P99；
- Error Rate；
- MTTR；
- Change Failure Rate；
- Lead Time for Changes；
- 单位请求成本；
- 同一次需求涉及的服务数量；
- 联调与发布时间。

## 5. LLM 成本治理：先归因，再优化

### 本轮不足

第一反应是上下文爆炸、缓存和任务断点复用，方向没错，但没有先回答“成本到底从哪里涨起来”。

### 成本归因模型

每次模型调用建议记录：

```text
tenant_id
scene
request_id
model
model_version
input_tokens
output_tokens
cached_tokens
retry_count
agent_rounds
rag_topk
embedding_calls
tool_calls
latency
cost
success
```

再按：

- 租户；
- 场景；
- 模型；
- 模型版本；
- Agent Step；
- Prompt Template；

聚合得到 Top N 成本来源。

### 成本治理闭环

```text
计量
 ↓
归因
 ↓
Top N 异常
 ↓
优化实验
 ↓
质量门禁
 ↓
灰度
 ↓
成本/质量复盘
```

### 常见优化手段

- 大小模型分层路由；
- Prompt 压缩；
- Context 去重/摘要；
- 限制 Agent 最大轮次；
- Prompt/前缀缓存；
- Embedding 缓存；
- 可安全复用的 Response Cache；
- 检索 TopK 控制；
- 结果复用；
- 失败步骤断点续跑；
- 租户预算和配额。

## 6. 如何用数据说服产品接受模型分层

### 本轮回答亮点

你抓到了“1% 质量提升是否值得 50% 成本增长”这个核心经济性问题。

### 更强答法

不要争论“大模型一定好/小模型够用”，而是直接做 A/B：

| 指标 | 全量大模型 | 分层路由 |
|---|---:|---:|
| 准确率 | 例如 94% | 93.7% |
| P95 | 8.0s | 5.1s |
| 单次成本 | 1.00 | 0.55 |
| 成功任务成本 | 1.10 | 0.62 |
| 用户投诉率 | 基线 | 无显著变化 |

然后回答：

> 如果质量下降在预设非劣效边界内，但成本显著下降，我会继续阶梯放量；如果关键业务指标越过质量护栏则自动回退。

### 要看边际成本

> 每提升 0.1% 准确率需要多花多少钱？用户是否感知？是否能形成收入或留存收益？

这比“成本太高”更有说服力。

## 7. 质量小幅回退时是否继续放量

### 本轮不足

你回答“可接受就继续观察”，但缺少预先定义的 SLO/护栏。

### 标准答案

必须提前定义：

- 质量非劣阈值；
- 关键任务成功率；
- 用户投诉率；
- 人工复核通过率；
- 延迟；
- 成本；
- 观察窗口。

例如：

```text
质量下降 < 0.3%
P95 改善 > 20%
单位成功任务成本下降 > 25%
关键客户成功率不下降
```

满足则继续从 5% → 20% → 50% → 100% 阶梯放量；越过硬护栏则自动回退。

## 8. 多租户隔离：Tag 只是起点

### 本轮不足

你能想到核心客户与普通租户分层，但一开始偏“核心用户优先”，没有马上讲资源隔离模型。

### 正确结构

多租户治理建议回答四层：

#### 8.1 隔离

- tenant quota；
- tenant concurrency limit；
- 有界队列；
- 高优租户预留容量；
- 必要时独立队列/Worker Pool/GPU Pool；
- 防止 noisy neighbor。

#### 8.2 限流

租户级与全局级同时存在：

```text
Tenant Token Bucket
        +
Global Admission Control
```

某租户不能因为自己还有 quota 就把全局资源打爆。

#### 8.3 降级

从轻到重：

1. 降低新任务并发；
2. 限制普通租户；
3. 缩短上下文/减少 TopK；
4. 大模型切小模型；
5. 关闭非关键 Tool；
6. 长任务改异步；
7. 低优请求快速失败；
8. 极端情况熔断。

#### 8.4 恢复

不能一下全开：

```text
探测
 ↓
10%
 ↓
25%
 ↓
50%
 ↓
100%
```

如果恢复阶段 P99、429、队列长度再次恶化，应自动退回上一档。

## 9. 限流/降级阈值：单一 GPU 利用率不够

### 本轮回答亮点

你已经给出了组合阈值：GPU 80%、队列 80%、延迟翻倍。

### 更成熟的做法

建议同时看：

- GPU Utilization；
- GPU Memory；
- Queue Utilization；
- Oldest Queue Age；
- P95/P99 Latency；
- 429 / timeout；
- Tokens/s；
- 当前租户公平性；
- 错误率。

示例分级：

```text
黄色：GPU > 70% 且 Queue > 60%
动作：降低普通租户并发

橙色：GPU > 80% 且 Queue > 80% 或 P95 > 2×基线
动作：模型降级 + 限制低优任务

红色：GPU > 90% 且 P99/超时持续恶化
动作：低优快速失败 + 熔断部分能力
```

注意：阈值必须来自压测与历史容量基线，而不是固定背诵。

## 10. 怎么避免误伤核心客户

必须补充：

- 白名单/优先级策略；
- 核心租户容量预留；
- 变更灰度；
- 租户维度 SLO；
- 真实混合流量压测；
- 限流规则审计；
- 一键回退；
- 混沌演练。

压测不能只压总 QPS，必须模拟：

```text
核心租户稳定流量
+ 普通租户稳定流量
+ 单个 noisy tenant 突发 10×
+ 模型变慢
+ 429/超时
+ backlog 恢复
```

## 11. 本轮必须背熟的 10 个结论

1. 微服务边界看独立变化/扩容/故障/安全，而不是看功能名字。
2. 过度拆分要用 Trace、变更同频、发布同频和联调成本证明。
3. 架构治理先建基线，再 Shadow/Canary，最后逐步下线旧链路。
4. 成本治理必须先计量和归因，再谈缓存、压缩和模型路由。
5. 最重要的成本指标是 Cost per Successful Task，而不是单 Token 单价。
6. 大小模型分层要通过非劣实验，而不是靠主观争论。
7. 多租户隔离至少包含 quota、并发上限、有界队列和容量预留。
8. 限流、降级、熔断必须分级，不能只有“拒绝请求”一个动作。
9. 恢复要阶梯放量，并允许自动退回上一档。
10. GPU 利用率只是信号之一，必须结合队列、延迟、错误率与公平性。
