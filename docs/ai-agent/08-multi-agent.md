# Multi-Agent 与协作机制

> 来源模块：模块八。本页保留完整标准答案、P7/P8 判断线和连续追问。

**不是 Agent 越多越高级，而是分工收益必须大于协调成本**

<blockquote>
<p><strong>本模块考察：</strong>重点判断候选人能否选择协作拓扑、设计 Handoff、共享状态、冲突处理和多 Agent 评估。</p>
</blockquote>

## Q073｜什么情况下 Multi-Agent 比单 Agent 更合适？

**考察意图｜**考察候选人是否会克制使用多 Agent。

**标准答案**

- 任务存在明确专业分工，不同子任务需要不同模型、工具、权限、上下文或安全边界时，多 Agent 有价值。

- 可并行的独立子任务很多，或上下文过大需要分区处理时，可以通过多个专家提升吞吐和聚焦度。

- 跨组织/跨系统协作中，远端能力拥有独立生命周期与责任边界时，也适合 Agent-to-Agent 委派。

- 如果只是给同一模型换几个角色名，且共享同样工具和上下文，通常只增加 Token、延迟和不稳定性。

- 选型前应与“单 Agent + 工具”“Router + Workflow”做基线比较，证明质量或组织边界收益。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能用实验比较单 Agent 与 Multi-Agent 的成功率、成本、延迟和失败模式。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建立协作准入标准和自治边界，避免平台演变为不可治理的 Agent 网络。</p>
</blockquote>

高频追问与参考答案

**追问 1｜两个角色互相讨论算 Multi-Agent 吗？
参考答案｜**未必。仅用两个角色 Prompt 轮流说话可能只是单 Agent 内的多阶段推理。更典型的 Multi-Agent 具有独立能力边界、状态或权限，并通过明确协议委派和交付任务；关键是自治责任分工，不是角色数量。

**追问 2｜并行子任务为什么不一定需要多个 Agent？
参考答案｜**如果子任务路径确定、只需并行调用工具或 Worker，用 DAG/并发 Workflow 更简单。只有子任务本身需要独立规划、长期状态或专业权限时，才值得建立专家 Agent。

**追问 3｜多 Agent 的最大成本是什么？
参考答案｜**最大成本通常不是模型数量本身，而是协调复杂度：重复上下文与检索、Token/延迟放大、冲突、循环委派、权限扩散以及更难的调试和责任归因。

## Q074｜Supervisor 架构与 Peer-to-Peer 架构如何选择？

**考察意图｜**考察候选人对多 Agent 拓扑与控制权的理解。

**标准答案**

- Supervisor 集中分配任务、管理状态和汇总结果，易于控制、审计和设置全局预算，但可能成为性能与单点瓶颈。

- Peer-to-Peer 允许 Agent 直接协作，灵活且减少中心协调，但更容易出现循环、权限扩散、协议不一致和责任不清。

- 企业生产通常采用受控 Supervisor 或层级式 Supervisor，Peer 通信需经过注册和策略限制。

- 对于超长任务可采用分层组织：顶层协调目标，中层管理领域，底层专家执行。

- 无论何种拓扑，都要限制最大跳数、可委派范围、共享数据和累计预算。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能画出两种拓扑并分析故障、扩展和一致性。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会支持拓扑动态编译、跨组织信任和去中心化协作中的策略执行。</p>
</blockquote>

高频追问与参考答案

**追问 1｜Supervisor 挂了怎么办？
参考答案｜**将 Supervisor 设计为无状态可复制组件，任务和路由决策持久化，通过队列、租约或领导者选举接管。故障时新实例从 Checkpoint 继续，必要时暂停高风险任务而不是丢失控制权。

**追问 2｜Peer 之间如何发现彼此？
参考答案｜**通过受控 Agent Registry/Agent Card 发布能力、版本、协议和安全属性，Peer 根据允许列表和能力匹配发现。生产环境不能依赖模型自由搜索任意未知 Agent。

**追问 3｜层级太深会有什么问题？
参考答案｜**层级越深，传递上下文越容易丢失，端到端延迟和成本呈累积增长，错误也更难定位。应限制最大 Hop、保持职责粗粒度，并让最终责任人清晰可见。

## Q075｜Handoff 与“把另一个 Agent 当作 Tool”有什么区别？

**考察意图｜**考察候选人对会话控制权和委派语义的理解。

**标准答案**

- Handoff 通常把当前对话或任务的主导权交给另一个 Agent，后者面向用户继续处理并可能成为最终回答者。

- Agent-as-Tool 由当前 Agent 调用专家 Agent 获取结构化结果，主 Agent 仍持有对话控制权并负责最终综合。

- 用户需要直接与专业助手交互、后续多轮都属于该领域时适合 Handoff；单次子任务、需要统一汇总时适合 Agent-as-Tool。

- Handoff 要明确传递哪些历史、身份、权限和未完成状态；不要默认把全部敏感上下文交给新 Agent。

- 两种方式都需要追踪委派原因、输入过滤、返回结果和责任边界。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计 Handoff 过滤、回退和用户体验。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会按用户意图、风险、成本和 Agent 能力动态选择委派方式，并支持跨协议协作。</p>
</blockquote>

高频追问与参考答案

**追问 1｜Handoff 后原 Agent 还能继续吗？
参考答案｜**可以，取决于状态机设计。Handoff 通常转移当前会话或任务责任，原 Agent 可进入等待、监控或在专家完成后恢复；必须明确 active owner，避免两个 Agent 同时代表用户执行。

**追问 2｜如何避免来回转交？
参考答案｜**记录 visited_agents、handoff_reason 和 hop_budget，对相同任务—能力的重复转交做循环检测；Router/Supervisor 应有稳定的责任边界，达到上限后转人工或由上级仲裁。

**追问 3｜专家 Agent 返回的结果需不需要验证？
参考答案｜**需要。专家身份不等于结果可信，仍要检查 Schema、证据、权限、时效和业务规则。高风险动作由调用方或独立 Verifier 做最终放行，不能把 Handoff 当作信任转移。

## Q076｜Multi-Agent 应使用共享状态还是消息传递？

**考察意图｜**考察候选人对一致性、耦合和可观测性的理解。

**标准答案**

- 共享状态/Blackboard 便于所有 Agent 查看统一任务事实和进展，但并发写入、权限和污染风险更高。

- 消息传递耦合较低、边界清晰，适合跨服务/组织，但需要处理消息顺序、重复、丢失和 Schema 版本。

- 常见组合是：共享一个版本化任务事实表，各 Agent 通过结构化消息提交提案和产物，只有协调器或特定角色可修改关键状态。

- 避免把自由文本聊天记录当成唯一共享状态；事实、结论、置信度、证据和待办应结构化。

- 读写范围按 Agent 身份和最小必要原则控制。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计状态 Schema、并发控制和消息幂等。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建设 Agent Blackboard/Message Bus 平台，支持血缘、策略、事件回放和跨区域一致性。</p>
</blockquote>

高频追问与参考答案

**追问 1｜多个 Agent 同时修改计划怎么办？
参考答案｜**计划应有单一写入者，通常由 Supervisor/Planner 管理；其他 Agent 只能提交提案或局部结果。若允许并发更新，要使用版本号、乐观锁和冲突合并规则，不能最后写入者覆盖一切。

**追问 2｜消息重复如何处理？
参考答案｜**消息带 message_id、task_id 和因果/序列信息，接收方维护幂等 Inbox 和处理状态。重复消息复用原响应或忽略，确认语义与业务提交要协调，避免已处理却未 ACK 的重复执行。

**追问 3｜共享状态是否会让上下文无限增长？
参考答案｜**会。因此共享层保存结构化事实、计划和 Artifact 引用，各 Agent 只读取职责相关的投影；历史消息定期压缩或归档，大对象不直接复制到所有上下文。

## Q077｜多个 Agent 结论冲突时怎么处理？

**考察意图｜**考察候选人是否具备证据驱动的冲突解决机制。

**标准答案**

- 先统一输出协议：结论、置信度、证据、假设、数据时间和适用范围，避免只比较自然语言意见。

- 对事实冲突优先查询权威源、实时工具和明确规则；对方案权衡使用预定义评分标准。

- 可引入独立 Verifier/Arbiter，但其权限和上下文要受控，不能只按“多数投票”。

- 无法消解的高风险冲突向人工展示差异和证据，不允许协调器编造折中答案。

- 记录冲突类型和最终裁决，用于更新专家能力、路由和评估集。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能实现证据化仲裁和冲突升级。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会基于专家历史校准、领域可信度和风险设计动态加权，而不是固定投票。</p>
</blockquote>

高频追问与参考答案

**追问 1｜三个 Agent 两个同意就算正确吗？
参考答案｜**不能。多个 Agent 可能使用同一模型、同一错误证据，错误高度相关；多数票只在独立性和校准成立时有意义。应比较来源权威性、证据质量、规则约束和任务专长。

**追问 2｜置信度可以直接比较吗？
参考答案｜**通常不能直接比较，不同模型和 Prompt 的自报置信度没有统一尺度。需要在标注集上做校准，或改用可验证证据分、历史准确率和成对排序。

**追问 3｜Arbiter 与 Supervisor 是否是同一个角色？
参考答案｜**可以由同一组件承担，但概念不同：Supervisor 负责调度和责任分配，Arbiter 专门解析冲突并给出依据。复杂或高风险系统最好分离，避免协调者既当参赛者又当裁判。

## Q078｜如何防止 Multi-Agent 死锁、活锁和循环委派？

**考察意图｜**考察候选人对分布式协作故障的理解。

**标准答案**

- 为每个任务设置最大委派深度、总跳数、每个 Agent 调用次数和全局 Deadline。

- 记录委派图和任务指纹，检测 A→B→A、相同子任务重复创建和状态长时间不变化。

- 资源锁使用统一顺序、租约和超时，避免多个 Agent 互相等待；长等待转为异步事件。

- 每个委派必须声明预期产物和完成条件，禁止“请继续分析”这类无边界请求。

- 触发循环后由 Supervisor 终止、降级为确定性流程或升级人工，并保留完整 Trace。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能实现委派图检测、租约和超时。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会用静态计划检查 + 运行时异常检测，治理大规模 Agent Mesh 中的级联故障。</p>
</blockquote>

高频追问与参考答案

**追问 1｜活锁与死锁有什么区别？
参考答案｜**死锁是各方互相等待，系统几乎没有动作；活锁是各方持续发送、重试或礼让，看似活跃但状态没有向目标推进。两者都需要依赖图、进展指标和超时检测。

**追问 2｜A2A 异步任务如何避免永久等待？
参考答案｜**任务设置 Deadline、租约、心跳和最大等待时间，调用方可轮询/订阅状态并支持取消；超时后进入可重试或人工队列。远端完成事件必须幂等处理，避免迟到结果重复推进。

**追问 3｜循环检测只看 Agent 名称够吗？
参考答案｜**不够。同一 Agent 在不同步骤被再次调用可能完全合理。循环检测应看 task_id、能力/动作、关键参数、状态哈希和依赖边，判断是否在相同状态重复相同语义动作。

## Q079｜Multi-Agent 应如何评估？

**考察意图｜**考察候选人是否会把最终答案指标拆解到协作过程。

**标准答案**

- 端到端评估任务成功、质量、延迟、成本和安全；组件级评估每个 Agent 的专业能力。

- 协作指标包括路由/委派准确率、Handoff 成功率、重复工作率、消息轮次、冲突率、循环率和上下文传递完整性。

- 轨迹评估检查是否选择了正确专家、是否调用多余 Agent、是否在必要时升级人工。

- 使用单 Agent 基线，只有质量增益超过协调成本时才证明 Multi-Agent 合理。

- 线上监控 Agent 负载不均、中心 Supervisor 瓶颈、跨 Agent 失败传播和权限异常。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能建立专家级、协作级和端到端三级评估。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会将评估结果用于动态路由、拓扑优化、专家淘汰与能力扩展。</p>
</blockquote>

高频追问与参考答案

**追问 1｜只看最终成功率有什么盲点？
参考答案｜**只看最终结果会掩盖碰巧成功、未经授权的工具调用、过高成本、无效争论和危险中间动作。还应评估轨迹正确性、角色贡献、Handoff、重复工作、延迟和安全。

**追问 2｜如何衡量重复工作？
参考答案｜**比较各 Agent 的查询、证据、工具调用和产物相似度，统计重复 Token、重复检索和无新增信息的步骤占比；也可做去掉某个 Agent 的消融实验，衡量其边际贡献。

**追问 3｜怎样评估 Handoff 上下文是否完整？
参考答案｜**定义必传字段、目标、约束、已完成动作、证据和未决风险的 Schema，检查下游是否因缺失信息再次询问或重复工作。通过 Handoff 专项集测字段覆盖率和语义一致性。

## Q080｜如何设计 Multi-Agent 的组织拓扑与成本控制？

**考察意图｜**考察候选人的系统级权衡能力。

**标准答案**

- 按领域、权限、数据位置和工具集合划分专家，不按“研究员、评论员”等抽象人格随意拆分。

- 控制每层扇出、最大深度和模型档位；入口先用廉价 Router，只有复杂任务进入高级协作。

- 共享检索、工具结果和中间产物，避免每个 Agent 重复读取相同上下文。

- 对专家设置预算、并发、SLO 和降级策略；不重要的子任务可合并或由小模型处理。

- 持续分析调用图，淘汰低收益专家和冗余往返，保持拓扑可解释。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能给出一套可落地的专家划分和预算模型。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会结合组织责任、跨域信任、在线负载和任务价值动态编排 Agent Team。</p>
</blockquote>

高频追问与参考答案

**追问 1｜专家越细分效果越好吗？
参考答案｜**不是。过细会增加路由、上下文复制和冲突成本，并造成能力重叠。专家边界应围绕稳定领域、独立权限或独特工具形成，只有边际质量收益明显时再拆分。

**追问 2｜如何避免每个 Agent 都重复 RAG？
参考答案｜**使用统一、带 ACL 的检索服务和任务级 Evidence Store，入口或研究 Agent 先检索，其他 Agent 通过引用复用；只有出现新的信息需求时做增量检索，避免每个 Agent 从头搜索。

**追问 3｜跨组织 Agent 如何计费和限额？
参考答案｜**对每个组织/租户记录模型 Token、工具调用、远端任务和存储用量，设置预算、并发、速率和最大 Hop；跨组织调用使用可验证身份、合同化 SLO 和用量签名，支持 Chargeback。
