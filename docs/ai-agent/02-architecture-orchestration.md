# Agent 架构与编排模式

> 来源模块：模块二。本页保留完整标准答案、P7/P8 判断线和连续追问。

**从单循环到可恢复、可治理的 Agent Runtime**

<blockquote>
<p><strong>本模块考察：</strong>重点判断候选人能否选择合适的编排模式，并处理状态、幂等、长任务和多租户等工程问题。</p>
</blockquote>

本模块共 10 题｜建议先用 90 秒作答，再接受 2—3 轮追问。

## Q011｜ReAct、Plan-and-Execute、Router 和 Supervisor 模式分别适合什么场景？

**考察意图｜**考察候选人对常见 Agent 范式的理解和选型能力。

**标准答案**

- ReAct 在“思考/决策—行动—观察”之间逐步循环，适合步骤数不确定、需要边查边做的任务，但容易产生冗余调用和循环。

- Plan-and-Execute 先生成整体计划，再逐步执行，适合多步骤任务和进度可视化；缺点是初始计划可能过早固化，需要允许增量重规划。

- Router 根据意图、领域或风险把请求分发给不同流程、模型或专家，适合任务边界较清楚的系统。

- Supervisor 由一个协调者选择子 Agent、汇总结果和处理冲突，适合能力分工明显的 Multi-Agent，但会形成中心瓶颈。

- 生产系统常常混合使用：入口 Router，复杂任务进入 Planner，执行过程中局部 ReAct，跨专家协作由 Supervisor 管理。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能结合实际项目说明为什么选择某种模式，并给出替代方案与失败模式。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会按任务风险和复杂度动态选择编排模式，而不是把所有请求都送入同一个通用循环。</p>
</blockquote>

高频追问与参考答案

**追问 1｜ReAct 为什么容易无限循环？
参考答案｜**ReAct 如果缺少可验证的成功条件、错误分类和预算约束，模型可能把相同观察解释成‘再试一次’，不断重复工具调用。应增加重复调用检测、状态增量判断、最大轮次和人工升级。

**追问 2｜Plan 生成后能否直接信任？
参考答案｜**不能直接信任。计划要经过 Schema、依赖、权限、成本、工具可用性和业务规则校验，执行过程中还要根据新证据增量重规划，而不是把初始计划当成不可修改的事实。

**追问 3｜Supervisor 发生故障时怎么办？
参考答案｜**Supervisor 应无状态或可横向扩展，任务状态放在持久化存储，通过租约、队列或领导者选举接管。故障时可以由备用协调者恢复，或把任务暂停在安全检查点，不能让状态只存在其内存。

## Q012｜为什么生产 Agent 往往要把确定性 Workflow 和模型决策混合起来？

**考察意图｜**考察候选人是否懂得把 LLM 放在最有价值、又可控的位置。

**标准答案**

- 身份校验、权限、金额计算、状态迁移、支付扣款等规则明确的步骤应保持确定性。

- 意图理解、信息归纳、模糊匹配、计划生成和异常解释适合由模型承担。

- 混合架构能让流程的关键边界可审计，同时保留模型处理非结构化输入和不确定性的优势。

- 每个模型节点都应定义输入 Schema、输出 Schema、失败分支、超时、重试和人工兜底。

- 不要让模型直接决定数据库事务是否提交；模型可以提出动作，业务服务验证并执行。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能把业务流程拆成确定性节点与智能节点，并解释每个边界的风险。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 能形成组织级“自治分级标准”，统一规定哪些动作允许自动执行、哪些必须审批或双重校验。</p>
</blockquote>

高频追问与参考答案

**追问 1｜哪些节点最不适合交给模型？
参考答案｜**身份认证、权限、金额计算、数据库事务、支付扣款、审批和不可逆状态迁移最不适合直接交给模型。模型可以提出候选动作，但最终应由规则服务校验并执行。

**追问 2｜模型节点失败时 Workflow 怎么继续？
参考答案｜**Workflow 应为模型节点定义超时、有限重试、备用模型、确定性降级和人工分支。失败状态要显式记录，使流程能从当前节点恢复，而不是从头重跑。

**追问 3｜怎样避免流程图被 Agent 逻辑打散？
参考答案｜**让 Workflow/状态机拥有任务生命周期和真实状态，Agent 逻辑只能存在于边界清晰、输入输出有 Schema 的节点内。模型不能随意新增隐藏分支，动态计划也要映射成可审计的版本化子流程。

## Q013｜Planner、Executor 和 Verifier 应如何解耦？

**考察意图｜**考察候选人是否具备可维护、可评估的任务分层设计。

**标准答案**

- Planner 输出结构化计划：步骤、依赖、预期产物、候选工具、成功标准和风险等级，而不是一段不可执行的自然语言。

- Executor 只负责按计划调用工具、维护幂等和写入状态，不应悄悄修改业务目标。

- Verifier 基于规则、测试、证据或独立模型检查结果是否满足成功标准，并决定结束、修复或重规划。

- 三者可以使用不同模型和权限：Planner 看全局，Executor 只拿当前步骤所需上下文，Verifier 尽量使用外部可验证信号。

- 共享的是版本化任务状态，不是无限增长的自由文本聊天记录。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计 typed plan 与状态转换，并建立每一层的独立指标。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会进一步支持策略可插拔、跨模型路由、计划审计、重放和面向不同业务的编排 DSL。</p>
</blockquote>

高频追问与参考答案

**追问 1｜Verifier 与 Critic 有什么区别？
参考答案｜**Critic 更偏向给出改进意见，可能是开放式和非决定性的；Verifier 应依据明确成功标准做通过、失败或需修复的判定，并能驱动状态机。高风险验证应尽量依赖外部规则与证据。

**追问 2｜Planner 计划过细会有什么问题？
参考答案｜**计划过细会增加模型调用、状态管理和验证成本，还容易在信息不足时过早承诺具体路径。更好的做法是规划到可验证的里程碑，局部细节由 Executor 在当前上下文中展开。

**追问 3｜执行中发现新信息由谁修改计划？
参考答案｜**Executor 只报告新观察和计划偏差，由 Planner/Replanner 生成新版本计划；若涉及目标、权限、成本或已执行副作用的变化，还应由 Verifier、策略层或人工批准。

## Q014｜状态机、DAG 和事件驱动编排分别怎么选？

**考察意图｜**考察候选人能否根据任务生命周期，而不是框架热度做架构选择。

**标准答案**

- 状态机适合状态有限、迁移规则明确、需要审批和恢复的任务，例如 KYC Case、退款和告警处置。

- DAG 适合依赖关系清晰、可并行的批处理或分析任务，但对动态循环和人工等待表达较弱。

- 事件驱动适合跨服务、长时间运行、异步回调和高并发任务，通过事件解耦生产者与消费者。

- 复杂 Agent 常用“状态机管理生命周期 + DAG 表达局部计划 + 事件驱动执行长任务”。

- 无论哪种方式，都要定义持久化状态、幂等键、事件顺序、超时和补偿。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能用任务实例说明状态模型，并给出一致性与恢复方案。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会把编排抽象为平台能力，支持版本迁移、跨区域调度、事件溯源和租户级资源隔离。</p>
</blockquote>

高频追问与参考答案

**追问 1｜DAG 中如何处理动态新增步骤？
参考答案｜**可把可变部分表示为运行时子图或状态机中的‘规划—执行’循环，新步骤写入版本化计划，而不是直接修改正在执行的静态 DAG。调度器只接受通过依赖和权限校验的节点。

**追问 2｜事件乱序怎么办？
参考答案｜**按 task_id 或聚合根分区保证局部顺序，同时使用 event_id、序列号、版本号和幂等消费。无法保证顺序时先缓冲，超时后基于当前状态做重放或补偿。

**追问 3｜状态机版本升级时存量任务怎么迁移？
参考答案｜**状态中显式记录 schema_version/runtime_version。存量任务可以固定在旧执行器，或只在安全 Checkpoint 通过迁移适配器升级；发布前必须验证旧状态向新结构的可逆迁移。

## Q015｜Agent Loop 应如何设计终止条件？

**考察意图｜**考察候选人是否意识到“不停调用直到模型说完成”是危险的。

**标准答案**

- 业务成功条件：产物通过 Schema、规则、测试或用户确认，而不是只看模型输出“完成”。

- 资源上限：最大轮次、模型调用数、Token、费用、墙钟时间和工具调用次数。

- 无进展检测：连续步骤没有新增证据、重复调用同一工具、计划状态不变化或相同错误反复出现。

- 风险终止：触发高风险动作、权限不足、证据冲突或置信度低时暂停并升级人工。

- 故障终止：不可重试错误、依赖熔断、任务被取消或租户额度耗尽。

- 终止后必须返回可解释状态：成功、部分成功、失败、等待用户、等待审批或可重试。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能实现循环检测和预算控制，并在 Trace 中清楚解释终止原因。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会基于任务价值动态分配预算，用边际收益判断是否值得继续下一步。</p>
</blockquote>

高频追问与参考答案

**追问 1｜如何判断“无进展”？
参考答案｜**判断连续若干步是否没有新增证据、状态字段无变化、验证分数不提升、重复调用相同工具/参数或同一错误循环出现。最好使用结构化状态差异，而不是让模型自己判断‘有没有进展’。

**追问 2｜最大轮次设多少合适？
参考答案｜**没有统一数字，应根据任务步骤分布、风险和预算通过离线回放确定。可以设置任务类型级软上限和平台硬上限，并同时限制时间、Token、费用与工具调用次数。

**追问 3｜部分完成的任务怎么对用户表达？
参考答案｜**明确列出已完成、失败、未执行和等待项，交付已有产物、失败原因、是否产生副作用以及下一步选择。不要用一句‘任务失败’掩盖已经成功或需要补偿的部分。

## Q016｜Agent 中的幂等应该怎么做？

**考察意图｜**考察候选人能否处理模型重试、网络超时和副作用重复执行。

**标准答案**

- 端到端使用 task_id、step_id、tool_call_id 和业务 idempotency_key 标识一次逻辑动作。

- 工具执行前先写调用记录或幂等占位，状态至少区分 PENDING、RUNNING、SUCCEEDED、FAILED、UNKNOWN。

- 超时不等于失败：必须查询下游最终状态，不能直接再次扣款、发信或创建工单。

- 对数据库更新可使用唯一键、条件更新、事务 Outbox；对外部系统使用其幂等接口或自建去重层。

- 模型重放时读取历史工具结果，而不是默认再次执行；确需重试时必须验证动作可重试。

- 工程上追求“至少一次执行 + 幂等去重”，不要轻易宣称跨系统 Exactly Once。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能完整描述一次工具超时后的状态查询与恢复路径。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会把副作用、幂等语义和补偿动作注册进工具元数据，由 Runtime 统一执行策略。</p>
</blockquote>

高频追问与参考答案

**追问 1｜工具返回超时但实际成功怎么办？
参考答案｜**把结果标记为 UNKNOWN，而不是失败；使用业务单号或 idempotency_key 查询下游最终状态。只有确认未执行且动作可安全重试时才重试，否则复用成功结果或进入人工核对。

**追问 2｜同一个业务动作由不同 Agent 发起怎么去重？
参考答案｜**幂等边界应下沉到共享业务服务或工具网关，以业务对象和动作生成全局键，并用唯一约束、条件更新或分布式锁去重。不能只依赖各 Agent 自己的 task_id。

**追问 3｜幂等结果需要返回第一次的完整响应吗？
参考答案｜**对客户端可观察的一致性而言，最好返回第一次的规范化业务结果，因此应保存完整响应或可重建所需字段。可以额外标记这是幂等重放，但不能把第二次请求简单返回‘重复’而丢失原结果。

## Q017｜长时间运行的 Agent 任务如何设计？

**考察意图｜**考察候选人对异步任务、可恢复执行和用户体验的理解。

**标准答案**

- 请求入口快速返回 job_id/task_id，客户端通过轮询、SSE、WebSocket 或回调获取进度。

- 每个可恢复边界持久化检查点，包括计划版本、已完成步骤、外部副作用和待审批信息。

- Worker 使用租约和心跳防止任务永久占用；租约过期后由其他 Worker 接管。

- 任务需要支持取消、暂停、继续、超时、优先级、重试和死信队列。

- 工具输出和中间产物应存对象存储或业务库，上下文只保存引用与摘要。

- 用户看到的进度应来自真实状态机，而不是模型随意生成“已完成 80%”。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计持久化任务表、Worker 领取模型和恢复流程。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会进一步考虑跨区域接管、版本兼容、任务迁移、配额调度和运行成本治理。</p>
</blockquote>

高频追问与参考答案

**追问 1｜Worker 在副作用执行后、写状态前宕机怎么办？
参考答案｜**在执行副作用前写调用记录/Outbox，调用时携带幂等键；恢复后先查询下游状态并对账，再决定补记成功、重试或补偿。这样避免‘实际成功但本地未知’导致重复执行。

**追问 2｜如何实现任务取消？
参考答案｜**任务状态增加 CANCEL_REQUESTED/CANCELLED，并向 Worker 传递取消令牌，停止调度后续步骤。正在运行的外部调用只能做协作式取消；已完成副作用需要按补偿策略处理，不能假设取消等于撤销。

**追问 3｜如何避免长任务占满高优先级队列？
参考答案｜**使用独立优先级队列和 Worker 池、租户配额、并发上限、短长任务隔离及 Aging。长任务只持有短租约并分段执行，避免单个任务长期占用线程和模型额度。

## Q018｜分布式 Agent 的会话状态应该放在哪里？

**考察意图｜**考察候选人是否把进程内对象或模型上下文误当成可靠状态。

**标准答案**

- 业务真实状态应保存在数据库、事件日志或专用 Checkpointer 中，模型上下文只是某一步的输入视图。

- 短期对话状态可以按 thread_id 保存检查点；长期记忆应存独立 Memory Store，并记录租户、用户、来源、置信度和 TTL。

- 并发修改需要版本号、乐观锁或单线程 Actor/分区顺序消费，避免两个 Worker 同时推进同一任务。

- 大对象和文件只保存引用，避免会话记录无限膨胀。

- 状态结构要版本化，支持旧任务在新代码上线后继续恢复。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能区分运行状态、会话历史、长期记忆和业务数据，并给出各自存储方案。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会设计统一 State Service，提供检查点、事件溯源、并发控制、数据保留和跨区域复制策略。</p>
</blockquote>

高频追问与参考答案

**追问 1｜Redis 能否作为唯一状态存储？
参考答案｜**通常不建议。Redis 适合缓存、锁和低延迟 Checkpoint，但要考虑淘汰、故障切换和持久化语义；关键业务状态最好以数据库、事件日志或可靠 Checkpointer 为事实源，Redis 作为加速层。

**追问 2｜两个请求同时推进同一会话怎么办？
参考答案｜**使用版本号和乐观锁，或按 session/thread_id 分区到单线程 Actor/顺序队列。后到的请求若基于旧版本应拒绝、合并或重新读取后重试，不能让两个 Worker 无约束并发写。

**追问 3｜状态 Schema 变更如何兼容？
参考答案｜**状态带 schema_version，读取端提供默认值和兼容适配器，发布期间可双写新旧字段。长任务在 Checkpoint 迁移，必要时让旧任务继续运行旧版本执行器，避免一次性强迁移。

## Q019｜多租户 Agent 平台需要重点隔离哪些资源？

**考察意图｜**考察候选人的平台化、安全与企业落地能力。

**标准答案**

- 身份与权限：每次模型和工具调用都携带可验证的 tenant/user/service identity，禁止只靠 Prompt 传租户信息。

- 数据与记忆：向量索引、会话、长期记忆、缓存和日志必须按租户分区或带强制过滤。

- 工具与凭证：工具白名单、OAuth Scope、密钥、网络出口和审批策略按租户配置。

- 资源配额：模型 Token、并发、队列、存储、工具 QPS 和费用预算需要限额与优先级。

- 发布与观测：Prompt、模型、工具版本可按租户灰度；Trace、指标和审计日志要防止跨租户泄漏。

- 高敏租户可能要求独立部署、区域驻留、专属密钥和单独加密。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能给出逻辑隔离方案和越权测试用例。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会设计共享控制面、隔离数据面的平台架构，并根据合规与成本提供多种隔离等级。</p>
</blockquote>

高频追问与参考答案

**追问 1｜向量库只加 tenant_id 过滤够吗？
参考答案｜**不够。tenant_id 过滤只是最后一道逻辑隔离，还需要源系统权限校验、索引/命名空间隔离、预过滤、密钥与凭证隔离、审计和越权测试；高敏租户可使用物理独立集群。

**追问 2｜缓存如何避免跨租户命中？
参考答案｜**缓存 Key 必须包含 tenant_id、用户/角色或 ACL 哈希、数据版本和模型/Prompt 版本。语义缓存若无法证明权限等价就不能跨用户共享，权限变化时要能按标签或版本立即失效。

**追问 3｜不同租户使用不同模型策略怎么实现？
参考答案｜**控制面维护租户级策略：允许模型、区域、预算、最大自治等级、工具白名单、专属 Endpoint 和密钥。运行时根据租户配置编译路由，并把策略版本写入 Trace 以便审计和回滚。

## Q020｜如何设计一个模型抽象层与 Model Router？

**考察意图｜**考察候选人是否具备多模型、多供应商和持续演进能力。

**标准答案**

- 统一请求/响应、消息、工具调用、结构化输出、流式事件、错误码、Token 使用和取消语义。

- 建立模型能力注册表：上下文长度、模态、工具能力、结构化输出、区域、价格、限流、延迟和安全等级。

- 路由策略结合任务类型、风险、租户策略、SLO、预算和在线健康度，支持主备、降级和熔断。

- 不同提供方语义不完全一致，抽象层不能假设所有参数和错误都能一一映射；应保留 provider-specific 扩展。

- 所有路由决策、模型版本和参数必须进入 Trace，便于回归、计费和问题定位。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能实现可用的适配器、回退链和模型健康检查。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会把质量评估结果纳入动态路由，构建“质量—延迟—成本—风险”的多目标策略，并支持区域级灾备。</p>
</blockquote>

高频追问与参考答案

**追问 1｜模型回退后 Prompt 是否需要变化？
参考答案｜**通常需要。不同模型的上下文窗口、Tool Calling、结构化输出、采样参数和指令习惯不同，回退时应使用模型能力适配器重新编译 Prompt、Schema 和工具范围，而不是原样转发。

**追问 2｜如何防止某个供应商故障引发重试风暴？
参考答案｜**使用供应商级熔断、集中式重试预算、指数退避加抖动、并发闸门和负载削减。故障时只允许一层负责重试，其他层透传可重试状态，避免层层重试形成放大。

**追问 3｜路由策略如何灰度和回滚？
参考答案｜**把路由规则作为版本化配置，通过 Shadow、按租户/任务类型 Canary 和指标门禁发布。出现成功率、安全或成本异常时，控制面可立即回滚到上一版本且不依赖重新部署。
