## Q030｜一个高质量 Tool Schema 应该包含哪些信息？

**考察意图｜**考察候选人是否懂得工具描述直接影响模型选择与参数质量。

**标准答案**

- 名称要稳定、语义单一，通常使用动词+对象，例如 get_order、cancel_order，避免万能工具 execute_action。

- 描述要明确“什么时候使用、什么时候不要使用、成功前置条件和副作用”，减少相似工具之间的歧义。

- 参数使用强类型、必填项、枚举、格式、范围和示例；复杂对象拆分，避免一个自由文本参数承载全部语义。

- 返回值使用统一 Envelope，包含 status、data、error_code、message、retryable、trace_id 和必要的业务版本。

- 工具元数据应声明风险等级、是否幂等、超时、权限 Scope、费用和是否需要人工审批。

- Schema 变更必须版本化并做兼容检查，因为模型 Prompt、评估集和消费者都依赖它。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能通过工具选择率和参数准确率迭代 Schema，而不是只凭感觉改描述。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建立 Tool Registry 与治理规范，自动生成 SDK、权限策略、评估样本和文档。</p>
</blockquote>

高频追问与参考答案

**追问 1｜工具描述应该写多长？
参考答案｜**描述要足以让模型区分‘何时用、何时不用、前置条件、主要副作用和返回含义’，但应简洁且无重复。长度没有固定值，目标是最小化歧义，而不是把整份接口文档塞进 Schema。

**追问 2｜一个工具参数太多怎么办？
参考答案｜**先判断是否职责过大。可把相关字段封装成嵌套对象、提供合理默认值，或拆成‘查询—确认—执行’多个工具；不要用几十个可选参数构造万能工具。

**追问 3｜错误信息应该直接返回异常堆栈吗？
参考答案｜**不应该。返回稳定的错误码、可重试标志、安全的说明、字段级错误和 correlation_id；异常堆栈只进入受控日志，避免泄露路径、密钥和内部实现。

## Q031｜多个工具功能重叠时，如何减少模型选错？

**考察意图｜**考察候选人对工具发现、路由与评估的理解。

**标准答案**

- 优先从产品和 API 边界上消除重叠，让每个工具承担清晰、互斥的能力。

- 使用命名空间、显式适用条件和反例，例如 refund_order 仅处理已支付订单，cancel_order 仅处理未发货订单。

- 先由 Router 根据领域、租户和任务阶段缩小可见工具集合，不要一次把几百个工具全部暴露给模型。

- 对高频混淆对构造专门评估集，分别统计工具选择、参数和最终执行正确率。

- 必要时增加确定性前置判断或两阶段选择：先选领域，再选具体工具。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能定位是描述歧义、上下文不足、模型能力还是业务边界本身导致误选。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会根据历史成功率、用户权限和当前任务状态动态编译工具集合，并实现工具检索。</p>
</blockquote>

高频追问与参考答案

**追问 1｜工具越少越好吗？
参考答案｜**不是越少越好，而是只暴露当前任务真正需要、语义互斥且粒度合适的工具。工具过多会增加选择难度，工具过少则会形成权限过大的万能接口。

**追问 2｜是否可以让一个小模型先选工具？
参考答案｜**可以。小模型、规则或向量检索可先筛选候选工具，再交给主模型决定参数；但风险策略和权限校验仍由应用层完成，不能把预路由结果直接视为授权。

**追问 3｜工具选择正确但参数错误如何评估？
参考答案｜**把工具选择正确率与参数正确率分开，再对必填、枚举、实体、跨字段和业务约束做字段级指标。可以统计部分正确用于诊断，但只有全部校验通过才允许真实执行。

## Q032｜Agent 调用工具时，权限和审批应该放在哪里？

**考察意图｜**考察候选人是否把安全边界错误地交给模型。

**标准答案**

- 权限必须在工具网关或业务服务侧强制执行，模型的“我有权限”不构成授权。

- 请求携带真实用户、租户、服务身份和最小 Scope，工具层做 RBAC/ABAC、对象级权限和数据范围校验。

- 按副作用和风险分级：只读低风险可自动执行；写操作、外发、删除、支付等需要二次确认或人工审批。

- 审批要绑定具体动作、参数、资源版本和有效期，防止批准 A 后被模型替换成 B。

- 每次拒绝、审批和执行都写入不可抵赖的审计日志。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计一条从用户身份到下游系统的完整授权传播链。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建设集中 Policy Engine，支持租户自定义、动态风险评分、Step-up Authentication 和合规审计。</p>
</blockquote>

高频追问与参考答案

**追问 1｜为什么不能把管理员 Token 放在 Agent 服务里？
参考答案｜**管理员 Token 权限范围过大，一旦发生 Prompt Injection、日志泄漏或代码漏洞，影响面就是整个系统。应使用代表当前用户或任务的短期、最小 Scope 凭证，并由工具网关做再次授权。

**追问 2｜审批后参数变化怎么办？
参考答案｜**审批必须绑定动作类型、对象、参数哈希、策略版本和有效期。任何影响风险的参数变化都使原审批失效，需要重新评估或审批，不能只审批一个模糊的自然语言意图。

**追问 3｜Agent 代表用户调用第三方 API 如何授权？
参考答案｜**使用 OAuth/OIDC 的 delegated authorization 或 on-behalf-of 流程，由 Token Broker 签发短期、细粒度 Scope 凭证。凭证存放在安全服务中，只在调用时注入，Agent 和模型都不应看到长期 Token。

## Q033｜代码执行、浏览器操作和文件处理工具为什么需要沙箱？

**考察意图｜**考察候选人对高风险工具隔离的理解。

**标准答案**

- 模型生成的代码、命令和网页操作都属于不可信输入，可能读取密钥、破坏文件、横向移动或访问恶意站点。

- 沙箱应限制 CPU、内存、磁盘、进程数、执行时间和系统调用，并采用临时文件系统与最小镜像。

- 网络默认拒绝，仅开放允许域名、端口和协议；敏感凭证按任务临时注入，不写入 Prompt 或永久磁盘。

- 宿主机、租户和任务之间要强隔离，执行后销毁环境并清理产物中的敏感信息。

- 所有命令、网络请求、文件变更和产物哈希进入 Trace；高风险动作仍需人工确认。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计容器级沙箱、网络出口和资源配额。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会评估容器、MicroVM、浏览器隔离和远程执行集群的安全/成本，并建设多租户沙箱调度平台。</p>
</blockquote>

高频追问与参考答案

**追问 1｜Docker 就一定足够安全吗？
参考答案｜**不一定。普通 Docker 仍共享宿主机内核，还可能因高权限、危险挂载、开放网络或逃逸漏洞被突破。高风险执行可增加 seccomp/AppArmor、只读文件系统、网络隔离，甚至使用 gVisor、Kata 或 MicroVM。

**追问 2｜沙箱如何安全访问私有代码仓库？
参考答案｜**通过凭证代理在任务运行时注入短期、只读、仓库级 Token，只允许访问白名单地址；克隆后立即撤销或过期，Token 不写入磁盘、日志和模型上下文，并审计每次访问。

**追问 3｜执行环境如何复用以降低启动延迟？
参考答案｜**使用预热的干净基础镜像或 MicroVM 快照，任务启动时创建独立写时复制层。可复用镜像和运行时缓存，但不能复用租户工作目录、环境变量和秘密；任务结束后销毁或彻底重置。

## Q034｜工具调用什么时候可以并行，什么时候必须串行？

**考察意图｜**考察候选人是否具备依赖分析、资源控制和副作用意识。

**标准答案**

- 相互独立的只读查询、不同数据源检索和无共享写冲突的分析任务通常可以并行。

- 存在数据依赖、顺序约束、共享锁、同一资源写入或前一步决定后一步参数时必须串行。

- 并行前要检查工具 QPS、第三方限流、租户配额和最大并发，避免瞬时放大。

- 聚合结果需要定义部分失败语义：全部成功、至少一个成功、法定必需源全部成功或超时降级。

- 并行任务应支持统一 Deadline、取消传播和 Trace 关联。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能把计划转换为依赖 DAG，并实现有界并发和部分失败处理。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会根据工具实时健康、成本和任务价值进行动态调度与投机执行。</p>
</blockquote>

高频追问与参考答案

**追问 1｜两个查询都读数据库就一定能并行吗？
参考答案｜**不一定。若两个查询依赖同一事务快照、会竞争锁、给数据库造成峰值压力，或第二个查询依赖第一个的实体范围，就应串行或受控并发。并行决策要同时考虑语义依赖和下游容量。

**追问 2｜并行后结果顺序如何保证？
参考答案｜**每个分支携带 step_id，聚合器按计划中的确定性顺序或键排序，而不是按完成时间拼接。若顺序本身有业务含义，还要在 Schema 中显式声明。

**追问 3｜一个分支失败是否取消其他分支？
参考答案｜**取决于汇聚语义。所有分支都必需时可 Fail-fast 并尝试取消；可容忍缺失时继续其他分支并返回部分结果。取消只是最佳努力，已产生副作用的分支仍要对账或补偿。

## Q035｜工具超时、重试、熔断和降级应该怎样设计？

**考察意图｜**考察候选人对外部依赖可靠性的工程能力。

**标准答案**

- 为整个任务和每个工具设置 Deadline，单次工具超时不能超过剩余总预算。

- 错误分为瞬时可重试、永久业务错误、权限错误、参数错误和结果未知；只有可重试且幂等的动作才自动重试。

- 使用指数退避、抖动、最大次数和 Retry-After，防止故障时形成同步重试风暴。

- 连续失败触发熔断，短期快速失败或切换备用数据源；半开阶段用少量探测恢复。

- 降级可以返回缓存、只读结果、简化答案、延迟处理或人工接管，但必须显式标注数据时效和能力缺失。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能给出每类错误的状态迁移和恢复策略。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会把工具 SLO、熔断、配额和成本统一纳入 Runtime 调度，并支持跨区域/跨供应商容灾。</p>
</blockquote>

高频追问与参考答案

**追问 1｜写操作超时后能直接重试吗？
参考答案｜**不能直接重试。超时只代表调用方不知道结果，应先用幂等键或业务单号查询最终状态；只有确认未执行且操作可安全重放时才重试。

**追问 2｜备用工具结果不完全一致怎么办？
参考答案｜**为主备工具定义统一能力契约和差异清单，降级结果要标注来源、时效和缺失字段。若差异可能影响高风险决策，应降低置信度、限制动作或转人工，而不是假装等价。

**追问 3｜如何防止 Agent 在熔断后不断换工具重试？
参考答案｜**工具网关维护全局熔断状态和任务级重试/切换预算，并把‘当前不可用能力’作为硬约束传给 Planner。对等价工具做同一能力组限额，防止模型在多个名字之间循环。

## Q036｜什么是 MCP？它的核心参与者和能力是什么？

**考察意图｜**考察候选人是否掌握当前 Agent 工具生态的标准化协议，而不是只会框架 API。

**标准答案**

- MCP（Model Context Protocol）用于标准化 AI 应用与外部上下文/能力之间的连接，典型参与者包括 Host、Client 和 Server。

- Server 可以向 Client 暴露 Tools、Resources 和 Prompts；Tools 供模型执行动作，Resources 提供可读取上下文，Prompts 提供可发现的模板化交互。

- Client 与 Server 在初始化时协商能力，协议还覆盖进度、取消、错误等通用机制；较新的规范也支持 Elicitation 等客户端能力。

- MCP 解决发现、描述和通信标准化，不自动解决业务权限、数据可信、工具安全和执行审计。

- 生产使用时要固定或协商规范版本，并验证 Server 身份、能力与 Schema。

<blockquote>
<p><strong>版本/实践提示：</strong>版本提示：本手册以 2026-07-28 MCP 规范为参考基线。</p>
</blockquote>

<blockquote>
<p><strong>P7 合格线：</strong>P7 能画出 Host—Client—Server 架构，说明本地 Server 与远程 Server 的部署差异。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会进一步设计企业 MCP Gateway、Registry、策略、授权代理、版本兼容和 Server 供应链治理。</p>
</blockquote>

高频追问与参考答案

**追问 1｜MCP Server 等于一个 Agent 吗？
参考答案｜**不是。MCP Server 是能力提供方，暴露 Tools、Resources 或 Prompts；它可以完全是确定性服务。Agent 是会围绕目标进行决策和循环执行的主体，两者可以组合但概念不同。

**追问 2｜Resources 与 Tools 的区别是什么？
参考答案｜**Resources 更像可寻址、可读取的上下文或数据，通常由应用选择后提供给模型；Tools 是可调用的操作，可能查询或产生副作用。二者在权限、确认和审计策略上通常也不同。

**追问 3｜MCP 能否直接解决权限问题？
参考答案｜**不能。MCP 规范化了能力发现和通信，但授权、用户同意、凭证管理、最小权限、沙箱和审计仍需 Host、Server 及下游系统共同实现。

## Q037｜MCP 与普通 Function Calling 有什么区别？

**考察意图｜**考察候选人能否区分模型层调用机制与跨应用连接协议。

**标准答案**

- Function Calling 是模型输出结构化工具调用意图的机制，应用负责把调用分发到实际函数。

- MCP 是客户端与外部 Server 之间的标准协议，提供能力发现、Schema 获取、资源读取、Prompt 获取和生命周期通信。

- MCP 暴露的 Tool 最终仍可能通过模型的 Tool Calling 被选择；两者是互补关系，不是替代关系。

- 普通 Function Calling 常与单个应用代码耦合，MCP 更便于多个客户端复用同一 Server 和跨语言互操作。

- 引入 MCP 后仍需在 Host/网关侧做工具筛选、权限、审批、隔离和审计。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能说明什么时候直接函数调用更简单，什么时候 MCP 的复用与生态价值更高。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会设计同时兼容原生工具、MCP、内部 RPC 和第三方 API 的统一工具控制面。</p>
</blockquote>

高频追问与参考答案

**追问 1｜一个内部单体应用是否值得上 MCP？
参考答案｜**不一定。单体内部只有少量稳定函数时，直接 Function Calling 更简单；当能力要被多个 Host/模型复用、需要标准发现、跨进程隔离或第三方互操作时，MCP 的价值更明显。

**追问 2｜MCP Tool Schema 与模型 Tool Schema 如何转换？
参考答案｜**由适配层把 MCP Tool 的名称、描述和 JSON Schema 映射为模型支持的工具格式，并处理命名空间、Schema 子集差异、错误和流式能力。不能假设所有模型都支持完全相同的 JSON Schema。

**追问 3｜远程 MCP Server 失败如何降级？
参考答案｜**对只读能力可回退到缓存、本地实现或备用 Server，并标注数据新鲜度；对写操作如果无法确认状态，应暂停并对账，不能静默切换到语义不等价的工具。

## Q038｜企业接入 MCP Server 时有哪些安全风险？

**考察意图｜**考察候选人对 MCP 供应链、身份和数据流风险的理解。

**标准答案**

- 恶意或被攻陷的 Server 可能提供误导性工具描述、诱导参数、泄露数据或返回间接 Prompt Injection 内容。

- Server 访问范围可能过大，例如同时获得文件、数据库、代码仓库和外网权限，导致横向影响。

- 需要验证来源、签名/版本、依赖和更新渠道，维护允许列表并对变更做审查。

- 授权使用短期、最小 Scope 的委托令牌，禁止共享长期管理员密钥；不同租户和任务隔离凭证。

- 远程通信使用 TLS、身份认证、速率限制和内容审计；高风险工具放入沙箱或审批链。

- Tool、Resource、Prompt 都要视作供应链输入，不能只审核可执行 Tool。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能完成 MCP Threat Model 和最小安全基线。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建设 MCP Registry 的准入、签名、SBOM、风险评级、运行时策略和持续监测。</p>
</blockquote>

高频追问与参考答案

**追问 1｜内部自研 MCP Server 是否无需审核？
参考答案｜**仍然需要。内部服务也可能存在代码漏洞、过度权限、依赖投毒、描述被篡改和运维账号失陷。应走代码审查、权限审计、威胁建模、签名发布和持续监控。

**追问 2｜Prompt 模板也可能攻击吗？
参考答案｜**可能。Prompt/模板本身可以诱导 Host 泄露上下文、选择危险工具或绕过业务边界，因此它和 Tool 描述一样属于供应链输入，需要来源验证、版本锁定和安全评审。

**追问 3｜如何让 Server 代用户访问下游而不泄露 Token？
参考答案｜**使用 OAuth/OIDC 的 on-behalf-of 或 Token Exchange，由凭证代理按用户、Server 和下游 Scope 签发短期 Token。Server 只在调用链中使用凭证，不把 Token 返回给模型或写入普通日志。

## Q039｜什么是 A2A？核心对象有哪些？

**考察意图｜**考察候选人对 Agent 间互操作协议的理解。

**标准答案**

- A2A（Agent2Agent）面向独立 Agent 系统之间的发现、通信与协作，允许双方内部实现保持相对不透明。

- Agent Card 描述远端 Agent 的身份、能力/技能、端点、支持模态、认证和协议能力，客户端据此发现与选择。

- Message 用于交互内容，Task 表示可跟踪的工作单元与生命周期，Artifact 表示远端 Agent 生成的具体交付物。

- 协议支持同步、流式和异步长任务等模式，并需要处理取消、错误、版本和认证。

- A2A 只提供互操作框架，业务信任、委托权限、结果验证和计费仍需应用层设计。

<blockquote>
<p><strong>版本/实践提示：</strong>版本提示：本手册将 A2A v1.0 作为面试讨论基线。</p>
</blockquote>

<blockquote>
<p><strong>P7 合格线：</strong>P7 能描述从发现 Agent Card、创建任务、接收流式进度到获取 Artifact 的完整流程。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会考虑跨组织身份、Agent Card 验签、协议版本协商、租户隔离和结果责任边界。</p>
</blockquote>

高频追问与参考答案

**追问 1｜Message 与 Artifact 有什么区别？
参考答案｜**Message 用于 Agent 间交换意图、上下文和阶段性交流；Artifact 是任务产生的可交付结果，例如报告、文件或结构化数据，通常有更稳定的标识、媒体类型和生命周期。

**追问 2｜A2A 远端 Agent 是否需要暴露内部工具？
参考答案｜**不需要。远端 Agent 只需通过能力描述和任务接口暴露它能完成什么，内部使用哪些模型、工具和编排可以保持封装；这也是 A2A 与直接共享工具列表的重要差别。

**追问 3｜如何发现可信 Agent？
参考答案｜**通过受控注册表或已验证的 Agent Card 发现候选，再结合域名/TLS、签名、发布者身份、允许列表、版本和安全评估建立信任。公开可发现不等于可直接授权调用。

## Q040｜A2A 与 MCP 的边界是什么？可以怎样组合？

**考察意图｜**考察候选人能否形成协议层次感。

**标准答案**

- MCP 主要解决“AI 应用/Agent 如何连接工具、资源和提示模板”；A2A 主要解决“一个独立 Agent 如何与另一个 Agent 协作”。

- MCP Server 通常暴露能力接口，调用方掌握主要编排；A2A 远端 Agent 可以拥有自己的规划、状态和执行逻辑，并返回任务/产物。

- 一个 Agent 可以通过 MCP 使用数据库和内部工具，同时通过 A2A 把专业任务委派给外部 Agent。

- 两者组合时要避免身份断链：用户授权、租户、任务 ID、数据使用范围和审计信息必须跨协议传播。

- 不要把每个微服务包装成 Agent；只有具备独立目标处理和能力自治的系统才适合 A2A。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能画出 MCP Tool 与 A2A Remote Agent 并存的架构。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会设计统一委托策略，决定何时本地工具执行、何时远程 Agent 承接，并管理信任、成本和 SLA。</p>
</blockquote>

高频追问与参考答案

**追问 1｜远端 Agent 能否被包装成 Tool？
参考答案｜**可以把简单、短时、无复杂生命周期的远端 Agent 包装成 Tool，但会弱化任务状态、流式进度、取消和 Artifact 等语义。复杂委派更适合保留 A2A 任务模型。

**追问 2｜什么时候用 A2A，什么时候用普通 RPC？
参考答案｜**目标服务是确定性、接口已知、一次请求即可完成时用普通 RPC；需要把目标委派给自治 Agent、存在长任务、能力协商、异步状态或多阶段结果时更适合 A2A。

**追问 3｜跨协议 Trace 如何关联？
参考答案｜**入口生成统一 trace_id，并通过 W3C Trace Context 等标准在 MCP、A2A 和内部 RPC 中传递；适配器把 A2A task_id、MCP request/tool_call_id 映射为 Span 属性和链接。

## Q041｜Agent 互操作时如何处理版本、流式、取消和错误？

**考察意图｜**考察候选人是否具备真正落地跨 Agent 协作的协议意识。

**标准答案**

- 发现阶段读取并缓存能力与协议版本，但要设置过期时间和变更通知，不能永久信任旧 Agent Card。

- 请求中携带协议版本和幂等任务标识；不兼容时明确拒绝或使用兼容适配层，避免静默降级。

- 长任务通过流式事件或异步任务状态返回进度，最终 Artifact 与中间 Message 分离。

- 取消应传播到远端任务，并定义“已取消但副作用可能完成”的状态，不能只断开客户端连接。

- 错误采用稳定分类：认证、授权、参数、能力不支持、限流、超时、任务不存在、内部错误和部分完成。

- 客户端必须验证 Artifact 类型、大小、来源和完整性，再写入本地系统。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计兼容层与任务状态机，并处理断线重连和重复消息。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会把协议协商、跨组织 SLO、计费、验签和争议审计纳入企业级 Agent Mesh。</p>
</blockquote>

高频追问与参考答案

**追问 1｜SSE 断线后如何续传？
参考答案｜**每个流事件带单调 event_id/sequence，服务端保存有限重放缓冲或持久化任务事件。客户端重连时携带 Last-Event-ID，从最后确认位置续传；超出保留期则读取任务快照并重新订阅。

**追问 2｜取消请求一定能撤销副作用吗？
参考答案｜**不一定。取消只能阻止尚未开始或支持协作取消的工作，已经完成的付款、发信等副作用不会自动撤销；系统必须返回取消边界，并对已执行动作做对账或补偿。

**追问 3｜远端 Agent 返回未知 Artifact 类型怎么办？
参考答案｜**先依据媒体类型和版本协商判断是否有兼容处理器；未知类型应作为不透明引用保存、请求兼容格式或明确拒绝，不能把未知内容直接执行或强行解析。
