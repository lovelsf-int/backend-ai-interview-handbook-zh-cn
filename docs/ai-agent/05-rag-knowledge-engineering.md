<blockquote>
<p><strong>本模块考察：</strong>重点判断候选人能否建设完整知识链路、理解召回/排序指标，并处理权限、时效、复杂文档和证据追踪。</p>

## Q042｜请完整描述一个生产级 RAG 的入库与查询链路。

**考察意图｜**考察候选人是否只停留在“切 Chunk、做 Embedding、存向量库”的 Demo 阶段。

**标准答案**

- 入库链路：数据源接入 → 文件安全检查 → 文档解析/OCR/版面与表格恢复 → Canonical Block → Chunk/父子关系 → Metadata/ACL/版本 → Embedding 与关键词索引 → 质量校验。

- 查询链路：问题理解 → 身份与权限过滤 → Query Rewrite/拆解 → Dense + Sparse/Keyword 混合召回 → 融合 → Rerank → 去重与上下文编排 → LLM 回答 → 引用与置信度。

- 每个 Chunk 需要稳定 ID、来源文档、页码/章节、字符范围、时间有效性、租户、权限、版本和哈希。

- 索引、Embedding、解析器和 Chunk 策略都要版本化，支持重建、双写、灰度和回滚。

- 系统还要有离线评估、在线反馈、坏文档隔离、增量更新、删除传播和监控。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能画出双流水线并解释每个阶段的输入输出、失败模式和指标。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会把 RAG 建设成知识平台，支持多模态、跨部门权限、生命周期治理、数据血缘和多策略检索。</p>
</blockquote>

高频追问与参考答案

**追问 1｜PDF 解析错了会影响哪些下游环节？
参考答案｜**解析错误会先破坏章节、表格、页码和阅读顺序，随后影响 Chunk 边界、Metadata、Embedding 与关键词索引；查询阶段会进一步造成召回、Rerank、上下文拼接和引用定位错误，最终表现为模型‘有资料却答错’。

**追问 2｜删除原文后如何保证向量和缓存也删除？
参考答案｜**建立 document_version 到 chunk_id、vector_id、倒排索引和缓存标签的完整 Manifest。删除时发布 Tombstone/删除事件，幂等清理所有派生物并做异步对账；审计中保留删除证明，但不保留被要求删除的正文。

**追问 3｜为什么 Rerank 不能替代召回？
参考答案｜**Rerank 只能重新排序已经召回的候选，正确证据若不在候选集合中就无法恢复。因此要先保证 Dense、Sparse、多路查询和权限过滤后的 Recall，再用 Rerank 提升前排精度。

## Q043｜Recall@K、Precision@K、MRR、nDCG 与答案准确率分别代表什么？

**考察意图｜**考察候选人是否能正确区分检索质量和最终答案质量。

**标准答案**

- Recall@K 衡量所有相关文档中有多少被前 K 个结果召回，适合回答“需要的证据有没有被找出来”。

- Precision@K 衡量前 K 个结果中有多少是真正相关的，反映上下文噪声大小。

- MRR 关注第一个相关结果出现得有多靠前，适合通常只需要一个关键答案的任务。

- nDCG 同时考虑多个相关结果及其相关等级，并对靠前结果给予更高权重，适合排序质量评估。

- 最终答案还要评估 Correctness、Faithfulness/Groundedness、Completeness、Citation Accuracy 等；检索好不代表模型一定使用正确。

- 指标必须基于人工标注或可信判定集，并按问题类型、知识源、语言和权限场景分层。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能用一条真实问题解释 Recall 与 Precision 的权衡，并把检索和生成错误分开归因。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会将离线指标与线上任务成功、人工升级、错误成本建立映射，而不是追求单一分数。</p>
</blockquote>

高频追问与参考答案

**追问 1｜K 越大 Recall 越高，为什么不能无限增大？
参考答案｜**K 增大会增加检索、Rerank 和 Context 成本，并引入相似但错误的噪声，导致 Precision 和生成质量下降。应在 Recall 拐点处控制候选数，再结合 Rerank 与动态 Context 预算。

**追问 2｜MRR 与 nDCG 怎么选？
参考答案｜**MRR 关注第一个相关结果的位置，适合每个问题通常只有一个关键答案的检索；nDCG 支持多个相关结果和分级相关性，适合需要综合多份证据的企业检索。

**追问 3｜答案错了怎样判断是不是召回问题？
参考答案｜**先检查黄金证据是否出现在 Top-K，再看是否进入 Rerank 后的最终 Context；若证据缺失是检索链路问题，证据已完整提供但结论仍错则主要是生成、提示或验证问题。

## Q044｜Chunk 应该如何切？为什么常用 Parent-Child？

**考察意图｜**考察候选人对语义边界、召回粒度和上下文完整性的理解。

**标准答案**

- Chunk 应优先遵循标题、段落、列表、表格、代码块和语义主题边界，而不是固定字符数硬切。

- 小 Chunk 更利于精确召回，但上下文可能不完整；大 Chunk 信息完整但向量语义混杂、成本高。

- Parent-Child 常用小的 Child 做索引和召回，命中后回取更大的 Parent 作为上下文，实现“精确找、完整读”。

- Overlap 只用于保持跨边界语义，不宜过大，否则索引膨胀、重复结果和评估虚高。

- 表格、合同条款、代码和对话需要专门策略，并保留结构、标题路径和行列关系。

- Chunk 策略应通过目标问答集评估，而不是复制固定参数。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能针对政策、FAQ、表格、代码分别给出切分方案。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会支持按文档类型和查询类型动态选择 Chunk/Parent，并实现索引策略实验平台。</p>
</blockquote>

高频追问与参考答案

**追问 1｜父片段太大怎么办？
参考答案｜**先用较小 Child 做高精度召回，再按命中位置自适应扩展父级窗口，而不是固定返回整个超大 Parent。可以设置最大 Token、只取相邻段落或按标题层级回溯。

**追问 2｜Overlap 设多少合理？
参考答案｜**没有统一值，应根据文档结构、句子完整性和检索评估确定。可以从约 10%—20% 的重叠做基线，但要监控重复召回、索引体积和边界问题，结构化文档优先按语义边界切而非机械重叠。

**追问 3｜表格跨页时如何保持结构？
参考答案｜**解析时保留表名、表头、行列关系、合并单元格和跨页 continuation 标识，并把重复表头关联到同一表。可同时保存面向 LLM 的 Markdown/HTML 与面向计算的结构化 JSON。

## Q045｜为什么企业 RAG 通常要做 Hybrid Search 和 Rerank？

**考察意图｜**考察候选人是否理解语义检索和精确检索的互补性。

**标准答案**

- Dense Search 擅长同义表达和语义相似，但对型号、姓名、合同号、金额、代码和冷门词可能不稳定。

- BM25/关键词检索擅长精确 Token 和稀有词，但对改写、跨语言和语义近义较弱。

- Hybrid Search 并行召回后可用加权分数或 RRF 融合，先保证候选集合覆盖。

- Reranker 对 Query 与候选进行更精细的相关性判断，把真正可回答的证据排到前面。

- Rerank 只能重排已召回候选，召回阶段漏掉的文档无法被补回来。

- 融合权重、召回数量和 Rerank TopN 应按查询类型评估，不能全局一套参数。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能实现 Dense、BM25、RRF 与 Cross-Encoder Rerank，并给出离线对比。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会做查询分类和策略路由，例如精确 ID 查询偏关键词，复杂语义查询扩大 Dense 与多路召回。</p>
</blockquote>

高频追问与参考答案

**追问 1｜RRF 为什么常用？
参考答案｜**Dense 与 BM25 分数分布不可直接比较，RRF 只使用各路排名进行融合，对分数校准不敏感、实现稳定，特别适合作为混合检索的可靠基线。

**追问 2｜Reranker 越大越好吗？
参考答案｜**不一定。更大的 Cross-Encoder 可能提高排序质量，也会增加 GPU、延迟和吞吐成本；应在有限 Top-N 上运行，并用领域数据比较 nDCG、答案质量和单位请求成本。

**追问 3｜如何控制 Hybrid Search 延迟？
参考答案｜**Dense 和 Sparse 并行执行，限制各路候选数，使用高效 ANN、过滤索引和 Query/Embedding 缓存；先轻量融合再只对少量候选 Rerank，并设置阶段性超时预算。

## Q046｜RAG 权限过滤应该放在哪一层？

**考察意图｜**考察候选人对数据越权和缓存泄漏的理解。

**标准答案**

- 权限应尽量在检索前或检索过程中强制过滤，确保无权文档不会进入候选集合和模型上下文。

- 索引元数据包含 tenant_id、用户/角色/部门、文档 ACL、密级、地域和有效期；查询时由可信身份服务生成过滤条件。

- 只在生成后过滤答案不安全，因为模型已经看到了敏感内容，Trace、缓存或中间结果也可能泄露。

- 向量库、关键词索引、Rerank、语义缓存和回答缓存都必须继承同样的权限边界。

- 复杂 ACL 可先做候选权限位图/策略服务，再检索；极高敏数据可采用物理索引隔离。

- 权限变更和用户离职要及时传播到索引与缓存。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计基于用户身份的预过滤与越权测试。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会权衡预过滤召回、索引规模和策略复杂度，提供逻辑隔离、分索引和独立部署多种等级。</p>
</blockquote>

高频追问与参考答案

**追问 1｜先向量召回再过滤会有什么问题？
参考答案｜**会先把无权文档纳入候选和相似度计算，可能造成侧信道、日志或缓存泄漏；过滤后候选不足还会降低 Recall。权限应尽量在召回前或检索引擎内部完成。

**追问 2｜ACL 频繁变化怎么更新？
参考答案｜**把 ACL 抽象为用户、组和资源策略的可查询索引，查询时实时获取当前主体权限并做预过滤；变更通过事件更新索引和缓存标签，高风险权限撤销需要同步或强一致失效。

**追问 3｜语义缓存的 Key 如何包含权限？
参考答案｜**Key 至少包含 tenant_id、用户或角色集合的 ACL 哈希、数据版本、模型/Prompt 版本、语言和规范化查询。无法证明权限集合等价时，不应共享语义缓存。

## Q047｜PDF、扫描件和复杂表格为什么是 RAG 最容易出问题的地方？

**考察意图｜**考察候选人对 Document AI 和知识入库质量的理解。

**标准答案**

- PDF 常只保存字符坐标而非语义结构，直接抽文本可能打乱多栏顺序、丢标题层级、页眉页脚混入正文。

- 扫描件需要 OCR，存在错字、漏字、方向、印章和低分辨率问题；OCR 置信度应保留。

- 表格的行列关系、合并单元格、跨页表头和脚注如果丢失，文本看似完整但语义已经改变。

- 解析输出应是带 block_type、heading_path、page、bbox、table cell、source span 的结构化文档，而不是纯字符串。

- 建立解析质量抽检和黄金文档集，单独评估阅读顺序、表格还原、页码引用和 OCR。

- 低质量文档应隔离或降权，不能无声进入索引污染答案。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能说明解析、Chunk、Embedding 和检索如何层层传递错误。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建设多解析器路由、质量评分、人工校正与可追溯文档生产线。</p>
</blockquote>

高频追问与参考答案

**追问 1｜OCR 错误如何影响向量召回？
参考答案｜**OCR 错字会破坏专有名词、编号、金额和否定词，既影响 Embedding 语义，也影响 BM25 精确匹配。应保留 OCR 置信度、原始图像坐标，并对关键字段使用规则或视觉模型二次校验。

**追问 2｜表格应该转 Markdown 还是 JSON？
参考答案｜**两者用途不同：Markdown/HTML 更利于模型阅读和引用，JSON 更利于字段校验、聚合和计算。生产系统通常同时保存结构化表格与可读渲染，并通过同一 table_id 关联。

**追问 3｜页眉页脚如何识别？
参考答案｜**可根据多页重复频率、固定页顶/页底坐标、字体样式和与正文的距离识别，再结合规则去除。法律声明、版本号等有业务意义的页眉不能盲删，应作为文档级 Metadata 保存。

## Q048｜多跳问题和 Query Decomposition 应怎么做？

**考察意图｜**考察候选人处理跨文档、跨实体推理的能力。

**标准答案**

- 先判断问题是否包含多个实体、时间条件、比较、因果或必须串联多个事实，再决定是否拆解。

- Planner 输出子问题、依赖关系和需要的证据类型；每个子问题独立检索并保存来源。

- 中间结论要区分“文档直接事实”和“模型推断”，后续步骤优先使用可验证事实。

- 对可并行子问题并行检索，对依赖前一步实体的子问题串行执行。

- 最终综合时检查是否所有关键子问题都有证据，避免一处错误在多跳链路中放大。

- 设置最大分解深度与预算；简单问题不要过度 Agent 化。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计分解、证据图和失败回退，并做子问题级评估。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会根据问题复杂度、证据覆盖和成本动态决定是否继续下一跳，支持知识图谱与文本检索混合。</p>
</blockquote>

高频追问与参考答案

**追问 1｜子问题拆错怎么办？
参考答案｜**先对分解结果做实体、时间和依赖校验，必要时同时保留原问题直搜或生成备选分解。子问题结果矛盾或覆盖不足时触发重规划，无法消歧则向用户澄清。

**追问 2｜多跳过程中如何避免把推断当事实？
参考答案｜**维护 Evidence Ledger，把每一步分成‘检索到的事实’‘工具计算结果’和‘模型推断’，推断不能作为下一跳的无条件事实。最终答案的关键结论应能回溯到每一跳原始证据。

**追问 3｜什么时候 GraphRAG 更合适？
参考答案｜**当问题高度依赖实体关系、跨多份文档的路径、影响链或全局社区结构时，GraphRAG 更有价值；简单语义问答、知识更新频繁或关系抽取质量不足时，成本往往不划算。

## Q049｜新旧政策、版本冲突和知识时效如何处理？

**考察意图｜**考察候选人对企业知识生命周期与时间语义的理解。

**标准答案**

- 文档元数据保存发布时间、生效时间、失效时间、版本、状态、适用地区/产品和 supersedes 关系。

- 检索时根据用户问题中的时间点和业务上下文过滤，默认优先当前有效版本，而不是简单按上传时间最新。

- 同一主题存在冲突时，不让模型自行猜测；可按权威等级、有效期和明确的替代关系解决。

- 无法确定时同时展示冲突证据并提示人工确认，尤其是合规、财务和安全领域。

- 增量更新要保证旧 Chunk 下线、新 Chunk 上线和缓存失效的一致性。

- 答案引用应展示版本与生效日期，便于审计。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计时态检索和冲突规则。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建设知识治理工作流，包含发布审批、权威源、冲突检测、变更影响分析和订阅通知。</p>
</blockquote>

高频追问与参考答案

**追问 1｜最新上传是否等于最新生效？
参考答案｜**不等于。文档需要区分上传时间、审批状态、发布日期、生效时间、失效时间、适用地区和版本优先级；只有满足当前时点和适用范围的已生效版本才应作为权威证据。

**追问 2｜用户问历史时点怎么查？
参考答案｜**使用带 valid_from/valid_to 的时间版本或双时态模型，并把用户问题中的‘截至某日’解析为 as_of 条件。检索和引用都固定到当时版本，而不是返回今天的最新内容。

**追问 3｜缓存答案如何随政策更新失效？
参考答案｜**答案缓存记录依赖的 document_version、policy_id 和生效区间。政策发布/撤销事件按依赖标签精准失效；无法精确追踪时提高数据版本号，让旧 Key 自然不可命中。

## Q050｜RAG 在什么情况下应该拒答或向用户澄清？

**考察意图｜**考察候选人是否具备可信回答与不确定性管理能力。

**标准答案**

- 权限不足、没有召回到最低证据、证据冲突、问题缺少关键条件或知识已过期时，应拒答、澄清或转人工。

- 不要只用向量相似度一个阈值；可综合 Rerank 分数、证据覆盖、来源权威、时间有效性和回答可支持度。

- 澄清问题应针对缺失字段，例如时间、产品版本、地区、订单号，而不是笼统说“请提供更多信息”。

- 拒答时说明已检查的范围和缺失原因，但不泄露无权文档或系统内部 Prompt。

- 记录拒答类型，用于发现知识缺口、检索问题和产品输入设计缺陷。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计可解释的 No-answer Policy，并评估误答率与过度拒答率。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会按风险等级优化拒答成本：高风险偏保守，低风险允许带不确定性回答并引导补证据。</p>
</blockquote>

高频追问与参考答案

**追问 1｜相似度低就一定拒答吗？
参考答案｜**不一定。相似度低可能来自罕见编号或跨语言表达，精确关键词却已命中；相似度高也可能是错误版本。拒答应综合实体匹配、证据覆盖、来源可信度、冲突和校准后的答案置信度。

**追问 2｜如何评估过度拒答？
参考答案｜**在有 answerable 标注的评估集上统计拒答 Precision/Recall、False Refusal Rate、错误作答率和用户澄清成功率。目标是在降低无依据回答的同时，不显著损害可回答问题的完成率。

**追问 3｜模型“知道”答案但知识库没证据时能答吗？
参考答案｜**在企业‘仅基于知识库’模式下通常不应把模型先验冒充权威答案，可明确说明缺少证据并请求补充。若产品允许一般知识回答，必须显著标注来源层级，且不能用于高风险决策。

## Q051｜RAG 的引用和证据链如何设计？

**考察意图｜**考察候选人是否能让答案可追溯、可审计。

**标准答案**

- 每个候选 Chunk 保留 document_id、version、page/section、source span、hash 和检索/重排分数。

- 生成时要求结论绑定 evidence_id，输出后校验引用是否真实存在、是否支持对应句子。

- 界面可展示文档名、章节、页码和高亮原文；敏感系统还要保存当时版本快照或内容哈希。

- 引用准确率要单独评估：链接存在不代表内容支持结论，不能把“有引用”当作可信。

- 复杂综合结论应标注哪些部分是来源事实、哪些是规则计算或模型推断。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能实现句子级或字段级 Evidence Mapping，并支持点击回源。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会将证据链贯穿检索、工具、规则和人工审批，形成可重放的决策凭证。</p>
</blockquote>

高频追问与参考答案

**追问 1｜一个答案引用多个来源怎么绑定？
参考答案｜**先把答案拆成可验证 Claim，每个 Claim 绑定一个或多个 source_id、chunk/span、页码和版本；多个来源可标记为共同支持、补充或相互冲突，而不是只在段尾堆一串链接。

**追问 2｜原文更新后历史引用怎么办？
参考答案｜**引用必须指向不可变的文档版本或内容哈希。原文更新后，历史回答仍可访问当时快照或受控归档，并清楚标注旧版本；不能让同一引用静默跳到新正文。

**追问 3｜如何检测伪引用？
参考答案｜**验证引用 ID 是否真实存在、用户是否有权访问，并用蕴含模型/规则检查引用片段是否支持对应 Claim。模型自由生成的页码、标题或 URL 不能直接当作有效引用。

## Q052｜答案错误时，如何区分是检索问题还是生成问题？

**考察意图｜**考察候选人的可观测与问题归因能力。

**标准答案**

- 先检查黄金证据是否存在于知识库且解析正确；不存在是数据/入库问题。

- 再看候选召回中是否出现黄金证据；未出现是 Query、索引或召回策略问题。

- 若召回但排位很低，是融合/Rerank 问题；若进入最终 Context 仍答错，是上下文编排、Prompt 或模型使用证据的问题。

- 若模型依据错误工具结果，则需要继续追踪工具数据和时效；若引用与结论不一致，是生成后校验问题。

- 使用组件级评估和完整 Trace，建立错误标签，不要只看最终“好/坏”。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能为一次错误给出可复现的根因树和修复验证。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会把错误归因自动化，形成数据、检索、重排、生成、工具和安全各团队的闭环指标。</p>
</blockquote>

高频追问与参考答案

**追问 1｜黄金证据本身标错怎么办？
参考答案｜**黄金证据也要版本化并经过双人复核或争议仲裁，允许标记‘标签错误/多解/已过期’。发现问题后修正标注并回算历史指标，不能为了维护分数强行把错误标签当真。

**追问 2｜召回到了但模型没用，怎么优化？
参考答案｜**检查证据是否被截断、排序过后或淹没在长 Context 中，再通过 Claim-first Prompt、逐项引用、结构化回答和上下文压缩强化使用；仍失败时再评估更合适的生成模型或微调。

**追问 3｜如何建立错误分类体系？
参考答案｜**按阶段建立层级标签：解析、权限、Query 理解、召回、融合、Rerank、Context、生成、引用、规则验证和产品交互，并记录根因、严重度、是否可重现和修复组件。

## Q053｜GraphRAG 适合什么场景？什么时候反而不值得用？

**考察意图｜**考察候选人是否理性看待知识图谱和复杂检索。

**标准答案**

- GraphRAG 适合实体关系密集、多跳推理、全局主题总结、影响分析和关系追踪，例如组织、供应链、案件和代码依赖。

- 它通常需要实体/关系抽取、消歧、图构建、社区或路径检索，建设和更新成本高。

- FAQ、短政策查找、精确编号查询等简单场景，Hybrid RAG 往往更便宜、更稳定。

- 图谱中的错误关系可能放大推理偏差，必须保留边的来源、时间和置信度。

- 常见做法是图检索提供实体路径，文本检索提供原始证据，最终答案仍回到可引用文本。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能给出 GraphRAG 与普通 RAG 的选型标准和评估方法。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会设计增量图更新、实体解析、跨源冲突、图与向量融合，以及面向不同查询的动态路由。</p>
</blockquote>

高频追问与参考答案

**追问 1｜知识图谱一定比向量库准确吗？
参考答案｜**不一定。知识图谱的准确率取决于实体消歧、关系抽取和更新质量，错误边会系统性传播；向量库在模糊语义检索上反而更稳。两者解决的问题不同，通常是互补而非替代。

**追问 2｜关系抽取错误怎么修？
参考答案｜**每条边保存来源、证据片段、抽取模型版本和置信度，支持人工纠正、批量重抽取和版本回滚。高风险关系要由规则或权威数据源确认，不能只靠模型抽取。

**追问 3｜图社区摘要是否会丢失细节？
参考答案｜**会。社区摘要是压缩后的导航层，容易遗漏例外和细粒度事实。可以用它定位相关社区，但最终回答仍应下钻到原始节点、边和文档证据。
