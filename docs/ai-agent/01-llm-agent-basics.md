# LLM 与 Agent 基础

> 来源模块：模块一。本页保留完整标准答案、P7/P8 判断线和连续追问。

**从“会调用模型”走向“理解 Agent 为什么成立”**

<blockquote>
<p><strong>本模块考察：</strong>重点判断候选人是否理解 Agent 的本质、模型能力边界、推理成本以及何时不应使用 Agent。</p>
</blockquote>

本模块共 10 题｜建议先用 90 秒作答，再接受 2—3 轮追问。

## Q001｜Agent、Chatbot、Workflow 和 RPA 的本质区别是什么？

**考察意图｜**考察候选人能否划清产品形态与工程实现的边界，而不是把所有“接了大模型”的系统都叫 Agent。

**标准答案**

- Chatbot 首先是一种交互形态，核心是多轮对话；它可以没有工具、没有状态，也不一定会执行动作。

- Workflow 的路径、条件和节点大多由研发预先定义，强调确定性、可审计和稳定交付；模型可以只是其中一个节点。

- RPA 主要按规则驱动界面或系统操作，适合固定流程和稳定页面，本质仍是确定性自动化。

- Agent 接收目标后，会基于上下文动态决定下一步，选择工具、观察结果、更新状态并循环，直到达成目标或触发终止条件。

- 判断是否属于 Agent，不看是否用了某个框架，而看系统是否具备“目标—决策—行动—观察—再决策”的闭环和一定程度的动态自治。

<blockquote>
<p><strong>P7 合格线：</strong>P7 需要给出一张“确定性、自治程度、动作风险、可解释性、适用场景”的对比矩阵，并能说明自己的项目为何选择 Agent 或 Workflow。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 还要把技术边界转化为业务决策：先证明动态决策能显著提升任务完成率，再用风险分级、审批和可回退机制限制自治范围。</p>
</blockquote>

高频追问与参考答案

**追问 1｜一个带 Tool Calling 的客服机器人一定是 Agent 吗？
参考答案｜**不一定。若系统只是按固定规则调用一个工具、没有持续的状态更新和‘决策—行动—观察—再决策’闭环，它更像带工具的 Chatbot 或 Workflow；只有当下一步由模型结合观察动态决定，并受终止与治理约束时，才更接近 Agent。

**追问 2｜什么场景更适合 Workflow，而不是 Agent？
参考答案｜**规则清晰、路径稳定、强合规、低延迟、高吞吐或包含不可逆动作的场景，更适合 Workflow。模型可以承担意图识别、摘要等模糊环节，但关键状态迁移仍应由确定性流程控制。

**追问 3｜RPA 与 Agent 结合时，谁负责决策，谁负责执行？
参考答案｜**通常由 Agent 负责理解目标、选择方案和决定是否执行，由 RPA 负责按既定步骤操作页面或遗留系统；权限、审批和最终放行应由独立策略层或人工控制，而不是交给任一方自行决定。

## Q002｜一个最小可用 Agent 的闭环由哪些部分组成？

**考察意图｜**考察候选人是否真正理解 Agent Runtime，而不只是会写一段 Prompt。

**标准答案**

- 输入与目标：明确用户意图、成功标准、约束和可用资源。

- 上下文组装：按当前步骤注入会话状态、业务状态、检索结果、工具定义和安全策略。

- 决策模型：生成回答、请求调用工具、委派任务或结束运行。

- 工具执行层：完成参数校验、鉴权、幂等、超时、重试、审计和结果标准化。

- 观察与状态更新：把工具结果写回运行状态，供下一轮决策使用。

- 终止控制：成功条件、最大轮次、时间/Token/费用预算、无进展检测、人工升级。

- 横切能力：Guardrail、Tracing、评估、版本管理和故障恢复。

用户目标 → 组装上下文 → 模型决策 → 工具执行
↑ ↓
终止/升级 ← 状态更新与校验 ← 工具观察结果

<blockquote>
<p><strong>P7 合格线：</strong>P7 应能画出 Runtime 状态机，并说明模型上下文与真实业务状态不能混为一谈。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 应进一步拆分控制面与执行面，支持多租户、跨区域、长任务恢复、版本治理和统一策略下发。</p>
</blockquote>

高频追问与参考答案

**追问 1｜工具结果应该只放回上下文，还是也要持久化？
参考答案｜**短期、低价值结果可以只进入当前上下文；影响业务状态、后续恢复、审计或幂等判断的结果必须持久化。大文件和长结果应存对象存储或业务库，上下文只保留摘要、哈希和引用。

**追问 2｜Agent 进程重启后如何继续？
参考答案｜**在每个可恢复边界保存 Checkpoint，包括 task_id、当前步骤、计划版本、工具调用记录、副作用状态和剩余预算。新进程读取状态后先做幂等与外部状态核对，再从未完成步骤继续。

**追问 3｜如何识别 Agent 已经陷入循环？
参考答案｜**可监控连续多轮没有新增证据、状态不变化、重复调用同一工具和参数、相同错误反复出现或验证分数不提升；达到阈值后触发停止、重规划或人工升级。

## Q003｜Transformer 推理特性为什么会直接影响 Agent 的延迟和成本？

**考察意图｜**考察候选人能否把模型原理映射到真实系统的容量、延迟和费用设计。

**标准答案**

- 一次模型调用通常包含 Prefill 和 Decode：Prefill 处理输入上下文，Decode 按 Token 串行生成输出。

- 在朴素注意力实现下，长上下文的计算和显存压力会快速增长；即使有 FlashAttention、分页 KV Cache 等优化，长 Prompt 仍然会抬高首 Token 延迟和成本。

- Decode 具有串行性，输出越长，端到端耗时越高；Agent 又常常需要多轮模型调用，因此延迟是逐轮累积的。

- 工具 Schema、历史消息、RAG 片段、工具结果都会占用上下文，不能只计算用户问题的 Token。

- 工程上要控制调用次数、上下文长度和输出长度，并通过模型路由、缓存、并行工具和提前结束降低总预算。

<blockquote>
<p><strong>P7 合格线：</strong>P7 要能给出一次任务的延迟拆解，并识别是 Prefill、Decode、排队还是工具调用造成瓶颈。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 要把 Token/s、并发、上下文分布、工具 P95 和重试放入容量模型，形成可执行的 SLO 与成本预算。</p>
</blockquote>

高频追问与参考答案

**追问 1｜KV Cache 能解决什么，不能解决什么？
参考答案｜**KV Cache 能避免 Decode 阶段反复计算既有 Token 的 Key/Value，也可在支持前缀缓存时复用公共前缀；它不能消除首次 Prefill、长上下文显存占用、逐 Token 串行生成，也解决不了排队和工具网络延迟。

**追问 2｜为什么 Agent 的 P99 往往比普通问答更差？
参考答案｜**Agent 一次任务通常包含多轮模型、多个外部工具、分支、重试和审批，尾延迟会被最慢步骤以及重试放大；普通问答多为一次模型调用，因此 P99 更容易控制。

**追问 3｜长上下文一定比 RAG 更好吗？
参考答案｜**不一定。长上下文会增加成本、首 Token 延迟和注意力稀释，还难以处理权限与知识时效；RAG 更适合按需获取新鲜、可授权的证据，生产中通常采用‘适度上下文 + RAG + 结构化状态’。

## Q004｜上下文窗口是什么？Agent 中为什么更容易溢出？

**考察意图｜**考察候选人对 Context Engineering 的基础理解。

**标准答案**

- 上下文窗口通常包含系统指令、用户与助手历史、工具定义、工具调用结果、检索文档以及模型准备输出的空间。

- Agent 每执行一步都会产生新观察；如果原样追加，历史、工具结果和计划会持续膨胀。

- 溢出不仅表现为超过硬上限，也表现为关键信息被淹没、Lost-in-the-Middle、模型注意力分散和费用失控。

- 常用手段包括滑动窗口、分层摘要、只保留结构化状态、按需检索长期记忆、工具结果裁剪、去重和步骤级上下文。

- 任何压缩都要保留可验证的原始证据引用，避免摘要错误成为后续步骤的“事实”。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计会话压缩策略，并说明哪些字段必须保真、哪些内容可以丢弃。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会把 Context 视为按节点动态编译的资源，建立 Token 预算器、信息优先级和回放能力，而不是统一拼接大 Prompt。</p>
</blockquote>

高频追问与参考答案

**追问 1｜工具结果很长时怎么裁剪？
参考答案｜**先按结构提取关键字段、错误码、前后若干行和统计摘要，再根据当前步骤只保留相关片段；完整结果存外部存储并附可追溯引用。对表格可保留表头、命中行和聚合值，而不是整表塞入 Prompt。

**追问 2｜摘要本身产生幻觉怎么办？
参考答案｜**摘要只能作为派生视图，必须保留原始证据与版本。可使用结构化抽取、事实逐项核验、独立 Verifier 和抽样回放来检测失真，高风险事实应直接引用原文而不是只依赖摘要。

**追问 3｜为什么只扩大上下文窗口仍然不够？
参考答案｜**更大的窗口仍会带来成本、延迟、Lost-in-the-Middle、无关信息干扰以及权限和时效问题。上下文管理的核心是把正确的信息在正确步骤送给模型，而不是把所有信息一次性塞进去。

## Q005｜Temperature、Top-p 和结构化输出在 Agent 中应如何使用？

**考察意图｜**考察候选人是否理解生成随机性与生产可控性的关系。

**标准答案**

- Temperature 和 Top-p 都会影响采样分布，通常不建议同时大幅调整；创意生成可以提高随机性，分类、抽取和工具参数生成应更稳定。

- 低 Temperature 只能降低随机性，不能保证完全确定，更不能替代 Schema、规则和业务校验。

- 工具调用与关键业务输出应使用结构化输出或 JSON Schema，配合类型、必填项、枚举、长度和业务约束。

- 对高风险动作，模型只负责提出候选动作，最终执行仍需策略引擎或人工审批。

- 推理型模型的行为控制可能与传统采样参数不同，工程上应以评估结果和提供方约束为准。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能为不同节点设置模型与采样策略，并说明为什么 Planner 和 Extractor 不应共用一套参数。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建立可回归的解码策略矩阵，把模型版本、参数、Schema 和 Prompt 作为一个整体发布单元。</p>
</blockquote>

高频追问与参考答案

**追问 1｜Temperature=0 是否等于确定性？
参考答案｜**不等于。Temperature=0 只是降低采样随机性，模型服务的并行计算、后端实现、版本更新和同分 Token 选择仍可能造成差异；确定性业务还需要固定版本、Schema、规则校验和可重放工具结果。

**追问 2｜结构化输出失败后如何重试？
参考答案｜**先用 Schema 和业务规则返回精确错误，再做一次针对性修复重试，而不是把整条链路重跑；仍失败时可简化 Schema、切换兼容模型或转人工，并设置严格的重试上限。

**追问 3｜什么时候允许自由文本，什么时候必须 Schema？
参考答案｜**解释、闲聊、创意文案等低风险内容可以自由文本；工具参数、工作流状态、金额、权限、合规结论以及任何要被下游程序消费的结果必须使用 Schema，并在应用层做语义校验。

## Q006｜Function Calling 为什么优于让模型直接输出一段可解析文本？

**考察意图｜**考察候选人对模型—应用边界和可靠工具调用的理解。

**标准答案**

- Function Calling 把“是否调用工具、调用哪个工具、参数是什么”表达为机器可校验的结构，而不是依赖正则解析自然语言。

- 工具 Schema 能提供参数类型、必填项、枚举和说明，降低格式错误并提升工具选择质量。

- 应用仍需进行语义校验、权限校验和业务约束校验，因为格式正确不代表参数合理。

- 工具执行结果应返回稳定的成功/失败结构、错误码和可重试标识，避免把异常堆栈直接交给模型。

- Function Calling 解决的是交互协议，不自动解决幂等、鉴权、超时和副作用控制。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计可用的工具契约，并把工具选择准确率、参数准确率和执行成功率分开评估。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会进一步建设统一 Tool Platform，让不同模型、Agent 框架和 MCP 客户端共享同一套治理能力。</p>
</blockquote>

高频追问与参考答案

**追问 1｜Schema 越详细越好吗？
参考答案｜**不是越详细越好。Schema 应完整表达必填项、类型、枚举、边界和关键语义，但过长、字段过多或描述重叠会占用上下文并增加选错概率；复杂能力应拆成职责清晰的小工具。

**追问 2｜模型选错工具时怎么定位？
参考答案｜**通过 Trace 记录当时可见工具、模型选择结果、参数和上下文，并在离线集上做工具混淆矩阵。重点检查工具名称/描述是否重叠、是否暴露了无关工具，以及路由 Prompt 是否缺少反例。

**追问 3｜工具参数格式正确但业务错误怎么办？
参考答案｜**格式校验之后还必须做业务校验，例如对象是否存在、金额是否合法、用户是否有权限、状态是否允许迁移。校验失败应返回结构化错误供模型修正，高风险参数变化则重新审批。

## Q007｜推理模型、小模型和通用模型在 Agent 中应怎样分工？

**考察意图｜**考察候选人是否具备模型路由和成本意识，而不是所有步骤都调用最贵模型。

**标准答案**

- 推理模型适合复杂规划、多约束权衡、代码修复和需要较强逻辑链的节点，但通常延迟和成本更高。

- 小模型适合意图分类、路由、信息抽取、内容审核、简单工具选择和结果压缩。

- 通用模型适合对话、综合生成和中等复杂度任务；多模态模型负责图像、音频或文档视觉理解。

- 路由依据应包括任务类型、风险等级、上下文长度、SLO、预算、历史成功率和供应商可用性。

- 降级不能只换模型，还要同步调整 Prompt、Schema、最大步骤数和可用工具范围。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能给出任务级路由规则和回退链，并通过离线评估证明路由不会明显伤害质量。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会构建能力注册表和在线决策策略，在质量、成本、延迟与合规之间做动态优化。</p>
</blockquote>

高频追问与参考答案

**追问 1｜模型路由由规则还是另一个模型完成？
参考答案｜**稳定、可解释且高风险的路由优先使用规则；意图模糊、类别多时可用小模型分类。生产中常用混合方式：模型给候选，规则根据风险、预算、区域和能力矩阵做最终裁决。

**追问 2｜如何避免回退模型能力不足导致危险动作？
参考答案｜**为每个模型维护能力矩阵和允许动作范围。回退到能力较弱模型时同步缩小工具集合、降低最大步数、禁止高风险写操作，并在必要时改为建议模式或强制人工审批。

**追问 3｜如何评估路由收益？
参考答案｜**在同一评估集和线上分流中比较任务成功率、延迟、Token/费用、重试率、人工升级率和安全事件，最终看风险调整后的单位任务成本，而不是只看单次模型价格。

## Q008｜Embedding 模型和生成模型分别解决什么问题？

**考察意图｜**考察候选人是否混淆向量检索与文本生成。

**标准答案**

- Embedding 把文本、图片等映射到向量空间，主要用于相似度检索、聚类、去重、推荐和语义匹配。

- 生成模型根据上下文预测输出 Token，用于回答、摘要、规划、抽取和工具调用。

- 向量相似并不等于事实正确；Embedding 负责“找候选”，生成模型负责“基于证据组织答案”。

- 企业检索通常需要 Dense Embedding 与关键词/BM25 混合，因为编号、名称、金额和代码更依赖精确匹配。

- Embedding 版本升级会改变向量空间，必须考虑重建索引、双写、灰度和可回滚。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能解释召回、重排和生成三个阶段的职责，并设计独立评估。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会考虑跨语言、领域漂移、索引版本、在线迁移和向量成本，形成平台级治理。</p>
</blockquote>

高频追问与参考答案

**追问 1｜为什么余弦相似度高仍可能检索错误？
参考答案｜**余弦相似度只说明向量空间中的语义接近，不代表事实、时间、权限和实体完全匹配。否定词、同名实体、旧版本、编号差异或切片上下文不足，都可能让高相似结果仍然错误。

**追问 2｜Embedding 维度越大越好吗？
参考答案｜**不一定。更高维度可能提升表达能力，也会增加存储、网络和 ANN 检索成本；应在自己的领域数据上比较 Recall、延迟和费用，选择收益拐点，而不是追求最大维度。

**追问 3｜模型升级后旧向量能否继续混用？
参考答案｜**通常不能直接混用，因为新旧模型的向量空间和分布可能不同。应建立版本化索引，进行全量重嵌入或双写双读灰度，验证完成后再切流，并保留回滚能力。

## Q009｜Agent 幻觉来自哪里？如何分层治理？

**考察意图｜**考察候选人是否只会回答“加 Prompt、降 Temperature”。

**标准答案**

- 来源包括模型先验错误、缺少证据、问题歧义、检索失败、旧知识冲突、工具返回异常、上下文压缩失真和模型过度推断。

- 第一层是任务边界：明确哪些问题允许回答、哪些必须拒答或转人工。

- 第二层是证据：RAG、实时工具、版本与时效过滤、引用和证据阈值。

- 第三层是输出约束：结构化输出、事实字段逐项校验、计算交给工具、禁止编造缺失字段。

- 第四层是验证：独立规则、交叉检索、Verifier、人工审核和离线/在线评估。

- 第五层是运营反馈：收集错误类型、归因到具体组件并形成回归集。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能把“回答错了”定位为检索、上下文、模型、工具或验证哪一层的问题。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建立风险分级的可信度策略：低风险可自动答，高风险要求双源证据、规则校验和人工签字。</p>
</blockquote>

高频追问与参考答案

**追问 1｜有引用就一定可信了吗？
参考答案｜**不一定。引用可能与结论无关、只支持部分事实、已过期，甚至由模型伪造。系统需要做引用存在性、版本、权限和语义蕴含校验，并让每个关键结论绑定到具体证据片段。

**追问 2｜如何区分检索没召回和模型没用好证据？
参考答案｜**用黄金证据做分层诊断：若正确证据不在候选集，是召回问题；在候选集但被 Rerank 丢掉，是排序问题；已进入最终 Context 但答案仍错，主要是生成或提示问题。

**追问 3｜Verifier 也会幻觉怎么办？
参考答案｜**Verifier 也必须视为不可靠组件。优先采用数据库查询、规则、测试和计算器等外部可验证信号，再结合多 Judge、一致性检查和校准；高风险场景仍需要人工兜底。

## Q010｜什么情况下不应该使用 Agent？

**考察意图｜**考察候选人是否具备技术克制和方案选择能力。

**标准答案**

- 流程完全固定、规则清晰、输入输出稳定时，普通服务、规则引擎或 Workflow 更便宜、更快、更可控。

- 毫秒级延迟、极高吞吐且没有复杂语义判断的场景，不适合引入多轮模型循环。

- 高风险不可逆动作如果缺少审批、回滚和审计能力，不应交给自治 Agent。

- 训练/评估数据不足、成功标准无法量化、业务方也无法定义“正确”时，不宜直接上线。

- 模型对关键语言、专业领域或数据类型能力不足时，应先补规则、工具或人机协同。

- 最稳妥的演进通常是：Copilot → 建议式 Agent → 有限自动化 → 风险分级自治。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能用业务收益、失败成本、SLO 和可评估性证明选型，而不是追热点。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会设计渐进式自治路线和退出机制，确保 Agent 失败时系统仍能退化为确定性流程。</p>
</blockquote>

高频追问与参考答案

**追问 1｜一个审批流程能否部分使用 Agent？
参考答案｜**可以。Agent 适合读取非结构化材料、抽取字段、解释风险和提出建议，审批状态迁移、权限判断和最终执行仍由确定性 Workflow 管理，这也是较稳妥的混合架构。

**追问 2｜如何量化“Agent 值得做”？
参考答案｜**比较 Agent 相对基线带来的任务完成率、处理时长和人工量改善，再扣除模型、平台、审核、错误补偿和合规风险成本。只有风险调整后的长期收益为正，且明显优于规则扩展成本，才值得做。

**追问 3｜从 Copilot 升级到自动执行需要哪些门槛？
参考答案｜**至少需要稳定的离线/在线评估、明确的低风险自治边界、权限最小化、幂等、审计、审批、回滚、SLO 和事故响应机制；通常按 Copilot、建议式、有限自动化、分级自治逐步升级。
