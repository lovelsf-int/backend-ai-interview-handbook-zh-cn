## Q081｜如何拆解一次 Agent 请求的端到端延迟？

**考察意图｜**考察候选人能否从“模型慢”进一步定位真实瓶颈。

**标准答案**

- 延迟通常包括网关与鉴权、排队、上下文/RAG、模型 Prefill、首 Token、Decode、工具调用、重试、验证和最终渲染。

- 多轮 Agent 的总延迟近似各轮关键路径之和；并行工具只缩短并行分支的最大值，不会消除模型轮次。

- 分别观察 p50、p95、p99 和超时率，尾延迟常由限流、冷启动、慢工具、重试和长上下文造成。

- 为总任务与每个节点分配 Deadline，后续步骤只使用剩余预算，避免局部超时叠加超过用户 SLO。

- Trace 必须能展示模型、检索、工具和队列的 Span，支持按模型、租户、工具和任务类型切分。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能拿真实 Trace 做 Critical Path 分析并提出优化。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建立分层 SLO、尾延迟治理和跨区域容量策略，把质量、成本和延迟统一管理。</p>
</blockquote>

高频追问与参考答案

**追问 1｜首 Token 快但总耗时长说明什么？
参考答案｜**说明模型开始响应快，但后续 Decode 很长，或真正耗时发生在流式首字之后的工具、重试和多轮 Agent Loop。不能只优化 TTFT，还要拆解完成时间、有效结果时间和每轮耗时。

**追问 2｜并行工具为什么仍可能变慢？
参考答案｜**并行会增加调度、连接和聚合开销，也可能触发下游限流、资源争用或重复查询；整体仍由最慢必需分支决定。只有独立且有足够容量的步骤并行才会真正降低延迟。

**追问 3｜P99 优化与平均延迟优化有什么不同？
参考答案｜**平均延迟优化更多依赖缓存、批处理和常见路径，P99 则要治理排队、重试、慢供应商、超长任务和资源争用。应使用超时预算、隔离池、尾部裁剪和降级，避免少量异常拖垮体验。

## Q082｜Agent 成本应如何优化？

**考察意图｜**考察候选人是否能把成本拆到具体决策点。

**标准答案**

- 成本来源包括输入/输出 Token、推理调用次数、Embedding/Rerank、工具/第三方 API、沙箱计算、存储和人工审核。

- 先减少无价值调用：意图路由、提前拒答、合并步骤、停止循环、复用工具结果和并行独立查询。

- 上下文去重、摘要、检索 TopK 控制、Prompt Cache/前缀缓存和短输出能降低 Token。

- 按节点选择模型，小模型做分类/抽取，大模型只处理复杂规划；用质量门槛保护降级。

- 缓存只适合可复用且权限/时效明确的结果，不能为了省钱复用过期或跨租户内容。

- 最终看每个成功任务成本 Cost per Successful Task，而不是单次模型价格。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能给出成本账单分解和一组不伤质量的优化实验。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建立租户预算、在线路由、单位业务价值和容量采购联动的 FinOps 体系。</p>
</blockquote>

高频追问与参考答案

**追问 1｜换便宜模型为什么可能总成本反而更高？
参考答案｜**便宜模型可能规划更差、输出更长、选错工具并触发更多重试和人工审核，最终每个成功任务成本反而更高。应比较‘单位成功任务的总成本’，而不是单次 Token 单价。

**追问 2｜Prompt Cache 适合哪些内容？
参考答案｜**适合稳定且大量重复的前缀，如 System Prompt、通用 Tool Schema、固定 Few-shot 和政策框架；动态用户数据、频繁变化的检索片段和高敏内容不宜盲目共享。缓存 Key 必须绑定模型与版本。

**追问 3｜如何量化人工审核成本？
参考答案｜**用人工每小时完全成本乘以实际处理、等待、复核和返工时间，再加入排班利用率、培训和错误成本。要比较 Agent 前后的总工作量和可释放产能，而不只是单票审核分钟数。

## Q083｜模型限流、配额耗尽和供应商故障时如何处理？

**考察意图｜**考察候选人对外部模型依赖的弹性设计。

**标准答案**

- 入口按租户、任务类型和模型实施令牌桶/漏桶限流，并为高优先级任务预留容量。

- 调用层识别 429、5xx、超时和配额错误，遵守 Retry-After，使用抖动退避与全局 Deadline。

- 建立按能力匹配的回退链：同供应商备用模型、跨供应商模型、简化流程或异步排队。

- 故障期间限制新长任务、缩短上下文、降低并发，防止重试放大；熔断后用探测请求恢复。

- 跨模型回退要重新验证工具能力、结构化输出、区域合规和质量门槛。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能实现多供应商适配、熔断与降级演练。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会做容量预留、实时健康评分、区域路由和供应商风险管理。</p>
</blockquote>

高频追问与参考答案

**追问 1｜429 应该立即换供应商吗？
参考答案｜**不一定。429 可能是短时速率限制、租户配额或区域容量问题，应先依据 Retry-After、优先级和任务 Deadline 做排队/退避。只有持续故障且备用能力等价时才切换，避免供应商间抖动。

**追问 2｜回退模型不支持相同 Tool Calling 怎么办？
参考答案｜**通过 Capability Adapter 重新编译 Prompt、Schema 和工具集合；不兼容时缩小为文本建议、确定性 Workflow 或人工处理。不能把原工具调用 JSON 原样发给不支持的模型。

**追问 3｜如何避免多个服务同时重试？
参考答案｜**使用统一的 Rate Limit/Retry Coordinator、共享令牌桶、指数退避加抖动和熔断。规定只有最靠近依赖的一层重试，上游根据状态排队或降级，避免多服务同时放大流量。

## Q084｜Agent 的 Streaming 应该流什么？

**考察意图｜**考察候选人对用户体验、状态一致性和取消的理解。

**标准答案**

- 可以流式返回文本 Token，也可以返回结构化事件：已理解目标、正在检索、工具开始/结束、等待审批、部分产物和最终状态。

- 进度必须来自真实状态机，不能让模型虚构百分比；对长任务优先展示阶段与已完成产物。

- 客户端需要处理事件序号、断线重连、重复事件和最终快照，不能只依赖一次 SSE 连接。

- 取消信号要传递到模型、工具和子任务；断开连接不等于取消任务。

- 敏感工具参数、内部推理和安全策略不应直接流给用户。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计事件协议、重连游标和最终一致快照。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会统一实时 Agent Event Bus，支持跨区域、A2A 子任务和多端订阅。</p>
</blockquote>

高频追问与参考答案

**追问 1｜SSE 与 WebSocket 怎么选？
参考答案｜**SSE 适合服务器到客户端的单向事件流，部署和断线恢复简单；WebSocket 适合高频双向交互、实时控制或多路复用。大多数 Agent 进度和文本流使用 SSE 已足够，交互式远程终端才更偏向 WebSocket。

**追问 2｜断线后如何避免丢事件？
参考答案｜**所有事件带 task_id、sequence/event_id，并写入可重放事件日志或短期缓冲；客户端保存最后确认位置，重连后从该位置续传。若历史已过期，则先获取任务快照再订阅增量。

**追问 3｜模型已经生成的 Token 取消后如何计费？
参考答案｜**通常已生成并被供应商计算的 Token 会计入用量，具体账单以供应商规则为准。平台应把取消前实际 usage 记录为已消耗，并尽早向下游传播取消，不能假设客户端没看到就不产生成本。

## Q085｜Agent 为什么常需要消息队列？队列怎么设计？

**考察意图｜**考察候选人对异步化、削峰和任务可靠性的理解。

**标准答案**

- 长任务、批量任务、第三方限流和高峰流量适合进入队列，入口快速返回任务 ID。

- 按优先级、租户、任务类型或模型资源拆队列，避免低价值长任务阻塞高优先级请求。

- 消费者使用可见性超时/租约、心跳和幂等；失败进入延迟重试或死信队列。

- 设置最大队列长度和背压策略：拒绝、降级、延迟受理或限制新任务，不能无限堆积。

- 队列指标包括等待时间、处理时间、重试率、DLQ、最老消息年龄和租户公平性。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计 Worker 领取、租约、重试和 DLQ 处理。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会做基于任务价值与资源类型的全局调度，支持抢占、配额和跨区域迁移。</p>
</blockquote>

高频追问与参考答案

**追问 1｜队列能保证 Exactly Once 吗？
参考答案｜**不能天然保证。大多数队列提供 At-least-once，ACK 丢失或 Worker 宕机会导致重投；业务通过 message_id、step_id、幂等 Inbox/Outbox 和状态条件更新获得等效一次结果。

**追问 2｜Worker 处理一半宕机怎么办？
参考答案｜**消息租约/可见性超时到期后会重新投递。Worker 必须在可恢复边界写 Checkpoint，恢复时先核对已完成副作用，再从未完成步骤继续，而不是从头无条件执行。

**追问 3｜如何避免大租户饿死小租户？
参考答案｜**按租户设置并发、速率和预算，采用加权公平队列、分租户分区或虚拟队列，并为小租户保留最小份额。大任务还要拆分，防止单条消息长期占用 Worker。

## Q086｜Agent 系统有哪些缓存层？分别有什么风险？

**考察意图｜**考察候选人对缓存命中、权限、时效和正确性的理解。

**标准答案**

- 模型响应缓存适合相同确定性请求；语义缓存对近似问题复用答案，但更容易出现意图误匹配。

- Prompt/前缀缓存复用稳定系统指令与工具定义，降低 Prefill 成本。

- RAG 缓存可缓存 Query Rewrite、召回结果、Rerank 和最终答案，但必须关联索引/文档版本。

- 工具缓存只适合只读且有明确 TTL 的结果，库存、价格、权限等数据要谨慎。

- Cache Key 至少包含租户/用户作用域、权限摘要、模型/Prompt/工具/知识版本、语言和关键参数。

- 需要负缓存、防击穿、热点保护和主动失效；命中后仍要执行安全与权限校验。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能为每层缓存定义 Key、TTL、失效和越权测试。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建设可观测缓存策略，按质量风险和成本收益动态启停。</p>
</blockquote>

高频追问与参考答案

**追问 1｜语义缓存为什么可能答非所问？
参考答案｜**语义相似不等于任务等价，否定词、时间、用户身份、权限、金额或上下文差异都可能被向量相似度忽略。命中后仍要做约束一致性检查，并限制在低风险、稳定知识场景使用。

**追问 2｜权限变化后缓存怎么失效？
参考答案｜**缓存条目绑定 ACL 哈希、tenant/user scope、数据和策略版本，权限撤销事件应主动失效；无法精确失效时使用短 TTL 或全局版本跃迁。绝不能仅按自然语言问题作为 Key。

**追问 3｜缓存工具失败结果有价值吗？
参考答案｜**有价值，但要区分错误类型。对确定不存在或短时依赖故障可做很短的 Negative Cache，降低击穿；鉴权失败、未知写操作结果和可能快速恢复的数据不应跨用户或长时间缓存。

## Q087｜为什么 Agent 系统通常只能实现 At-least-once + Idempotency？

**考察意图｜**考察候选人对分布式一致性和 Exactly Once 边界的理解。

**标准答案**

- 网络超时无法区分请求未到达、执行中还是已成功但响应丢失，因此重试可能重复。

- 跨模型、队列、数据库和第三方系统缺少一个覆盖全部资源的原子事务。

- 实际做法是至少一次投递/执行，配合业务幂等键、唯一约束、调用记录和状态查询去重。

- 对外部副作用保存 request_id 与结果，重放时返回第一次成功结果，避免下游二次执行。

- 无法幂等或不可逆的动作需要审批、单次令牌或补偿流程。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能用支付、邮件或工单例子说明超时后的正确处理。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会定义工具级一致性语义和端到端副作用账本，向上层隐藏大部分重复执行复杂度。</p>
</blockquote>

高频追问与参考答案

**追问 1｜消息消费提交 Offset 前宕机会怎样？
参考答案｜**消息会被再次投递，因此同一步可能重复执行。消费者应先查幂等记录，若已成功就返回原结果；若状态 UNKNOWN 则查询下游，不能直接再做一次副作用。

**追问 2｜返回第一次完整响应为什么重要？
参考答案｜**客户端第一次超时后会重试，如果服务只返回‘重复请求’，客户端仍不知道真实业务结果。保存并返回第一次的规范化响应，才能保证重试在用户看来与原请求一致。

**追问 3｜第三方不支持幂等怎么办？
参考答案｜**在工具网关建立幂等 Ledger，用业务唯一键、查询接口、条件更新或本地锁避免重复；若第三方既无幂等也无状态查询，高风险写操作就不应自动重试，只能人工核对或设计补偿。

## Q088｜如何为工具和外部依赖定义 SLO？

**考察意图｜**考察候选人能否把“工具不稳定”量化为可治理指标。

**标准答案**

- 每个工具定义可用性、成功率、p95/p99 延迟、超时、数据新鲜度、参数错误率和副作用一致性。

- 区分系统错误与业务拒绝，例如余额不足不是工具故障；否则会错误触发重试和熔断。

- 建立健康检查、熔断、容量配额和依赖地图，关键工具配置备用源或人工兜底。

- 工具结果应带数据时间、来源和 trace_id，方便判断过期与关联下游故障。

- Agent SLO 由关键路径依赖组合而成，不能只看模型可用性。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能建立工具 Dashboard、错误分类和告警。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会把工具 SLO 纳入 Planner/Router，让 Agent 根据实时健康选择策略。</p>
</blockquote>

高频追问与参考答案

**追问 1｜业务 404 算工具失败吗？
参考答案｜**通常不算技术失败。404 可能是合法的‘对象不存在’业务结果，应与超时、5xx、协议错误分开统计。SLO 应同时定义技术可用性和业务有效响应率。

**追问 2｜多个工具串联时整体可用性如何估算？
参考答案｜**若依赖必须串行且近似独立，整体可用性大致是各依赖可用性的乘积，延迟则累加并受尾部放大；实际还要考虑降级和相关故障。系统 SLO 不能简单复制单工具 SLO。

**追问 3｜数据新鲜度如何定义 SLO？
参考答案｜**用 as_of 时间、最大允许陈旧度、更新延迟 P95/P99 和在阈值内的数据比例定义。例如‘99% 查询使用不超过 5 分钟前的数据’，并对不同数据源设置不同目标。

## Q089｜Agent 进程、节点或区域故障后如何恢复任务？

**考察意图｜**考察候选人对持久化状态、接管和跨区容灾的理解。

**标准答案**

- 任务状态、检查点、工具调用账本和产物必须在外部持久化，不能依赖进程内内存。

- Worker 使用租约；故障后租约过期，其他 Worker 读取最后检查点并核对未决副作用。

- 恢复时使用版本化编排和工具契约，旧任务可以继续运行或迁移到兼容版本。

- 区域级故障需要明确会话归属、数据复制、RTO/RPO、模型与工具在备用区的可用性。

- 对无法跨区的数据或第三方依赖，任务应进入等待/人工状态，而不是假装恢复成功。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能完成节点故障与重复领取演练。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会设计区域级任务接管、数据驻留、流量切换和灾备演练体系。</p>
</blockquote>

高频追问与参考答案

**追问 1｜恢复后如何确认上一步是否已执行？
参考答案｜**读取执行 Ledger、Checkpoint 和下游业务状态，使用 tool_call_id/idempotency_key 对账。只有确认上一步未执行才继续调用；已成功则补写本地状态，未知则暂停或人工核对。

**追问 2｜正在等待人工审批的任务怎么迁移？
参考答案｜**审批任务应持久化为 WAITING_APPROVAL，包含审批人/组、动作哈希、截止时间和通知状态，与原进程和区域解耦。迁移后重新注册通知或回调，但不能改变已审批参数。

**追问 3｜跨区复制延迟会造成什么问题？
参考答案｜**可能出现同一任务被两区同时推进、旧状态覆盖新状态、事件乱序和重复副作用。应设置任务 Home Region 或单写者、版本冲突控制，并明确 RPO 下哪些任务必须暂停对账。

## Q090｜模型、Prompt 或编排升级如何做 Canary 与回滚？

**考察意图｜**考察候选人是否具备 Agent 变更的安全发布能力。

**标准答案**

- 先离线回归，再影子流量，最后按租户、用户或任务类型小比例 Canary；高风险动作可只生成建议不执行。

- 比较任务成功、质量、工具选择、错误类型、延迟、Token、费用、安全和人工升级，而不是只看点赞。

- 发布单元包含模型、Prompt、工具 Schema、检索策略、Memory 策略和编排版本，避免单项版本错配。

- 设置自动停止阈值和一键回滚；正在执行的长任务默认固定原版本，或经过显式迁移。

- 保留旧版本依赖与评估数据，确保回滚后仍能正常调用。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计完整灰度指标和回滚路径。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会实现多版本并行、租户策略、自动质量门控和长任务版本迁移。</p>
</blockquote>

高频追问与参考答案

**追问 1｜只升级模型不改 Prompt 可以吗？
参考答案｜**可以，但仍必须评估。模型升级即使 Prompt 不变，也可能改变工具选择、输出格式、拒答和安全行为；Prompt 与模型是耦合发布单元，至少需要兼容性回归和 Canary。

**追问 2｜长任务跨发布怎么办？
参考答案｜**为长任务固定 runtime/model/prompt/tool-policy 版本直到完成，或只在明确定义的 Checkpoint 迁移，并运行状态与计划兼容校验。不能让一次任务中途无记录地切换行为。

**追问 3｜Canary 样本太少如何判断？
参考答案｜**先扩大离线和 Shadow 回放，使用序贯检验、贝叶斯区间或更长观察期；安全指标采用零容忍门禁，高风险样本定向过采样。样本不足时宁可延长 Canary，也不凭均值草率全量。

## Q091｜Agent 的版本对象应该包含哪些内容？

**考察意图｜**考察候选人是否能保证问题可追踪、可复现。

**标准答案**

- 模型提供方、模型 ID/快照、推理参数和区域。

- System/Developer Prompt、Few-shot、输出 Schema 和安全策略版本。

- 工具定义、MCP/A2A 协议版本、业务 API 版本和权限策略。

- RAG 解析器、Embedding、索引、Chunk、融合、Rerank 和知识快照版本。

- 编排图、Memory 策略、终止/重试/预算策略及代码发布版本。

- Trace 中记录一次运行实际使用的完整 Release Manifest，而不是只写一个“Agent v2”。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计 Release Manifest 和兼容检查。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建设 Agent Artifact Registry，实现签名、依赖解析、回放、灰度和合规审批。</p>
</blockquote>

高频追问与参考答案

**追问 1｜为什么只记录 Git Commit 不够？
参考答案｜**Git Commit 只描述应用代码，不包含实际模型快照/Endpoint、Prompt 制品、Tool Schema、路由策略、Guardrail、知识库和运行配置。缺少这些就无法解释同一代码为何产生不同结果。

**追问 2｜知识库每天更新，如何定义版本？
参考答案｜**生成不可变 Knowledge Manifest，记录文档版本集合、解析器/Embedding、索引构建号、ACL 快照和 as_of 时间。每天更新可以形成新的数据版本，即使应用代码完全未变。

**追问 3｜外部模型悄悄更新怎么办？
参考答案｜**优先使用可固定的模型版本；无法固定时记录提供方指纹、响应元数据，并持续跑 Canary 基准检测漂移。发现行为越界时自动降级或切备用模型，同时通过合同和通知机制降低风险。

## Q092｜如何做 Agent 容量规划？

**考察意图｜**考察候选人能否把 DAU/QPS 转换为模型、队列和工具资源。

**标准答案**

- 从到达率、任务类型分布、平均/尾部步骤数、每步 Token、模型吞吐、工具延迟和重试率建立工作负载模型。

- 并发可用 Little 定律近似：系统内并发约等于到达率 × 平均响应时间，但要单独考虑长任务和峰值。

- 模型侧关注请求并发、输入/输出 Token/s、上下文长度和供应商配额；工具侧关注 QPS、连接池和第三方限流。

- 按 p95/p99 规划队列与 Worker，预留突发和故障回退容量，避免主供应商故障时备用立即打满。

- 压测使用真实步骤分布、长上下文、失败重试和工具慢响应，不能只压一个模型接口。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能给出容量表、瓶颈和扩容策略。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会做跨区域容量池、成本采购、峰谷调度和业务优先级抢占。</p>
</blockquote>

高频追问与参考答案

**追问 1｜10 万 DAU 如何估算峰值并发？
参考答案｜**先估算每用户每日 Agent 任务数和峰值小时占比，再乘平均任务时长、模型轮次与工具并发。例如峰值到达率 λ 乘平均在途时间 W，可用 Little 定律估算并发 L=λW，并对 P95 和活动波峰留冗余。

**追问 2｜模型 Token/s 与请求 QPS 有什么区别？
参考答案｜**QPS 是请求进入/完成的频率，Token/s 是模型处理输入输出 Token 的吞吐。相同 QPS 下，长上下文和长输出会消耗更多 Token/s 与并发槽，因此模型容量不能只按请求数估算。

**追问 3｜压测为什么要注入失败？
参考答案｜**真实系统大量容量消耗来自超时、重试、限流、慢工具和恢复。只压正常路径会低估队列堆积与重试放大，也发现不了幂等、熔断和降级缺陷，因此需要系统性故障注入。

## Q093｜Agent 的数据血缘和审计日志应该记录什么？

**考察意图｜**考察候选人对可解释、合规和事故取证的理解。

**标准答案**

- 记录用户/服务身份、租户、任务与会话 ID、输入来源、权限快照和时间。

- 记录模型/Prompt/工具/知识/策略版本、检索候选、引用、模型输出、工具参数与结果状态。

- 记录每个决策、Handoff、Guardrail、审批、拒绝、修改和最终副作用，并关联下游 trace_id。

- 敏感内容按分类脱敏、加密和最小化；默认可只存元数据或哈希，调试内容受权限与保留期限制。

- 日志应防篡改、可检索、可导出，并满足用户删除、区域驻留和合规保留的冲突要求。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能通过 Trace 还原一次错误动作的完整路径。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建设统一 Decision Ledger，为审计、评估、争议处理和模型治理提供证据。</p>
</blockquote>

高频追问与参考答案

**追问 1｜是否应该记录完整 Prompt？
参考答案｜**不应无条件明文记录完整 Prompt。默认记录模板/版本、哈希、Token 统计和关键结构化字段；仅在受控采样或事故调查中加密保存必要内容，并做脱敏、最小访问和短 TTL。

**追问 2｜日志里出现 PII 怎么处理？
参考答案｜**在采集前识别并脱敏/令牌化 PII，敏感原文进入独立加密仓，日志平台只保留替代标识。使用细粒度访问、审计、地域隔离和保留期限，禁止调试日志成为第二份业务数据库。

**追问 3｜如何证明某次工具动作经过审批？
参考答案｜**审批记录应包含 action_id、参数哈希、对象、发起人与审批人、时间、策略/Prompt 版本、审批结论和不可篡改签名；执行日志再引用同一个 action_id，证明实际执行与获批内容一致。

## Q094｜Agent 系统应该怎样做混沌测试和故障演练？

**考察意图｜**考察候选人是否只在正常路径下验证 Demo。

**标准答案**

- 注入模型 429/5xx/超时/慢响应、结构化输出损坏、上下文超限和供应商区域故障。

- 注入工具超时但实际成功、重复回调、错误数据、权限拒绝、限流和熔断。

- 注入队列重复投递、乱序、Worker 崩溃、Checkpoint 写失败、缓存陈旧和区域切换。

- 安全演练包括 Prompt Injection、Memory Poisoning、恶意 MCP Server、越权参数和敏感数据外泄。

- 验证系统是否在预算内恢复、是否重复副作用、是否正确降级/升级人工，以及 Trace 是否完整。

- 演练结果进入回归集和 Runbook，不只做一次性报告。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能构建故障矩阵和自动化演练。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会按关键业务 SLO 定期进行跨团队 GameDay，并量化韧性改进。</p>
</blockquote>

高频追问与参考答案

**追问 1｜工具“超时但成功”怎么模拟？
参考答案｜**构造一个测试工具：接收请求后异步完成副作用，但调用端在结果返回前强制超时。Agent 恢复时必须通过幂等键查询到成功并复用结果；若出现第二次副作用，说明恢复设计失败。

**追问 2｜故障演练如何避免影响真实用户？
参考答案｜**优先在隔离环境、影子流量或专用测试租户进行，并限定故障范围、时间和依赖，设置 Feature Flag、实时监控和一键终止。生产演练从只读、低风险和小比例开始逐级扩大。

**追问 3｜哪些失败必须触发人工接管？
参考答案｜**副作用状态 UNKNOWN、高风险权限/Guardrail 失效、证据严重冲突、关键合规依赖不可用或补偿连续失败时必须人工接管。触发条件应写入策略，不由模型临场决定。
