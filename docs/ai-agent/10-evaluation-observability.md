# Evaluation 与 Observability

> 来源模块：模块十。本页保留完整标准答案、P7/P8 判断线和连续追问。

**没有评估闭环，就无法知道 Agent 是真的变好，还是更会解释错误**

<blockquote>
<p><strong>本模块考察：</strong>重点判断候选人能否建设离线数据集、轨迹评估、LLM Judge、在线实验和端到端可观测。</p>
</blockquote>

本模块共 10 题｜建议先用 90 秒作答，再接受 2—3 轮追问。

## Q095｜如何构建 Agent 的离线评估集？

**考察意图｜**考察候选人是否能把主观体验转成可重复的质量门槛。

**标准答案**

- 数据来自真实流量抽样、历史失败、人工设计边界案例、对抗样本和新功能需求，不能只用理想问题。

- 按任务类型、难度、语言、租户、风险、工具路径、文档类型和权限场景分层，保证关键长尾有覆盖。

- 每条样本定义输入、环境/工具 Mock、可接受结果、禁止动作、证据和评分 Rubric。

- 区分黄金答案与开放式 Rubric：有些任务可以精确比对，有些只能评估事实、完整性、风格和安全。

- 数据集版本化，标注来源、质量和争议；线上新错误持续进入回归集，同时防止只对固定集过拟合。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能建立覆盖主要失败类型的回归集，并接入 CI/CD。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建设评估数据平台、采样策略、标注治理和跨业务共享的基准体系。</p>
</blockquote>

高频追问与参考答案

**追问 1｜评估集需要多少条？
参考答案｜**没有固定条数，关键是覆盖主要任务、长尾、风险等级和已知故障模式。早期可以数百条建立基线，成熟平台通常需要数千甚至更多；样本量还应满足要检测的最小质量差异和置信度。

**追问 2｜真实用户数据如何脱敏？
参考答案｜**遵循最小化原则，去除直接标识、对实体做一致性假名化，敏感字段令牌化或合成替代，并限制访问与地域。脱敏后要复核任务语义没有被破坏，尤其是实体一致性和时间关系。

**追问 3｜如何避免对固定测试集过拟合？
参考答案｜**分离开发集、公开回归集和隐藏 Holdout，定期从新生产错误中更新，并限制研发直接看到最终测试答案。对同一题型增加参数化变体，避免只针对固定样例调 Prompt。

## Q096｜为什么 Agent 需要组件级评估和端到端评估同时存在？

**考察意图｜**考察候选人是否具备可归因的质量体系。

**标准答案**

- 端到端评估回答“用户任务是否成功”，但失败时无法直接定位是路由、检索、计划、工具、Memory 还是生成。

- 组件级评估分别测意图分类、工具选择、参数、检索召回、Rerank、计划质量、证据使用、Guardrail 和恢复。

- 组件指标好不代表整体一定好，因为组合、上下文和延迟会产生交互效应。

- 发布时既要保证关键组件不回退，也要看完整轨迹与业务结果。

- 指标需要按错误成本加权，高风险误执行比低风险措辞问题更严重。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能建立“最终失败 → 组件根因”的诊断树。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会把组件评估、在线 Trace 和业务指标联动，形成自动归因与责任闭环。</p>
</blockquote>

高频追问与参考答案

**追问 1｜检索 Recall 提高但最终质量下降为什么？
参考答案｜**召回更多可能同时带来更多近似、过期或冲突证据，挤占正确片段的 Context，最终让生成变差。组件指标必须与后续 Precision、Context 覆盖和端到端答案质量联合观察。

**追问 2｜如何给不同错误加权？
参考答案｜**建立业务成本矩阵，例如漏掉高危告警的权重远高于多一次模型重试；按严重度、用户影响、可逆性和合规损失给错误加权，并同时报告未加权指标，避免平均值掩盖事故。

**追问 3｜组件 Mock 与真实环境差异怎么处理？
参考答案｜**Mock 适合稳定复现逻辑，但无法覆盖真实延迟、限流、Schema 漂移和认证。应组合单元 Mock、契约测试、录制回放以及真实 Sandbox/Canary 集成测试，并明确各层覆盖边界。

## Q097｜LLM-as-a-Judge 应如何使用？有哪些偏差？

**考察意图｜**考察候选人是否会把 Judge 当成绝对真值。

**标准答案**

- Judge 适合开放式质量、相关性、完整性、风格和成对比较，但需要明确 Rubric 和可见证据。

- 常见偏差包括位置偏差、长度偏好、同源模型偏好、措辞偏好、自我评判偏差和对事实缺乏外部知识。

- 通过随机交换答案顺序、隐藏模型身份、使用多个 Judge、与人工校准和提供参考证据降低偏差。

- 高风险事实和副作用不能只依赖 LLM Judge，必须使用规则、工具状态或人工。

- 持续监控 Judge 与人工一致率，Judge/Prompt/模型升级也要版本化。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计可复现 Judge Rubric，并报告校准结果。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建立分层评估：规则优先、专用模型/LLM Judge 辅助、争议样本人工仲裁。</p>
</blockquote>

高频追问与参考答案

**追问 1｜用更强模型当 Judge 就一定可靠吗？
参考答案｜**不一定。更强模型仍可能误解 Rubric、偏好冗长表达、受位置和品牌影响，也可能缺少领域知识。Judge 必须通过人工标注集校准，并对高风险结论保留人工或规则验证。

**追问 2｜同一个模型评自己有什么问题？
参考答案｜**容易产生 Self-preference 和相关偏差，例如偏好自身写作风格、忽略相同推理错误。可使用不同模型、隐藏来源、交换答案顺序和多 Judge，但仍需外部标注校准。

**追问 3｜成对比较与打分哪个更稳？
参考答案｜**成对比较只要求判断相对优劣，通常比绝对打分更稳定，适合模型/Prompt 排序；绝对分数适合质量门槛和问题定位，但 Rubric 要更具体并做尺度校准。

## Q098｜人工评估应该怎样设计，才能减少主观差异？

**考察意图｜**考察候选人对标注规范和质量控制的理解。

**标准答案**

- 把抽象“好不好”拆成事实正确、证据支持、任务完成、完整性、安全、表达等维度，并给正反例。

- 评审员先培训与校准，复杂样本采用双标或多标，计算一致性并由专家仲裁争议。

- 隐藏候选模型和版本，随机顺序，避免品牌和位置偏差。

- 记录失败原因标签与评论，而不是只给总分，便于工程归因。

- 对高风险领域使用有资质的业务专家，并控制敏感数据访问。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能制定 Rubric、采样、双标和仲裁流程。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会优化标注成本、主动采样最有信息量的样本，并治理评审漂移。</p>
</blockquote>

高频追问与参考答案

**追问 1｜一致率低说明什么？
参考答案｜**可能说明 Rubric 不清、样本本身多解、标注员训练不足或领域知识不够。先分析分歧项，完善示例和边界，再培训与仲裁；不能简单用多数票掩盖定义问题。

**追问 2｜是否所有样本都需要双标？
参考答案｜**不需要。可对高风险样本、边界样本和随机抽样做双标，其余单标；通过持续计算一致率决定抽样比例。安全和合规关键样本通常需要双标或专家复核。

**追问 3｜业务专家与普通用户评分冲突怎么办？
参考答案｜**拆成不同维度：业务专家评价事实/合规，普通用户评价可理解性和实用性。产品目标预先定义权重和最低门槛，不能把两种评价简单平均后掩盖任一方的严重问题。

## Q099｜Agent Trajectory 应评估哪些内容？

**考察意图｜**考察候选人是否关注过程正确性，而不是只看最终文本。

**标准答案**

- 是否正确理解目标、选择合适模式、生成合理计划并按依赖执行。

- 工具选择、参数、调用顺序、重复调用、无用步骤、错误恢复和副作用是否正确。

- 是否使用了正确证据、Memory 和权限，是否在高风险节点请求审批或升级人工。

- 是否在预算内完成，调用数、Token、延迟和成本是否合理。

- 最终答案偶然正确但过程越权或调用错误工具仍应判为失败；相反，合理拒答可能是正确轨迹。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能定义关键路径、允许路径和禁止路径，并进行结构化轨迹评分。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会使用 Trace 数据做大规模轨迹聚类、异常发现和策略优化。</p>
</blockquote>

高频追问与参考答案

**追问 1｜最终答案正确为什么还可能不合格？
参考答案｜**它可能通过越权、危险或极高成本的路径‘碰巧’得到正确答案，例如读取不该看的数据或重复发送操作。生产 Agent 必须同时满足结果、过程约束和资源预算。

**追问 2｜多条合理路径如何评估？
参考答案｜**不要求逐步完全一致，而是定义允许的关键约束、必需证据和禁止动作。可使用部分顺序图或里程碑评价，多条路径只要都安全、有效且成本合理就视为正确。

**追问 3｜怎样定义“多余工具调用”？
参考答案｜**若调用没有新增所需信息、结果未被后续使用、与已有调用等价，或移除后任务质量不下降，就可视为多余。可结合调用重合度、边际信息增益和消融回放判断。

## Q100｜Tool Calling 应评估哪些指标？

**考察意图｜**考察候选人是否能把工具问题拆到选择、参数和执行。

**标准答案**

- Tool Selection Accuracy：该调用时是否调用、选了哪个工具、是否调用了不必要工具。

- Argument Accuracy：字段格式、实体、时间、金额、枚举和跨字段约束是否正确。

- Execution Success：工具是否实际成功，失败是否正确分类和恢复。

- Side-effect Correctness：是否重复执行、越权、在未审批时写入或产生错误副作用。

- Efficiency：调用次数、并行度、缓存命中、超时和单位任务成本。

- 对写工具必须使用沙箱/Mock 或可回滚测试环境，不能在评估中触发真实危险操作。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能建立工具级基准和错误矩阵。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会把工具评估结果反馈到 Schema、路由、权限和实时健康策略。</p>
</blockquote>

高频追问与参考答案

**追问 1｜参数正确率怎么定义部分正确？
参考答案｜**按字段重要性拆分：必填参数、实体、枚举、格式、跨字段约束和业务状态分别评分。诊断时可给部分分，但真实执行必须通过全部强约束；可选描述字段错误的权重应低于收款账户错误。

**追问 2｜不调用工具也是一种正确结果吗？
参考答案｜**是。若上下文已有充分证据、用户只需解释，或请求未获授权/存在风险，正确行为可能是不调用工具。评估集应同时包含 must-call、may-call 和 must-not-call 样本。

**追问 3｜评估写操作如何保证安全？
参考答案｜**使用 Mock、测试账户、Sandbox、Dry-run 或可回滚事务，并为每个写调用注入唯一测试幂等键。评估环境与生产凭证完全隔离，禁止用真实用户和真实资金做自动回归。

## Q101｜Agent 在线 A/B Test 应注意什么？

**考察意图｜**考察候选人对在线实验、安全门槛和统计有效性的理解。

**标准答案**

- 先通过离线门槛和安全审查，再进入在线实验；高风险功能可先影子运行，只比较建议不执行。

- 随机化单位根据产品选择用户、会话、租户或任务，避免同一用户跨组造成学习和记忆污染。

- 同时看主指标、护栏指标和成本：任务成功、人工升级、错误副作用、延迟、Token、投诉和留存。

- 确保两组流量、工具、数据时效和外部环境可比，记录版本与曝光。

- 设置最小样本、实验周期、提前停止规则和分层分析，避免被短期新鲜感或总体平均误导。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计一场有明确假设与护栏的实验。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建立实验平台，处理长期效应、网络效应、多租户异质性和风险加权决策。</p>
</blockquote>

高频追问与参考答案

**追问 1｜为什么不能按请求随机模型但共享同一 Memory？
参考答案｜**Memory 会造成实验串扰：同一用户在 A 组写入的偏好可能影响 B 组结果，无法归因。应按用户/账户稳定分桶，并让 Memory、缓存和版本命名空间与实验组绑定。

**追问 2｜实验中出现安全事故怎么办？
参考答案｜**安全是停止指标，不等待统计显著。立即触发 Kill Switch、阻断危险工具、固定证据和日志、通知安全/业务负责人并调查影响；只有完成修复和回归后才能重新开始。

**追问 3｜统计显著但业务收益很小是否上线？
参考答案｜**不一定。上线决策要看预设的最小实际收益、成本、风险和复杂度；样本很大时微小差异也可能统计显著，但不足以覆盖迁移成本或新增安全暴露。

## Q102｜Agent Trace 至少应该包含哪些 Span 和字段？

**考察意图｜**考察候选人对 GenAI 可观测性的理解。

**标准答案**

- 顶层 run/task Span，子 Span 覆盖模型调用、检索、Rerank、工具执行、Handoff、Guardrail、审批和自定义节点。

- 记录 trace_id、task/thread/tenant、模型与版本、Prompt 版本、输入/输出 Token、首 Token/总延迟、finish reason 和错误。

- 工具 Span 记录 tool_name、call_id、参数摘要/哈希、结果状态、重试、幂等键和下游 trace_id。

- 检索 Span 记录 query、索引版本、过滤、候选 ID/分数、最终 Context 和引用。

- 默认最小化敏感内容，完整 Prompt/工具参数需显式开启、脱敏、权限控制和保留期。

- 使用统一语义字段有利于跨框架与观测平台比较，但业务字段仍需自定义。

<blockquote>
<p><strong>版本/实践提示：</strong>可参考 OpenTelemetry GenAI Semantic Conventions 的 invoke_agent、chat、execute_tool 等语义。</p>
</blockquote>

<blockquote>
<p><strong>P7 合格线：</strong>P7 能用 Trace 定位慢调用、循环和错误工具路径。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建设统一 OpenTelemetry/GenAI 语义体系、采样策略和跨 Agent 链路关联。</p>
</blockquote>

高频追问与参考答案

**追问 1｜完整 Prompt 是否应该默认记录？
参考答案｜**不应默认明文记录。常态只记录 Prompt/Context 版本、哈希、Token 和经过脱敏的结构；对必要样本使用加密、严格权限和短期保留。事故调查也应遵循最小化和审批。

**追问 2｜采样后如何保证高风险事件不丢？
参考答案｜**使用 Tail-based Sampling：正常请求按比例采样，但所有高风险动作、错误、Guardrail 命中、人工升级和异常延迟强制保留。采样决策在 Trace 完成后根据结果做，避免开头随机丢掉事故。

**追问 3｜跨 MCP/A2A 如何传递 Trace Context？
参考答案｜**通过协议 Metadata 传递 W3C traceparent/tracestate 和必要 baggage。MCP request_id/tool_call_id、A2A task_id 作为 Span 属性或 Span Link 关联，跨异步队列则保存父 Trace Context。

## Q103｜如何建立 Agent 的自动化回归测试？

**考察意图｜**考察候选人是否能把 Agent 质量纳入工程流水线。

**标准答案**

- 单元层测试 Prompt 模板、Schema、工具参数、策略和状态转换；工具使用 Mock/Contract Test。

- 组件层测试检索、路由、Planner、Verifier 和 Memory，固定输入与环境快照。

- 端到端层执行黄金任务和对抗任务，检查最终结果、轨迹、禁止动作、延迟与成本阈值。

- 对非确定输出使用属性断言、Rubric、多个可接受答案和统计重复运行，而不是只做字符串相等。

- 发布门槛包含“不得新增严重安全错误”“关键场景不得回退”“成本/延迟不超过阈值”。

- 线上错误自动生成可匿名化 Replay Case，人工审核后加入回归集。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能把评估接入 PR/发布流水线并阻止回归。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建设跨模型批量评估、历史重放、差异分析和自动根因聚类。</p>
</blockquote>

高频追问与参考答案

**追问 1｜模型随机性下如何避免测试抖动？
参考答案｜**避免断言逐字相等，改测 Schema、事实、工具约束和业务不变量；固定模型版本、使用录制结果或多次运行统计区间。对仍有随机性的质量指标设置容忍范围和失败重试诊断，而非掩盖真实回归。

**追问 2｜Mock Tool 会不会掩盖真实问题？
参考答案｜**会。Mock 往往过于理想，掩盖真实鉴权、限流、超时、Schema 漂移和数据问题。因此必须补充契约测试、录制回放和真实 Sandbox 的小规模集成测试。

**追问 3｜每次提交都跑全量评估吗？
参考答案｜**不需要。每次提交跑快速、确定性的单元与核心 Smoke；合并或夜间跑中型回归；模型、Prompt、工具或发布前跑全量与高风险评估。按变更影响选择测试集，同时保留定期全量基线。

## Q104｜Agent 技术指标如何映射到业务 KPI？

**考察意图｜**考察候选人是否能证明项目价值。

**标准答案**

- 先定义业务任务与基线，例如客服一次解决率、告警真实事件发现率、KYC 审核时长、代码修复通过率。

- 技术指标解释过程：工具成功、检索 Recall、事实准确、自动化率、人工升级、延迟和成本。

- 业务 KPI 看最终价值：处理时长、转化、损失降低、用户满意、人工节省和风险事件。

- 避免把“模型回答准确率”直接等同业务收益；需要控制流量结构、人员策略和其他产品变化。

- 对高风险场景使用风险调整指标，例如自动化节省减去误执行预期损失。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能建立指标树并通过实验或前后对照证明收益。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会用单位经济模型指导自治阈值、人工投入和模型预算，持续优化业务组合。</p>
</blockquote>

高频追问与参考答案

**追问 1｜自动化率越高越好吗？
参考答案｜**不是。自动化率过高可能来自错误放行、过度处理或把复杂问题拒绝掉。必须同时满足正确率、安全、投诉、回滚和单位成本门槛，风险越高可接受的自动化边界越低。

**追问 2｜告警场景中 Precision 和 Recall 如何映射损失？
参考答案｜**Precision 低意味着误报多、浪费人工或误封正常对象；Recall 低意味着真实威胁漏掉，潜在损失更高。应按告警等级建立成本矩阵，高危场景通常优先 Recall，再通过分层处置降低误报影响。

**追问 3｜如何证明节省的人力是真实节省？
参考答案｜**用前后对照的工作量、队列积压、SLA、加班、外包/招聘支出和人员重新配置证明。处理时长下降只有在实际释放产能或支撑更多业务量时才是节省，不能把理论分钟数直接换算为现金。
