## Q064｜短期记忆、长期记忆、语义记忆、情景记忆和程序性记忆分别是什么？

**考察意图｜**考察候选人是否有清晰的 Memory Taxonomy。

**标准答案**

- 短期记忆通常是 thread/session 范围内的运行状态与近期上下文，用于保持当前任务连续性。

- 长期记忆跨会话保存，服务于后续个性化或任务复用。

- 语义记忆保存相对稳定的事实和偏好，例如用户语言、常用产品、组织规则。

- 情景记忆保存发生过的事件与结果，例如上次任务失败原因、用户曾拒绝某类方案。

- 程序性记忆保存“怎样做”的策略、流程或技能，但在企业系统中通常更适合版本化配置或知识库，而非模型自由改写。

- 这些类型在工程上可能落入不同存储和检索策略，不能全部塞进一个向量表。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能把记忆类型映射到存储、TTL、更新和权限策略。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会设计统一 Memory Service，同时保持业务真值、用户偏好和 Agent 经验之间的责任边界。</p>
</blockquote>

高频追问与参考答案

**追问 1｜会话历史等于短期记忆吗？
参考答案｜**不完全等于。会话历史只是短期记忆的一种原始材料，真正可用的短期记忆还包括当前目标、结构化任务状态、已完成步骤、工具结果和待确认事项；原样历史通常噪声过多。

**追问 2｜程序性记忆为什么风险更高？
参考答案｜**程序性记忆会改变 Agent ‘以后如何行动’，例如默认流程、工具偏好或策略，影响范围比事实记忆更大，也更容易被注入污染。它必须版本化、评审、受权限控制，不能由一次对话自动改写。

**追问 3｜长期记忆一定用向量库吗？
参考答案｜**不一定。精确偏好、账户设置和时间状态更适合关系库或 KV；事件经历可用事件库，关系知识可用图。向量库只适合语义召回，通常与结构化存储组合。

## Q065｜哪些信息值得写入长期记忆？

**考察意图｜**考察候选人是否理解记忆质量比记忆数量更重要。

**标准答案**

- 只保存对未来任务有稳定价值、用户已明确表达或可从可信业务系统确认的信息。

- 优先保存偏好、长期约束、已确认事实和高价值历史结果，不保存每句闲聊、临时情绪和未经确认的推断。

- 每条记忆带 subject、内容、类型、来源、创建时间、最后验证时间、置信度、作用域、TTL 和权限。

- 敏感信息需要明确目的和同意，不应因为“以后可能有用”就永久保存。

- 模型建议写入的记忆必须经过 Schema、去重、冲突和策略校验；高风险信息可让用户确认。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能制定记忆写入准则并实现用户查看、纠正和删除。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会通过长期任务收益和错误成本评估记忆价值，动态控制写入与保留。</p>
</blockquote>

高频追问与参考答案

**追问 1｜用户随口说一句偏好要不要记？
参考答案｜**不应默认记录。只有用户明确表达、在多次交互中稳定出现、未来确有价值且风险较低的偏好才适合保存；模糊或敏感内容应先确认，并允许用户查看、修改和删除。

**追问 2｜模型推断出的职业可以保存吗？
参考答案｜**不建议直接保存。模型推断可能错误，职业又可能属于敏感或影响决策的信息；只有在明确业务目的和合法依据下，经用户确认后才能作为低置信度、带来源的记忆。

**追问 3｜如何处理一次性临时约束？
参考答案｜**把它标记为 session/task scope，并设置短 TTL 或明确的 valid_until，不进入长期偏好。任务结束后自动失效，除非用户明确要求转为长期设置。

## Q066｜Memory Extraction 与 Consolidation 应怎么做？

**考察意图｜**考察候选人是否能把对话转成稳定、去重的记忆。

**标准答案**

- 在合适的时机对新会话片段做结构化抽取，而不是每个 Token 实时写库；可在一轮结束、任务完成或后台批处理时执行。

- 抽取器输出候选事实、类型、主体、置信度、来源片段和是否需要用户确认。

- Consolidation 对同类记忆去重、合并、更新和建立 supersedes 关系，避免同一偏好出现几十条近义记录。

- 冲突时优先可信来源和更新证据，必要时保留多个时间版本，不让模型静默覆盖。

- 原始对话与提炼记忆分开保存，任何记忆可追溯到来源。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能实现抽取、去重、冲突处理与来源回溯。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会做多源记忆融合、批量质量审计、反馈学习和跨模型兼容。</p>
</blockquote>

高频追问与参考答案

**追问 1｜每轮都抽取会有什么问题？
参考答案｜**每轮抽取会增加成本、延迟和噪声，也容易把随口表达或攻击内容固化为长期记忆。应在用户明确声明、任务完成、重复偏好出现等有意义事件触发，或异步批量 Consolidation。

**追问 2｜两条相反偏好怎么合并？
参考答案｜**不要简单覆盖或平均。分别保留来源、时间、适用场景和置信度，优先用户最新且明确的声明；若可能是场景差异则形成条件化偏好，无法判断时向用户确认。

**追问 3｜摘要记忆是否需要保留原文？
参考答案｜**需要。摘要记忆必须带 provenance，能回溯到原始对话/事件的受控引用和版本；否则无法核验、纠错或响应删除请求。原文可以按隐私策略单独加密和限期保存。

## Q067｜长期记忆应该如何检索和排序？

**考察意图｜**考察候选人是否会避免把所有记忆注入上下文。

**标准答案**

- 先按用户/主体、租户、作用域、权限和有效期过滤，再做语义与关键词检索。

- 排序可综合相关性、最近性、重要性、置信度、来源权威和显式用户固定权重。

- 只注入对当前步骤真正有用的少量记忆，并清晰标注来源和时间，避免干扰当前意图。

- 对互相冲突或低置信度记忆，向用户澄清或在上下文中明确冲突，不能选一条当事实。

- 记录本次命中了哪些记忆、是否影响决策，以便评估错误个性化。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能设计混合检索与 rerank，并评估记忆命中准确率和误用率。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会根据任务类型和用户反馈学习个性化排序，同时满足可解释、可删除和公平性约束。</p>
</blockquote>

高频追问与参考答案

**追问 1｜相关记忆越多越好吗？
参考答案｜**不是。过多记忆会占用 Context、引发冲突并让模型错误套用旧信息。通常按相关性、显式程度、置信度、最近性、重要性和作用域综合排序，只注入少量高价值记忆。

**追问 2｜最近性和重要性冲突时怎么选？
参考答案｜**取决于任务：安全约束和用户明确的长期偏好通常优先于最近一次偶然行为；临时日程则最近性更重要。应把各因子显式打分，并允许硬约束覆盖软排序。

**追问 3｜如何发现一条记忆被错误复用？
参考答案｜**Trace 记录实际检索和注入的 memory_id、版本及影响的输出；发生用户纠正或错误时做反事实回放，移除该记忆比较结果。若错误与其强相关，就降权、失效或修正。

## Q068｜如何防御 Memory Poisoning？

**考察意图｜**考察候选人是否意识到记忆是长期攻击面。

**标准答案**

- 任何用户文本、网页、工具结果和远端 Agent 输出都不能未经校验直接写入高信任记忆。

- 按来源划分信任等级，业务系统事实、用户明确确认和模型推断使用不同权限与置信度。

- 记忆写入执行内容安全、提示注入检测、Schema 校验、去重、异常频率和租户隔离。

- 高影响程序性记忆或执行规则只能由受控发布流程更新，不允许普通对话永久改变。

- 提供版本历史、回滚、用户查看/删除和批量隔离能力；监控异常工具选择与记忆命中。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能建立记忆来源和信任模型，并构造投毒测试。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会把记忆供应链治理、异常检测和取证纳入 Agent 安全平台。</p>
</blockquote>

高频追问与参考答案

**追问 1｜用户明确要求“以后都自动转账”能直接记吗？
参考答案｜**不能。‘以后自动转账’属于高风险、长期授权，不能由对话记忆替代每次身份、额度和审批策略。最多记录用户的服务偏好，真实转账仍需独立授权和交易级确认。

**追问 2｜内部工具结果是否天然可信？
参考答案｜**不是。内部工具可能有 Bug、权限配置错误、数据被污染或供应链被攻破。结果要保留来源、签名、时间和信任等级，高风险事实还需权威源或规则交叉验证。

**追问 3｜如何隔离被污染的历史记忆？
参考答案｜**立即停止检索该记忆并打上 quarantine/tombstone，追踪其派生摘要和被影响任务，重新从可信原始来源构建干净版本。对已执行高风险动作进行审计、通知和必要补偿。

## Q069｜记忆的 TTL、衰减和遗忘机制怎么设计？

**考察意图｜**考察候选人对时效、隐私和错误累积的理解。

**标准答案**

- 不同类型使用不同生命周期：会话状态随任务结束归档，临时偏好短 TTL，稳定偏好长期但需要定期确认。

- 根据时间、使用频率、最后验证、来源置信度和用户反馈做衰减，低价值记忆可归档或删除。

- 业务事实变更时用事件主动失效，不应只等 TTL；例如组织、权限、订阅状态。

- 删除要传播到主存储、向量索引、缓存、备份策略和派生摘要，并保留合规要求的最小审计。

- 遗忘策略必须可解释，用户应能查看哪些信息被记住并主动纠正。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能为不同记忆类型定义生命周期和删除链路。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会在个性化收益、隐私风险、存储成本和法规之间建立分层保留策略。</p>
</blockquote>

高频追问与参考答案

**追问 1｜TTL 到期就直接物理删除吗？
参考答案｜**通常先逻辑失效，使在线检索立即不可见，再由后台任务做物理清理、索引删除和缓存失效。可保留不含正文的删除审计记录，以证明处理过程。

**追问 2｜用户修改偏好后旧记忆怎么办？
参考答案｜**新偏好写成新版本并显式 supersede 旧版本，检索只使用当前有效版本。旧内容如因审计需要保留，应严格限权且不能再进入模型上下文。

**追问 3｜备份里的数据如何处理删除请求？
参考答案｜**按照数据保留策略让删除 Tombstone 传播到所有备份和灾备副本；可采用密钥分层与 Crypto-shredding。任何备份恢复流程都必须先重放删除日志，避免已删除数据重新上线。

## Q070｜跨设备和跨渠道如何保证记忆不串用户？

**考察意图｜**考察候选人的身份、作用域与租户隔离意识。

**标准答案**

- 记忆绑定的是经过认证的主体 ID，而不是浏览器 Cookie、设备 ID 或自然语言中的姓名。

- 匿名会话与登录用户合并需要明确规则和用户同意，不能自动把公共设备历史归到新登录账号。

- 所有 Memory API 强制检查 tenant_id、subject_id、channel scope 和权限，服务端生成过滤条件。

- 共享家庭、企业代理和代办场景要区分操作者、被代理人和组织主体。

- 缓存、Trace、Embedding 索引和导出同样按身份隔离，并通过越权测试验证。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能画出身份解析、账号合并和记忆访问链路。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会设计跨组织身份联邦、委托授权和数据主权策略。</p>
</blockquote>

高频追问与参考答案

**追问 1｜游客转登录用户时历史怎么合并？
参考答案｜**先建立足够强的身份绑定并征得用户同意，只合并低风险、来源明确的历史；冲突偏好要保留 provenance 并请求确认。匿名阶段的敏感信息或其他人的设备数据不能自动并入。

**追问 2｜客服代用户操作时记忆记到谁名下？
参考答案｜**同时记录 subject_user_id 和 actor_id。记忆若描述被服务用户，应归属于 subject；客服人员的操作和判断进入审计，不应被误写成用户偏好，除非用户之后确认。

**追问 3｜同名用户如何避免混淆？
参考答案｜**所有隔离依赖租户内不可变 user_id、账号绑定和会话主体，而不是姓名、手机号后几位等弱标识。跨渠道通过经过验证的身份映射关联，无法确认时保持独立。

## Q071｜Checkpointer 与 Long-term Store 有什么区别？

**考察意图｜**考察候选人能否区分任务恢复与跨会话记忆。

**标准答案**

- Checkpointer 保存某个 thread/task 的图状态快照，用于会话连续、暂停恢复、人工审批和故障容错。

- Long-term Store 保存应用定义的跨线程数据，例如用户偏好、事实、经验和共享知识。

- Checkpointer 通常按 thread_id 访问，状态强关联编排版本；Store 按命名空间、主体和查询条件访问。

- 检查点中的中间工具结果不应自动升级为长期记忆，长期记忆也不应代替业务数据库真值。

- 两者生命周期、隐私、删除和一致性要求不同，应在架构上分离。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能给出两种存储的表结构或接口，并处理恢复与记忆检索。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会建设统一但逻辑隔离的 State/Memory 基础设施，支持版本、回放、跨区和政策治理。</p>
</blockquote>

高频追问与参考答案

**追问 1｜为什么不能把所有状态都放向量库？
参考答案｜**向量库是近似语义检索，不适合保存精确状态、顺序、锁、版本和事务结果，也难以保证覆盖更新。Checkpoint 需要可恢复的一致结构，应使用数据库、事件存储或专用 Checkpointer。

**追问 2｜任务结束后 Checkpoint 是否删除？
参考答案｜**取决于恢复、审计和隐私要求。任务结束后可从热存储归档，超过 TTL 后删除大体积中间状态；涉及合规或补偿的关键记录按政策保留，不能一结束就全部清空。

**追问 3｜长期记忆变更会影响正在执行的任务吗？
参考答案｜**正在运行的任务最好固定 memory snapshot/version，避免同一步骤前后语义漂移。新记忆在下一个明确 Checkpoint 或重新规划时按策略加载；高风险变更可触发重新验证。

## Q072｜如何评估个性化 Memory 是否真的有价值？

**考察意图｜**考察候选人是否能避免“记得越多体验越好”的主观判断。

**标准答案**

- 建立有/无 Memory 的对照，评估任务成功率、重复提问减少、用户修改次数、响应长度和满意度。

- 同时监控错误个性化、错误主体、陈旧记忆、敏感信息暴露和过度推断。

- 离线数据包含稳定偏好、变更偏好、冲突记忆、无关记忆、恶意记忆和跨用户隔离样本。

- 线上 A/B 要分任务类型和用户阶段，避免总体平均掩盖某类用户受损。

- 提供“为什么这样推荐/回答”的来源解释和一键纠正，纠正率是重要负面指标。

<blockquote>
<p><strong>P7 合格线：</strong>P7 能定义 Memory Precision、Useful Recall、False Memory Rate 和用户纠正率。</p>
</blockquote>

<blockquote>
<p><strong>P8 加分点：</strong>P8 会将长期收益、隐私风险和信任损失纳入决策，动态选择是否启用个性化。</p>
</blockquote>

高频追问与参考答案

**追问 1｜Memory 命中率高为什么可能仍然不好？
参考答案｜**命中率只说明‘检索到了记忆’，不说明记忆相关、正确或有帮助。还要看任务成功率、用户纠正率、个性化满意度、Token 成本、过时记忆率和安全/泄漏事件。

**追问 2｜如何构造跨用户泄漏测试？
参考答案｜**为不同用户和租户植入唯一、无害的 Canary Memory，并用相似问题、身份混淆和恶意提示尝试跨域检索；任何非所属主体命中都应视为严重失败，同时检查缓存和 Trace 泄漏。

**追问 3｜用户满意度提升如何排除其他因素？
参考答案｜**按用户随机进行长期 A/B，固定模型、Prompt 和其他产品变化，比较任务质量、留存、处理时长和纠正率；使用分层分析和足够观察周期，避免把同期功能更新误认为 Memory 收益。
