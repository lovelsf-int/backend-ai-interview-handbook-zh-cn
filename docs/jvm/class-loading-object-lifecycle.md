# JVM 类加载、对象生命周期与内存边界

> 类的生命周期和对象的生命周期是两条相关但不同的链：类先经过加载、链接和初始化，对象才可能被分配与构造；对象不可达后由 GC 决定回收，类卸载还要求其定义类加载器具备可回收条件。

## 90 秒回答骨架

类从使用到可执行，通常经过加载、链接和初始化。加载根据二进制名称获取 Class 文件并创建运行时表示；链接包含验证、准备和解析，验证检查结构和字节码约束，准备为静态字段分配并设置初始值，解析把符号引用转换为直接引用且可能按需延迟；初始化才执行静态字段赋值和静态代码块。

对象创建时，JVM 先保证目标类已完成必要初始化，再分配内存、设置对象初始状态并执行构造链。HotSpot 常通过 TLAB 降低并发分配竞争，但这是实现策略，不是 Java 语言对所有 JVM 的保证。对象不再被 GC Roots 可达后才具备回收资格；“离开方法作用域”不等于马上回收。

类泄漏往往不是 Class 对象单独存活，而是自定义类加载器被线程、ThreadLocal、静态注册表、驱动或缓存引用，导致它定义的整批类和相关元数据无法卸载。

## 加载、链接、初始化必须分开

| 阶段 | 做什么 | 高频误区 |
|---|---|---|
| Loading | 按二进制名称获取定义并创建运行时 Class 表示 | “加载等于执行静态代码” |
| Verification | 校验 Class 文件结构、类型和字节码约束 | “校验只是检查魔数” |
| Preparation | 为静态字段分配存储并设置默认初始值 | “这里已执行所有静态赋值表达式” |
| Resolution | 解析常量池中的符号引用 | “一定在初始化前一次性全部完成” |
| Initialization | 执行类初始化方法，完成静态赋值与静态块 | “new 对象才会触发初始化” |

链接要求验证与准备在初始化前完成，但解析允许实现按使用需要推进。面试时不要把教科书流程图误说成所有动作严格一次性串行完成。

## 哪些行为会触发初始化

典型主动使用包括：

- 创建该类的新实例；
- 调用该类声明的静态方法；
- 读取或写入该类声明的非编译期常量静态字段；
- 某些反射调用；
- 初始化子类前先初始化其父类；
- JVM 启动时初始化包含入口方法的初始类。

边界题：

- 读取可在编译期内联的 `static final` 常量，可能不会触发声明类初始化；
- 创建某类型数组不会因此初始化数组元素类型；
- 通过子类引用父类声明的静态字段，通常初始化实际声明字段的类；
- `Class.forName(name)` 默认会初始化，带 `initialize=false` 的重载可只加载而不初始化。

## 父加载器委派要讲成模型，不是口号

常见 JDK 运行时有 Bootstrap、Platform 和 Application ClassLoader。`ClassLoader.loadClass` 的典型流程会先检查是否已加载，再委派父加载器，父级无法完成时再尝试自身查找。

委派的价值是：

- 避免核心类被应用重复定义；
- 让共享 API 由稳定加载器定义；
- 降低同名类的类型冲突和安全风险。

但它不是“任何类加载器都必须无条件父优先”的简单规则。插件容器、模块系统、应用服务器和热部署框架可能使用子优先、双亲可见性或多层加载器；设计时要明确哪些包由父级共享，哪些由插件隔离。

## 类身份为什么包含定义加载器

运行时类型身份不仅由类的二进制名称决定，还与定义它的 ClassLoader 有关。两个加载器分别定义同名同字节码类，这两个运行时类型仍不相同，可能出现看似“把 A 转成 A”却抛出 `ClassCastException`。

插件系统的稳定做法通常是：

- SPI 接口和共享 DTO 由父加载器定义；
- 插件实现由各自子加载器定义；
- 跨边界只传共享类型、基本值或明确序列化协议；
- 插件卸载时清理线程、ThreadLocal、注册表、驱动和缓存。

## 对象创建不是一句 new 完成

从概念上可以分成：

1. 检查类是否已完成必要的加载、链接和初始化；
2. 根据对象布局申请内存；
3. 将实例字段置为语言规定的默认值；
4. 设置对象运行时元数据；
5. 执行父类到子类的构造初始化链；
6. 将引用安全发布给其他线程。

“构造完成”不自动等于“并发安全发布”。如果在构造函数中让 `this` 逸出，其他线程可能观察到尚未完成初始化的状态。不可变对象还需要正确使用 `final` 字段并避免构造期间逸出。

## TLAB、栈上分配与逃逸分析

高并发分配若都竞争共享堆指针，成本会很高。HotSpot 常为线程分配 TLAB，使大多数小对象先在线程私有分配区快速申请；TLAB 用尽或对象过大时再走其他路径。

JIT 还可能通过逃逸分析进行标量替换、锁消除等优化，使源码中的对象不一定真的以传统形式分配在堆中。面试要说“可能优化”，不能承诺所有未逃逸对象都会栈上分配；是否发生取决于代码形态、编译层级和具体 JVM。

## GC Roots 与可达性

判断对象是否存活，不能使用“引用计数为零”的简单模型。Tracing GC 从根集合出发扫描可达对象。常见 Roots 来源包括：

- 活跃线程栈中的局部引用；
- 已加载类的静态字段；
- JNI 全局或局部引用；
- JVM 内部结构、同步和运行时持有对象。

对象从业务容器删除后，如果仍被 ThreadLocal、静态 Map、监听器、定时任务、线程或本地库引用，仍然可达，不具备回收条件。

## 强、软、弱、虚引用的工程边界

| 引用 | 典型语义 | 不应该怎么用 |
|---|---|---|
| Strong | 普通强可达关系 | 无界静态集合长期持有大对象 |
| Soft | 内存压力相关的回收提示 | 把它当可预测 TTL 缓存策略 |
| Weak | 不阻止目标被回收 | 用于必须稳定存活的业务状态 |
| Phantom | 与引用队列配合跟踪回收后清理 | 直接通过引用取回对象 |

缓存应使用明确容量、权重、过期和观测策略，不要只靠软引用猜测回收时机。外部资源优先使用 `try-with-resources` 的确定性关闭；`Cleaner` 只能作为防泄漏兜底，不能保证及时执行。

## finalization 为什么不应再作为方案

Finalization 已被弃用并计划移除。它具有执行时机不可预测、性能和安全风险，且对象可能在终结过程中复活。新代码不应依赖 `finalize` 释放文件、连接或锁等关键资源。

正确顺序是：

1. `AutoCloseable` + `try-with-resources`；
2. 明确的所有权与生命周期；
3. 必要时使用 Cleaner 作为最后兜底并监控泄漏；
4. 进程退出不能代替资源治理。

## Metaspace 为什么会泄漏

Metaspace 存放类元数据，使用本地内存。类通常只有在其定义 ClassLoader 可回收且 JVM 满足卸载条件时才可能卸载。常见泄漏路径：

- 线程上下文 ClassLoader 长期指向已下线应用；
- ThreadLocal Value 引用插件对象；
- JDBC Driver、日志、MBean、序列化缓存或 SPI 注册未注销；
- 应用创建非守护线程且未停止；
- 动态生成大量代理类且加载器生命周期失控。

排查时结合多次 Full GC 后的 Metaspace 基线、ClassLoader 数量、类加载/卸载计数、JFR、`jcmd VM.classloader_stats` 和 Heap Dump 的 GC Roots，而不是只调大 `MaxMetaspaceSize`。

## OOM 必须先分类型

| 现象 | 重点证据 | 常见方向 |
|---|---|---|
| Java heap space | GC 后老年代、分配速率、Dump Dominator | 泄漏、缓存、批量对象、堆过小 |
| Metaspace | 类数量、ClassLoader、动态代理 | 热部署或类加载器泄漏 |
| Direct buffer memory | RSS 与堆差值、Buffer Pool、NMT | NIO/Netty 直接内存、释放延迟 |
| Unable to create native thread | 线程数、栈大小、进程/容器限制 | 线程泄漏、平台线程过多、系统限制 |
| GC overhead / allocation failure | 分配速率、回收收益、停顿 | 活跃集过大、内存泄漏或容量不足 |

虚拟线程数量大时，也不能只看 Java Heap。任务关联对象、ThreadLocal、Socket、直接内存、下游连接和日志队列都可能成为真实瓶颈。

## P7/P8 连续追问

### static 字段在准备阶段和初始化阶段分别是什么值

准备阶段先设置类型默认值；初始化阶段才执行程序员编写的静态赋值表达式和静态代码块。编译期常量可能进入常量属性，具体回答应区分语言语义与 Class 文件实现。

### 为什么线上热部署几次后 Metaspace 才爆

每次部署创建新 ClassLoader，但旧线程、ThreadLocal、驱动或注册表仍引用旧加载器，导致旧类集合无法卸载。多轮部署累积后才超过本地内存边界。修复要清理泄漏链和生命周期，不只是扩大 Metaspace。

### 对象离开方法后为什么不一定回收

局部变量生命周期只是一个来源；对象可能被返回、写入字段、缓存、线程、JNI 或其他可达对象引用。GC 只按可达性和收集时机工作，不按源码作用域立即回收。

### 双亲委派能否防止所有核心类被替换

不能把它当完整安全边界。标准加载器的父优先有助于保护核心类，但自定义加载器、模块边界、启动参数和运行时注入还涉及更完整的安全与部署控制。
