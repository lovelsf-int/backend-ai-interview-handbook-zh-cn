# 两个线程交替打印奇偶数：边界与退出

## 完整题目

两个线程分别输出奇数与偶数，按顺序输出 1 到 N。N 可以是 0、1 或任意非负 int，不能多打印、漏打印或结束时留下等待线程。N<0 拒绝。

与 ABC 固定每个角色 N 次不同，奇数上限时两个线程的工作量不同。N=9 时奇数线程输出 5 次，偶数线程输出 4 次，不能让两者机械循环同样次数。

## 共享状态与实现

用共享 next 表示下一待输出数字。奇数角色编号 1，偶数角色编号 0，通过 next % 2 判定轮次；next 的读取、输出和递增都在同一锁下。

## 为什么等待条件包含 next 不超过上限？

等待条件是“任务还没完成，并且暂时没轮到我”。如果只判断奇偶，不检查完成条件，最后一个数字输出后，另一线程可能再次进入等待，后面再也无人通知。

唤醒后先检查 next > limit；到达终点时 notifyAll 并退出，确保另一角色有机会观察结束状态。共享 next 使用 long，是为了 limit=Integer.MAX_VALUE 时最后一次递增不溢出成负数；这不是鼓励用终端实际打印几十亿个数，默认运行还有时间预算。

## 边界手推

| 输入 | 正确结果 | 要验证的点 |
| --- | --- | --- |
| 0 | 空输出 | 两个角色均退出 |
| 1 | 1 | 偶数角色无任务，仍能退出 |
| 2 | 1、2 | 首次交棒 |
| 9 | 1 到 9 | 两个角色工作量不同 |
| 100 | 1 到 100 | 多轮交替，无额外 101 |

## 常见追问与答案

**问：next 加 volatile 能去掉 synchronized 吗？**不能直接去掉。当前实现靠监视器让条件检查、输出和递增构成协议。volatile 的可见性不等于把这组动作变成原子操作，wait/notifyAll 也要求持有该监视器。可以另写满足严格单写轮次条件的自旋协议，但它有 CPU、取消和维护成本，不是简单加一个关键字。

**问：为什么 while(true) 在锁里不会让另一个线程一直进不来？**轮次不匹配时 wait 会释放锁。当前角色每输出一个数字就切换奇偶，下一轮自然进入等待；到终点则直接退出同步块。不可把 wait 换成持锁的空转循环。

**问：能不能让线程各自维护一个数字，一个每次加 2？**能得到各自的奇数/偶数序列，但不能自动保证两个序列的全局交错。仍需要交棒；而奇数终点时两边次数不同，还要处理最终退出。

**问：如果输出函数抛异常呢？**核心任务失败，统一监督器取消剩余任务。不能 catch 后继续递增计数并当作成功，否则会漏数字；也不能退出单个线程后放任另一线程永久等待。

**问：打印日志看起来有序，能说明共享状态一定安全吗？**不能。控制台输出自身可能带同步，偶然掩盖问题。测试应在内存中记录输出，检查全序和数量，再结合锁的作用范围证明；不能用一次观察替代分析。

## 从面试题迁移到工程

打印题把“获取轮次”和“产生输出”放在一个临界区，以方便证明。生产中的网络输出可能超时，不能长时间持有全局锁；可以让业务并行计算，再用单独的有序提交阶段输出，配套序号、失败占位、背压与取消。是否必须严格有序，应由业务需求决定。
