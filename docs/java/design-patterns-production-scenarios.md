# Java 设计模式的生产场景与边界

模式定义与支付示例已有完整 canonical 页面：[支付架构设计模式](../finance-payment-ddd/03-design-patterns.md)。本页不重复背 UML，而用一个 P8 判断链：

> 变化点 → 不变量 → 模式 → 失败路径 → 运维证据 → 何时不用

## 选择地图

| 生产问题 | 主要模式 | 保护的边界 |
|---|---|---|
| 多支付渠道协议不同 | Adapter + ACL | 渠道 DTO/错误码不污染领域层 |
| 渠道路由与产品规则变化 | Strategy + Registry | 规则可替换，注册完整且可审计 |
| 支付状态只能合法演进 | State Machine | 单调迁移、幂等与乱序处理 |
| Agent 工具调用需要治理 | Command | 参数校验、审批、执行、审计和补偿 |
| RAG 有多段处理步骤 | Pipeline/Chain | 步骤可组合，失败和观测语义明确 |
| 统一重试、Trace、熔断 | Decorator/Proxy | 横切能力不侵入领域实现 |
| Agent 工作流是树 | Composite | 叶子与组合节点统一调度 |
| 上层需要稳定用例 API | Facade | 隔离内部编排与领域对象 |

## 支付：Strategy、Adapter 与 Registry

变化点要拆成两类：

- Strategy 选择“做哪套业务规则”，例如按地区、币种、产品和风险选择支付策略。
- Adapter 解决“如何与某个渠道通信”，包括签名、DTO、错误码、回调和能力差异。

Factory/Registry 负责发现实现，但必须有启动时校验：重复 Key、缺少必选渠道、配置引用不存在实现时直接失败。运行时热配置还要有版本、审批、灰度和回滚，不能让一个未校验字符串决定资金路由。

高风险做法是把实时成功率直接反馈给路由，造成短期波动被放大。应使用最小样本、平滑窗口、滞后、熔断与人工护栏，并保留路由决策审计。

何时不用：只有两个稳定分支且不会独立演进时，显式 `if` 往往更清晰。模式不能成为隐藏简单业务的理由。

## State Machine：状态不是普通 Setter

支付、订阅和 Agent 工具执行都需要合法迁移矩阵：

- 旧状态 + 事件决定新状态；
- 条件更新或版本号保证并发安全；
- 重复事件返回已有结果；
- 晚到失败不能覆盖已确认成功；
- `UNKNOWN` 是待查询/对账状态，不等同于失败。

实现不一定需要状态模式类层级。状态较少时，数据库约束 + 显式迁移表 + 领域服务更易审计。若每个状态有大量独立行为，才考虑 State 对象。

## Agent 工具：Command 是执行治理单元

把每次工具调用封装成 Command，可统一携带：

- `commandId`、调用者、Tenant、权限和 Deadline；
- 经过 Schema 校验的参数；
- Dry-run/审批策略与风险级别；
- 幂等键、执行状态、结果摘要和审计证据；
- 取消、查询、重试或补偿能力。

Command 不意味着所有副作用都能 Undo。删除云资源、发邮件或支付退款可能无法原样回滚；此时要明确补偿动作、人工审批和不可逆边界。

## Chain 与 Pipeline 不要混用

责任链通常表示“处理者可决定是否继续”；Pipeline 强调固定或配置化阶段依次处理。RAG 中清洗、切分、Embedding、召回、Rerank 更像 Pipeline；风控规则逐条判定并可提前拒绝更像 Chain。

P8 设计必须定义：

- 步骤输入输出 Schema 和版本；
- 同步/异步边界；
- 失败是终止、跳过、降级还是进入 DLQ；
- 每一步的 Trace、质量指标和成本；
- 配置变化如何回放与复现。

## Decorator 与 Proxy

Decorator 给同一接口叠加行为，例如为 `ModelClient` 组合指标、重试、限流与缓存。Proxy 强调访问控制或远程替身，例如 Spring AOP 事务代理或 RPC Stub。

横切层的顺序影响语义：

```text
Metrics(Retry(Bulkhead(Timeout(Client))))
```

它与 `Retry(Timeout(Client))` 的超时预算不同。重试若放在限流外可能重复竞争许可，缓存若包住权限校验可能造成越权。顺序必须用失败场景测试，而非随意叠注解。

## Composite：Agent 工作流树

叶子节点执行检索、模型或工具；组合节点表达串行、并行、条件和聚合。Composite 让调度器统一处理节点，但运行时还需要：

- DAG 校验与最大深度，防止循环和递归爆炸；
- 每节点 Deadline、预算与重试上限；
- 并行 Fan-out 上限；
- Checkpoint 与恢复语义；
- Prompt/工具/模型版本可追溯。

如果流程只有固定三步，普通函数组合比可配置工作流引擎更可靠。

## Facade：稳定应用用例，不泄漏内部编排

Controller 或 MCP Tool 不应直接编排 Repository、Kafka、模型和支付渠道。Facade/Application Service 暴露稳定用例，例如 `AnalyzeAlert`、`CreatePayment`，内部协调领域对象和端口。

Facade 不是“万能大 Service”。它应只做用例编排，领域不变量仍在聚合/领域服务，下游差异仍由端口与 Adapter 隔离。

## 过度设计检查

每引入一个模式，回答五个问题：

1. 当前真实变化点是什么，而不是未来也许会发生什么？
2. 不用模式时已有何种可观测痛点？
3. 新抽象怎样降低修改范围或错误概率？
4. 它增加了多少类、配置、动态分派和调试成本？
5. 有什么删除/合并条件？

如果答案只是“符合开闭原则”，还没有达到生产设计深度。

## P8 压力追问

### 新增渠道仍要改 Factory，是否违反开闭原则

开闭原则不是零修改。重点是变化被限制在实现、声明式注册和配置，核心支付状态与用例无需改；注册表还必须能验证完整性。为了绝对零修改引入运行时扫描和动态脚本，可能让安全与可观测性更差。

### 为什么不用规则引擎

规则频繁由非研发维护、需要组合和版本化时规则引擎有价值；固定少量高风险逻辑用类型化 Java 更易测试、评审和回滚。先验证规则复杂度和治理能力。

### 设计模式如何证明有效

看变更 Lead Time、缺陷逃逸率、渠道契约测试覆盖、回滚时间和事故影响面。类图不是证据。

## 证据边界

页面中的项目场景来自候选人材料。接入渠道数、交付周期、吞吐和故障数据必须由本人核验；不能把示例模式包装成实际生产经历。
