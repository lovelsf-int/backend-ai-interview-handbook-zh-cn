# Spring 生产故障排查

## 排障总原则

先确定故障阶段，再收集证据：启动期、请求入口、Bean 方法、事务资源、异步执行器还是下游。用时间线、指标、日志、Trace、线程转储和配置快照建立事实，不要先通过重启掩盖根因。

## 启动失败

### BeanDefinition 冲突

检查 Bean 名称、类型、扫描范围、自动配置条件、Profile 和上下文层次。记录两个定义分别来自哪个配置类或资源，再决定重命名、Qualifier、Primary 或排除自动配置。

### UnsatisfiedDependencyException

最外层通常只是包装。沿 cause 找到“没有候选”“多个候选”“创建候选失败”中的哪一种，再检查类型、泛型、限定符和候选 Bean 自身初始化异常。

### 循环依赖

先画依赖图，区分构造器环还是属性环。生产修复优先拆职责或事件解耦，不以重新开启循环引用作为终点。

### 启动卡住

获取线程转储，定位初始化方法中的网络连接、数据库迁移、锁等待或无限重试。Bean 构造和 PostConstruct 不应执行无超时的远程操作。

## 注解不生效

统一检查七项：

1. 对象是否由容器管理。
2. 调用是否经过代理。
3. 方法是否匹配且可增强。
4. 注解读取位置是否正确。
5. 基础设施是否启用并注册。
6. 多个 Advisor 的顺序。
7. 是否切换线程或跨上下文。

该清单适用于事务、缓存、异步、重试和方法安全。

## 事务异常

### 事务未回滚

检查异常是否被吞、是否满足回滚规则、是否调用了错误实例、是否自调用、是否使用了正确事务管理器。通过数据库结果与事务日志确认，而不是只看业务日志里出现异常。

### 连接池耗尽

关注 active、idle、pending、获取等待、事务 P95/P99 和慢 SQL。常见原因包括远程调用放在事务中、REQUIRES_NEW 嵌套、锁等待、连接泄漏和突发并发。扩池前先确认数据库承载能力。

### UnexpectedRollback

通常是内层加入同一事务后标记 rollback-only，外层捕获异常仍尝试提交。修正异常契约或事务边界，不要简单忽略异常。

## Web 请求问题

- 404：路由映射、Context Path、网关改写和部署版本。
- 400：数据绑定、校验、反序列化、字符集和时间格式。
- 415/406：Content-Type、Accept 与消息转换器。
- 500：异常解析器是否命中、Filter 异常是否被统一处理。
- 延迟：拆分网关排队、Servlet 线程、业务、连接池、下游和序列化。

## 异步与任务积压

检查执行器活跃数、队列长度、拒绝数、任务年龄、超时和取消。无界队列会把过载变成延迟和内存问题；CallerRuns 可能反压入口，也可能阻塞不该阻塞的线程。为不同下游建立隔离舱，不共用一个“万能线程池”。

## 内存与上下文泄漏

常见来源：ThreadLocal 未清理、无限缓存、监听器重复注册、ClassLoader 被静态引用、请求/响应大对象日志、未关闭客户端和执行器。使用 heap dump、对象支配树、类加载统计和线程引用链定位。

## 优雅停机

```text
停止接收新流量
-> readiness 变为不可用并等待路由收敛
-> 停止拉取新消息/任务
-> 等待有界 drain
-> 持久化长任务检查点或释放租约
-> 关闭执行器、客户端、连接池
-> 超过上限后明确中断与恢复策略
```

长 Agent 任务不应靠无限延长关机时间，应有 task_id、租约、状态和可恢复检查点。

## 事故复盘模板

1. 用户影响与时间范围。
2. 首个异常信号与为何未更早发现。
3. 请求、线程、连接、事务和下游时间线。
4. 直接原因与系统性原因。
5. 临时止血是否引入新风险。
6. 代码、配置、容量、监控和流程改进。
7. 每项措施的负责人、验证方式和截止条件。

## 面试场景题

### 场景一：加了 Transactional 仍出现部分数据

先确认数据是否在同一数据源和事务管理器；检查自调用、异步、异常吞掉和外部系统副作用。若 MySQL 回滚但 ES 已写入，这是跨系统一致性问题，不是本地事务“部分提交”。

### 场景二：开启虚拟线程后吞吐没提升

线程可能已不是瓶颈。检查数据库连接池、HTTP 连接池、下游限流、CPU 与锁。用 Little 法则和端到端时延估算在途量，再设置下游并发预算。

### 场景三：发布后部分实例接口 404

比较实例版本、路由注册表、条件配置、Profile 与扫描范围；确认滚动发布期间新旧接口兼容。不要只在网关反复刷新路由。

### 场景四：缓存数据长期不一致

确认缓存写删顺序、失败重试、TTL、Key 版本和多实例本地缓存。数据库事务提交并不能保证缓存动作成功，需要可观测和收敛机制。
