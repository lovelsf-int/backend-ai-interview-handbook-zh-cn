# 注解、事件、缓存与异步

## 先建立统一认知

`@Transactional`、`@Cacheable`、`@Async`、`@Scheduled` 等注解只是声明元数据。配置解析器、后置处理器、Advisor、事件广播器和任务处理器负责把元数据转为运行时行为。面试时先回答“谁读取注解、在哪个阶段、最终如何调用”。

## Spring 事件

`ApplicationEventPublisher` 发布应用内事件，监听器默认可在发布线程同步执行；一个慢监听器会延长发布方时延，异常也可能影响调用链。异步监听需要明确执行器、拒绝策略、上下文传播和丢失语义。

### TransactionalEventListener

它可以绑定事务阶段，例如提交前、提交后、回滚后或完成后。提交后监听并不意味着与外部系统原子一致；进程在提交后、执行监听前崩溃，事件仍可能丢失。关键业务事件应使用 Outbox 等持久化机制。

## 缓存注解

### Cacheable

命中时跳过目标方法，未命中时执行并写缓存。需要定义稳定 Key、空值策略、TTL、序列化、并发击穿和多级缓存一致性。

### CachePut

始终执行方法，再更新缓存。它不自动把数据库提交与缓存更新变成原子操作。

### CacheEvict

用于删除缓存；删除时机和事务提交顺序需要设计。先删后回滚会产生缓存缺失，先更新 DB 后删缓存失败会产生旧值，需要重试、消息或版本化策略。

自调用同样可能绕过缓存代理。

## Async

`@Async` 通常通过代理把方法提交到 TaskExecutor。生产必须显式配置：

- 核心与最大并发或虚拟线程策略。
- 队列/并发闸门。
- 拒绝策略。
- 任务超时与取消。
- 异常观测。
- Trace、MDC 和安全上下文传播。
- 优雅停机和未完成任务处理。

返回 `void` 的异步异常无法通过调用者 Future 传播，必须配置异常处理与指标。线程切换也不会继承调用线程事务。

## Scheduled

定时注解只解决触发，不自动解决集群单执行、重入、幂等、错过补偿和长任务接管。多实例部署要使用分布式调度、租约或数据库锁，并记录计划时间与实际执行时间。

## 多注解叠加

```text
@Async + @Transactional
@Cacheable + @Transactional
@Retryable + @Transactional
@Scheduled + 分布式锁
```

要分析代理顺序和线程边界。例如 Async 在外层时，事务在异步线程内开启；事务在外层而 Async 提交任务后立即返回时，任务并不处于原事务。不要靠注解书写顺序推断实际顺序。

## 高频面试题

### Q1. Spring 事件能替代 Kafka 吗？

不能一概而论。应用内事件适合同进程解耦，默认没有跨进程持久化、重放和消费组语义；可靠跨服务事件需要消息系统与 Outbox/幂等。

### Q2. Cacheable 为什么可能失效？

检查对象是否由容器管理、是否自调用、Key 是否稳定、缓存管理器是否正确、方法是否匹配，以及返回值/异常是否满足缓存条件。

### Q3. Async 为什么会把数据库打满？

异步只把等待从调用线程转移到执行器，不增加数据库连接和 QPS 容量。无界提交会在队列、内存或连接池形成积压，应设置并发上限与背压。

### Q4. 事务提交后再更新缓存就安全吗？

只能避免未提交数据进入缓存，不能保证更新动作必达。提交后进程崩溃仍可能遗漏，需要删除重试、消息驱动或可接受的 TTL 收敛策略。

## 生产答题模板

> 我先确认注解对应的执行基础设施和代理顺序。异步任务使用独立执行器和并发闸门，任务内部开短事务；关键事件通过业务表与 Outbox 同事务持久化。缓存采用稳定 key、TTL、删除重试和热点保护，不能把缓存注解当成一致性协议。所有异步和定时任务都有 task_id、状态、重试次数、积压和失败告警。
