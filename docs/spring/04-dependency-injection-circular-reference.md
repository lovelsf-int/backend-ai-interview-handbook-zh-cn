# 依赖注入与循环依赖

## 注入方式选择

构造器注入适合必需依赖，能够形成创建时不变量；Setter 适合可选依赖；字段注入虽然简短，但隐藏依赖、难以直接构造测试对象，也不利于不可变设计。一个类构造器参数过多通常是职责过载信号，不应靠字段注入掩盖。

## 什么是循环依赖

```text
A 依赖 B
B 又依赖 A
```

循环引用不只是容器技术问题，往往意味着职责边界、事件方向或领域依赖方向不清。生产设计应优先重构，而不是先寻找开关。

## 三级缓存的角色

经典 singleton 创建流程中，`DefaultSingletonBeanRegistry` 维护：

```text
singletonObjects       一级：完整单例
earlySingletonObjects  二级：已获取的提前引用
singletonFactories     三级：用于生成提前引用的 ObjectFactory
```

三级缓存的关键价值不是简单“多存一份”，而是延迟决定提前暴露的引用。若 Bean 需要 AOP，`getEarlyBeanReference` 可以提前返回代理，使其他 Bean 注入的引用与最终对外对象保持一致。

## 能解决与不能解决的范围

### 可能被容器打破的场景

- 单例 Bean。
- 依赖通过属性或方法填充，实例可以先创建再注入。
- 没有原始对象与最终代理引用冲突。

### 通常不能解决的场景

- 构造器循环依赖：双方都必须先完成构造。
- prototype 循环依赖：容器没有可复用的全局单例创建状态。
- 跨线程或非容器对象依赖。
- 复杂代理和过早注入导致最终对象不一致的场景。

## 为什么不应依赖循环引用机制

它会让启动顺序、代理时机和测试变复杂，也掩盖模块耦合。更好的处理方式包括：

1. 提取第三个协调服务。
2. 让双向调用改成单向领域事件。
3. 把查询接口与命令接口拆分。
4. 对真正延迟访问的依赖使用 `ObjectProvider` 或 `@Lazy`，但明确其生命周期与失败语义。
5. 重新划分聚合或模块边界。

## 高频面试题

### Q1. 二级缓存为什么不够？

如果只提前放原始对象，其他 Bean 可能注入原始对象，而容器最终暴露代理，造成身份不一致。三级工厂允许在真正需要提前引用时执行代理创建逻辑。

### Q2. `@Lazy` 是否真正消除了循环依赖？

它可能把某一侧替换为延迟代理，从而推迟实际解析，但业务依赖环仍存在。需要说明这是技术解耦还是仅延后故障。

### Q3. 构造器注入为什么更容易暴露循环依赖？

因为必需依赖必须在对象构造前就绪，环无法被半成品对象掩盖。这个失败通常是好事，它迫使团队修正设计。

### Q4. AOP 与循环依赖为什么容易冲突？

其他 Bean 可能在目标 Bean 完成初始化前就需要其引用。自动代理创建器必须确保提前引用和初始化后返回的代理一致，否则会出现一处调用经过增强、另一处直接调用原对象的问题。

## 面试高分回答

> Spring 对部分 singleton 的 Setter/字段循环依赖可以通过提前暴露引用打破。一级缓存保存完整单例，三级缓存保存生成提前引用的工厂，二级缓存保存已经生成的提前引用；三级工厂还允许 AOP 提前返回代理。它不能解决构造器环和 prototype 环，而且循环依赖通常反映设计问题。我会优先通过职责拆分、事件解耦或接口方向调整消除，只在明确的延迟依赖场景谨慎使用 Lazy 或 ObjectProvider。
