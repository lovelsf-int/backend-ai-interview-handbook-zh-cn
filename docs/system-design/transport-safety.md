## 道路运输安全平台

<p><strong>简历事实摘要</strong></p>
<p>担任后端工作组长；针对日均 100 万+ GPS/报警数据导致的单体架构卡顿，主导 Spring Cloud 微服务拆分，引入 Kafka 解耦和异步处理；设计时间分表、应用层读写分离和 Geohash 位置查询优化；简历给出的系统故障发生率由 15% 降至 3%，查询由 500ms 缩至 100ms 内。</p>

**Q 单体系统为什么会卡顿？**

> **面试官意图：**判断你是否做过瓶颈定位，而非为拆而拆。
>
> **高分要点：**说明 GPS 写入、告警计算、查询、报表和普通业务之间的资源竞争；给出线程池、锁、数据库和 GC 证据。
>
> **连续追问：**峰值 QPS；最慢 SQL；CPU/IO/锁哪项是主瓶颈。

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：峰值 QPS？

**标准答法：**填真实峰值，说明 GPS 上报的潮汐或集中上线场景，不能用日均 100 万证明高并发。最好给单设备频率、设备数和峰值持续时间。

Q2：最慢 SQL？

**标准答法：**准备一条真实慢 SQL：查询条件、表量、执行计划、扫描行、索引和优化后 P95。没有具体 SQL 会让‘500ms→100ms’缺乏可信度。

Q3：CPU？

**标准答法：**先用指标和火焰图/线程栈判断是否 CPU，常见是序列化、循环计算或 GC；不要提前断言。回答要给当时证据。

Q4：IO？

**标准答法：**查看磁盘利用率、IOPS、await、数据库缓冲命中和写放大；GPS 批量写、索引过多或随机写可能是 I/O 瓶颈。按真实观测回答。

Q5：锁哪项是主瓶颈？

**标准答法：**通过慢 SQL、InnoDB 锁等待/死锁、线程栈和事务时间判断。若主瓶颈是锁，说明统一更新顺序、缩短事务或索引优化；如果不是，不要为完整而说全都有。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

> **回答风险：**只说“代码越来越多”。

**Q 微服务按什么边界拆分？**

> **面试官意图：**考察业务边界和负载特征。
>
> **高分要点：**按车辆/设备、GPS 数据、告警、企业、权限、报表等业务能力和伸缩需求拆分。
>
> **连续追问：**服务之间数据如何共享；分布式事务；调用链。

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：服务之间数据如何共享？

**标准答法：**每个服务拥有自己的权威数据，跨服务通过 API 或事件共享，不直接跨库随意 Join。高频只读数据可做本地投影，但要明确一致性和版本。

Q2：分布式事务？

**标准答法：**优先本地事务加可靠事件/Saga，避免分布式强事务覆盖高频链路；补偿动作必须幂等。只有明确必要时才考虑强一致协调。

Q3：调用链？

**标准答法：**使用 trace_id 贯穿网关、RPC、Kafka 和数据库，结合调用拓扑、日志和指标。异步消息还要传递 causation_id/correlation_id，不能只靠时间猜链路。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

> **回答风险：**按 Controller 或数据库表机械拆分。

**Q 拆分后新增了哪些复杂度？**

> **面试官意图：**确认你理解微服务不是免费午餐。
>
> **高分要点：**网络故障、分布式事务、链路追踪、配置、测试、发布、数据一致性和运维成本。
>
> **连续追问：**如何治理超时；如何灰度；如何排查跨服务问题。

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：如何治理超时？

**标准答法：**为每一跳设置基于总预算的连接/读取超时，外层超时应大于内层但不能简单叠加；配合熔断、限流和隔离。重试只放在明确的一层，避免放大。

Q2：如何灰度？

**标准答法：**通过网关或服务网格按用户/租户/实例分流，数据库变更先兼容，指标达到阈值逐步放量；异常自动或人工回滚。

Q3：如何排查跨服务问题？

**标准答法：**先确认时间、发布和受影响链路，再从 Trace 找最长/失败 Span，结合日志、线程池、连接池、Kafka lag 和依赖指标。不能只登录每台机器 grep。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

> **回答风险：**只讲收益不讲代价。

**Q 为什么 Kafka 比线程池更适合？**

> **面试官意图：**考察持久化异步与本地异步的区别。
>
> **高分要点：**线程池只解决单实例内并发；Kafka 提供持久化、削峰、重放、多消费者、独立扩容和故障隔离。
>
> **连续追问：**消息顺序；重复消费；积压。

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：消息顺序？

**标准答法：**只在同一业务键需要时保证分区内顺序，例如 vehicle_id；跨分区不承诺全局顺序，业务状态带版本防旧消息覆盖。

Q2：重复消费？

**标准答法：**使用 event_id/业务唯一键、唯一索引和幂等状态机。消费者成功但 Offset 未提交导致重复是正常场景。

Q3：积压？

**标准答法：**看 lag、最老消息年龄和清空预计时间；临时扩 Consumer 前确认分区数和下游容量，必要时降级非关键处理、批量化和限流，不能只盲目加实例。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

> **回答风险：**仅以“性能更高”解释。

**Q 时间分表按天还是按月？如何跨表查询？**

> **面试官意图：**考察数据规模与查询模式。
>
> **高分要点：**根据日增量、查询范围、单表大小、归档和运维成本选择；根据时间路由、并行查询、TopN 归并和游标分页。
>
> **连续追问：**跨月分页；历史归档；新增分表。

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：跨月分页？

**标准答法：**按时间定位涉及的月表，每表用同一排序键取候选，再做归并；使用 (time,id) 游标而非跨表深 offset。限制最大查询窗口。

Q2：历史归档？

**标准答法：**热数据保留在线，历史按月/季度归档到低成本库或离线系统；查询路由区分热冷，归档前校验完整性和审计要求。

Q3：新增分表？

**标准答法：**通过预创建任务提前建表、索引和权限，幂等执行并监控失败；应用路由对未来表有兜底，避免跨月零点才临时 DDL。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

> **回答风险：**没有真实数据量和查询比例。

**Q Geohash 原理和边界问题是什么？**

> **面试官意图：**考察空间索引理解。
>
> **高分要点：**经纬度二分编码，前缀近似空间邻近；边界点可能前缀不同，需要查询周边格子并计算真实距离过滤。
>
> **连续追问：**精度如何选；高纬度影响；附近 N 公里查询。

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：精度如何选？

**标准答法：**根据目标距离和候选量选择 Geohash 长度，通过真实位置分布测试召回和扫描量；精度太粗候选多，太细需查更多邻格。最后仍计算真实距离。

Q2：高纬度影响？

**标准答法：**经纬度格子实际面积随纬度变化，高纬度经度方向更窄，因此同一前缀长度覆盖面积不恒定。需要按区域验证或使用专门空间索引。

Q3：附近 N 公里查询？

**标准答法：**先算查询圆覆盖的目标格和相邻格，按前缀召回候选，再用 Haversine/地理函数计算精确距离并排序；边界必须查邻格，不能只查中心格。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

> **回答风险：**把前缀相同等同于距离一定最近。

Q1：Redis 不可用？

**标准答法：**先区分短故障和长故障。已有会话可使用本地短期缓存或要求重新登录，登录/刷新等强依赖操作限流或降级；Redis 恢复后避免全量会话同时回源。敏感会话不能长期放宽校验。

Q2：Session 固定路由是否可替代？

**标准答法：**粘性会话可以降低共享存储需求，但实例故障会丢会话、扩缩容和发布复杂，不能替代跨实例一致性。可作为短期优化，不是主要可靠方案。

Q3：TTL 续期？

**标准答法：**使用滑动过期但避免每次请求写 Redis，可在剩余 TTL 低于阈值时刷新；设置绝对最大会话寿命，退出/密码变更主动失效。

### 22.1 微服务、Kafka、分表、Geohash、需求与管理连续追问

#### 1. 海康项目为什么需要微服务拆分？

**面试官意图：**考察是否把微服务当银弹。

**高分回答：**要从真实瓶颈出发：GPS 高频写入、告警处理、查询和普通业务互相争抢资源，发布和故障影响面大。拆分边界应结合业务域和负载特征，而不是按 Controller。还要承认网络调用、分布式事务和运维复杂度。

**连续追问：**拆成哪些服务？ / 数据怎么拆？

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：拆成哪些服务？

**标准答法：**按真实业务边界回答，例如车辆/设备、轨迹采集、告警、企业监管、用户权限和报表；拆分依据是业务归属、负载与发布独立性，不是按 Controller 数量。

Q2：数据怎么拆？

**标准答法：**每个服务拥有权威表，跨服务用 API/事件；轨迹高频数据与主业务库分离，必要的查询投影异步构建。历史单库若未完全拆，要说明过渡方案而非声称数据库彻底独立。

**体现资深水平：**微服务收益必须大于复杂度。

#### 2. 为什么 Kafka 比线程池异步更合适？

**面试官意图：**考察消息中间件价值。

**高分回答：**线程池只解决单实例内异步，进程重启可能丢任务，也不支持多消费者、重放和独立扩容。Kafka 提供持久化、削峰、解耦和消费组。选择仍需结合真实峰值和处理耗时。

#### 3. 时间分表怎么选按天还是按月？

#### 4. Geohash 如何做附近车辆查询？
