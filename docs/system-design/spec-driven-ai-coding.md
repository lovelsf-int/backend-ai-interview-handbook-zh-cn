# Spec-driven AI Coding 生产实践

## 生产级流程与规格模板

<p><strong>核心观点</strong></p>
<p>探索阶段可以 Vibe，生产阶段必须 Spec-first；执行方式可以 Agentic，但最终责任必须由工程师承担。</p>

| **方式**           | **核心特点**                     | **适合场景**               | **主要风险**                 |
|--------------------|----------------------------------|----------------------------|------------------------------|
| Vibe Coding        | 自然语言快速试错、边聊边改       | 原型、技术探索、一次性脚本 | 需求漂移、架构失控、不可维护 |
| AI-assisted Coding | AI 辅助分析、编码、测试和文档    | 日常研发和局部重构         | 错误建议未验证、过度依赖     |
| Agentic Coding     | Agent 可读代码、改文件、运行命令 | 跨文件任务和自动修复       | 权限过大、错误传播           |
| Spec-driven Coding | 先规格、计划和验收，再实现       | 复杂生产项目和团队协作     | 前期规格成本                 |

<p><strong>面试总回答</strong></p>
<p>我不会把一句模糊需求直接交给 AI 生成完整功能。正式开发前先定义目标、范围、业务不变量、接口契约、异常场景和验收标准；让 Agent 先分析代码并输出计划；再按小任务、小 Diff、小提交执行；每一步通过编译、测试、静态扫描、专项 Review、灰度和监控验证。支付、权限、事务、幂等、跨区一致性和数据迁移由人主导，AI 是效率工具，不是责任主体。</p>

### 11.1 生产级完整流程

风险分级 → 上下文准备 → 规格定义 → 实施计划
→ 小步编码 → 自动验证 → 双重 Review → 灰度反馈

| **风险等级** | **适合交给 AI 的范围** | **示例**                                         |
|--------------|------------------------|--------------------------------------------------|
| 低风险       | 可较多委托，仍需测试   | DTO、Mapper、测试数据、文档、局部重构            |
| 中风险       | AI 辅助、人主导        | 普通接口、消息消费、缓存、渠道适配、复杂 SQL     |
| 高风险       | 不得由 AI 独立决策     | 支付、认证、权限、数据迁移、跨区一致性、生产处置 |

**Q 你如何给 AI 准备上下文？**

> **面试官意图：**判断是否只是写 Prompt。
>
> **高分要点：**分为仓库级、模块级、任务级：技术栈和规范；领域状态和调用关系；当前目标、相关文件、限制和验收。上下文要相关、可信、无冲突。
>
> **连续追问：**是否把整个仓库塞给模型；规则冲突怎么办；如何更新知识。

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：是否把整个仓库塞给模型？

**标准答法：**不应无差别塞整个仓库。先让 Agent 定位相关模块和调用链，提供仓库级规则、模块领域知识与任务所需文件；敏感和无关目录默认不可读。上下文质量比数量重要。

Q2：规则冲突怎么办？

**标准答法：**建立优先级：当前明确任务与权威架构决策高于旧文档；冲突时 Agent 必须停下并列出冲突，由人确认，不能自行挑一个。规则带版本和 Owner。

Q3：如何更新知识？

**标准答法：**把稳定架构事实写入仓库规则，易变业务写入版本化文档；变更随 PR 更新并设定 Review。定期扫描失效链接、旧接口和相互矛盾规则。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

> **回答风险：**上下文越多越好。

**Q 为什么让 AI 先输出计划？**

> **面试官意图：**考察可审查性和修改控制。
>
> **高分要点：**计划应包括现状理解、影响模块、修改文件、数据/事务变化、风险、测试和回滚；存在歧义或不可逆变更时停止编码。
>
> **连续追问：**如何判断计划错误；计划与代码偏离怎么办。

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：如何判断计划错误？

**标准答法：**让计划列出对现有代码的理解、影响文件、状态/事务、测试和风险，人工对照源码和 Spec 审核。出现公共接口变化、不可逆迁移、无幂等键或大量无关改动就是停止信号。

Q2：计划与代码偏离怎么办？

**标准答法：**每个小任务完成后对照 Spec 和计划做差异检查；合理偏离要更新计划并说明原因，方向性偏离则回滚到最近小提交。不能让最终代码和批准计划完全失联。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

> **回答风险：**计划只是形式化文档，后续不校验。

**Q 如何控制 AI 的修改范围？**

> **面试官意图：**考察工程纪律。
>
> **高分要点：**一个任务一个问题；规定允许文件和禁止接口；不做无关格式化、依赖升级和全局重构；大 Diff 重新拆分。
>
> **连续追问：**最大 Diff 多少；跨模块变更怎么办。

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：最大 Diff 多少？

**标准答法：**没有通用行数。可设置团队门槛，例如超过 \[真实值\] 文件或 \[真实值\] 行、涉及公共 API/数据库就必须拆分和二次评审；阈值只是预警，风险比行数更重要。

Q2：跨模块变更怎么办？

**标准答法：**先拆成跨模块契约和各模块独立任务，接口/事件 Schema 先行；每个模块单独提交，使用集成测试验证。无法独立验证的‘大爆炸式’修改应重新设计。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

> **回答风险：**一次生成几十个文件再看测试是否通过。

**Q AI 生成的测试可信吗？**

> **面试官意图：**考察验证独立性。
>
> **高分要点：**先定义验收和让测试失败；增加反例、并发、重复、乱序、超时和部分成功；让独立上下文从测试/SRE/安全视角挑错。
>
> **连续追问：**如何防止为通过测试而改测试；删除关键逻辑测试会不会失败。

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：如何防止为通过测试而改测试？

**标准答法：**核心验收测试先由人或独立上下文确定并保护；测试修改单独 Review。Bug 修复先提交能复现失败的测试，放宽/删除断言必须说明业务依据。

Q2：删除关键逻辑测试会不会失败？

**标准答法：**应做变异式验证：临时删除幂等、状态检查或权限校验，相关测试必须失败；若不失败，说明测试只覆盖表面路径，需要补强。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

> **回答风险：**同一个 Agent 写实现和测试，绿了就合并。

**Q 如何度量 AI Coding 的收益？**

> **面试官意图：**判断是否只追求代码量。
>
> **高分要点：**交付周期、首次 Review 通过率、返工率、缺陷密度、缺陷逃逸、回滚率、Review 时间和成本。
>
> **连续追问：**AI 代码占比是多少；效率提升百分比怎么统计。

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：AI 代码占比是多少？

**标准答法：**不要追求一个总比例。可说：样板、测试和文档 AI 参与较高，支付状态机、权限和一致性主要由人设计；我不以生成行数评估价值。若公司要求数字，按任务类型统计并说明口径。

Q2：效率提升百分比怎么统计？

**标准答法：**先建立人工基线：交付周期、首次 Review 通过率、返工、缺陷逃逸、回滚率和模型成本；对同类任务做前后或对照比较。不能用主观‘快了 80%’，且速度提升若伴随缺陷上升不算提效。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

> **回答风险：**随口说效率提升 80%。

### 11.2 可复用的任务规格模板

#### 任务名称（模板）

### 背景与问题
当前行为、业务影响、为什么需要修改。

### 目标 / 非目标
明确完成后必须具备的行为，以及本次不解决什么。

### 业务不变量
- 相同事件只能产生一次业务效果
- 旧状态不能覆盖新状态
- 高危动作必须经过权限和审批

### 技术约束
修改范围、公共接口、事务、幂等、安全、兼容和日志。

### 验收标准
使用 Given / When / Then。

### 测试要求
单元、集成、并发、重复、乱序、超时、回归。

### 执行顺序
第一步只分析；第二步输出计划；确认后小步编码。

### 完成定义
编译、测试、扫描、文档、灰度和回滚。

### 11.3 Java 项目的仓库级规则要点

- Controller 不承载业务逻辑；领域逻辑不直接依赖第三方 DTO；外部渠道通过 Adapter。

- 明确事务边界；事务内避免慢远程调用；数据库与消息按既定 Outbox 方案。

- 消息消费和回调必须说明幂等键；重试前分析副作用。

- 不记录密钥、Token、支付凭证和敏感个人信息；外部输入必须校验。

- 新增查询说明索引；数据库变更考虑兼容上线顺序和回滚。

- Bug 修复先增加可复现测试；不得为了通过而删除有效测试。

- 不做无关重构，不自动升级无关依赖，大范围修改前先输出计划。

### 11.4 AI Code Review 的两遍检查

| **审查维度** | **重点**                                               |
|--------------|--------------------------------------------------------|
| 功能与业务   | 需求、状态迁移、错误码、兼容性、验收覆盖               |
| 并发         | 竞态、锁、原子性、重复处理、资源限制                   |
| 一致性       | 部分成功、消息重复/乱序、补偿、Offset、Outbox          |
| 安全         | 越权、注入、敏感日志、密钥、Prompt Injection、工具权限 |
| 性能         | N+1、全表扫描、无界并发、连接池、缓存和远程调用        |
| 可维护性     | 过度抽象、重复、隐式状态、异常吞掉、命名和复杂度       |

### 11.5 面试高频问答

**Q AI 生成的代码占比是多少？**

> **面试官意图：**诱导你给夸张数字。
>
> **高分要点：**不同任务差异大；样板、测试和文档参与高，支付状态机和一致性核心由人设计；更关注交付和缺陷指标。
>
> **回答风险：**以 AI 代码占比作为能力证明。

**Q 哪些代码不能让 AI 独立完成？**

> **面试官意图：**考察责任和风险意识。
>
> **高分要点：**生产权限、支付结算、认证授权、密钥、不可逆迁移、事故处置和复杂一致性。AI 可协助分析和测试，但人确认不变量和回滚。

**Q AI Review 能替代人工 Review 吗？**

> **面试官意图：**判断是否放弃责任。
>
> **高分要点：**不能。AI 增加覆盖面，关键业务仍需模块、业务或安全责任人审批。

**Q 资深工程师在 AI Coding 时代的价值是什么？**

> **面试官意图：**考察职业认知。
>
> **高分要点：**定义正确问题、识别隐性约束、做架构取舍、建立验证机制、协调团队并承担线上结果。

<p><strong>最终记忆公式</strong></p>
<p>生产级 AI Coding = Spec-first + Small Diff + Test-first + Human Review + CI Gate + Observable Release</p>

## 深度面试与连续追问

你的简历明确写了 AI Agent/Vibe Coding 辅助需求拆解、接口契约、测试用例、技术文档和代码 Review。本章将其升级为资深工程师可复用的生产流程。

**【核心立场】**探索阶段可以 Vibe，生产阶段必须 Spec-first；Agent 可以执行，工程师必须对架构、验收和结果负责。

### 24.1 两分钟标准回答

#### 面试回答

我会使用 Vibe Coding，但不会在生产项目中采用完全无约束的边聊边改。我的做法更接近 Spec-driven AI Coding：先明确业务目标、范围、状态机、业务不变量、接口契约、异常场景和验收标准，再让 Coding Agent 阅读相关代码，输出影响分析和实施计划。计划确认后按小任务、小 Diff 修改，每一步必须编译、测试、静态扫描和 Review。DTO、测试数据、文档和局部重构可以更多交给 AI；支付、权限、事务、幂等、跨区一致性和数据迁移必须由人主导。AI 生成的变更仍进入分支、PR、CI、灰度和回滚流程。我不以 AI 代码占比衡量效率，而是看交付周期、首次 Review 通过率、返工率和缺陷逃逸率。

### 24.2 高频连续追问与高分回答

#### 1. Vibe Coding 与 Spec Coding 的本质区别是什么？

**面试官意图：**考察是否跟风使用概念。

**高分回答：**Vibe Coding 以快速对话和反馈探索为主，适合原型；Spec Coding 先固化目标、边界、不变量和验收，再生成计划和实现，适合生产协作。两者不是互斥：探索可 Vibe，确定需求后转入 Spec。

**连续追问：**小 Bug 也要写完整 Spec 吗？

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：小 Bug 也要写完整 Spec 吗？

**标准答法：**不需要。按风险采用轻量规格：一个明确小 Bug 至少写复现、期望行为、修改范围和测试；涉及状态、数据、权限或跨模块才使用完整 Spec。规格深度与失败成本成正比。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

**答题风险：**不要把 Spec 变成厚重文档。

**体现资深水平：**规格深度应与风险匹配。

#### 2. 你如何给 AI 准备上下文？

**面试官意图：**考察上下文工程。

**高分回答：**分三层：仓库级放技术栈、架构和通用规则；模块级放领域模型、状态机和调用关系；任务级放目标、范围、相关文件、验收和禁止修改项。只提供可信且相关信息，避免把整个仓库和冲突文档无差别塞入。

**连续追问：**上下文过期怎么办？

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：上下文过期怎么办？

**标准答法：**规则和文档带版本、Owner 与适用路径；Agent 开始前读取当前分支的最新内容，发现代码与规则不一致时停止并报告。定期把已失效约束删除或归档，避免上下文长期污染。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

**答题风险：**不是越多越好。

**体现资深水平：**相关性、可信度和版本同样重要。

#### 3. 为什么要让 Agent 先输出计划？

**面试官意图：**考察可控执行。

**高分回答：**计划阶段暴露它是否理解代码、影响范围、事务边界和测试方式。需求有多种解释、修改公共接口、不可逆数据变更或幂等键不清时应停止编码。计划是低成本发现方向错误的门禁。

**连续追问：**计划也可能错怎么办？

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：计划也可能错怎么办？

**标准答法：**计划是门禁不是真理。人工抽查关键源码、让 Agent列证据和替代方案，先做小的可验证步骤；每步测试与 Diff 对照计划。发现偏差立即更新/回滚，不因已经写了很多代码而继续。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

**答题风险：**不要把计划当形式。

**体现资深水平：**人工审查“理解和边界”，再允许执行。

#### 4. 如何控制 AI 不做大范围无关修改？

**面试官意图：**考察工程纪律。

**高分回答：**任务明确允许文件、禁止接口、非目标和最大范围；一个任务只解决一个问题。Diff 超过阈值或出现依赖升级、全局格式化和无关重构时重新计划。分阶段提交，每步可回滚。

**连续追问：**阈值多少？

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：阈值多少？

**标准答法：**没有通用阈值。团队可把超过 10-20 个文件、数百行、公共 API/数据库/依赖升级设为强制二次计划的起点，但风险优先于行数。面试说出你会根据仓库规模校准，而不是宣称固定数字是最佳实践。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

**答题风险：**不要给虚假统一行数。

**体现资深水平：**范围由风险和可审查性决定。

#### 5. AI 生成的测试可信吗？

**面试官意图：**考察验证独立性。

**高分回答：**不能天然相信，因为实现和测试可能共享同一错误理解。先由人确定验收标准，新增行为先看到测试失败；再用独立上下文生成反例，检查删除关键逻辑后测试是否失败。关键场景补充重复、乱序、并发、超时和部分成功。

**连续追问：**同一个 Agent 能不能写测试？

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：同一个 Agent 能不能写测试？

**标准答法：**可以，但不能只由同一上下文完成并自证正确。先有人确认验收与核心测试，再让同一 Agent补普通用例；关键边界由独立 Agent/人工从反例视角生成，确保实现和测试不共享一个错误假设。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

**答题风险：**可以写初稿，不能作为唯一证明。

**体现资深水平：**验证必须尽量独立。

#### 6. 如何防止 AI 为了通过测试而修改测试？

**面试官意图：**考察治理。

**高分回答：**核心验收测试受保护，测试修改单独 Review；要求解释每个断言与业务规则的映射。Bug 修复先提交复现测试，再改实现。删除或放宽断言必须有明确理由。

**连续追问：**测试脆弱怎么办？

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：测试脆弱怎么办？

**标准答法：**脆弱测试通常过度依赖实现细节、时间或外部不稳定。把断言对准业务行为，使用可控时钟/稳定夹具，减少无意义 Mock，分层区分单元、契约和集成测试；修改实现不应频繁重写验收标准。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

**答题风险：**不能一概禁止改测试。

**体现资深水平：**区分需求变更、错误测试和逃避失败。

#### 7. 哪些代码不能让 AI 独立完成？

**面试官意图：**考察风险分级。

**高分回答：**支付结算、认证权限、密钥、不可逆迁移、生产事故处置、复杂分布式一致性和高危 Agent 工具都必须人工主导。AI 可帮助分析、生成测试和 Review，但业务不变量、权限和回滚由责任人确认。

**连续追问：**SQL 迁移能否生成？

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：SQL 迁移能否生成？

**标准答法：**可以生成初稿，但数据迁移是高风险任务：人工确认锁表、兼容上线顺序、默认值、回滚/补偿、批量大小和备份；先在等规模副本验证。Agent 不得直接连接生产执行。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

**答题风险：**可以生成初稿，但执行计划和回滚人工审核。

**体现资深水平：**按错误成本与可逆性分级。

#### 8. AI Code Review 能替代人工 Review 吗？

**面试官意图：**考察责任边界。

**高分回答：**不能。AI 适合作为第二审查者，覆盖并发、安全、性能和边界；但不了解全部隐性业务和组织责任。关键改动仍由模块、业务或安全负责人审批。

**连续追问：**AI Review 的优势？

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：AI Review 的优势？

**标准答法：**速度快、可同时从并发、安全、性能、可维护性多个视角扫描，擅长发现重复模式和遗漏测试；还可以对照 Spec 检查范围。但它缺少全部业务上下文，会误报/漏报，最终审批仍由人。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

**答题风险：**不要否定 AI 价值。

**体现资深水平：**增加覆盖，不转移责任。

#### 9. 如何验证事务、幂等和并发问题？

**面试官意图：**考察 Java 生产实践。

**高分回答：**要求 Agent 显式列出事务边界、远程调用、幂等键、状态迁移和锁；测试覆盖重复回调、并发消费、超时、重试和部分成功；再做专项 Review。必要时故障注入和压测。

**连续追问：**只用单测够吗？

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：只用单测够吗？

**标准答法：**不够。跨模块事务、数据库约束、序列化、Kafka、Redis、权限和真实依赖需要集成/契约测试；高并发和故障场景还要压测、故障注入和灰度。单测只能证明局部代码在假设环境下工作。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

**答题风险：**单测无法证明分布式语义。

**体现资深水平：**规格、代码、集成测试和运行观测共同验证。

#### 10. 如何防止敏感信息泄露给模型？

**面试官意图：**考察企业应用安全。

**高分回答：**最小权限、目录白名单、生产数据脱敏、密钥扫描、禁止读取 secret 和生产配置、企业数据策略、审计。Coding Agent 不应拥有生产数据库、主分支直写或发布权限。

**连续追问：**本地模型是否就安全？

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：本地模型是否就安全？

**标准答法：**不一定。本地模型减少数据出域，但仍可能读取过多目录、泄露到日志、执行危险命令、被供应链/提示注入利用；模型权重和运行环境也需保护。安全由权限、沙箱、审计和数据策略决定，不由部署地点单独决定。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

**答题风险：**仍需权限和数据治理。

**体现资深水平：**安全问题不只在传输。

#### 11. 如何处理 AI 编造不存在的 API？

**面试官意图：**考察实战经验。

**高分回答：**让 Agent 基于项目实际依赖版本回答，要求定位源码或官方文档；编译和测试验证。不能接受“可能存在”的方法。把多次出现的幻觉沉淀成仓库规则或 Skill。

**连续追问：**编译通过是否就对？

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：编译通过是否就对？

**标准答法：**编译只证明语法和类型，不证明业务、并发、安全、性能和兼容。还需测试、静态扫描、依赖检查、Diff Review、数据库/消息兼容和灰度观察。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

**答题风险：**语义仍需验证。

**体现资深水平：**工具验证 + 业务 Review。

#### 12. 如何避免架构漂移？

**面试官意图：**考察长期维护。

**高分回答：**仓库规则明确分层、依赖方向、事务和错误处理；修改前输出影响分析；架构测试和 Review 阻止跨层调用、重复组件和公共接口漂移。定期清理过时规则。

**连续追问：**规则太多怎么办？

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：规则太多怎么办？

**标准答法：**规则分层、保持短小且只写长期稳定约束；细节变成按需加载的模块文档/Skill。定期统计命中、冲突和过期规则，合并重复；规则冲突时按权威和就近原则裁决。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

**答题风险：**规则应简洁且无冲突。

**体现资深水平：**稳定事实放规则，多步骤流程做 Skill。

#### 13. 如何衡量 AI Coding 是否提效？

**面试官意图：**考察数据意识。

**高分回答：**不看 AI 生成行数，关注需求交付周期、首次 Review 通过率、返工率、缺陷逃逸率、回滚率、PR 审查时间和模型成本。速度提高但线上缺陷上升，说明流程失败。

**连续追问：**如何建立基线？

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：如何建立基线？

**标准答法：**选择一类重复任务，记录引入 AI 前 4-8 周的中位交付周期、Review 时间、返工和缺陷，再用同口径试点；控制任务复杂度并记录模型成本。样本少时不宣称统计显著，只做趋势判断。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

**答题风险：**不能主观说提升 80%。

**体现资深水平：**以团队历史和同类任务对比。

#### 14. 如何在团队推广 AI Coding？

**面试官意图：**考察领导力。

**高分回答：**从低风险高重复任务试点，建立统一任务模板、仓库规则、权限、测试门禁和 Review；沉淀常用 Skill；用指标评估并培训成员解释自己提交的代码。不要强制 AI 使用率或代码占比。

**连续追问：**成员过度依赖怎么办？

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：成员过度依赖怎么办？

**标准答法：**要求每个提交者能解释设计、风险和测试，Review 随机追问；高风险代码人工主导。培训如何拆任务和验证，而不是禁止使用；持续出现无法解释或缺陷时缩小其 Agent 权限和任务范围。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

**答题风险：**工具推广不是买许可证。

**体现资深水平：**流程、能力和责任一起建设。

#### 15. 工具如何选择？

**面试官意图：**考察工具中立性。

**高分回答：**看代码库理解、多文件修改、命令执行、规则、权限、审计、PR/CI 集成和企业数据策略。IDE 适合实时结对，终端 Agent 适合本地执行，云端 Agent 适合隔离分支任务。核心流程不绑定品牌。

**连续追问：**哪个工具最好？

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：哪个工具最好？

**标准答法：**没有绝对最好。按代码库理解、多文件执行、终端/IDE、沙箱、权限、审计、模型质量、企业数据策略和 CI/PR 集成选择；做同一任务基准。流程应工具中立，避免把能力绑定品牌。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

**答题风险：**不要陷入品牌比较。

**体现资深水平：**任务和风险决定工具。

#### 16. 资深工程师在 AI Coding 时代的价值是什么？

**面试官意图：**考察职业判断。

**高分回答：**价值从输入每行代码转向定义正确问题、识别约束、做架构取舍、建立验证机制、推动协作并承担线上结果。AI 可以生成实现，但不能替代业务责任和风险判断。

**连续追问：**初级开发还有价值吗？

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：初级开发还有价值吗？

**标准答法：**有。AI 降低样板编码成本，但初级开发仍通过实现、测试、排障和 Review建立系统理解；团队要给可验证的小任务并训练判断力。若只让 AI 代写且不理解，成长才会受损。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

**答题风险：**不要把 AI 描述成裁员工具。

**体现资深水平：**工程判断和学习能力更重要。

### 24.3 可复用的 Spec 模板

| **规格项** | **必须写清的内容**                                     |
|------------|--------------------------------------------------------|
| 背景       | 当前问题、业务影响、为什么现在要改。                   |
| 目标       | 完成后可验证的业务行为。                               |
| 非目标     | 本次明确不解决的内容。                                 |
| 业务不变量 | 重复、乱序、权限、状态和资金方面永远不能被破坏的规则。 |
| 接口与数据 | 请求、返回、错误码、表、消息、幂等键和兼容性。         |
| 异常场景   | 超时、部分成功、重试、结果未知、人工介入。             |
| 非功能需求 | 性能、可用性、安全、审计、成本和回滚。                 |
| 实施计划   | 影响文件、步骤、风险、测试和发布。                     |
| 完成定义   | 编译、测试、扫描、文档、灰度、监控和回滚均满足。       |

## 核心立场

探索阶段可以快速对话试验；进入生产变更后必须明确目标、非目标、不变量、接口、异常、验收和回滚。AI 可以执行任务，但工程师对架构、事实、测试、合规和上线结果负责。
