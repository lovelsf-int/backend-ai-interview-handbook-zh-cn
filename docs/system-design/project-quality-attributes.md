# 项目架构能力：高性能、高可靠与高扩展性

三项能力都应回答“什么约束下达到什么结果、靠什么机制、付出什么代价、怎样验证”。本页及项目页新增总览是设计建议和面试训练，不代表全部已在生产实施；所有新增数字明确作为教学假设。

## 从技术组件转向可验证目标

| 能力 | 需要证明的结果 | 设计抓手 | 不充分的回答 |
| --- | --- | --- | --- |
| 高性能 | 指定负载和错误率下，关键请求达到延迟与吞吐目标 | 减少关键路径工作、批处理、缓存、索引、有界并发 | “用了 Redis 和虚拟线程” |
| 高可靠 | 故障下业务结果仍正确，且可在期限内恢复 | 事实源、幂等、状态机、持久交接、隔离、对账和容灾 | “部署三副本，Kafka 不丢” |
| 高扩展性 | 流量、数据和新功能增长时可受控扩展 | 无状态服务、分区、资源配额、稳定契约、适配层、版本迁移 | “微服务可以随便加机器” |

高可靠不仅是可用率。重复发货、越权封禁或返回陈旧权益，即使 HTTP 全部成功也可能是业务失败。高扩展性同时包含容量扩展和功能演进，必须分别回答。

## 高性能：先预算，再优化，再回归

每条核心链路都记录入口峰值、有效任务比例、下游调用放大率、平均及尾延迟、请求大小和部署资源。把“日订单”“业务事件”“模型调用”“ES 文档”分别计数。

教学算例：峰值 1200 个业务请求/秒，每请求需要两次下游调用，下游平均 0.2 秒，则下游约 2400 次调用/秒、稳定平均在途约 480。这个数不是直接配置的并发上限，还需考虑长尾、限额与内存。若下游只能处理 1800 次/秒，加应用实例也无法长期消化 2400 次/秒的需求。

容量模型可写为：

- 单位统一后的链路吞吐上限，受最小阶段有效容量约束。
- 有持续流入时，积压清空时间约为“积压量 /（有效处理率－新增率）”；差值非正时清不空。
- 教学 N+1 算例：单实例满足 SLO 的实测能力假定为 200 QPS，总峰值 1000 QPS，失去一实例后仍留 20% 余量，则需满足 `(n-1) × 200 × 0.8 >= 1000`，得到至少 8 实例。该推导只在下游能承受总负载且单机能力可复用时成立。

优化顺序：用 Trace 和资源指标确认瓶颈，减少不必要查询/模型调用，再控制批次、缓存和索引，最后扩并发与实例。批处理提高吞吐可能增加等待时间；缓存提高命中可能增加陈旧窗口；并发提高吞吐可能耗尽连接。每次实验都要同时观察吞吐、P99、错误率和单位成功任务成本。

压测要覆盖稳态、突发、热点、冷缓存、下游变慢和单节点故障。请求生成器按计划到达率发请求并记录排队等待，避免系统变慢后发压端也自动减少请求，从而把过载隐藏起来。

## 高可靠：区分成功、不成功和未知

先写业务不变量：同一订单不得重复发货；同一授权操作不能换参数执行；已经确认的事实不能被旧重放覆盖。然后逐一说明哪条唯一约束、哪次条件更新、哪个外部幂等协议保护它。

| 崩溃窗口 | 所需机制 | 不能依赖什么 |
| --- | --- | --- |
| 本地事务提交前 | 回滚、原业务键重试 | 内存中记住已执行 |
| 提交后响应丢失 | 原键查询既有结果 | 换新订单或新操作号 |
| 状态已提交、事件未发出 | 同事务 Outbox 与恢复投递 | 先写 DB 再发消息且无补偿 |
| 外部已执行、结果未落库 | UNKNOWN、按原操作号查证或人工 | 把超时直接当失败 |
| 消费者换代、旧 Worker 仍运行 | 版本条件、幂等或目标端 fencing | 只拦截旧 Offset 提交 |

至少一次与去重需要跨越真正的业务边界；Kafka 事务不能自动覆盖任意外部数据库、ES 或工具。见 [Kafka 设计说明](https://kafka.apache.org/40/design/design/)。

SLO 按用户结果定义：受理成功率、期限内完成率、结果正确率分别统计，不能把进 DLQ 算业务完成。教学例：30 天 100 万个合格任务、目标成功率 99.9%，允许失败预算为 1000 个任务；这不是 43.2 分钟的时间预算，分母不同不能互换。预算策略可参考 [Google SRE SLO 实施](https://sre.google/workbook/implementing-slos/)。

容灾还须记录 RPO、RTO 与失效条件。异步跨区复制不能承诺任意故障下 RPO=0；接管需要隔离旧写者、核对数据缺口、迁移路由和验证业务，不是只切负载均衡。备份应做恢复演练，副本也会复制误删。

## 高扩展性：为容量和变化分别留边界

| 扩展对象 | 首选边界 | 必须解释的限制 |
| --- | --- | --- |
| 应用吞吐 | 无状态 API、副本扩展 | 共享 DB、连接和供应商限额不随之增加 |
| 消费吞吐 | 分区与 Worker | 热 key、顺序要求、分区所有权及再均衡 |
| 数据规模 | 时间/租户/业务 ID 分片 | 跨分片查询、热点、重建与迁移 |
| 新渠道或新工具 | 稳定业务接口与能力声明 | 不支持幂等、查询或退款的能力不能伪装成统一支持 |
| 新协议或模型 | schema/model/prompt 版本 | 旧任务恢复、旧消费者兼容和回退 |
| 新租户或新区域 | 配额、隔离池、路由版本 | 数据驻留、归属迁移、跨区写冲突 |

扩展验证不是证明“新服务能启动”。新增一个渠道要有契约测试、幂等/超时语义、灰度、监控与停用路径；从旧分片迁移到新分片，要明确快照水位、增量补齐、单写权转移、影子读对比和回退条件。

容量扩展分阶段做：先移除无关依赖与重复工作，再拆资源池/热租户，再做分片。迁移采用兼容字段先上线、新旧读写契约并存、验证完成再停旧路径；数据库新增字段与数据回填不等于随时可删旧字段回滚。

## 面试展示模板与证据清单

每个项目先用 90 秒讲三件事：“性能上我针对什么瓶颈做了什么；可靠性上保护什么不变量、怎样恢复；扩展性上怎样新增负载或能力而不破坏已有契约。”再选择一个真实决策深入，而不是复述所有组件。

| 待填事实 | 应准备的证据 | 无证据时怎么表达 |
| --- | --- | --- |
| 性能优化前后 | 相同负载、数据分布、硬件、版本的报告 | “这是目标/设计推导，尚无实测结果” |
| 故障恢复 | 演练时间线、未决任务、业务对账结果 | “方案覆盖这些窗口，尚未验证跨区极端故障” |
| 容量扩展 | 扩容前后吞吐、热点、成本曲线 | “只验证到当前规模，不能线性外推” |
| 功能扩展 | 新旧接口契约、实际接入改动、回退记录 | “已定义扩展点，但未接入第二种实现” |
| 个人贡献 | 负责模块、决策记录、代码和协作边界 | “我负责其中这一段，其他由团队负责” |

这些证据清单是待执行的项目验收，不是本次文档发布已完成的压测或容灾测试。过载治理参考 [Google SRE](https://sre.google/sre-book/handling-overload/)，ES 的批量与拒绝处理参考 [Elastic 写入优化](https://www.elastic.co/docs/deploy-manage/production-guidance/optimize-performance/indexing-speed)。
