# P7/P8 架构决策实战：容量、恢复、评估与治理

本文用 P7/P8 表示两种训练深度，不代表任何公司的正式职级评审标准。全部数字都是明确假设下的教学算例，不能写入简历当作个人业绩。已有项目介绍见 [SOC Agent](./soc-agent.md) 和 [海外支付](./overseas-payment.md)，本文重点练习如何做决策与证明决策有效。

## 能力差异：从负责系统到推动跨团队结果

| 维度 | P7 训练目标 | P8 进一步追问 |
|---|---|---|
| 问题定义 | 明确业务需求、约束和成功标准 | 判断是否值得做，找出比技术改造更小的解决办法 |
| 技术深度 | 解释关键机制并处理异常路径 | 找到跨组件瓶颈，解释复杂性和收益如何分配 |
| 容量可靠性 | 算容量、建监控、能恢复 | 按故障域分配预算，协调平台和业务的 SLO |
| 方案取舍 | 比较候选方案并落地 | 把迁移、团队学习、运维和退出成本算进去 |
| 交付组织 | 负责模块或系统完整交付 | 协调依赖、兼容契约、负责人和推广顺序 |
| 结果证据 | 给出前后指标与事故闭环 | 证明收益可重复、可推广，且没有转嫁成本 |

P8 不能靠少讲原理、多讲管理来替代技术深度；P7 也需要理解业务收益。训练时先回答“我怎么让这个系统正确运行”，再回答“多个团队为什么愿意采用，长期由谁负责”。

## 场景一：SOC 流量增长十倍，先扩哪里

**完整题目：**假设每日接收 900 万条事件，高峰为日均的 8 倍；规则压缩后 2% 进入模型，每个任务平均调用模型 2 次。模型服务限额为 200 次请求/秒、400 个在途请求，平均调用耗时 3 秒。如何设计十倍增长方案？

### P7 标准答案：先统一单位再找最小容量

日均入口约为 `9,000,000 / 86,400 = 104.2 条/秒`，高峰约 `833.3 条/秒`。模型高峰需求为 `833.3 × 2% × 2 = 33.3 次调用/秒`，十倍增长后约为 `333.3 次调用/秒`。

模型能力同时受请求速率和在途配额限制。在耗时保持 3 秒的理想稳定条件下，在途配额对应约 `400 / 3 = 133.3 次调用/秒`，已经低于 200 次/秒的速率限额，因此不能只按供应商 QPS 规划。

优先动作是重新评估规则压缩比例、缓存可复用性、大小模型路由及供应商容量，再配置入口准入、模型并发门禁和有界等待。Kafka 承接短时突发；若长期到达率高于处理能力，必须拒绝、延后或降低进入模型的任务比例。

这只是起算值。模型还有 Token 配额、输入长度、输出长度和尾延迟约束，应使用真实任务分布压测。虚拟线程降低等待时线程占用，不增加模型吞吐。

### P8 深挖答案：按业务价值分配有限资源

先与安全团队定义风险分层：高风险任务预留容量，低风险可以延迟或走规则结果；关键判断不能通过无提示丢弃实现“降级”。建立租户份额、最大借用额度和回收策略，空闲容量允许借用，但恢复时不能把低优先级请求全部瞬间重试。

候选方案至少比较三种：扩供应商容量、减少模型调用、异步分层服务。比较每个方案的质量损失、延迟、单位成功任务成本、依赖锁定和上线时间。按场景做小流量对照，质量不满足预设护栏就回退。

### 追问与答案

**问：平均并发可以直接设成并发上限吗？**不能。`平均在途数 = 吞吐 × 平均耗时` 适用于稳定统计边界，是估算关系。长尾、突发、连接建立和重试都会改变负载；并发上限还受内存、连接池和下游约束，最终取压测中满足 SLO 的安全范围。

**问：队列堆积 18 万条，处理 150 条/秒、持续流入 100 条/秒，多久清空？**净消化速度为 50 条/秒，理想情况下约 3600 秒。若处理量只等于新增量，永远清不空；加入重试和优先级后要重新测有效吞吐。

**验收证据：**入口峰值、压缩比、模型调用放大率、Token 吞吐、队列最老任务年龄、分租户 P99、正确率、积压清空时间。记录各指标是在事件、任务还是调用层统计。

## 场景二：依赖变慢，重试为什么把系统拖垮

**完整题目：**一次查询需要访问数据库和模型，客户端总预算 2 秒。模型调用偶发超时，SDK、网关和业务层各自最多尝试 3 次。你如何止血并重构恢复策略？

### P7 标准答案：总 Deadline 约束所有步骤

三层各最多尝试 3 次时，极端情况下一个业务请求可产生 `3 × 3 × 3 = 27` 次底层尝试；“重试三次”是否包含首次调用必须明确。

选定一个承担重试的层，关闭无协调的叠加重试。按剩余 Deadline 分配连接、读取和重试预算，给队列等待也设置上限。超时后传递取消信号，但取消是尽力而为，远端仍可能执行。

先区分临时错误、永久错误和结果未知。只对允许安全重放的操作重试，使用退避、抖动和次数/时间预算。副作用超时进入 UNKNOWN，按原业务请求号查证，不能更换幂等键重新执行。

### P8 深挖答案：重试也是受配额管理的流量

平台统一定义原请求和重试请求的预算、指标与熔断策略。过载阶段优先保护健康流量，恢复阶段少量探测并逐步放量；全租户同时恢复会再次造成拥塞。

SDK 默认行为、网关超时和服务端资源回收必须写进兼容契约。推广时统计总尝试数与成功请求数的比率，验证延迟改善是否只是把等待转移到调用方。

### 追问与答案

**问：熔断打开后能否直接换备用模型？**只有在任务能力、数据权限、区域、输出契约和质量护栏兼容时才可以；备用模型还需要独立容量。两个服务名共用同一上游集群时，切换并未隔离故障。

**问：2 秒预算怎么拆？**先量测关键路径，确定必需步骤、可并行步骤和可降级步骤。给每步设上限，并动态扣除已花费时间；各阶段独立设置 2 秒会让总耗时失控。不能直接相加各组件 P99 来承诺端到端 P99。

**验收证据：**调用放大率、到期任务是否仍占用资源、取消延迟、熔断恢复时间、备用链路质量、重试流量占比。

## 场景三：Kafka、ES 和状态库部分成功后怎样恢复

**完整题目：**Kafka 消费到一批记录，ES Bulk 部分成功；其中一条 Mapping 错误、一条 429。进程随时可能崩溃，还会发生分区再均衡。怎样避免漏处理、旧任务覆盖和业务乱序？

### P7 标准答案：分开消费确认与业务完成

逐条记录结果。Mapping 错误修复前通常不可通过原样重试恢复，可靠转存 DLQ 并告警；429 按退避策略重试或持久化转交可靠重试链路。HTTP 请求成功不等于所有 Bulk Item 成功。

只有前缀内每条已投递记录都被成功处理，或被持久化交给约定的后续链路，才能推进该分区提交位置。提交语义是下一消费位置；Kafka 的数值 Offset 可能存在间隙，不能机械等待每个整数都出现。

ES 写入使用稳定文档 ID，并通过版本策略处理乱序。ID 相同只保证标识相同，不能阻止旧结果覆盖新状态。DLQ 交接意味着消费链路可继续，不代表业务已完成。

### P8 深挖答案：恢复协议必须跨越所有权变更

分区撤销时停止接收新任务，处理或取消已有任务，严格按消费客户端模型提交。新的消费者取得分区后，旧 Worker 仍可能完成外部调用；因此外部状态写入也需要版本条件、业务幂等或所有权代次验证，不能只依赖 Kafka 拒绝旧消费者提交 Offset。

跨系统无法用 Kafka 事务自动包住 ES 和数据库。选择一个业务事实源，投影允许重建；转交重试、DLQ 和提交之间的崩溃窗口以至少一次加幂等收敛。同业务实体如果必须按序处理，转入重试链路后仍须阻止后续状态越过失败步骤。

### 追问与答案

**问：失败消息写入 DLQ 后就能处理同订单后续消息吗？**取决于不变量。分析类事件可能允许；支付状态或严格状态依赖不允许随意越过，需要按业务键阻塞、暂存、版本拒绝或重建状态。

**问：如何证明没有漏数据？**对账生产事实、消费确认、业务终态和索引投影，追踪差异数量与最老差异年龄。不能只以 Kafka Lag 为零作为业务完整性证明。

**验收证据：**在 Bulk 返回后、DLQ 转交后、提交前后、分区撤销时注入进程退出，核对重复、漏处理、旧版本覆盖和恢复时长。

延伸阅读：[ES 面试复盘](../elasticsearch/14-mock-interview-review-2026-09-04.md)、[Kafka 重试与一致性](../kafka/07-retry-dlq-business-consistency.md)。

## 场景四：模型准确率提升，为什么仍不能上线

**完整题目：**候选 RAG 策略整体准确率从 90% 提升到 92%，成本下降 20%，但高风险攻击样本的漏判增加。产品希望全量上线，你如何决策？

### P7 标准答案：先按风险分层评估

整体准确率掩盖类别比例。先固定数据集、标注定义和版本，分开评估高风险召回、误报、证据完整性、拒答和处置正确性。检索遗漏、排序丢失、上下文截断、生成错误、工具错误分别归因。

高风险漏判越过事先约定的硬护栏，应阻止该场景放量；可以独立评估低风险场景是否满足上线条件。用相同任务做成对比较并分析错误样本，避免把样本组成变化当成策略收益。

### P8 深挖答案：建立质量、成本和责任的决策制度

将风险损失、质量约束、人工复核和成本纳入评审，而非让单一准确率决定上线。回归集按租户、攻击族、时间和案例来源划分，防止同一工单切片出现在训练与评估两侧。另留时间外测试集，观察真实分布变化。

模型裁判只是辅助，需校准其偏差和与人工判断的一致性。Shadow 阶段只生成计划与结果比较，不执行生产封禁等副作用；灰度阶段锁定模型、Prompt、Embedding、Chunk 与检索版本，确保可以定位差异并回滚。

### 追问与答案

**问：高风险样本只有 20 条，20 条都答对能说 100% 可靠吗？**只能报告在这 20 条上的观察结果。样本少、覆盖不足，不能据此证明真实漏判率为零；需要增加代表性样本、独立复核和不确定性区间。

**问：人工兜底就能无限降级吗？**不能。人工有容量和等待 SLA，需预测升级量、值班能力及积压；否则只是把系统超时转成工单积压。

**验收证据：**分层样本数、漏判与误报定义、人工一致性、时间外表现、回滚后版本一致性、人工升级积压。

延伸阅读：[RAG 评估与知识工程](../ai-agent/05-rag-knowledge-engineering.md)、[平台治理复盘](../ai-agent/13-mock-interview-review-2026-09-04.md)。

## 场景五：大租户打满共享系统，如何保护其他租户

**完整题目：**一个租户仅占总请求的 5%，却消耗 70% 的 ES 查询时间和 60% 的模型 Token。入口 QPS 限流没有效果，怎么办？

### P7 标准答案：按资源成本限额

QPS 相同不代表资源相同。对 ES 限制时间范围、聚合规模、并发和超时；对模型同时管理请求数、Token 和在途数；对任务约束最大步骤数与总预算。

身份和租户过滤由可信网关注入。按租户建立独立队列或调度份额，避免大任务占满所有 Worker。超大租户可独立索引或资源池，但隔离粒度应由热点与维护成本决定。

### P8 深挖答案：保证最低服务并控制借用

定义保底份额、突发额度和租户成本归属。共享池可借用空闲容量，但必须有可执行的归还规则；物理隔离只在明确收益超过集群、索引和运维成本时采用。

控制面更新配额需要版本、审计和回退；数据面不能因为配置服务短暂故障就无限放行。对已有可信配置限定有效期，过期后按业务风险采用保守额度或拒绝高风险请求。

### 追问与答案

**问：独立索引就实现安全隔离了吗？**没有。索引组织、访问授权和物理资源隔离是不同维度；还要控制查询权限、缓存键、日志、Rerank、模型上下文和工具资源边界。

**验收证据：**单租户压测时其他租户 P99、拒绝率、等待时间、资源用量；撤销权限后缓存与检索链路是否同步生效。

## 场景六：99.9% 可用性怎么变成发布决策

**完整题目：**接口 HTTP 成功率超过 99.9%，但大量 Agent 任务只返回“已接收”后一直未完成。业务认为系统不可用，研发认为达标，如何统一？

### P7 标准答案：测用户任务结果

把接收成功和任务完成拆开。为任务定义完成时限、成功终态、必要证据与处置确认；明确取消、超时、重复任务和人工接管如何计数。端到端业务指标不能只用网关 200 状态码替代。

请求型 SLO 的错误预算可按 `合格请求总数 × (1 − 目标比例)` 计算。例如窗口内 100 万次合格请求、目标 99.9%，预算为 1000 次未达标请求。不能把请求比例预算直接等同于固定停机分钟数。

### P8 深挖答案：把预算绑定行动

与产品、平台和运维确认统计边界、负责人和发布规则。预算消耗过快时限制高风险变更、优先可靠性修复；并非所有发布一律冻结，紧急修复还需独立判断。

使用长短窗口联合观察预算消耗速度，区分快速大故障与持续小退化。任务完成、数据正确性和高风险动作权限分别设护栏，不能以可用性预算允许越权或重复扣款。

**验收证据：**任务终态对账、超时归因、告警能否触发明确动作、灰度自动停止条件。SLI/SLO 与预算概念参见 [Google SRE](https://sre.google/sre-book/service-level-objectives/) 和 [SLO 实施指南](https://sre.google/workbook/implementing-slos/)。

## 场景七：三个团队要统一 Agent 平台，何时不该做

**完整题目：**三个业务团队都有 Tool 调用、Prompt 管理和任务恢复逻辑。是否立即统一成平台？你负责决策和推广。

### P7 标准答案：先统一契约再选择复用方式

梳理共同不变量：身份、工具 Schema、幂等键、错误分类、审计和任务状态。比较共享库、模块化服务和独立平台三种方案。需求稳定且调用语义接近时才抽象，保留场景特有流程。

不能把一个业务的全部字段做成“通用平台配置”。先选一个真实接入方试点，验证契约能够减少重复工作且不阻断业务演进。

### P8 深挖答案：平台收益必须覆盖组织成本

核算各团队重复投入、迁移成本、平台值班和支持成本、版本兼容负担及故障扩大风险。明确 API Owner、变更审批、弃用窗口和业务退出能力。

如果业务差异大、需求快速变化、缺少平台维护者，先统一安全和观测标准，保留独立实现。平台化不是默认终点。试点以接入周期、重复故障下降、单位维护成本和业务自主交付能力验收。

### 追问与答案

**问：其他团队不愿迁移怎么办？**先查真实阻力：能力缺口、额外延迟、责任不清或迁移成本。提供兼容适配、迁移支持和可回退试点；收益无法证明时应调整方案，而非靠行政要求制造使用量。

**问：如何证明是你的贡献？**列出你负责的决策、验证、协调和结果，区分团队共同产出。没有可验证跨团队案例时，讲设计思路而不冒领落地经历。

## 场景八：三个月只做三件事，怎么排技术债

**完整题目：**当前同时有慢 SQL、旧 SDK、重试风暴、缺少 RAG 评估和大租户投诉。只有三个月和两名工程师，如何排序？

### P7 标准答案：用风险和可交付性排序

先确认业务影响、发生概率、恢复成本和依赖关系。活跃故障先止血；对重试风暴等跨链路放大风险优先治理，再根据慢 SQL 和租户问题的真实影响决定下一项。把“升级 SDK”追溯到具体兼容或故障问题，不能因版本旧就自然优先。

每项拆成可独立上线的小步，设置验收指标、负责人、预算和回退条件。对 RAG 先建最小高风险回归集，不必第一天建设完整评估平台。

### P8 深挖答案：让选择与机会成本可复核

列出“不做会怎样”“可以先做多小”“与其他团队有什么依赖”。不要把风险评分伪装为精确收益预测；用区间和假设记录不确定性，设置阶段检查点，证据变化就调整排序。

建立可评审的决策记录：约束、候选方案、拒绝理由、成功标准、退出条件。用事故频率、交付周期、成本和业务体验证明收益，不能以重构代码量作为成绩。

## 一页架构决策记录模板

| 字段 | 必须回答 |
|---|---|
| 问题 | 影响谁、频率多高、为什么现在解决 |
| 不变量 | 什么不能丢、不能重复、不能越权 |
| 已知事实 | 监控窗口、规模、版本、个人职责 |
| 未知项 | 如何量测、负责人、何时影响决策 |
| 备选方案 | 至少两个可行方案及维持现状的代价 |
| 容量模型 | 单位、平均/峰值、放大率、最小瓶颈 |
| 异常矩阵 | 超时、重复、乱序、部分成功、所有权变化 |
| 迁移 | 试点、兼容、放量、回滚和旧路径退出 |
| 验收 | 正确性、延迟、恢复、成本、运维负担 |
| 复查条件 | 什么证据会让你推翻当前选择 |

## 模拟面试评分与练法

每题按问题定义、原理、容量、异常恢复、证据取舍五项各评 0–2 分：0 分代表缺失或严重错误，1 分代表方向正确但落地不足，2 分代表能解释执行与验证方法。总分用于训练趋势，不映射正式录用职级。

P7 训练要求先稳定给出主路径与失败恢复；P8 加练跨团队依赖、推广成本和长期责任。出现把设计当经历、把超时当确定失败、或靠无限重试保证成功等问题，应先纠错再评分。

建议每题先录 90 秒答案，再接受三个问题：为什么不用另一方案、最坏故障怎样恢复、什么证据证明有效。最后用一张决策记录整理薄弱点，回填到 [冲刺与缺口地图](../guide/interview-sprint-gap-map.md)。
