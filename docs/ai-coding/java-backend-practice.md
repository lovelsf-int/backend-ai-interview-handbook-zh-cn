# Java 后端 AI 编程实战

## 实战一：支付创建接口的幂等改造

任务描述不能停在“加 Redis 防重复”。先定义 tenant 与幂等键的唯一范围、请求摘要、状态和返回契约。本节为设计练习，未提供已运行的完整 Spring Boot 工程。

```text
输入：tenantId（由认证上下文提供）、idempotencyKey、订单、金额、币种。
不变量：同一租户和幂等键只对应一个业务操作。
同键同请求：返回已有结果或明确的处理中状态。
同键异请求：拒绝，不能复用另一笔金额的结果。
渠道超时：结果未知，进入查询/对账流程，不能直接当失败重扣。
```

先在数据库用唯一约束决定并发竞争结果，并将业务状态与待发送事件放在同一本地事务。事务提交后发送渠道请求；发送者使用稳定的外部幂等键。数据库事务不能把外部 HTTP 调用变成原子操作，必须处理外部成功而本地未记录的窗口。

| 注入条件 | 验收结果 |
| --- | --- |
| 两请求并发使用相同键 | 一个业务操作；另一请求读到已有状态 |
| 同键不同金额 | 明确冲突；不调用渠道 |
| 本地提交后发送前崩溃 | 待发送记录可恢复 |
| 渠道成功后响应丢失 | 通过幂等键查询/对账恢复，不盲目重扣 |
| 回调重复和乱序 | 验签后按允许的状态迁移处理，不回退终态 |

**追问：Redis 锁能否替代唯一约束？** 不能。租约到期、进程暂停和重试都可能产生竞争；锁可减少争抢，持久化约束与状态机决定正确性。如果渠道既不支持幂等也无法查询，无法承诺任意崩溃下绝不重复执行，必须引入对账、人工介入或调整业务流程。

## 实战二：线程池与超时治理

让 AI 修改前先读任务提交点、线程池配置、外部连接池和调用方超时。测量活跃线程、队列长度、等待时间、拒绝数及下游延迟，区分 CPU 计算和阻塞等待。

```text
目标：下游变慢时，订单查询接口资源占用仍有界。
约束：线程数、队列长度、并发请求和重试次数均有上限。
要求：传播截止时间；排队消耗预算；下游调用设置连接/读取超时。
失败：过载时快速拒绝或按业务降级，禁止静默丢弃关键写任务。
验收：慢响应、连接耗尽、取消、调用方中断、恢复后积压消退。
```

假设到达率为 200 请求/秒、平均占用时间 0.1 秒，平均在途量约 20；下游变慢到 2 秒时约 400。这只是容量教学估计，不是线程池配置结论；还要看波动、资源上限和服务目标。无界排队会把过载转成内存增长和过期请求继续执行。

**追问：CompletableFuture 超时后任务停止了吗？** 超时完成不保证底层计算或网络调用已停止。要检查执行器、任务协作中断、客户端取消行为以及外部调用是否已经发生。不能仅断言返回了 TimeoutException 就通过验收。

## 实战三：数据库字段迁移

假设将展示名称从单字段改为结构化字段，AI 需要处理新旧应用并存和回填，不只生成 ALTER TABLE。

1. 扩展：新增兼容字段，旧字段仍可读；确认 DDL 在真实数据库版本上的锁和执行行为。
2. 兼容写：确定字段权威来源及双写冲突策略。
3. 回填：按稳定主键范围分批、限速、记录进度；避免覆盖更新期间的新数据。
4. 校验：检查漏填、编码、长度截断和新旧读结果。
5. 切读：逐步启用新读路径，保留回退开关。
6. 收缩：确认旧版本退出与回滚窗口结束后，另行删除旧结构。

**追问：回滚应用就算恢复吗？** 不一定。新数据可能无法被旧代码读取，已删除字段也不会随代码恢复。回滚方案必须包含数据兼容、前向修复和必要的备份恢复演练。

## 审查 Java 生成代码时重点看什么

| 位置 | 典型问题 | 验证方式 |
| --- | --- | --- |
| Spring 事务 | 自调用、异常被吞、外部调用拖长事务 | 实际代理调用的集成测试与事务日志 |
| 金额 | 浮点误差、币种精度和舍入未定义 | 明确业务示例与边界断言 |
| SQL | 租户条件遗漏、N+1、分页不稳定 | 执行计划、跨租户用例和真实分布数据 |
| 并发 | 锁顺序、可见性、无界队列 | 可控并发调度与超时测试 |
| 日志 | 凭据泄露、异常无关联 ID | 脱敏检查和跨请求追踪 |
