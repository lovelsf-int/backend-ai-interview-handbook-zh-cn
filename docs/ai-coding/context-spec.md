# Prompt、上下文与 Spec 驱动开发

## 系统提示、任务和用户提示分别是什么

| 概念 | 负责什么 | 后端编程例子 |
| --- | --- | --- |
| 系统或开发者指令 | 平台设定的长期行为与约束 | 工具权限、输出要求、执行限制 |
| 仓库规则 | 项目约定和可重复执行的知识 | 构建入口、模块依赖、禁止绕过租户鉴权 |
| Task / Spec | 本次任务的业务契约 | 订单幂等键的范围、冲突行为、恢复规则 |
| 用户提示 | 发起或修正当前请求 | “增加支付超时后的查询补偿” |
| 上下文材料 | 支持判断的数据 | 代码、日志、DDL、接口文档、测试结果 |

Task 通常是业务组织形式，不必然是模型 API 的独立消息角色。仓库里的文字和工具返回的内容也不会因写着“系统命令”就自动获得更高权限；具体加载、作用范围和优先级由宿主工具决定。

## 足够上下文如何组织

先给目标、约束、验收，再给最相关的调用链和失败证据。大型仓库先用目录、符号和依赖搜索定位，再读取相关实现，避免全仓库倾倒。长任务把确定事实、决策理由、未验证项和文件位置保存为交接记录，恢复任务时重新核对当前提交。

Claude Code 官方实践强调可验证目标和上下文管理；这为任务组织提供参考，具体仓库仍需要自己的业务验收。[官方最佳实践](https://code.claude.com/docs/en/best-practices)

## 仓库规则写什么

```text
项目环境：填写真实 JDK、构建工具和数据库版本。
构建入口：填写仓库已存在且可执行的命令。
模块边界：HTTP 层只处理协议；业务规则在应用/领域层。
关键约束：租户身份来自认证上下文；金额明确币种与精度。
验证要求：说明单元测试、数据库集成测试分别如何运行。
交付要求：报告实际验证结果及未验证项，附迁移和恢复说明。
```

AGENTS.md、CLAUDE.md 等名称与识别机制取决于工具，不能假定所有工具加载相同文件。把稳定规则放仓库，把一次性的需求放任务；规则需要负责人和版本，不保存密钥、真实客户数据或未经验证的历史判断。

## 将“可靠”写成 Spec

以支付请求为例，一份最小规格要覆盖：

| 项目 | 必须回答的问题 |
| --- | --- |
| 身份 | tenant、业务订单、幂等键如何绑定？ |
| 冲突 | 同一键不同金额或币种是否拒绝？ |
| 并发 | 哪个持久化约束决定唯一结果？ |
| 不确定结果 | 渠道超时后进入哪个状态，谁来查询？ |
| 恢复 | 崩溃发生在外部成功和本地提交之间怎么办？ |
| 兼容 | 旧客户端和旧消息如何继续工作？ |
| 验收 | 如何构造并发、重放、乱序和崩溃用例？ |

先定义这些，再让 AI 生成实现和测试。需要改变业务语义时同步更新规格、代码与验收；文档和代码分离演进会形成两个互相冲突的事实来源。

## 追问：上下文压缩会不会丢掉关键约束

会。交接记录保留目标、不可破坏的不变量、关键决定及理由、当前提交、失败证据和下一步；不能只写“已经实现大半”。恢复后检查代码和测试是否仍匹配记录，对金额、鉴权和状态机等关键事实回到原始来源确认。

## 追问：Spec 写错了，测试全绿有意义吗

只能说明实现符合当前测试，无法证明需求正确。用业务方确认的例子、历史事故反例、接口契约和人工审查建立独立依据。让同一个模型根据同一段错误理解同时生成实现与测试，可能得到一致但错误的结果。
