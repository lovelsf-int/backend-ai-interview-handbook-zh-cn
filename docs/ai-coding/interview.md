# AI Coding P7/P8 面试题与追问

## Q1：你实际如何用 AI 完成一个后端需求

**回答：** 先说明需求和约束，再读取调用链、写验收用例、按范围实现、运行验证、审查 diff，最后发布观察。用一个真实任务说明 AI 贡献和本人负责的决策，不笼统说“全自动开发”。

**追问：没有真实指标怎么办？** 展示可核对的需求、PR、失败用例和审查发现。没有测量就明确未量化，不借用教学算例作为个人成果。

## Q2：CLI、IDE 和云端 Agent 怎么选

**回答：** 根据任务耦合度、环境需求和交互频率选择。局部调试需要快速人工反馈；批量修改需要脚本和构建能力；独立任务可异步处理。对比完整交付成本，而不是只看生成速度。

**追问：长任务迁移到云端有什么新问题？** 环境依赖、权限、基础提交、数据访问和日志可追溯都需要明确；本地成功不意味着云端具备同一 JDK、数据库或网络条件。

## Q3：怎样提供大仓库上下文

**回答：** 从目标和验收出发，搜索入口与调用链，再加载实现和测试。保留文件依据、版本与未证实假设，长期约束进入仓库规则。

**追问：检索到旧文档与代码冲突怎么办？** 先标出冲突，结合现有测试、提交记录和业务契约确定哪一方过时；不能单凭更长或更新的文本决定业务语义。

## Q4：Spec Coding 的价值是什么

**回答：** 将业务不变量、边界、失败结果和验收显式化，降低模型与人的理解偏差。规格粒度随任务风险调整，小修复不必写长篇设计。

**追问：需求变化怎么办？** 记录变化原因与影响，更新规格、实现和验收，检查已发布客户端及存量数据；避免只修改提示词而丢失决策历史。

## Q5：AI 生成实现和测试，如何避免一起错

**回答：** 从业务确认样例、历史故障和真实组件语义引入独立依据；重点审查断言是否能区分正确和错误实现。数据库并发不能全部用 Mock 证明。

**追问：全绿还会出事故吗？** 会，测试只覆盖执行过的条件。补充风险驱动的集成、负载、故障和发布观察，并明确剩余风险。

## Q6：AI 把支付重试写错了，如何审查

**回答：** 查幂等键范围、请求摘要、唯一约束、事务与外部调用边界，尤其是结果未知时的查询和恢复流程。

**追问：加三次重试能提高可靠性吗？** 只有错误可重试、剩余预算充足且动作幂等时才可能改善；不确定结果盲重试可能重复扣款，重试风暴还会压垮下游。

## Q7：如何评审 AI 的并发代码

**回答：** 检查共享状态、同步关系、锁顺序、队列边界、取消和资源释放，用可控交错制造反例。

**追问：压测十万次没错够吗？** 不够。随机压测未必触发特定竞争，应结合 Java 内存模型推理和定向测试；不把暂未复现当作不存在。

## Q8：Skills、MCP 和 Hooks 有什么区别

**回答：** Skill 提供可复用流程；MCP 接入工具和资源；Hook 在生命周期节点执行逻辑。三者解决的问题不同，可以组合。

**追问：Hook 拦住危险命令就安全了吗？** 还要核对是否可绕过、是否覆盖其他执行路径，以及账户和网络权限。最终依赖运行时授权与环境隔离，不能只靠自然语言规范。

## Q9：多 Agent 一定更快吗

**回答：** 只有子任务可分离且集成成本可控时，才可能缩短周期。先明确契约和可写范围，再评估上下文复制、协调、冲突与验证成本。

**追问：两个 Agent 各自测试通过，合并后失败怎么办？** 单独通过不代表集成正确。固定候选提交做统一回归，分析共享接口、配置、数据与版本假设的冲突。

## Q10：P7 如何体现技术深度

**回答：** 展示能识别并修复模型遗漏的生产边界，例如 Spring 事务代理、自调用、SQL 租户隔离、超时未取消、幂等恢复。讲清原理、反例、修改和验证证据。

**追问：工具用得熟为什么还不够？** 工具操作不等于对业务正确性负责；资深工程师需要判断方案是否成立、故障如何恢复和成本是否可接受。

## Q11：P8 如何设计团队 AI Coding 平台

**回答：** 平台提供仓库与身份接入、隔离执行环境、任务和产物存储、模型与工具网关、验证门禁和审计。业务团队定义契约；平台保证执行边界和证据可追踪。

**追问：高性能、高可靠和扩展性怎么体现？** 按租户控制排队与并发；任务持久化、心跳与租约恢复；外部动作使用幂等和状态核查；模型与工具适配器保持版本化契约。扩容受下游配额限制，增加 worker 不会自动增加模型吞吐。

## Q12：如何证明 AI 提效而没有牺牲质量

**回答：** 对同类任务比较总人时、交付周期、缺陷逃逸、返工、回滚和成本，记录复杂度与参与者差异；生成行数和采纳率只能作过程指标。

**追问：什么时候停止推广？** 当审查和返工抵消收益、缺陷增加或权限边界无法落实时缩小范围，修复问题后重新试点。停止条件应事先确定，避免只挑成功案例。
