# AI Coding 的质量、安全与团队效能

## 合并前需要什么证据

PR 记录需求、关键不变量、实际修改、验证命令与结果、未验证项、迁移和恢复方式。所有结果绑定提交版本：测试通过后又修改代码，应重新执行受影响验证；基础分支变化后检查集成结果。

| 层次 | 发现的问题 | 局限 |
| --- | --- | --- |
| 编译与静态检查 | 类型、格式、部分危险调用 | 不证明业务正确 |
| 单元测试 | 局部边界和状态逻辑 | Mock 可能掩盖实际数据库语义 |
| 集成与契约测试 | 事务、序列化、旧调用方兼容 | 环境和数据分布可能不同 |
| 性能与故障演练 | 过载、恢复、尾延迟和资源上限 | 结论只适用于测试条件 |
| 人工审查与发布观察 | 业务语义、架构取舍、真实影响 | 仍需要清晰负责人和止损机制 |

测试应从规格、事故和反例产生。不要让“覆盖率提高”掩盖无有效断言、全部 Mock 或重复实现逻辑的问题。

## 把三个架构目标写进验收

高性能：说明工作负载、数据倾斜、并发、延迟分位数和资源预算。比较时固定环境与数据，不把缓存预热后的单次结果当整体改善。

高可靠：列出超时、重复、乱序、崩溃和依赖不可用的结果。用业务成功率、恢复耗时和数据丢失范围衡量，HTTP 200 不能代表支付或消息真正完成。

高扩展性：用第二个渠道、第二种模型或新字段验证扩展边界；检查旧版本兼容、迁移成本、隔离和容量。预先增加许多抽象类不是扩展能力证据。

## 提示注入与供应链边界

外部 issue、网页和代码注释可能含有诱导命令或泄露信息的指令。执行前按任务目标检查其相关性，权限由工具身份和运行环境限制。隔离不只是限制文件目录，还包括联网、凭据、子进程和共享服务。

依赖名称、版本和 API 要用项目锁文件、官方文档及真实构建核验。模型生成不存在的依赖或看似合理的命令时，应纠正依据；不能为了通过构建随意关闭校验、扩大权限或禁用测试。

## 团队试点如何计算收益

记录同类任务的实现、等待、审查、返工和故障处理耗时；区分总人时与交付周期。AI 并行跑一小时可能不占人时，但会增加算力成本，也不意味着周期只剩一小时。

```text
净人时节省 = 可比基线总人时 - AI 流程总人时
总成本 = 人时成本 + 模型成本 + 执行环境成本 + 返工与故障成本
```

教学例子：人工基线 6 人时；AI 辅助实现 1.5、审查 1.5、返工 1、验证 0.5，共 4.5 人时，节省 25%。不能只比较“写代码 6 小时变 1.5 小时”后宣称全流程提效 75%。这是算例，不是实测收益。

任务按复杂度和风险分层，试点期间保持相似人员与代码范围；同时统计缺陷逃逸、回滚、审查负担和交付周期分布。样本少时呈现原始分布与不确定性，不泛化为全团队结论。

## 追问：P8 如何推广

先选规则清晰、可恢复的任务类型，明确工具接入、仓库规则、门禁、审查负责人和异常升级路径。试点达标后扩大范围；对权限过大、质量下降或总成本恶化设定停止条件。平台统一提供环境和证据收集，业务团队仍负责不变量与发布决定。

## 追问：如何避免泄露真实数据

使用脱敏样本和最小数据集；控制工具可访问范围及日志留存。脱敏不仅替换姓名，还要检查 token、连接串、订单关联与可重新识别信息。数据处理和保留策略应按组织要求及所用服务实际配置核实。
