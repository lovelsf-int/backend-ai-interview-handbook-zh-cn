# 缓存一致性与二级缓存

## 第六章 缓存更新策略与数据一致性

### 6.1 两种经典更新方案对比

#### 6.1.1 先删缓存，再更新数据库

**问题**：删缓存后、数据库提交前，读请求可能回填旧值。若没有 TTL、后续失效或补偿，旧值可能长期保留。

<a id="_6-1-2-先更新数据库-再删缓存-生产推荐"></a>

#### 6.1.2 先提交数据库事务，再删缓存

这是常用的 Cache-Aside 写入顺序，但不构成严格一致性保证。数据库提交后删除缓存可能失败；更早读到旧值的慢请求，也可能在删除之后回填旧值。脏数据持续多久取决于 TTL、失效重试、回填并发和恢复能力，不能仅以“概率低”排除风险。

需要严格一致的裁决应由数据库事务、条件更新等事实源完成。缓存用于加速读取，不能单独裁决资金、库存或订单状态。

### 6.2 最终一致性优化方案

- 删除失败：通过可靠任务或 Outbox/CDC 驱动失效重试，保证重试幂等，并监控积压。
- 旧值回填：可结合版本检查、同 Key 并发控制或延迟二次删除；延迟双删依赖时序假设，不能证明严格一致。
- 漏失效：TTL、定时校验和重建作为兜底。TTL 从回填时计算，不能直接当成数据库提交后的绝对陈旧上限。
- Redis Pub/Sub 适合低延迟失效通知，但属于至多一次投递，断线期间消息不会自动补发；需要可恢复的失效链路或 TTL 兜底。

## 第七章 本地缓存+Redis 二级缓存架构（高频架构题）

### 7.1 什么时候需要加本地缓存？

#### 7.1.1 建议引入本地缓存场景

超高QPS热点场景：首页配置、字典、地区编码、热门商品

Redis降级兜底：网络抖动、Redis短暂不可用保可用

准静态数据：极少更新、一致性要求低

解决热点Key打爆Redis带宽/CPU问题

#### 7.1.2 不建议引入场景

强一致性业务（金融、交易）

高频更新数据（库存、在线状态）

数据量过大，易引发JVM OOM、频繁GC

### 7.2 二级缓存核心风险与解决方案

#### 7.2.1 分布式一致性问题

多节点本地缓存私有，更新后各节点数据不一致

**常用缓解**：失效通知 + 短 TTL，并按可接受陈旧窗口决定是否使用可靠事件和版本校验。Pub/Sub 不能单独保证通知到达，参见 [最终一致性优化方案](#_6-2-最终一致性优化方案)。

#### 7.2.2 JVM内存溢出风险

限制最大缓存数量、启用LRU/LFU淘汰、监控内存占用与淘汰率

#### 7.2.3 热点Key雪崩

TTL随机偏移、超级热点Key短周期续期，避免批量过期击穿Redis

### 7.3 二级缓存标准读写流程

读：本地缓存 -\> Redis -\> DB，逐级回填

写：提交 DB 事务 -\> 删除 Redis 缓存 -\> 通知各节点清除本地缓存；失败按上文重试/补偿。三个步骤不属于一个原子事务，读写并发仍可能出现短暂旧值。
