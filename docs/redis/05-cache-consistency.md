# 缓存一致性与二级缓存

## 第六章 缓存更新策略与数据一致性

### 6.1 两种经典更新方案对比

#### 6.1.1 先删缓存，再更新数据库

**问题**：删缓存未更新DB期间，读请求回填旧缓存，导致**永久数据不一致**。

#### 6.1.2 先更新数据库，再删缓存（生产推荐）

极端场景存在短暂不一致，但概率极低、无永久脏数据，是工业界最优折中方案。

### 6.2 最终一致性优化方案

延迟双删策略

Redis Pub/Sub 分布式缓存失效通知

定时兜底刷新缓存

## 第七章 本地缓存+Redis 二级缓存架构（高频架构题）

### 7.1 什么时候需要加本地缓存？

#### 7.1.1 建议引入本地缓存场景

超高QPS热点场景：首页配置、字典、地区编码、热门商品

Redis降级兜底：网络抖动、Redis短暂不可用保可用

准静态数据：极少更新、一致性要求低

解决热点Key打爆Redis带宽/CPU问题

#### 7.1.2 不建议引入场景

强一致性业务（金融、交易）

高频更新数据（库存、在线状态）

数据量过大，易引发JVM OOM、频繁GC

### 7.2 二级缓存核心风险与解决方案

#### 7.2.1 分布式一致性问题

多节点本地缓存私有，更新后各节点数据不一致

**解决方案**：Redis发布订阅失效通知 + 短TTL被动兜底

#### 7.2.2 JVM内存溢出风险

限制最大缓存数量、启用LRU/LFU淘汰、监控内存占用与淘汰率

#### 7.2.3 热点Key雪崩

TTL随机偏移、超级热点Key短周期续期，避免批量过期击穿Redis

### 7.3 二级缓存标准读写流程

读：本地缓存 -\> Redis -\> DB，逐级回填

写：更新DB -\> 删除Redis缓存 -\> 发布失效通知清空本地缓存
