# 事务、Lua 与 Functions

> 核心边界：Redis 事务不会像关系数据库一样在运行时错误后自动回滚；Lua 的原子执行也不代表脚本错误会恢复已经产生的副作用。

## 第十章 Redis 事务机制（P7高频漏考点）

### 10.1 Redis 事务核心原理

Redis 事务三指令：**MULTI / EXEC / DISCARD**，Watch 为乐观锁辅助。

Redis 事务本质：**命令批量打包、一次性串行执行**。

执行三阶段：

**开启事务(MULTI)**：客户端进入事务状态，后续命令不执行、入队缓存

**命令入队**：批量写入命令队列

**执行事务(EXEC)**：按队列顺序执行，期间其他客户端命令不能插入；逐条检查返回结果，运行时错误不触发回滚。

### 10.2 Redis 事务三大特性（面试必背）

**1、单独隔离性**

事务执行过程中，其他客户端命令**绝对无法插队**，保证批量命令连续执行。

**2、无回滚机制（最大坑点）**

**Redis 事务不支持事务回滚**！

入队错误（如参数个数或命令名错误）：Redis 2.6.5+ 在 `EXEC` 时拒绝整个事务；

运行时逻辑错误（比如对String执行List操作）：**错误命令报错，正确命令照常执行**，不会回滚。

**3、区分执行隔离与失败回滚**

“命令连续执行”不等于“所有命令都成功”。入队失败、`WATCH` 冲突与执行期错误的结果不同，不能概括为业务层的全成全败。

### 10.3 Watch 乐观锁机制（CAS）

**作用**：解决事务期间数据被其他线程修改的并发问题。

原理：

Watch 监听若干 Key

若事务提交前 Key 被修改，**事务直接放弃执行**

无版本号，靠服务端数据变动检测

**缺陷**：仅支持乐观锁，不适合高并发争抢场景。

### 10.4 Redis 事务为什么不支持回滚？（P7经典面试题）

官方理由是保持实现简单与性能；应用仍必须处理类型错误、资源不足等失败，不能把“应避免编程错误”当成错误不会发生。需要失败回滚的业务应选择支持该语义的事务存储。

<a id="_10-5-redis-cluster-集群事务致命问题"></a>

### 10.5 Redis Cluster 的同槽边界

**集群下不支持跨哈希槽事务**

槽是分片单元，一个节点可负责多个槽；Redis Cluster 没有把跨槽命令变成分布式事务的协调协议。

**解决方案**：

**HashTag** 强制多个Key落到同一个哈希槽，支持事务/批量操作

Lua/Functions 也在单个节点执行，不能绕过跨节点事务限制；Redisson 锁不能让跨槽写入自动原子提交。需要跨资源一致性时，应重新划分数据边界或使用具备相应事务语义的事实源。

### 10.6 Redis事务 vs Lua脚本（面试高频对比）

- **MULTI/EXEC**：连续执行预先入队的命令；运行时某条命令失败，其他命令仍执行，不回滚。
- **Lua/Functions**：在服务端做读取、判断和写入，执行期间其他客户端不能插入；脚本报错前成功的写入仍保留，不自动回滚。
- **选型**：简单批量操作可用事务，条件逻辑可用脚本/函数；需要跨节点事务或失败回滚时，两者都不能直接满足。

### 10.8 Lua 脚本完整考点（面试必问：Lua 是什么？优势？原理？）

#### 10.8.1 Lua 脚本是什么

Lua 是一种**轻量、嵌入式脚本语言**，Redis 原生内置 Lua 解释器，支持客户端将**多条 Redis 命令 + 业务逻辑**封装成一段脚本，一次性提交给 Redis 服务端执行。

简单理解：**Lua = Redis 服务端批量原子编程能力**。

#### 10.8.2 Lua 脚本核心执行特性（面试核心）

**服务端原子执行**：执行期间其他客户端命令不能插入；这里强调隔离，不承诺运行时错误后的回滚。

**网络开销极低**：多次命令合并为一次网络 IO，极大降低客户端与服务端的往返耗时。

**支持逻辑运算**：Lua 支持 **if/else、循环、变量、判断返回值**，适合在服务端完成短小的条件读写。

**脚本可缓存复用**：通过 SHA1 摘要缓存脚本，无需每次传完整代码，性能更高。

<a id="_10-8-3-为什么-lua-比-redis-原生事务更强"></a>

#### 10.8.3 Lua 出错后的状态

`redis.call()` 报错会终止脚本；`redis.pcall()` 可把错误交给脚本处理，但两者都不会撤销此前已完成的写入。例如先 `SET` 成功、再对同一 Key 执行错误类型的 `LPUSH`，脚本失败后 `SET` 的值仍存在。

先校验参数、Key 类型和业务条件，再执行尽可能少的写入；这能减少失败窗口，不能替代回滚。对比见 [事务与 Lua 的语义边界](#_10-6-redis事务-vs-lua脚本-面试高频对比)。

#### 10.8.4 Lua 脚本生产使用规范（P7架构考点）

**禁止死循环、禁止超长耗时逻辑**：Lua 阻塞服务请求，超过执行阈值不会自动回滚或安全中断已写入的脚本；

**脚本尽量短小**：只做 Redis 读写判断，不做业务计算、RPC、DB 查询；

**集群按单槽 Key 设计**：显式声明所访问的 Key，并用 HashTag 保证同槽。部分版本的 `allow-cross-slot-keys` 可放宽脚本内部的槽检查，但声明的 Key 仍须同槽，也不能跨节点访问或提供分布式事务；不要依赖它规避分片边界。

**统一治理脚本**：版本管理、预加载、SHA 缓存，并处理重启/故障转移后的 `NOSCRIPT`；Redis 7.0+ Functions 改善函数部署与持久化，不改变无回滚和单节点执行边界。

#### 10.8.5 Lua 典型落地场景

分布式锁加解锁的条件读写（如 Redisson 的相关 Lua 脚本）

库存扣减、防超卖原子操作

限流计数器原子更新

多 Key 批量原子读写、条件更新

<a id="_10-7-面试终极总结-可直接口述-1"></a>

### 10.7 面试终极总结（可直接口述）

Redis 事务、Lua 与 Functions 都不提供自动失败回滚。Lua 的优势是服务端条件逻辑与执行隔离，不能用来绕过跨节点事务边界。选型以 [语义对比](#_10-6-redis事务-vs-lua脚本-面试高频对比) 和 [同槽约束](#_10-5-redis-cluster-的同槽边界) 为准。
