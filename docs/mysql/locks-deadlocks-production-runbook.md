# InnoDB 锁、死锁与生产排障

## 核心模型：访问路径决定锁范围

不能只根据 `UPDATE`、`DELETE` 或 `SELECT ... FOR UPDATE` 的文字判断锁了多少行。InnoDB 通常锁定扫描到的索引记录及相关间隙，最终范围由以下因素共同决定：

- 隔离级别；
- 使用的索引与访问类型；
- 唯一等值、范围还是全扫描；
- 谓词能否在存储引擎层提前过滤；
- 外键、唯一性检查和语句类型。

因此生产排障要把 SQL、参数、事务、索引、执行计划和锁等待图放在一起看。

## 锁类型与用途

| 锁 | 锁住什么 | 典型用途或风险 |
|---|---|---|
| Record Lock | 索引记录 | 精确记录并发修改 |
| Gap Lock | 索引记录之间、之前或之后的间隙 | 抑制范围内插入；本身不锁已有记录 |
| Next-Key Lock | Record + 前置 Gap | RR 锁定读/写中的范围保护 |
| Intention Lock | 表级意向 | 表示事务将申请行级 S/X 锁，便于表锁冲突判断 |
| Insert Intention | 插入前的间隙意向 | 不同位置的并发插入可共存 |
| MDL | 表等数据库对象元数据 | 保护对象定义；长事务可能阻塞 DDL |

Gap Lock 是“抑制插入”的锁，不应套用普通 S/X 锁的互斥直觉。两个事务的 Gap Lock 可以共存，因为它们主要阻止其他事务在该间隙插入。

## RC 与 RR 的差异

- RR 下，范围锁定访问通常使用 Next-Key Lock，以保护扫描范围。
- RC 下，普通搜索和索引扫描的 Gap Lock 大多禁用，但外键检查与重复键检查仍可能使用；不等于“RC 完全没有 Gap Lock”。
- 唯一索引完整等值命中通常可以收敛为记录锁；联合唯一索引只使用前缀时仍可能是范围。

回答时应给出具体 SQL、索引和隔离级别，不能只背“RR 有间隙锁，RC 没有”。

## 没有索引不是“锁对象退化成表锁”

源文档把无索引更新描述为“行锁升级为表锁”，这不准确。InnoDB 不会因为扫描多就简单创建一个表锁对象；当没有合适索引而执行全表扫描时，可能锁住扫描到的每条索引记录，效果上会阻塞大量并发，甚至阻止插入。

二者的工程差别很重要：

- 根因是访问路径过宽，而不是 InnoDB 自动锁升级。
- 增加正确索引、收敛谓词、缩小批次和事务范围才是修复方向。
- 只看“锁了几行”而不看执行计划，会错过真正原因。

## 死锁不是异常事件，而是并发系统的正常分支

两个事务以不同顺序获取互斥资源，就可能构成环：

```text
T1: lock order 1001 -> wait order 1002
T2: lock order 1002 -> wait order 1001
```

InnoDB 检测到死锁后选择一个事务回滚。应用必须把死锁当成可重试错误，但重试需要满足三个前提：

1. 重试整个事务单元，而不是从失败 SQL 中间继续；
2. 每次重试重新读取状态，使用有限次数、指数退避与抖动；
3. 外部副作用有业务幂等键，不能因数据库重试而重复扣款或发消息。

## 五步生产排障闭环

### 1. 先保留证据

记录错误码、SQL 模板、参数摘要、连接/事务 ID、调用链、事务开始时间和发布版本。短暂锁等待可能很快消失，必须在应用侧保留关联信息。

### 2. 看最近死锁

```sql
SHOW ENGINE INNODB STATUS\G
```

需要持续收集时，可评估 `innodb_print_all_deadlocks`，但先确认日志量与敏感参数脱敏策略。

### 3. 用 Performance Schema 画等待边

MySQL 8 应优先使用：

```sql
SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;
```

旧资料常见的 `INFORMATION_SCHEMA.INNODB_LOCKS` 和 `INNODB_LOCK_WAITS` 已不应作为 MySQL 8.4 主路径。把等待锁、阻塞锁与 `performance_schema.threads`、语句事件关联，才能定位到会话和 SQL。

### 4. 还原访问顺序与计划

对每个参与事务确认：

- SQL 实际执行顺序是否一致；
- 谓词是否使用预期索引；
- 是否一次锁定太多行或批量过大；
- 是否在持锁期间调用远程服务；
- 是否存在二级索引扫描后回表导致的额外锁定；
- 是否有外键、唯一检查或级联更新。

### 5. 按根因修复并验证

优先级通常是：统一资源访问顺序、补正确索引、缩短事务、拆小批次、把远程调用移出事务、为热点资源做串行化或分片。上线前用相同并发模型复现，并验证吞吐与 P99 没有被“修复”拖垮。

## MDL：为什么一个小 DDL 能拖垮业务

元数据锁保护表定义与正在执行的语句。典型事故链：

1. 长事务访问表后一直未提交；
2. DDL 请求排队等待更强的 MDL；
3. 后续业务语句又排在 DDL 后方；
4. 连接池被逐步耗尽，表现为全站数据库超时。

处理时不要立刻盲杀所有连接。先确认阻塞链、事务持有者、DDL 可否取消、业务影响和回滚成本。在线 DDL 能降低部分建表变更成本，但不代表没有 MDL 获取阶段，也不保证所有操作都无阻塞。

## 悲观锁、乐观锁与租约边界

| 机制 | 适合场景 | 主要风险 |
|---|---|---|
| `SELECT ... FOR UPDATE` | 冲突高、事务短、资源在同库 | 持锁时间、死锁、热点串行化 |
| 版本号 CAS | 冲突较低、允许应用重试 | 高冲突下重试风暴 |
| 唯一约束 + 幂等键 | 去重与单次创建 | 仍需定义重复请求返回语义 |
| 分布式租约 | 跨进程协调 | 超时不等于旧持有者停止；需要 fencing token |

数据库行锁只保护数据库事务范围。涉及 Kafka、支付渠道或跨 Region 写入时，应使用业务幂等、状态机与 fencing，而不是假设一个本地锁能覆盖所有系统。

## 高频错误口径修正

| 错误说法 | 修正 |
|---|---|
| 无索引时 InnoDB 行锁升级为表锁 | 可能扫描并锁住大量索引记录；根因是访问路径过宽 |
| RR 完全解决所有幻读 | 要区分快照读、当前读、索引范围与业务观察 |
| RC 完全没有 Gap Lock | 外键与重复键检查等场景仍可能使用 |
| 死锁只要杀掉一个事务即可 | 应恢复业务并修复顺序、索引、事务边界，应用还要幂等重试 |
| 在线 DDL 不会阻塞 | 仍有 MDL 获取与切换阶段，能力取决于具体操作和版本 |

## 值班 Runbook

### 触发条件

- 锁等待 P99 或数据库错误率持续超过 SLO；
- `Threads_running`、活跃事务或连接池等待同步升高；
- DDL 执行期间业务请求堆积；
- 死锁率相对历史基线突增。

### 止血

1. 暂停新 DDL、离线批次或异常流量入口。
2. 确认阻塞事务的业务身份与可回滚性。
3. 优先取消等待中的非关键操作；终止持锁事务前评估回滚量。
4. 对应用侧重试限流，避免重试风暴。

### 根因与复盘

- 保存锁图、执行计划、事务时间线和发布差异。
- 区分“锁冲突增加”与“数据库整体变慢导致持锁时间增加”。
- 写出能自动检测的先兆指标和明确的回滚阈值。
- 用故障演练验证值班人员可以在不依赖个人记忆的情况下完成操作。

## P8 连续追问

### 为什么补了索引仍可能死锁

索引只收敛访问范围，不会自动统一不同业务路径的加锁顺序；二级索引更新、唯一检查、外键和批量语句仍可能形成不同顺序。

### 为什么数据库 CPU 不高但请求超时

锁等待是排队而非计算。少数长事务就能让大量线程休眠等待，CPU 可能不高，但连接池和业务延迟已经失控。

### 要不要关闭死锁检测

高热点下死锁检测本身可能有成本，但关闭后依赖锁等待超时，故障恢复更慢。除非已经证明检测开销是瓶颈并有明确的并发控制方案，否则不应把关闭检测当常规优化。
