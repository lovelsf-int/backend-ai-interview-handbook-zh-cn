## 11. MySQL MVCC 如何实现？

**面试官意图：**考察基础但要联系业务。

**高分回答：**通过隐藏事务信息、Undo 版本链和 Read View 提供快照读；当前读仍会加锁。支付状态更新、幂等和并发扣减不能误以为有 MVCC 就自动安全，通常需要条件更新、版本号或锁。

**连续追问：**RR 为什么仍可能幻读？

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：RR 为什么仍可能幻读？

**标准答法：**RR 的一致性读通过 Read View 看不到后插入行，但当前读/锁定读会读取最新并加 next-key/gap 锁；不使用合适索引、不同语句或业务层多次查询仍可能观察到所谓幻象。回答要区分 SQL 标准幻读、快照读和当前读，而不是一句‘RR 完全没有幻读’。

## 12. 如何定位 MySQL 死锁？

**面试官意图：**考察排障。

**高分回答：**先获取死锁日志和事务 SQL，画出锁等待关系，检查访问顺序、索引命中、事务范围和批量大小。通过统一锁顺序、缩短事务、增加合适索引、拆批和重试处理。

**连续追问：**重试是否幂等？

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：重试是否幂等？

**标准答法：**死锁回滚后的事务可以重试，但前提是整个业务操作幂等、重新读取当前状态，并限制次数与随机退避。支付扣款等外部副作用不能仅重跑数据库方法。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

**答题风险：**不要只说“杀事务”。

**体现资深水平：**根因通常是访问顺序和锁范围。

## 13. 联合索引如何为用户最近 100 条订单设计？

**面试官意图：**考察索引与分页。

**高分回答：**典型查询按 user_id 等值、create_time 倒序，可建立 (user_id, create_time, id) 联合索引，并使用游标条件避免深 offset。具体还要结合状态和覆盖字段。

**连续追问：**为什么加 id？

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：为什么加 id？

**标准答法：**同一 create_time 可能有多条记录，只用时间游标会重复或漏数据。把 id 作为稳定的唯一 tie-breaker，查询条件用 \`(create_time \< ?) OR (create_time=? AND id\<?)\`，索引 \`(user_id, create_time, id)\` 支持稳定排序。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

**答题风险：**不要机械套最左原则。

**体现资深水平：**为稳定排序和 Seek Pagination 服务。

## 14. 分库分表后如何扩容？

**面试官意图：**考察迁移能力。

**高分回答：**避免一次停机重哈希。可通过新旧路由版本、双写或变更日志、数据回填、校验、灰度切读、停止旧写和清理完成。每一步都要幂等、可暂停、可回滚。

**连续追问：**双写不一致？

追问标准答案（可直接口述，方括号内容须替换为真实信息）

Q1：双写不一致？

**标准答法：**双写期间以变更日志/Outbox 记录每次写，目标端幂等应用；定期对账和校验。写一边成功一边失败进入重试队列，切读前必须达到一致性门槛；若双写复杂，可采用单写旧库+CDC 回填降低风险。

使用提醒：先理解逻辑，再替换成自己的真实参数和项目事实；不要逐字背诵。

**答题风险：**不要只说一致性哈希。

**体现资深水平：**迁移是一个状态机。

## 回答边界

- MVCC 不会自动保护支付状态机、额度扣减或外部副作用。
- 索引设计必须从查询条件、排序、选择性、回表和写入成本出发。
- 分库分表扩容是可暂停、可校验、可回滚的数据迁移状态机。
- 版本、隔离级别、执行计划、数据分布和真实 SQL 是结论成立的前提。
