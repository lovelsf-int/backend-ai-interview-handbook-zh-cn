# 金融支付领域基础

> 本手册用于架构学习和面试准备，不构成财务、法律、合规或生产变更意见。具体辖区要求需要由相应专业人员审查。

## 使用说明与面试地图

### 1.1 这套资料怎么用

本资料不是“模式名词大全”，而是一套能直接用于面试表达的作战手册。建议按四层使用：

1.  **教材层**：先理解支付领域、不变量、SOLID 和模式的真实边界。
2.  **题库层**：用快速问答检查概念是否能在 30-90 秒内说清。
3.  **案例层**：用支付编排、账务、对账、路由四个系统设计题练深度。
4.  **模拟层**：按评分卡进行 45-60 分钟完整模拟，并复盘表达和取舍。

| **准备时间** | **推荐路径**                     | **目标**                   |
|--------------|----------------------------------|----------------------------|
| 30 天        | 全文顺序学习 + 4 次模拟          | 建立完整体系，补齐项目故事 |
| 14 天        | 第 1-10 章 + 题库 + 2 次模拟     | 面向近期面试快速成型       |
| 3 天         | 速查表 + 4 个系统设计 + 事故案例 | 保住核心信号，避免低级错误 |

**P8 面试的本质**

面试官通常不是在确认你是否背过“单一职责”和“策略模式”，而是在确认你是否能：识别资金系统的不变量；处理结果未知、重复执行和跨系统不一致；在正确性、可用性、成本、延迟和组织复杂度之间做有依据的取舍；最后把方案推动到多个团队长期使用。

### 1.3 通用答题结构

系统设计、模式选择和事故复盘都可以使用同一套结构：

**业务目标 -\> 核心不变量 -\> 约束与规模 -\> 可选方案 -\> 最终选择 -\> 失败场景 -\> 可观测与运维 -\> 演进路径**

#### 1.3.1 90 秒模式题模板

这个场景的主要变化轴是 X，稳定不变量是 Y。我会把 Y 放在核心领域模型中，把 X 作为扩展点。首选模式是 Z，因为它能隔离……。不过它会引入……成本；当实现数量很少、变化频率低时，我会先使用更简单的组合或条件分支。生产上还需要补充契约测试、监控和灰度机制。

#### 1.3.2 10 分钟系统设计模板

1.  明确范围、成功定义和量级。
2.  主动提出业务不变量。
3.  建立领域模型和状态机。
4.  画主流程和事务边界。
5.  逐项处理重复、超时、乱序、宕机和数据差错。
6.  给出容量、高可用、安全和观测方案。
7.  说明取舍、迁移与组织落地。

## 金融与支付领域基础

### 2.1 先分清信息流、资金流和账务流

支付系统至少同时存在三条链路：

- **信息流**：支付请求、渠道响应、回调、查询、事件。
- **资金流**：付款人、发卡行、收单机构、商户之间真实资金移动。
- **账务流**：公司内部用账户和分录表达资产、负债、收入、费用和应收应付。

三条链路的完成时间可能不同。API 返回成功并不一定代表资金已结算；渠道已扣款也不代表内部账务已经正确入账；账本已记录应收也不代表银行账户已经收到资金。

支付生态中的角色与主要链路

### 2.2 核心角色

| **角色**          | **主要职责**                 | **面试中常见混淆**            |
|-------------------|------------------------------|-------------------------------|
| 付款人            | 提供资金并完成认证           | 用户看到成功，不代表已结算    |
| 商户              | 发起收款并履约               | 商户订单状态不能替代支付状态  |
| 支付平台 / PSP    | 接入、编排、路由、状态与通知 | 不一定直接持有资金            |
| 收单机构 / 渠道   | 接收商户侧交易并连接清算网络 | 不同渠道能力和错误语义不同    |
| 发卡行 / 付款行   | 决定授权或扣款               | 拒绝码可能只对渠道有意义      |
| 卡组织 / 清算网络 | 路由和清算交易               | 授权、清算和结算不是同一步    |
| 账务系统          | 记录内部财务事实             | 不是简单的 payment 表余额字段 |
| 清结算 / 对账     | 计算应收应付并核对多方数据   | 对账不是事后补丁，而是安全网  |

### 2.3 支付生命周期

#### 2.3.1 支付意图与支付执行

推荐把业务意图和渠道执行拆开：

- `PaymentIntent`：商户或用户想完成的一笔支付。
- `PaymentAttempt`：针对某个渠道的一次具体执行。

一笔意图可能有多个 Attempt，例如：第一次在渠道 A 明确失败，路由到渠道 B；或者一次强认证流程先创建、后确认。需要强调：当渠道 A 的结果为 UNKNOWN 时，不能直接创建渠道 B 的新 Attempt，除非先确认 A 未执行。

支付意图与执行尝试的正交状态

#### 2.3.2 常见操作

| **操作**   | **含义**                   | **关键约束**                |
|------------|----------------------------|-----------------------------|
| Authorize  | 冻结或承诺可用额度         | 不等于商户已经拿到资金      |
| Capture    | 将已授权金额转为待清算交易 | 可支持全额或部分请款        |
| Void       | 在清算前撤销授权/交易      | 能否撤销取决于渠道阶段      |
| Pay / Sale | 授权与请款合并             | 同步接口背后仍可能异步完成  |
| Refund     | 已完成支付后的资金返还     | 需要限制累计退款金额        |
| Reversal   | 冲正异常或超时交易         | 与用户主动退款语义不同      |
| Chargeback | 持卡人争议导致的拒付       | 有独立证据、时限和账务周期  |
| Settlement | 渠道或银行实际结算         | 可能按批次、净额和 T+N 完成 |

### 2.4 四类必须分开的状态

1.  **业务订单状态**：待履约、已发货、已完成、已取消。
2.  **支付状态**：创建、处理中、成功、失败、取消。
3.  **渠道尝试状态**：已发送、批准、拒绝、待定、未知。
4.  **账务/结算状态**：未入账、已入账、待结算、已结算、差错。

把它们压缩进一个超级枚举会产生状态爆炸。例如“订单已取消但退款处理中”“支付成功但渠道未结算”“渠道成功但账务补记中”都是合法组合。

### 2.5 支付系统的十条核心不变量

1.  同一业务幂等请求不能产生两次扣款。
2.  一个稳定的渠道请求号只代表一次外部操作。
3.  结果未知不能当作明确失败。
4.  终态不能被迟到回调随意覆盖。
5.  累计退款和请款金额不能超过允许上限。
6.  金额、币种和商户归属在执行后不能随意修改。
7.  重复事件不能重复产生记账、发货或退款效果。
8.  账务事务必须借贷平衡，历史分录不可直接覆盖。
9.  所有资金相关人工修复必须有双人或审批控制及审计记录。
10. 内部状态最终必须能与渠道、银行和账务数据对账收敛。

**面试表达重点**

先讲不变量，再讲 Redis、Kafka、分库分表。技术组件只是实现手段；资金正确性和业务语义才决定架构。

### 2.6 高频失败场景

| **场景**             | **直接风险**       | **正确方向**                   |
|----------------------|--------------------|--------------------------------|
| 客户端重复提交       | 重复扣款           | API 幂等 + 数据库唯一约束      |
| 渠道超时             | 交易可能已执行     | UNKNOWN + 查询/回调/对账恢复   |
| 同步响应与回调并发   | 状态覆盖、重复事件 | 状态机 + 版本/锁 + 幂等完成    |
| 数据库成功、消息失败 | 下游永远不知道     | Transactional Outbox           |
| 消息重复投递         | 重复记账、发货     | Inbox / 业务唯一键             |
| 部分退款并发         | 超额退款           | 原子条件更新或聚合锁           |
| 渠道文件重复导入     | 重复结算或差错     | 文件指纹 + 批次版本 + 行唯一键 |
| 人工直接改状态       | 审计链断裂         | 命令化修复 + 审批 + 不可变审计 |
