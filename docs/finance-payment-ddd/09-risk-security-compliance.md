# 支付风险、安全与合规边界

> 合规边界：资料中的控制项只能作为设计检查表。数据驻留、支付牌照、隐私、制裁、KYC/AML、PCI 等要求必须按业务所在地和处理范围由合规与安全团队确认。

## 安全设计

### 9.9.1 敏感数据最小化

- 优先使用 Token，不在业务系统存储原始卡数据；
- 传输和静态数据加密；
- 日志、消息和分析平台默认脱敏；
- 不同敏感级别采用不同访问控制和保留期限；
- 生产数据不得随意复制到测试环境。

### 9.9.2 密钥与证书

- 使用受控密钥管理系统；
- 密钥有用途、版本、轮换和吊销；
- 应用只获得最小权限；
- 证书到期提前告警；
- 双密钥窗口支持平滑轮换；
- 禁止把私钥写进代码、镜像或普通配置中心。

### 9.9.3 Webhook 安全

1.  验证 HTTPS 和证书策略；
2.  使用签名并验证时间戳；
3.  设置重放窗口；
4.  原始请求体参与验签，避免序列化差异；
5.  `provider + event_id` 去重；
6.  异常来源和连续验签失败告警；
7.  响应尽量快速，业务处理异步化。

### 9.9.4 权限与审计

- 退款、调账、解冻、重放事件均是独立权限；
- 高金额或高风险动作需要审批/双人控制；
- 审计日志不可被普通业务管理员修改；
- 记录操作者、原因、前后状态、关联工单和审批链；
- 定期复核权限和离职回收。

**面试红线**

不要提出“为了可用性，风控和账务挂了就先全部放行”“人工直接改数据库状态”“把完整渠道请求响应都打印日志”。这些回答会暴露对资金和合规风险缺乏敬畏。
