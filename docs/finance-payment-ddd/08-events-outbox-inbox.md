# 领域事件、Outbox、Inbox 与补偿

> Outbox 缩小的是“业务状态已提交但事件未可靠发布”的窗口；它不自动保证消费者副作用唯一，也不能替代 Inbox、幂等、补偿和对账。

## Observer、Domain Event 与可靠事件

内存 Observer 只适合同一进程的非关键通知。支付成功后触发账务、发货和通知需要可靠消息：

    领域状态 + OutboxEvent 在同一事务提交
    -> Relay 发布
    -> 消费者 Inbox / 唯一约束
    -> 业务副作用

“用了事件驱动”不代表自动解耦。事件所有者、契约版本、数据最小化、消费幂等和事件血缘都需要治理。

## Saga：长事务与补偿

购买数字商品：

    支付成功 -> 记账 -> 创建订单 -> 发放权益

若发放权益失败，无法回滚外部渠道历史，只能发起业务补偿，例如退款、冲销账务和取消订单。补偿本身也可能失败，需要状态、重试和人工处理。

### 4.12.1 Orchestration 与 Choreography

| **方式**      | **优点**                   | **缺点**           | **适合场景**                 |
|---------------|----------------------------|--------------------|------------------------------|
| Orchestration | 全局流程清晰、补偿顺序明确 | 协调器可能膨胀     | 强审计、步骤多、失败分支复杂 |
| Choreography  | 服务解耦、易增加消费者     | 流程隐式、排障困难 | 简单事件扩散、弱流程依赖     |

P8 的答案通常不是二选一：核心资金流程可采用显式编排，外围通知和分析采用事件协作。

## Transactional Outbox 与 Inbox

直接这样写存在双写窗口：

    更新数据库
    发布消息

数据库成功、消息失败会丢事件；消息成功、数据库回滚会产生幽灵事件。

### 6.8.1 Outbox 模式

在同一个本地事务中：

1.  更新业务状态；
2.  插入 `outbox_event`；
3.  提交事务。

Relay 通过轮询或 CDC 发布。发布成功后标记或删除记录；删除也要容忍重复发布。

### 6.8.2 Inbox / 消费者幂等

消费者在本地事务内先插入：

    UNIQUE (consumer_name, event_id)

首次插入者执行副作用；冲突者直接返回。对于账务，最好再使用 `business_type + business_id` 唯一约束作为第二道业务防线。

Outbox 与 Inbox 的业务效果一次性

**关于 exactly once 的正确表达**

消息系统可以提供某些范围内的 exactly-once 能力，但跨数据库、消息、外部渠道和下游副作用时，仍需按“至少一次传输 + 业务幂等 + 状态机 + 对账”设计。面试中不要把资金正确性完全交给 MQ 配置。

## Saga 与补偿

补偿不是技术回滚，而是新的业务动作：

- 支付已成功但权益发放失败：发起退款，而不是“回滚支付”。
- 账务已入账后支付被冲正：创建冲正分录，而不是删除原分录。
- 商户出款失败：恢复应付款或冻结余额，并记录失败原因。

Saga 需要记录每一步状态、幂等键、补偿命令和人工接管入口。补偿也可能 PENDING 或 UNKNOWN。
