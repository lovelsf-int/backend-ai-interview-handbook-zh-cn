# 支付架构面试题库与训练计划

## 100 道高频快问题库与参考答案

建议先遮住答案，在 30-90 秒内口述；答完后检查是否包含业务语义、失败场景和取舍。

### 15.1 SOLID 与面向对象快速题

1.  **一个类有十个方法是否一定违反 SRP？**
    不一定。判断标准是这些方法是否围绕同一责任和同一变化原因。一个状态丰富的聚合可能有很多行为但仍然单一；一个只有三个方法的 Service 也可能同时处理渠道、账务和通知而违反 SRP。

2.  **如何识别一个模块的主要变化轴？**
    观察谁会提出修改、修改频率、业务规则来源和失败责任。渠道协议由接入团队变化，账务规则由财务/账务域变化，状态不变量由支付核心变化；变化来源不同通常需要边界。

3.  **PaymentService 中的 switch provider 必须马上重构吗？**
    少量、稳定分支且生命周期短时可以接受。渠道数量持续增长、分支包含认证/错误映射/能力差异、多人并行修改时，应收敛到 Adapter + Registry，并用契约测试保护。

4.  **开闭原则是否意味着核心代码绝不能修改？**
    不是。核心不变量变化时必须有计划地修改和迁移。OCP 的目标是让常见扩展发生在稳定协议后面，降低无关修改，而不是把旧代码冻结成不可理解的层层补丁。

5.  **如何防止插件式策略破坏资金不变量？**
    插件只返回受限决策或候选结果，最终状态迁移、额度检查和账务平衡仍由核心域执行。配合接口契约、白名单能力、沙箱/回放、版本治理和灰度发布。

6.  **支付渠道实现同一接口时，LSP 最容易被什么破坏？**
    状态、错误、超时和幂等语义不一致。最典型的是把“已受理”映射成成功，或把读超时映射成失败，使调用方在替换实现后产生错误发货或双扣。

7.  **UnsupportedOperationException 为什么常常说明 LSP/ISP 有问题？**
    它表明父接口承诺了子类型无法履行的能力。应拆成 Authorizable、Refundable、Queryable 等能力接口，并在路由前进行能力过滤。

8.  **能力型接口会不会导致接口爆炸？**
    会有风险。治理方式是围绕稳定业务能力而不是供应商每个 API 拆接口，用能力元数据做发现，限制公共接口数量，并定期合并没有独立变化价值的抽象。

9.  **领域 Port 应由谁定义？**
    通常由需要它的高层领域/应用层定义，而不是由供应商 SDK 或基础设施团队反向决定。这样依赖方向指向稳定业务语义，Adapter 负责满足契约。

10. **是否每个类都需要接口以满足 DIP？**
    不需要。纯值对象、稳定领域对象和没有替换需求的类无需空洞接口。DIP 针对高层策略依赖低层易变细节的场景。

11. **继承和组合在支付系统中如何选择？**
    优先组合，因为渠道、风控、路由和监控能力会独立变化，组合更容易测试和重排。只有明确的 is-a 关系、稳定模板和受控扩展时使用继承。

12. **抽象类和接口如何选择？**
    接口表达能力和契约，适合多实现与解耦；抽象类可复用受保护状态或模板骨架，但会带来继承耦合。支付渠道通常用接口 + 组合，少量稳定公共逻辑放 Helper/Pipeline。

13. **为什么 Money 应是值对象？**
    它由金额和币种共同定义，无独立身份，适合不可变、按值相等并在构造/运算中保护币种和溢出。这样能消灭 long + String 在各层漂移。

14. **实体和值对象的区别是什么？**
    实体通过稳定身份跨时间存在，即使属性变化仍是同一个对象；值对象由属性定义且通常不可变。Payment 是实体，Money 和 ProviderRequestId 是值对象。

15. **聚合应多大？**
    只包含必须在一个本地事务中维护的不变量。不要为了导航方便把商户、支付、账本和结算放进一个聚合；跨聚合用 ID、命令和事件协作。

16. **贫血模型一定错误吗？**
    不是绝对。简单 CRUD 场景可以贫血；但支付状态、退款额度和合法迁移有丰富不变量，若全部散落在 Service，容易被不同入口绕过，应由聚合或明确领域服务保护。

17. **服务拆分是否等同于单一职责？**
    不等同。一个微服务内部仍可能是大泥球；一个模块化单体也可以有清晰责任。服务边界还要考虑数据所有权、容量、发布、合规和组织成本。

18. **如何识别过度设计？**
    抽象没有第二个真实实现、调用链无法追踪、修改一条规则要跨多层工厂、模式名多于业务名、配置无法回放，都是信号。以当前复杂度和明确演进路径为依据。

19. **Factory 与 DI 容器的区别？**
    DI 容器适合创建和装配稳定服务；Factory 适合运行时按商户/渠道动态选择、复杂构造、对象族和生命周期管理。不要用 Factory 重复容器已经做好的工作。

20. **代码评审时如何快速发现 SOLID 问题？**
    看修改原因是否混杂、是否到处 switch/instanceof、接口是否有不支持方法、领域是否依赖 SDK、状态是否有公开 setter，以及新增渠道是否需要修改多个核心类。

### 15.2 设计模式与 DDD 快速题

21. **Strategy 和 State 的本质区别？**
    Strategy 是为同一目标选择不同算法，通常由外部上下文选择；State 是对象生命周期驱动允许行为变化。路由用 Strategy，PaymentAttempt 迁移用 State。

22. **Adapter 和 Facade 的区别？**
    Adapter 改变接口/语义以满足目标契约；Facade 为复杂子系统提供简化入口，但不一定改变模型。渠道防腐通常是 Adapter/ACL，支付平台统一入口可以是 Facade。

23. **Command 和 Domain Event 的区别？**
    Command 表示希望系统执行的意图，可能失败；Event 表示已经发生的事实，不应被拒绝。RefundCommand 与 RefundSucceeded 语义不同。

24. **Template Method 与 Strategy 如何选择？**
    Template 固定流程骨架并通过继承替换步骤；Strategy 把整个算法作为组合对象替换。现代支付系统通常优先组合的 Pipeline + Strategy，避免深继承。

25. **责任链与规则引擎的边界？**
    固定顺序、数量有限、逻辑可代码审查时责任链简单可靠；规则大量动态配置、运营频繁调整时可引入规则引擎，但必须补充版本、解释、回放和治理。

26. **Specification 适合什么，不适合什么？**
    适合可组合的布尔资格判断，如币种、国家、商户准入；不适合包含多步副作用的支付执行流程。最好返回失败原因和证据。

27. **Decorator 与 Proxy 的区别？**
    Decorator 重点是叠加功能，Proxy 重点是控制访问或代表远程对象。监控/追踪常是 Decorator，远程渠道客户端、缓存、权限可视为 Proxy。实践中结构可能相同，意图不同。

28. **为什么内存 Observer 不适合支付成功通知账务？**
    进程宕机就会丢失，无法跨服务持久化和重试。关键事件应通过状态 + Outbox 同事务、消息至少一次投递和消费者幂等实现。

29. **Saga 能保证强一致吗？**
    不能提供全局原子回滚。它通过持久化步骤、幂等命令和业务补偿实现可恢复的最终一致；每个本地步骤仍需强一致。

30. **Orchestration 和 Choreography 如何选择？**
    复杂资金流程、补偿顺序和审计要求高时偏编排；简单外围事件扩散偏协作。常见组合是核心流程编排，通知/分析事件化。

31. **Repository 为什么不应成为通用 SQL 工具？**
    它应表达聚合加载和保存语义，保护领域与持久化细节。通用查询和报表可走专门 Query/Read Model，不要让领域层随意拼 SQL。

32. **Unit of Work 在支付中承担什么？**
    把聚合更新、幂等记录、状态历史和 Outbox 放入同一本地事务统一提交。它不应该跨外部渠道或多个独立数据库假装全局事务。

33. **CQRS 是否等于两个服务两套数据库？**
    不等于。它首先是读写模型职责分离，可以同库不同模型；只有容量和组织需要时才物理拆分。

34. **Event Sourcing 是否是金融系统标配？**
    不是。它提供完整事件历史，但引入事件版本、投影、重放副作用和隐私治理成本。不可变账务分录、状态历史和审计日志往往足够。

35. **ACL 为什么比简单 DTO Mapper 更重要？**
    它保护核心领域不被遗留系统或供应商的概念、错误码和状态污染，通常还包含协议、同步、容错和模型转换。

36. **Domain Service 与 Application Service 的区别？**
    Domain Service 承载无法自然放入单一实体/值对象的纯领域规则；Application Service 负责编排用例、事务、权限和调用 Port，不应塞入所有业务规则。

37. **领域事件应该包含完整聚合快照吗？**
    通常不应。只包含下游完成职责所需的最小事实和关联 ID，降低敏感数据、耦合和版本成本；更多数据通过受控查询获取。

38. **如何给事件做版本兼容？**
    优先新增可选字段、不改变旧字段语义；事件类型或 schema 有版本，生产者兼容期内双写/适配，消费者做契约测试和滞后监控。

39. **契约测试如何支撑 OCP 和 LSP？**
    所有渠道实现运行同一套成功、拒绝、超时、幂等、金额和脱敏测试，确保新增实现不用修改调用方且语义可替换。

40. **设计模式什么时候会变成反模式？**
    当它不再对应真实变化、隐藏业务语义、增加层次而无测试/治理、或阻止核心模型演进时。模式是沟通和结构工具，不是目标。

### 15.3 支付领域快速题

41. **PaymentIntent 和 PaymentAttempt 为什么要分开？**
    Intent 表达一笔业务支付意图，Attempt 表达一次渠道执行。分开后可记录多次明确失败的尝试、路由原因和 UNKNOWN 恢复，同时保持业务支付只成功一次。

42. **Authorize 和 Capture 有什么区别？**
    Authorize 通常冻结/承诺额度，Capture 才提交清算或完成扣款。它们可能分离、部分执行或有有效期，状态和金额上限需独立建模。

43. **Void 和 Refund 有什么区别？**
    Void 通常在交易进入最终清算前撤销，可能不形成正式扣款；Refund 是支付完成后的返还，是一笔新的资金操作。渠道能力和时限不同。

44. **PENDING 与 UNKNOWN 为什么必须分开？**
    PENDING 是渠道明确受理且处理中；UNKNOWN 是不知道是否受理。PENDING 等待，UNKNOWN 先查询确认；两者的安全重试策略不同。

45. **渠道超时后为什么不能直接重试？**
    请求可能已在渠道执行，只是响应丢失。盲重试尤其换新请求号会双扣，应保持稳定请求号并查询、等回调或对账。

46. **什么时候可以安全切换备用渠道？**
    调用前已知不可用，或渠道明确证明原请求未受理且业务允许时。读超时、连接中断等不确定场景必须先恢复原渠道结果。

47. **幂等键由谁生成、作用域多长？**
    通常客户端生成，服务端按商户+操作隔离。保留期至少覆盖客户端重试、渠道恢复和业务争议窗口；具体时间由产品和存储策略决定。

48. **为什么幂等键要绑定请求指纹？**
    防止客户端误用同一个 key 发送不同金额、订单或收款对象。相同 key 不同指纹必须冲突，而不是返回错误交易结果。

49. **如何处理重复回调？**
    验签后按 provider+event_id 插入 Inbox 唯一键；在同一事务锁定交易、应用状态机和写 Outbox。重复事件返回 2xx，但不重复副作用。

50. **回调无法找到内部交易怎么办？**
    保留原始事件进入孤儿队列，按请求号/交易号/商户账户再关联并告警。不能直接丢弃，因为可能是内部写入失败或渠道异常成功。

51. **如何防止并发部分退款超额？**
    用聚合锁或原子条件更新预占可退款额度，成功/失败后转换或释放预占；同时对退款命令和渠道请求做幂等。

52. **业务订单状态为什么不能复用支付状态？**
    履约、支付、退款和结算生命周期独立。订单取消时可能退款处理中，支付成功时也可能尚未发货，强行合并会产生状态爆炸。

53. **路由为什么先做能力过滤？**
    不支持币种、国家或操作的渠道没有评分意义。硬约束必须先排除，避免执行时才发现不支持并制造线上失败。

54. **支付成功率如何正确计算？**
    明确分母和排除项，按商户、国家、支付方式、卡段等细分；区分业务拒绝、平台错误、渠道错误和用户放弃，并处理小样本与时间窗口。

55. **支付成功的定义是什么？**
    取决于业务：可能是授权、请款、渠道确认或资金结算。设计前必须与产品明确，否则状态、SLO 和发货时点都会错。

56. **为什么 API 必须允许 PROCESSING？**
    银行转账、钱包、强认证、异步渠道和 UNKNOWN 恢复都无法在一次同步调用内确定终态。强行同步只会制造超时和错误失败。

57. **Chargeback 与 Refund 的区别？**
    Refund 通常由商户/平台主动返还；Chargeback 是付款人争议经银行/卡组织发起，有独立证据、时限、费用和账务处理。

58. **Settlement 与支付成功有什么关系？**
    支付成功表示业务交易已被接受或扣款，Settlement 是后续真实资金转移，可能 T+N、净额并扣费。两者状态必须分开。

59. **merchant_order_id 能否作为 payment_id？**
    不建议。一个订单可能多次尝试支付或有多个意图，平台 ID 需全局稳定；商户订单号作为业务关联和可选唯一约束。

60. **如何证明系统没有重复扣款？**
    用幂等记录、Attempt、稳定渠道请求号、渠道交易记录/文件和账务 Journal 多源核对，并建立重复候选检测。单看接口日志或 payment 当前状态不足以证明。

### 15.4 一致性与稳定性快速题

61. **Outbox 解决了什么？**
    解决本地业务状态与待发布事件的原子提交，消除数据库成功而消息丢失的窗口。它不消除重复发布，所以消费者仍要幂等。

62. **Inbox 解决了什么？**
    消费者通过 event_id 或业务唯一键认领事件，使 MQ 重投、消费者重启时副作用只发生一次。Inbox 与业务更新最好同一事务。

63. **为什么不能只说 Kafka exactly once？**
    该能力有作用范围，无法自动覆盖业务数据库、外部渠道和第三方副作用。资金系统仍需业务幂等、状态机和对账。

64. **为什么外部渠道调用不应放在长事务里？**
    会占用连接和锁，扩大故障；更重要的是数据库回滚无法回滚渠道。应分成准备事务、事务外调用、完成事务。

65. **渠道成功后应用宕机如何恢复？**
    事务 A 已保存 Attempt 和稳定请求号。恢复任务查询渠道或等回调，再幂等执行完成事务；不能重新创建一笔调用。

66. **同步响应和回调同时到达怎么办？**
    二者映射到统一结果，使用锁/版本和状态机只允许首次有效迁移产生事件。兼容重复直接返回，冲突进入调查。

67. **乐观锁和悲观锁如何选择？**
    冲突低、可安全重试用乐观锁；同一支付同时受回调/恢复竞争且临界区短时可用悲观锁。两者都不能替代业务幂等。

68. **分布式锁在支付中是什么角色？**
    可以降低重复并发和热点，但不是最终正确性保证。数据库唯一约束、状态条件和渠道幂等才是兜底。

69. **Saga 补偿为何不等于回滚？**
    外部支付和已提交分录无法回到从未发生，只能创建退款、冲正等新业务动作，保留历史且补偿也可能失败。

70. **如何设置重试预算？**
    同时限制次数和总时长，使用指数退避和抖动，并按错误语义决定。预算必须小于上游超时且不能让故障产生查询/重试风暴。

71. **Circuit Breaker 能否解决双扣？**
    不能。它防止继续调用故障依赖，但已发出的请求仍可能 UNKNOWN。双扣靠稳定请求号、幂等、查询和对账。

72. **Bulkhead 为什么重要？**
    把线程、连接、队列和配额按渠道/租户隔离，防止一个慢渠道耗尽平台资源。恢复流量也应与在线交易隔离。

73. **限流应该按什么维度？**
    商户、渠道、操作、支付方式和全局容量；还要区分在线支付、查询、退款和恢复任务的优先级。

74. **过载时应优先保护什么？**
    幂等、支付完成、UNKNOWN 恢复、账务和关键回调。可降级推荐、报表、非关键通知和低优先级批任务。

75. **支付 SLO 为什么不能只有 99.99% HTTP 成功？**
    接口返回 200 可能仍是 PROCESSING/UNKNOWN，或业务成功率下降。需要同时看业务成功、最终收敛、重复扣款和资金差错。

76. **多区域如何避免同一支付双写？**
    为每笔支付确定唯一 Home Region，使用全局路由、租约/fencing token 和稳定操作 ID；切换前阻断旧主并验证渠道执行。

77. **什么是 split brain 的资金风险？**
    两个区域都认为自己可写，可能各自创建渠道请求和状态，导致双扣或冲突。必须以唯一主写权和渠道幂等防护。

78. **数据修复为什么不能直接 UPDATE 状态？**
    会绕过状态机、事件、账务和审计。应通过受控修复命令、审批和可重放流程产生明确状态/调整记录。

79. **事件重放如何避免重复副作用？**
    消费者按 event_id/业务键幂等，重放工具限定范围和版本，外部副作用使用稳定请求号，并先做 dry-run/影响评估。

80. **最关键的稳定性观测是什么？**
    按业务维度的成功率、UNKNOWN、恢复账龄、Outbox 积压、重复拦截、账务不平衡和未解释资金敞口，而非只看 CPU 和异常数。

### 15.5 账务、对账与安全快速题

81. **双式记账为什么适合支付？**
    每个财务事实由平衡借贷表达，可验证完整性、追踪资金归属并支持冲正。它不能替代业务状态，但提供财务事实来源。

82. **为什么历史 Posting 不可直接修改？**
    修改会破坏审计和余额可解释性。错误通过冲正或调整 Journal 修复，并关联原交易、原因和审批。

83. **余额快照是否是事实来源？**
    通常不是，事实是不可变分录；余额是查询投影。投影损坏可由分录和快照重建。

84. **如何保证同一业务事件只入一次账？**
    账务命令使用 business_type+business_id 唯一约束，重复内容返回原 Journal，不同内容冲突报警；消费者 Inbox 可作为前置防线。

85. **跨币种如何保持平衡？**
    分别记录原币和目标币金额、汇率与舍入，使用换汇桥接/差额账户表达，不把不同币种数字直接相加判断平衡。

86. **冻结余额如何设计？**
    用 Reservation 或专用科目表达，必须有预占、确认、释放和过期状态，操作幂等，并能从交易/分录解释可用余额。

87. **热点总账户如何扩展？**
    按法律实体、渠道、币种、日期或业务子账户分片，采用顺序日志/批量投影，避免所有交易更新同一行。

88. **账务服务短时不可用，支付能否继续？**
    若账务是异步子账，可先提交支付和 Outbox，在风险阈值内继续；积压超过保护线必须降级/停流。实时余额扣减场景则可能是前置强依赖。

89. **交易对账、账务对账、资金对账的区别？**
    分别验证内部支付与渠道交易、业务事件与 Journal、结算应收应付与银行真实入账。三层共同证明资金闭环。

90. **渠道文件重复到达怎么处理？**
    使用来源+业务日期+文件类型+版本和 checksum 幂等；同标识不同内容报警，更正版保留历史并重算受影响结果。

91. **对账匹配规则如何排序？**
    从唯一交易号精确匹配到组合键、时间窗口和容差匹配；低置信匹配保留证据和规则版本，不自动执行高风险修复。

92. **外有内无差错如何处理？**
    先确认渠道权威记录，定位是否内部写入/回调丢失；恢复 Payment、补发账务命令或退款，并评估双扣和用户影响。

93. **什么差错可以自动修复？**
    证据充分、动作幂等、金额和法律风险低、规则可审计的场景。证据冲突或影响用户资金的必须审批/人工。

94. **银行总额对上是否代表系统正确？**
    不代表。总额可能掩盖一增一减或重复/缺失，需要交易级、账务级和资金级逐层解释。

95. **手续费差异如何建模？**
    记录渠道费率/规则版本、预估费用和实际结算费用；差异形成独立调整或应收应付，不直接覆盖原交易金额。

96. **Tokenization 的主要价值？**
    减少业务系统接触原始敏感支付数据的范围，降低泄露风险和合规边界；Token 仍需访问控制和用途绑定。

97. **Webhook 验签的关键点？**
    对原始请求体和时间戳验签、限制重放窗口、密钥轮换、事件去重并快速响应。不能先解析重序列化后再验签。

98. **密钥轮换如何做到不中断？**
    版本化密钥、双密钥验证窗口、提前部署新密钥、分阶段切换并监控；私钥只在受控密钥系统中访问。

99. **资金人工操作需要哪些审计？**
    操作者、角色、原因、工单、审批、前后状态、金额、关联交易、时间和结果；高风险操作双人控制且日志不可被普通管理员修改。

100. **P8 如何领导一次支付事故？**
     先控制危险动作和资金敞口，建立统一指挥与事实时间线，协调渠道/账务/客服，完成用户补救；复盘技术、检测和流程根因，并把改进平台化、演练化和量化。

共 100 题。建议标记为 A（流畅）、B（需补例子）、C（概念不稳），优先复习 C 类。

## 12 组真题式深挖链

本章按面试官逐层追问的方式组织。练习时先只看“起始题”，连续回答 8-12 分钟，再核对后面的得分点。

### 16.1 深挖链一：渠道超时与双扣

#### 16.1.1 起始题

用户支付请求调用渠道 2 秒超时，你会怎么处理？

#### 16.1.2 参考回答主线

1.  先区分连接前失败、明确未受理、读超时和结果未知。
2.  对 UNKNOWN 保存稳定 `provider_request_id`，Payment 保持 PROCESSING。
3.  不直接切备用渠道；优先查询原渠道、等待回调、定时恢复和对账。
4.  恢复处理与同步响应/回调并发时通过锁、状态机和幂等完成。
5.  对用户返回可查询的 Payment ID，商户通过 Webhook/查询获取终态。
6.  监控 UNKNOWN 比例、最老账龄和恢复成功率。

#### 16.1.3 继续追问

- **如果渠道不支持查询？** 依赖渠道幂等、回调、交易文件和人工差错工作流；提高调用前健康判断，并限制该渠道的自动故障切换。
- **用户再次点击支付？** 相同幂等键返回原 PROCESSING；新 key 是否允许创建新意图由产品规则决定，但必须提示可能重复并检查原交易。
- **查询也超时？** 继续 UNKNOWN，指数退避，设置最大自动恢复时长和人工升级，不把“不知道”转换成失败。
- **什么时候可以切换渠道？** 确认原渠道不存在该请求或明确未受理后，创建新的 Attempt，并保留关联和路由原因。
- **如何验证没有双扣？** 内部 Attempt、渠道交易号、渠道文件和账务/对账多源核验。

#### 16.1.4 失分回答

- “超时重试三次，再切到备用渠道”；
- “用 Redis 锁防止重复”；
- “返回失败，让用户重新支付”。

### 16.2 深挖链二：并发部分退款

#### 16.2.1 起始题

一笔 100 元支付，同时收到两笔 80 元退款请求，如何保证不超额？

#### 16.2.2 参考回答主线

- API 幂等不能解决两个不同 key 的合法并发，需要退款额度不变量。
- 锁定 PaymentRefundBalance 或原子条件更新预占额度。
- 成功创建退款后，渠道调用使用稳定退款请求号。
- 退款成功：reserved -\> refunded；明确失败：释放；UNKNOWN：保持预占直到恢复。
- 回调、查询和人工修复共用状态机。

#### 16.2.3 继续追问

- **锁会不会成为瓶颈？** 单笔支付退款并发通常低；可以用条件更新减少锁，热点按 payment_id 分散。
- **退款请求创建后服务宕机？** 退款记录和预占在事务内已保存，Recovery 继续调用或查询，不释放后重新创建。
- **渠道只支持全额退款？** 能力过滤，产品 API 拒绝部分退款或由业务层聚合为一次全额操作，不能假装支持。
- **多币种退款？** 通常按原交易币种和金额上限，汇兑差异独立记账，不随意用当前汇率重算原支付金额。

### 16.3 深挖链三：回调乱序和状态冲突

#### 16.3.1 起始题

先收到支付成功回调，后收到失败回调，怎么办？

#### 16.3.2 参考回答主线

- 验签、去重并保留原始事件。
- 失败事件可能是迟到、冲正、撤销或渠道错误，不能简单覆盖。
- 根据渠道事件类型和序列/时间判断，映射到不同领域动作。
- 不允许 `SUCCEEDED -> FAILED` 的无解释迁移；冲正用 `REVERSED` 或独立 Reversal。
- 冲突进入查询/对账和告警，保留证据。

#### 16.3.3 继续追问

- 渠道没有事件序列怎么办？使用事件时间、状态查询和对账，不把到达顺序当业务顺序。
- 同一个 event_id 内容不同怎么办？安全异常，拒绝覆盖并报警。
- 回调处理失败是否返回 500？只有希望渠道重试且处理可幂等时返回失败；验签错误通常拒绝并告警，不要让恶意请求制造无限重试。

### 16.4 深挖链四：支付成功但账务失败

#### 16.4.1 起始题

渠道扣款成功，账务服务不可用，如何保证资金正确？

#### 16.4.2 参考回答主线

- 支付完成事务写 Payment 状态和 Outbox；账务异步幂等消费。
- 账务不可用时事件积压，不丢失；恢复后按业务唯一键入账。
- 设置积压年龄和未入账金额风险阈值；超过阈值暂停相关交易或降级。
- 对账比较 PaymentSucceeded 与 Ledger Journal，发现缺失自动补发/人工处理。

#### 16.4.3 继续追问

- **支付是否立即返回成功？** 如果账务不是实时余额强依赖，通常可以；但需产品和风险政策。
- **Outbox 表也坏了？** Payment 与 Outbox 同事务，定期审计“成功支付无事件”，并有事件重建工具。
- **账务消费重复十次？** Inbox + `business_type/business_id` 唯一键。
- **入账规则变更？** 事件携带业务事实，账务记录 rule version；历史重放使用当时或明确迁移规则。

### 16.5 深挖链五：路由模型事故

#### 16.5.1 起始题

新路由模型上线后成功率下降 5%，你如何处理？

#### 16.5.2 参考回答主线

1.  立即确认是否是统计口径、渠道整体故障或模型选择导致。
2.  通过规则版本和路由解释快速回滚到上一版本。
3.  限制模型份额，保护大商户和高价值交易。
4.  对比 Shadow 预测、实际候选集、细分成功率和 UNKNOWN。
5.  找到特征漂移、小样本、健康指标滞后或成本权重问题。
6.  增加灰度、自动回滚阈值、离线回放和探索保护。

#### 16.5.3 继续追问

- 如何避免“所有流量追逐当前最优”？份额约束、平滑、最小样本、滞后和渐进升流。
- 如何衡量模型收益？净支付收入/转化，而不只看授权成功率；纳入成本、拒付、延迟和用户流失。
- 是否允许商户自定义？在平台硬约束内提供策略参数和白名单，不能绕过合规与安全。

### 16.6 深挖链六：外部成功、内部失败的对账差错

#### 16.6.1 起始题

对账发现渠道成功 100 笔，但内部全部显示失败，如何处理？

#### 16.6.2 参考回答主线

- 先停止可能产生二次支付的自动重试/故障切换。
- 验证渠道文件真实性、业务日期和账户。
- 用请求号/交易号关联 Attempt，评估用户和金额影响。
- 恢复内部状态、补发账务/通知；若业务已重新支付，识别双扣并退款。
- 保留修复命令、审批和关联证据。
- 根因可能是错误映射、事务 B 失败、回调验签或渠道文档变更。

#### 16.6.3 继续追问

- 是否可以批量 UPDATE payment？不可以直接改事实；使用受控、幂等、可审计的恢复命令，触发正常状态机和事件。
- 已发货但账务未入怎么办？优先补账并核实商户应付；根据敞口阈值限制后续交易。
- 如何防止复发？契约测试、渠道沙箱黄金样例、UNKNOWN 比例告警、对账前移。

### 16.7 深挖链七：多区域故障切换

#### 16.7.1 起始题

主区域故障，支付平台如何在 5 分钟内切到备区域而不双扣？

#### 16.7.2 参考回答主线

- 每笔支付有唯一 Home Region 和全局操作 ID。
- 切换前通过租约/fencing 阻止旧主继续创建新 Attempt。
- 备区确认复制进度和未完成 Attempt，优先恢复而非重发。
- 渠道请求号跨区域稳定且渠道幂等。
- 对复制延迟窗口中的交易执行渠道查询/对账。
- 切换演练包括旧区域网络孤岛而非只测试完全断电。

#### 16.7.3 继续追问

- DNS 切换够不够？不够，只改变流量入口，不能解决双主写和正在执行的外部调用。
- RPO 不为零怎么办？利用渠道查询/文件重建缺失 Attempt，明确资金敞口；不能假设丢失交易不存在。
- 是否多活更好？只有业务收益覆盖全局一致性、数据跨境和运营复杂度时采用。

### 16.8 深挖链八：接入一个能力差异巨大的新渠道

#### 16.8.1 起始题

新渠道只支持全额退款、没有查询接口、回调可能延迟 30 分钟，如何接入？

#### 16.8.2 参考回答主线

- 通过能力模型明确 `partialRefund=false`、`query=false`、异步时延。
- 产品层在请求前拒绝不支持能力，而不是执行后报错。
- Adapter 统一错误和 PENDING/UNKNOWN 语义。
- Recovery 依赖回调/文件，设置更长 SLA 和差错工作流。
- 路由策略考虑回调时延、UNKNOWN 恢复能力和运营成本，而不仅是费率。
- 契约测试覆盖渠道特性，不能为了统一接口伪造能力。

### 16.9 深挖链九：超级商户热点

#### 16.9.1 起始题

一个商户贡献 40% 流量，merchant_id 分片发生热点，怎么办？

#### 16.9.2 参考回答主线

- 对超大商户按 hash(payment_id) 二级分片，保持商户聚合查询走读模型。
- 商户限流与公平调度独立于数据库分片。
- 幂等键需要可路由，可使用商户 + key 哈希。
- 运营查询异步索引，避免跨分片扫描主交易库。
- 渠道配额、线程池和 Outbox 发布也要防单租户挤占。

#### 16.9.3 继续追问

- 商户订单号全局唯一如何保证？可建立轻量全局索引/目录，或把幂等语义放到可确定分片的键上。
- 二级分片迁移怎么办？使用虚拟分片、双读/影子校验、逐批搬迁和路由版本。

### 16.10 深挖链十：修改运行多年的状态机

#### 16.10.1 起始题

需要新增 `REQUIRES_ACTION` 状态，旧客户端只认识 PROCESSING，如何演进？

#### 16.10.2 参考回答主线

- 内部状态与外部 API 状态分层；新增内部细粒度状态，旧 API 可继续投影为 PROCESSING。
- 事件和 API schema 向后兼容，新增字段 `next_action`。
- 明确存量数据迁移和合法迁移表。
- 双写新旧状态/影子验证，按客户端版本灰度。
- 回调、查询、报表和对账全部做兼容测试。

#### 16.10.3 继续追问

- 是否直接改枚举？还要检查数据库约束、序列化、缓存、数据仓库和下游消费者。
- 如何回滚？保留旧投影和兼容映射，新状态不能产生不可逆副作用后再回滚。

### 16.11 深挖链十一：支付平台化迁移

#### 16.11.1 起始题

公司有五套支付系统，如何统一到一个平台？

#### 16.11.2 参考回答主线

1.  盘点共同能力和差异，不直接大爆炸重写。
2.  定义统一 Payment/Attempt 模型、API、事件和接入标准。
3.  用 ACL 包装旧系统，建立双写/影子调用和结果对比。
4.  按商户、国家或支付方式渐进迁移。
5.  提供迁移工具、SLO、支持和收益指标。
6.  旧系统先冻结新功能、只读，最后下线。

#### 16.11.3 继续追问

- 业务团队不愿迁移？量化成功率、接入周期、合规和运维收益；提供兼容层、迁移预算和共同路线图。
- 特殊业务怎么办？把真正稳定差异做成受治理扩展点，不为每个历史特例污染核心。
- 如何衡量平台成功？渠道接入周期、复用率、迁移率、事故率、成本和业务成功率。

### 16.12 深挖链十二：重大支付事故复盘

#### 16.12.1 起始题

请讲一次你主导处理的重大线上事故。

#### 16.12.2 高分结构

1.  **影响**：交易笔数、金额、商户、用户和监管/声誉风险。
2.  **发现**：哪个业务指标告警，检测是否及时。
3.  **止损**：关闭什么、保留什么，为什么。
4.  **事实**：明确成功、明确失败和 UNKNOWN 分组。
5.  **协同**：渠道、账务、客服、财务、管理层的工作机制。
6.  **修复**：数据、用户补救、商户沟通和资金核对。
7.  **根因**：代码、设计、测试、监控、流程和组织。
8.  **长期改进**：平台化能力、SLO、演练和指标结果。

#### 16.12.3 低分信号

- 只讲自己修了一个 Bug；
- 没有资金影响评估；
- 没有说明为什么采取某个止损动作；
- 把责任推给渠道或同事；
- 复盘只有“加强测试”。

### 17.2 STAR-L 答题法

- **S - Situation**：业务背景和约束，控制在 20%。
- **T - Task**：你的职责和目标，明确你本人负责什么。
- **A - Action**：关键判断、方案、推动和困难，约占 50%。
- **R - Result**：量化结果、业务影响和遗留问题。
- **L - Learning**：复盘、后续机制和若重来会怎么做。

避免用“我们”掩盖个人贡献，也避免把团队成绩全归自己。可以说：“团队完成 X，我负责 Y 决策和 Z 推动”。

### 17.4 20 道行为面试题与作答要点

1.  **你主导过最复杂的支付项目是什么？** 讲复杂度来源、你的架构判断、跨团队落地和量化结果。
2.  **一次你做错的技术决策。** 说明当时信息、错误假设、如何发现、止损和机制改进。
3.  **业务要求快速上线但你认为有资金风险。** 把风险转成金额/用户影响，提供分层方案、保护阈值和可逆灰度。
4.  **如何推动五个团队采用统一接口？** 共同设计、迁移工具、兼容层、SLO、治理和收益指标。
5.  **团队反对你的架构方案怎么办？** 先理解目标，列方案和证据，做小规模试验；关键风险保留底线。
6.  **如何处理强势资深同事的分歧？** 聚焦决策标准和可验证假设，记录决策，必要时升级但不人格化。
7.  **你如何定义路线图？** 从业务目标、风险和能力缺口出发，区分基础能力、增长和技术债，并设置结果指标。
8.  **如何衡量支付平台价值？** 成功率、成本、接入周期、复用率、事故、差错和团队效率。
9.  **如何培养下一位技术负责人？** 给真实所有权、明确反馈、让其主持设计/事故，并逐步退出关键路径。
10. **如何处理表现不佳成员？** 明确期望和证据、了解原因、提供支持和时间边界，公平记录并及时决策。
11. **项目延期如何汇报？** 及时说明事实、影响、根因、选项和新承诺，不用乐观假设掩盖风险。
12. **如何平衡重构与业务需求？** 把重构拆成与业务结果绑定的增量，设置接口/测试护栏，避免大爆炸重写。
13. **如何决定自研还是采购支付能力？** 比较核心差异化、合规、总成本、供应商锁定、SLO、数据和退出方案。
14. **如何应对模糊需求？** 明确成功指标和不变量，建立最小模型/试点，用反馈逐步收敛。
15. **你如何做技术评审？** 先审业务语义和失败模型，再审边界、容量、安全、迁移和可运维性。
16. **一次跨组织事故如何协调？** 单一指挥、事实时间线、清晰角色、固定节奏、用户/资金优先。
17. **如何处理历史遗留系统？** ACL、冻结新增、影子对比、分批迁移、可回滚和下线指标。
18. **如何让架构原则不靠口号？** 模板、契约测试、平台能力、自动检查、指标和例外审批。
19. **你如何向非技术高管解释技术风险？** 用业务损失、概率、可逆性和方案成本表达，不堆术语。
20. **为什么你适合 P8/专家岗位？** 结合一个深技术案例、一个跨团队案例和一个业务结果，证明可持续影响。

### 17.5 行为面试答案样例：平台化改造

背景是公司五条业务线各自接入支付渠道，模型和状态不统一，新渠道平均要三个月，过去一年出现过两次重复扣款隐患。我负责统一支付平台的技术方向和迁移。我们没有直接重写，而是先定义 PaymentIntent/Attempt、错误语义和幂等标准，用 ACL 包装两套旧系统，并建立影子请求和结果对比。最大的阻力是业务担心平台限制定制，我把需求分成核心不变量、受治理扩展和历史特例，给每条业务线保留路由/费率策略扩展，同时禁止绕过状态机。九个月内迁移了 70% 流量，新渠道接入从 12 周降到 3 周，UNKNOWN 交易平均收敛从 40 分钟降到 6 分钟。复盘看，前期低估了运营工作台的重要性，后续专门投入差错和迁移可视化，降低了业务团队使用门槛。

### 17.6 行为面试答案样例：重大事故

某次渠道 SDK 升级后，读超时被错误映射为明确失败，自动故障切换可能形成双扣。告警来自该渠道 UNKNOWN 率反而下降、但对账外有内无突增。我作为事件负责人先关闭自动切换而不是关闭所有支付，把受影响交易按渠道请求号分组，协调渠道提供交易查询，并让客服暂停引导用户重试。我们识别出 1,200 笔结果不确定，其中 37 笔渠道已成功，全部恢复内部状态并补发账务；3 笔用户已二次支付，主动退款。根因不只是 Mapper Bug，还包括契约测试没有覆盖读超时、监控只看失败率。后续我们统一四态结果模型、增加渠道契约测试和 UNKNOWN 账龄告警，并把故障切换前置条件做成平台策略。之后一年没有再发生同类双扣。

## 面试现场速查表

### 21.1 一句话总纲

资金系统先保护不变量，再以幂等、状态机、稳定外部请求号、可靠事件、恢复和对账把分布式不确定性收敛；设计模式用于隔离变化，而不是替代业务语义。

### 21.2 十条必说不变量

1.  同一业务意图不重复扣款。
2.  渠道请求号稳定且唯一。
3.  UNKNOWN 不等于失败。
4.  终态和合法迁移受保护。
5.  累计退款/请款不超上限。
6.  状态与 Outbox 同事务。
7.  重复事件无重复副作用。
8.  Journal 借贷平衡且不可变。
9.  人工资金操作可审批、可审计。
10. 内外数据最终可对账。

### 21.3 模式速查

| **问题**     | **模式**            | **最重要的边界**           |
|--------------|---------------------|----------------------------|
| 渠道协议差异 | Adapter / ACL       | 统一状态、错误、金额和幂等 |
| 路由算法     | Strategy            | 先硬过滤，后评分，可解释   |
| 生命周期     | State               | 合法迁移、终态保护、并发   |
| 操作意图     | Command             | 幂等键、审计和权限         |
| 校验链       | CoR / Specification | 短路、原因、规则版本       |
| 可靠事件     | Outbox/Inbox        | 至少一次 + 业务幂等        |
| 跨服务流程   | Saga                | 补偿不是回滚               |
| 聚合持久化   | Repository/UoW      | 本地事务和数据所有权       |

### 21.4 错误处理速查

| **情况**          | **处理**                       |
|-------------------|--------------------------------|
| 明确业务拒绝      | 返回 DECLINED，不技术重试      |
| 明确未发送/未受理 | 在预算内用同一幂等键重试       |
| PENDING           | 等待回调/查询                  |
| UNKNOWN           | 不换渠道；查询、恢复、对账     |
| 消费重复          | Inbox/业务唯一键               |
| 状态冲突          | 不覆盖；查询权威来源并差错处理 |

### 21.5 系统设计开场白

我先确认支付成功定义、同步/异步方式、账务和结算是否在范围，以及规模与 RTO/RPO。然后我会先给出核心不变量和领域模型，再展开主流程、失败恢复和容量设计。

### 21.6 P8 取舍句式

- “这里我优先保证资金正确性，因此……”
- “这个能力是高频变化轴，适合作为扩展点；核心不变量仍由……”
- “方案 A 在当前阶段更简单，但达到 X 规模后瓶颈是……，演进到 B 的触发条件是……”
- “这个失败无法靠重试解决，因为结果可能未知；恢复路径是……”
- “我不会直接拆服务，先确认数据所有权、团队边界和分布式一致性成本……”
- “这个指标必须按商户/渠道/支付方式细分，否则总体平均值会掩盖问题……”

### 21.7 现场常见错误

- 一上来堆组件，不讲业务定义；
- 超时自动重试/切换；
- 把 Payment、订单、账务、结算状态合并；
- 认为 Redis 锁或 MQ 自动保证 exactly once；
- 账务只设计余额字段；
- 不讲人工差错和运营工作台；
- 没有量化影响和迁移路径；
- 只说“我们”，说不清个人判断。

## 术语表

| **术语**            | **面试中的简明定义**                  |
|---------------------|---------------------------------------|
| Payment Intent      | 一笔业务支付意图，可包含多个执行尝试  |
| Payment Attempt     | 对某个渠道的一次具体执行              |
| Authorization       | 冻结/承诺资金或额度                   |
| Capture             | 将授权转为待清算/完成扣款             |
| Void                | 清算前撤销授权或交易                  |
| Refund              | 支付完成后的返还操作                  |
| Reversal            | 对异常交易的冲正动作                  |
| Chargeback          | 由付款人争议触发的拒付流程            |
| Clearing            | 计算参与方应收应付和净额              |
| Settlement          | 真实资金在账户之间结算                |
| Reconciliation      | 比较内外事实并处理差错                |
| Idempotency         | 重复输入只产生一次允许的业务效果      |
| Request Fingerprint | 绑定幂等键的请求内容摘要              |
| PENDING             | 渠道明确受理但尚未完成                |
| UNKNOWN             | 不知道渠道是否执行                    |
| Outbox              | 业务状态与待发布事件同事务保存        |
| Inbox               | 消费者对事件或业务操作去重            |
| Saga                | 通过本地事务和补偿组织长流程          |
| Compensation        | 新的业务修复动作，不是技术回滚        |
| Ledger              | 记录财务事实的账户和分录系统          |
| Journal             | 一组完整、平衡的账务事务              |
| Posting             | Journal 中的单条借/贷分录             |
| Reservation         | 对余额或额度的预占/冻结               |
| Balance Projection  | 从事实分录维护的查询优化余额          |
| ACL                 | 防止外部/遗留模型污染核心领域的防腐层 |
| Home Region         | 某个实体唯一负责写入的区域            |
| Fencing Token       | 阻止旧主在失效后继续写入的单调令牌    |
| SLO                 | 面向用户/业务结果的服务目标           |
| RTO                 | 故障后恢复服务所需目标时间            |
| RPO                 | 可接受的数据丢失时间窗口              |
| Bulkhead            | 按依赖/租户隔离资源，防止故障扩散     |
| Circuit Breaker     | 暂停调用持续失败的依赖                |
| Load Shedding       | 过载时主动拒绝低优先级工作            |
| Contract Test       | 所有实现必须通过的统一语义测试        |
| Shadow Traffic      | 不影响主结果的影子调用/评估流量       |
| Rule Version        | 让策略决策可解释、可回放的规则版本    |
| Funds Exposure      | 尚未解释或未结算的资金风险金额        |
