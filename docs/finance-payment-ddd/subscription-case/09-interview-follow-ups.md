# 订阅支付架构评审追问

## 高频追问

### 为什么 PaymentOrder 与 Subscription 不能放在一个聚合？

生命周期、事务边界、并发热点和失败补偿不同；支付事实先稳定，订阅再由事件驱动收敛。

### 为什么需要支付渠道 ACL？

渠道模型、金额单位、状态和错误语义持续变化。ACL 保护领域语言，并集中承担验签、审计和能力差异。

### 为什么不使用覆盖整条链路的分布式事务？

渠道回调和长时间异步流程无法形成现实的全局 ACID 边界。系统使用聚合内事务、Outbox/Inbox、幂等、重试、补偿和对账收敛。

### 如何证明没有重复扣款？

说明端到端幂等键、支付尝试模型、渠道流水唯一约束、状态条件更新、UNKNOWN 查询策略和对账证据，而不只回答“加 Redis 锁”。

### 百万订阅续费如何削峰？

先给到期分布、渠道配额和 SLO，再讨论分桶扫描、队列、Worker 幂等、分级重试、宽限期和对账，不把固定并发数字当通用答案。

### 何时拆成微服务？

当组织、发布、容量或故障隔离收益超过分布式一致性和运维成本时拆分；否则保留边界清晰的模块化单体。
