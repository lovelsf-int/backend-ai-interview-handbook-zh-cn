# 支付容量、可靠性与可观测性

## SLO 从业务结果定义

支付系统的 SLO 不应只有接口可用率。至少要覆盖：

| **指标**       | **说明**                     |
|----------------|------------------------------|
| API 可用率     | 请求是否得到协议层响应       |
| 业务成功率     | 明确成功交易占有效交易比例   |
| UNKNOWN 比例   | 结果不确定的交易比例         |
| 最终收敛时长   | PENDING/UNKNOWN 到终态的延迟 |
| 重复扣款率     | 资金级严重指标，目标接近零   |
| 账务差错率     | 未平衡、重复或缺失 Journal   |
| 对账差错账龄   | 资金不一致持续时间           |
| 商户通知成功率 | Webhook 最终投递和延迟       |

渠道业务拒绝不应计入平台可用性故障，但渠道技术错误和平台错误必须分开统计。

## 超时预算

假设 API 端到端预算为 3 秒，不能给每个依赖都配置 3 秒。应分配：

    网关与鉴权        100 ms
    商户/风险读取      250 ms
    路由               50 ms
    渠道调用          1800 ms
    本地完成事务       300 ms
    缓冲与网络抖动     500 ms

预算仅为示例。实际应基于支付方式、地域、SLO 和渠道分布。内部超时要小于上游超时，留出结果落库和安全响应时间。

## 重试矩阵

| **错误类型**     | **可否重试** | **要求**                   |
|------------------|--------------|----------------------------|
| 本地读取瞬时失败 | 可以         | 有总预算、退避和抖动       |
| 限流             | 条件允许     | 尊重 Retry-After，防止惊群 |
| 渠道明确未受理   | 可以         | 使用相同渠道幂等键         |
| 业务拒绝         | 通常不重试   | 除非用户改变支付方式或信息 |
| 连接前失败       | 可以         | 能证明请求未发送           |
| 读超时/连接中断  | 不可盲重试   | 标记 UNKNOWN 并查询        |
| 消息消费失败     | 可以         | 消费者业务幂等、死信治理   |

重试必须有：次数、总时长、退避、抖动、可观测、熔断联动和业务安全判断。

## Circuit Breaker、Bulkhead 与限流

### 9.4.1 Circuit Breaker

防止持续调用已故障依赖，缩短失败时间。它不能解决已经发出的请求是否执行，因此不能把 UNKNOWN 自动变成失败。

### 9.4.2 Bulkhead

按渠道、商户或支付方式隔离：

- 线程池/协程并发；
- HTTP 连接池；
- 队列；
- 数据库资源；
- 恢复任务配额。

一个慢渠道不应耗尽整个支付平台的资源。

### 9.4.3 限流与容量保护

- 商户级限流防止单租户挤占；
- 渠道级限流遵守外部配额；
- 操作级限流区分支付、查询和退款；
- 恢复流量单独配额，避免故障时查询风暴；
- 过载时优先保护支付完成和状态恢复，降级报表等非关键功能。

## 降级原则

可以降级：推荐排序、非关键特征、实时通知、运营报表。

谨慎降级：风控、合规、账务、幂等、状态机。必须有明确业务政策，例如风险服务不可用时按商户/金额分层：低风险小额进入保守规则，高风险交易拒绝，而不是全量放行。

## 多区域与灾备

### 9.6.1 先问业务目标

- RTO 和 RPO；
- 是否允许区域内写主；
- 同一商户是否固定归属区域；
- 渠道请求是否具有全球幂等；
- 数据跨境和合规限制；
- 故障切换时是否可能双写。

### 9.6.2 常见策略

1.  **单区域主写 + 异地灾备**：正确性简单，切换需要流程。
2.  **按商户/地区分片主写**：每个支付有唯一 Home Region，全球路由到主区域。
3.  **多活写**：复杂度最高，需要全球唯一约束、冲突避免和渠道级幂等，通常只对确有业务收益的场景采用。

切换时最危险的是旧区域仍在处理、而新区域又创建新渠道请求。应使用租约、fencing token、全局操作 ID 和演练验证。

## 可观测性

### 9.7.1 业务指标

- 支付成功率，按商户/渠道/国家/支付方式拆分；
- 渠道拒绝率、技术失败率和 UNKNOWN 率；
- 路由选择分布和回退率；
- 支付、退款、回调和恢复延迟；
- 幂等命中与冲突；
- 重复事件拦截；
- 未处理 Outbox/Inbox 积压；
- 对账差错笔数、金额和账龄；
- 账务不平衡数，必须为零。

### 9.7.2 日志与追踪

统一携带：

    trace_id
    merchant_id
    payment_id
    attempt_id
    provider
    provider_request_id
    idempotency_key_hash
    rule_version

不要记录完整卡号、密钥、验证码、原始认证数据或不必要的个人信息。幂等键也可做哈希后记录。

### 9.7.3 告警设计

优先使用用户/资金影响告警，而不是单机 CPU 告警。示例：

- 某渠道 UNKNOWN 比例超过阈值；
- 支付成功率相对基线下降；
- Outbox 最老未发布事件超过 2 分钟；
- 账务不平衡出现任何一笔；
- 对账未解释金额超过风险阈值；
- 回调验签失败突增。

## 事故响应

P8 候选人应能说清：

1.  先确认影响面和资金风险；
2.  暂停危险动作，例如自动重试或渠道切换；
3.  建立统一事件指挥和时间线；
4.  区分明确失败、UNKNOWN 和已成功交易；
5.  通过渠道查询/文件确认真实结果；
6.  修复数据并与账务、客服和商户同步；
7.  复盘技术根因、检测缺口、流程和组织原因；
8.  把改进沉淀成平台能力和演练。
