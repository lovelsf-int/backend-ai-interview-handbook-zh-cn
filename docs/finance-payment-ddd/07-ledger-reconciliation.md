# 账务、清结算与对账

## 账务账本与资金正确性

### 7.1 支付订单不等于账务事实

支付订单表达“用户或商户想完成什么”；账务表达“公司在财务上拥有、欠付或确认了什么”。二者可能因结算周期、退款、拒付和手续费产生不同时间线。

不可变双式账本模型

### 7.2 双式记账核心模型

常见对象：

- `LedgerAccount`：账务账户；
- `JournalTransaction`：一次完整会计事务；
- `Posting`：借方或贷方分录；
- `BalanceProjection`：为查询优化的余额投影；
- `Reversal`：对历史错误的冲正或调整。

#### 7.2.1 核心不变量

1.  每个 Journal 内借方总额等于贷方总额。
2.  每个 Journal 使用确定币种，跨币种通过独立换汇事务表达。
3.  已过账分录不可直接 UPDATE 或 DELETE。
4.  相同业务事件不能重复入账。
5.  余额可由分录重建，快照不是唯一事实来源。
6.  账户和科目映射有版本，历史交易保留当时规则。

### 7.3 简化分录示例

以下仅用于系统设计表达，实际科目由法律实体、牌照、合同和会计政策决定。

#### 7.3.1 收到一笔 100 元支付，商户应收 97，平台手续费 3

    借：渠道应收款        100
    贷：商户应付款         97
    贷：手续费收入           3

#### 7.3.2 渠道结算到银行账户

    借：银行存款           100
    贷：渠道应收款         100

#### 7.3.3 向商户出款 97

    借：商户应付款          97
    贷：银行存款            97

#### 7.3.4 用户退款 20，手续费不退的简化情形

    借：商户应付款          20
    贷：退款应付款          20

渠道完成退款时，再根据真实资金路径冲销退款应付款。面试中应先说明“分录由业务资金路径决定”，不要死背一套科目。

### 7.4 冻结、在途和可用余额

余额通常不止一个数字：

    账面余额 = 已过账分录净额
    冻结余额 = 已保留但尚未最终完成的金额
    可用余额 = 账面余额 - 冻结余额 - 风险准备金
    在途余额 = 已发起结算/出款但尚未确认的金额

冻结可以通过独立 Reservation 模型或账务科目表达。选择取决于是否需要会计审计、规模和实时性能。关键是状态转换要幂等，并能在失败时释放。

### 7.5 账务入账接口

    public record PostingCommand(
        String businessType,
        String businessId,
        String ruleVersion,
        List<PostingLine> lines
    ) {}

数据库唯一约束：

    UNIQUE (business_type, business_id)

同一命令重复到达时返回原 Journal ID；内容不一致则报警并拒绝。

### 7.6 余额计算与性能

事实表可追加写；余额表作为投影：

    UPDATE ledger_balance
    SET debit_total  = debit_total  + :debit,
        credit_total = credit_total + :credit,
        version      = version + 1
    WHERE account_id = :account_id
      AND currency   = :currency
      AND version    = :expected_version;

热点账户可通过：

- 按商户或子账户拆分；
- 分区 Journal；
- 批量聚合更新；
- 单账户顺序执行；
- 把查询投影与事实写入解耦。

不能为了性能牺牲可重建和审计能力。

### 7.7 多币种、汇率与舍入

必须记录：

- 原始金额与币种；
- 目标金额与币种；
- 汇率数值、精度和来源；
- 汇率时间和版本；
- 舍入模式；
- 汇兑差额和手续费。

不要使用 `double` 表示货币。整数最小单位适合固定小数位货币；换汇计算通常使用受控精度的 `BigDecimal`，并在边界统一舍入。

### 7.8 冲正与调整

错误分录不能直接修改。创建与原交易关联的反向或调整 Journal：

    original_journal_id
    reversal_journal_id
    reason_code
    operator / approval
    created_at

这保留完整审计链，也允许对账解释余额变化。

### 7.9 账务系统面试追问

1.  如何证明余额正确？
2.  余额快照损坏怎么办？
3.  同一个事件重复十次如何保证只入一次账？
4.  一个 Journal 中某条分录写入失败怎么办？
5.  跨币种交易如何保持借贷平衡？
6.  退款、拒付和冲正的区别如何体现在账务上？
7.  热点总账户如何扩展？
8.  是否需要 Event Sourcing？为什么？
9.  账务服务不可用时支付能否继续？
10. 人工调账如何授权、审批和审计？

## 清算、结算与对账

### 8.1 概念区分

- **清算 Clearing**：计算各参与方应收应付、费用和净额。
- **结算 Settlement**：真实资金在银行或清算账户之间转移。
- **对账 Reconciliation**：比较多个事实来源，确认交易、金额、状态和资金是否一致。

不同机构使用术语可能略有差异。面试时应先说明自己使用的定义。

### 8.2 三层对账

1.  **交易对账**：内部 PaymentAttempt 与渠道交易记录。
2.  **账务对账**：支付/退款事件与内部 Ledger Journal。
3.  **资金对账**：结算批次、银行流水与内部应收应付。

只做第一层不能证明资金已到账；只做银行余额也无法解释每一笔交易。

对账接入、匹配与差错工作流

### 8.3 数据接入

渠道可能通过文件、API、SFTP 或消息提供数据。接入层需要：

- 文件名、大小、校验和和业务日期；
- 文件版本、重发和更正标记；
- 字符集、时区、金额单位；
- 行级唯一键和原始内容留存；
- PGP/签名校验和访问控制；
- 断点续传与重复导入幂等。

### 8.4 匹配阶梯

推荐从高置信度到低置信度：

1.  `provider_transaction_id` 精确匹配；
2.  `provider_request_id` 或商户订单号匹配；
3.  组合键：金额、币种、时间窗口、支付方式；
4.  容差或人工匹配。

任何非精确匹配都应保留规则版本、置信度和证据，不能悄悄修改事实。

### 8.5 差错类型

| **类型**      | **示例**             | **常见处理**                   |
|---------------|----------------------|--------------------------------|
| 外有内无      | 渠道成功，内部无记录 | 恢复支付状态、补记账、调查双扣 |
| 内有外无      | 内部成功，渠道无记录 | 查询渠道、冲正或人工确认       |
| 状态不一致    | 内部失败，渠道成功   | 标记差错并恢复/退款            |
| 金额/币种差异 | 手续费或换汇错误     | 规则校验、调整分录             |
| 重复          | 同一外部交易出现多次 | 去重、检查重复结算             |
| 结算差异      | 应收与银行入账不一致 | 建立资金敞口和责任归属         |

### 8.6 自动修复边界

可自动修复：证据充分、动作幂等、金额风险可控、规则可审计的场景。

必须人工：证据冲突、可能影响用户资金、跨法律实体、需要渠道确认或金额超过阈值的场景。

差错工作流应记录：责任团队、资金敞口、账龄、下一动作、审批、关联 Journal 和最终原因。

### 8.7 对账系统指标

- 文件到达及时率；
- 数据完整率；
- 自动匹配率；
- 差错笔数和金额；
- 差错账龄 P50/P95；
- 自动修复成功率；
- 未解释资金敞口；
- 重跑次数和人工操作量。
