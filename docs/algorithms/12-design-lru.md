# 12 LRU 手写与生产追问

设计题不仅考察数据结构，也考察状态一致性。先给出单线程算法模型，再讨论真实缓存的并发、容量、TTL 与观测边界，避免把 LeetCode 实现直接当生产组件。

## LC 146 LRU 缓存 {#lc-146}

[原题与约束](https://leetcode.com/problems/lru-cache/) · 本节为本站原创题意概括与解法。

**题意与思路：**HashMap 定位节点，双向链表维护访问顺序；头部最新、尾部最旧。get/put 命中后移到头，超容量淘汰尾节点。

**为什么正确：**哈希表与链表一一对应；每个命中访问都将节点置于最新位置；尾节点始终是最久未访问者，容量超限时恰好淘汰它。

**手推例子：**容量 2：put(1,1)、put(2,2)、get(1)、put(3,3)，因 1 被访问过，淘汰 2；get(2) 返回 -1。

**复杂度：**get/put 期望 O(1)，容量为 C 时空间 O(C)；哈希定位为期望复杂度，链表移动是常数次指针更新。

**易错点：**淘汰必须同时删除链表节点与 map 条目；更新已有 key 不应重复新增节点；head/tail 哨兵不能被当作数据淘汰。

**面试追问与回答：**只换成 ConcurrentHashMap 能线程安全吗？不能，map 查询、链表摘除/插入、容量检查和淘汰需要保持整体不变量。必须设计合适同步或分片策略。

## P7/P8 追问：从手写题到生产缓存

**为什么不用单链表？** 已知节点时，单链表缺少前驱，删除和移到头可能需要 O(C) 查找；双向链表可直接定位前后节点。

**LinkedHashMap 能替代吗？** accessOrder 模式可维护访问顺序，但面试要求手写时仍应解释底层结构。工程上选择成熟缓存库前，还要明确并发、统计、异步加载和淘汰需求，而不是只看一段短代码。

**LRU 是最优淘汰吗？** 不是。顺序扫描大量只访问一次的数据会污染缓存；必须根据访问分布和命中率评估其他策略。算法模型中的容量单位是条目数，真实缓存可能需要按权重或字节估算。

**TTL 怎么加入？** 过期时间与访问顺序是不同维度；需要惰性校验、定期清理或专门过期索引，并定义读取过期项和后台淘汰的并发语义。

**单机 LRU 与 Redis 的淘汰完全等价吗？** 不能直接等同。这里是精确的进程内访问顺序模型，真实中间件的策略、采样、容量与持久化行为应查对应版本并单独分析。

## 复现与边界
